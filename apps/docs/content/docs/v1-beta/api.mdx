The Ouitransfer API is a REST API built with Fastify 5, Zod, and TypeScript. It powers all operations in the platform: the web frontend communicates with it directly via `/api/*` routes, but you can also call it directly for automation, integrations, or custom clients.

## Base URL

The API server runs on port **3333** by default (configurable via the `PORT` environment variable). For direct API access, use the server URL:

```
http://your-server:3333
```

<Callout type="info">
  In production, a reverse proxy (like Traefik) routes the `/api/*` path directly to the Fastify backend. In development, a Next.js edge middleware rewrite forwards `/api/*` requests to the Fastify port (3333). For direct API access (scripts, CI/CD, custom clients), always target the Fastify server port 3333 directly.
</Callout>

To expose the API port in Docker Compose, add `ports: ["3333:3333"]` to the `server` service. See the [Quick Start guide](/docs/v1-beta/quick-start) for a full deployment example.

## Authentication

The API uses **httpOnly signed cookies** for authentication: there is no API key system. Authenticate by calling the login endpoint, then include the returned cookies in subsequent requests.

### Login flow

1. **Get a CSRF token**: `GET /csrf-token` returns a `token` value and sets a `_csrf` cookie.
2. **Login**: `POST /auth/login` with credentials. On success, the server sets `token` (JWT access token) and `refreshToken` cookies.
3. **Make requests**: include cookies on all subsequent requests. The JWT is short-lived (15 minutes); use `POST /auth/refresh` to obtain a new one. The refresh endpoint returns no token in the response body: both the new access token and the rotated refresh token are set as httpOnly cookies.

### CSRF protection

All **mutating requests** (POST, PUT, PATCH, DELETE) require a CSRF token, unless the endpoint is explicitly exempt. Ouitransfer uses the **double-submit cookie** pattern:

- The `_csrf` cookie contains a secret set by the server.
- The client must send a matching token in the `X-CSRF-Token` request header.
- Obtain the token from `GET /csrf-token`.
- GET, HEAD, and OPTIONS requests do not require the CSRF header.

<Callout type="warn">
  CSRF token is required for **all POST, PUT, PATCH, and DELETE requests**, even endpoints marked `Auth: Public` (public). Public mutations like file downloads (`POST /files/download-url`) still require a valid `X-CSRF-Token` header unless explicitly listed as CSRF-exempt. See the exempt list below.
</Callout>

**CSRF-exempt endpoints** (public or unauthenticated mutations): `/auth/login`, `/auth/refresh`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/2fa/login`, `/register-with-invite`, share and reverse share password-access endpoints, and all reverse share public upload endpoints.

### Example: curl login

```bash
# 1. Get CSRF token
CSRF=$(curl -s -c cookies.txt http://localhost:3333/csrf-token | jq -r '.token')

# 2. Login
curl -s -b cookies.txt -c cookies.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF" \
  -d '{"emailOrUsername":"admin@example.com","password":"yourpassword"}' \
  http://localhost:3333/auth/login

# 3. Make authenticated requests (cookies are sent automatically)
curl -s -b cookies.txt http://localhost:3333/files
```

## Interactive documentation

When API docs are enabled (always in development, opt-in in production via `ENABLE_API_DOCS=true`), two interactive documentation UIs are available:

- **Scalar**: `http://localhost:3333/docs`
- **Swagger UI**: `http://localhost:3333/swagger`

Both provide endpoint exploration, request builders, and response visualization generated from the Zod schemas.

<Callout type="warn">
These UIs are **off by default** in production and only registered when you opt in with `ENABLE_API_DOCS=true`. When enabled they are reachable **without authentication** and expose the full API surface (every route and schema), so `ENABLE_API_DOCS=true` is **not** intended for internet-facing deployments — prefer leaving docs disabled in production.
</Callout>

## Endpoint reference

### Authentication

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | `/auth/login` | Public | Login with email/username and password |
| POST | `/auth/2fa/login` | Public | Complete login with 2FA verification code |
| POST | `/auth/logout` | Public | Logout and clear session cookies |
| GET | `/auth/me` | Public | Get current authenticated user (returns `null` if not logged in) |
| POST | `/auth/forgot-password` | Public | Request password reset email |
| POST | `/auth/reset-password` | Public | Reset password using token from email |
| POST | `/auth/refresh` | Public | Refresh access token using refresh token cookie (token rotation; old refresh token is invalidated) |
| GET | `/auth/config` | Public | Get auth configuration (whether password auth is enabled) |
| GET | `/auth/trusted-devices` | User | List trusted 2FA devices |
| DELETE | `/auth/trusted-devices/:id` | User | Remove a specific trusted device |
| DELETE | `/auth/trusted-devices` | User | Remove all trusted devices |
| GET | `/csrf-token` | Public | Get a CSRF token (sets `_csrf` cookie) |

**Note on optional-auth endpoints:** `/auth/me` returns the current user if a valid session exists, `null` otherwise: it doesn't require authentication to call. `/auth/logout` clears session cookies even without a valid session. Neither returns a `401` when called without credentials. Note that `/auth/logout` still requires a CSRF token (like all POST endpoints) even though it doesn't require a JWT session.

**Login** returns the user object on success. If the account has 2FA enabled, it returns `{ requiresTwoFactor: true, challengeToken: "..." }`: pass the challenge token and TOTP code to `/auth/2fa/login` to complete authentication.

**Rate limits:** Login: 5 attempts per minute per IP. Forgot password: 3 per minute per IP. Reset password: 3 per minute per IP. Token refresh: 10 per minute per IP.

**Account lockout:** After 10 consecutive failed login attempts within 15 minutes, the account is temporarily locked and returns an `ACCOUNT_LOCKED` error code with `403 Forbidden`. The lockout expires automatically after 15 minutes from the oldest failed attempt; no administrator intervention is required. A successful login resets the failure counter.

| POST | `/shares/alias/:alias/identify` | Public | Submit visitor identification form (name/email) |

**Share access:** For password-protected shares, the password must be sent in the request body via the `/access` endpoints; never as a query parameter. Non-password-protected shares are accessible without authentication.

**Tracking tokens:** Share access endpoints accept an optional `?t=<token>` query parameter. When present, the visitor is automatically identified as the recipient who owns that tracking token. See [Shares: Visitor identification](/docs/v1-beta/shares#visitor-identification).

**Share visits:** The `GET /shares/:shareId/visits` endpoint returns paginated visit records. Query parameters: `page` (default 1), `limit` (default 10), `action` (`access` or `download`), `identified` (`true` or `false`). Only the share owner can access this endpoint. Each record includes an `identificationSource` field (`tracking_token`, `cookie`, `authenticated_user`, or `anonymous`) and an `isOwner` boolean indicating whether the visit was attributed to the share creator.

## Common response codes

| Code | Meaning |
|------|---------|
| 200 | OK: request succeeded |
| 201 | Created: resource created successfully |
| 302 | Redirect: OAuth/OIDC flow redirects |
| 400 | Bad Request: validation failure (Zod schema) |
| 401 | Unauthorized: not authenticated, invalid token, or CSRF mismatch |
| 403 | Forbidden: authenticated but insufficient permissions |
| 404 | Not Found: resource does not exist |
| 409 | Conflict: duplicate resource or file-in-shares conflict |
| 410 | Gone: share or reverse share has expired |
| 413 | Payload Too Large: request body exceeds the 50 MB body size limit |
| 429 | Too Many Requests: rate limit exceeded |
| 500 | Internal Server Error |

All error responses follow a consistent JSON shape:

```json
{
  "error": "Human-readable description",
  "code": "ERROR_CODE",
  "statusCode": 400,
  "timestamp": "2025-01-15T12:00:00.000Z"
}
```

The `error` field contains a human-readable message, `code` is the machine-readable error code (e.g. `VALIDATION_ERROR`, `NOT_FOUND`, `ACCOUNT_LOCKED`), and `timestamp` is an ISO 8601 string. Some errors include an additional `details` object with structured metadata.

## Rate limiting

Global rate limit: **100 requests per minute per IP**. Individual endpoints may impose stricter limits:

| Endpoint | Limit |
|----------|-------|
| `POST /auth/login` | 5 / minute |
| `POST /auth/2fa/login` | 5 / minute |
| `POST /auth/forgot-password` | 3 / minute |
| `POST /auth/reset-password` | 3 / minute |
| `POST /auth/refresh` | 10 / minute |
| `POST /auth/2fa/verify` | 5 / minute |
| `GET /files/presigned-url` | 30 / minute |
| `POST /files/download-url` | 20 / minute |
| `POST /files/download` | 20 / minute |
| `GET /csrf-token` | 30 / minute |

When rate-limited, the server returns `429 Too Many Requests` with a `retryAfter` field indicating seconds until the limit resets.

<Callout type="info">
  Rate limit error responses have a different shape from standard API errors; they don't include the `code` or `timestamp` fields. A rate limit response looks like:

  ```json
  { "error": "Too many requests", "message": "Rate limit exceeded. Try again in 15 seconds.", "retryAfter": 15 }
  ```
</Callout>

### Request size limits

The API enforces a **50 MB** body size limit on non-multipart requests. File uploads bypass this limit by using S3 presigned URLs; the file content goes directly to S3, not through the API server.
