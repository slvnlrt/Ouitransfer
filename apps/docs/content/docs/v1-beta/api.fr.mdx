L'API Ouitransfer est une API REST construite avec Fastify 5, Zod et TypeScript. Elle alimente l'ensemble des opérations de la plateforme : le frontend web communique directement avec elle via les routes `/api/*`, mais vous pouvez également l'appeler directement pour l'automatisation, les intégrations ou des clients personnalisés.

## URL de base

Le serveur API s'exécute sur le port **3333** par défaut (configurable via la variable d'environnement `PORT`). Pour un accès direct à l'API, utilisez l'URL du serveur :

```
http://your-server:3333
```

<Callout type="info">
  En production, un reverse proxy (comme Traefik) route le chemin `/api/*` directement vers le backend Fastify. En développement, un middleware Edge Next.js redirige les requêtes `/api/*` vers le port Fastify (3333). Pour un accès direct à l'API (scripts, CI/CD, clients personnalisés), ciblez toujours directement le port 3333 du serveur Fastify.
</Callout>

Pour exposer le port de l'API dans Docker Compose, ajoutez `ports: ["3333:3333"]` au service `server`. Consultez le [guide de démarrage rapide](/docs/v1-beta/quick-start) pour un exemple de déploiement complet.

## Authentification

L'API utilise des **cookies httpOnly signés** pour l'authentification : il n'existe pas de système de clé API. Authentifiez-vous en appelant le point de terminaison de connexion, puis incluez les cookies retournés dans les requêtes suivantes.

### Flux de connexion

1. **Obtenir un jeton CSRF** : `GET /csrf-token` retourne une valeur `token` et pose un cookie `_csrf`.
2. **Connexion** : `POST /auth/login` avec les identifiants. En cas de succès, le serveur pose les cookies `token` (jeton d'accès JWT) et `refreshToken`.
3. **Effectuer des requêtes** : incluez les cookies dans toutes les requêtes suivantes. Le JWT est de courte durée (15 minutes) ; utilisez `POST /auth/refresh` pour en obtenir un nouveau. Le point de terminaison de rafraîchissement ne retourne aucun jeton dans le corps de la réponse : le nouveau jeton d'accès et le jeton de rafraîchissement rotatif sont tous deux posés comme cookies httpOnly.

### Protection CSRF

Toutes les **requêtes mutantes** (POST, PUT, PATCH, DELETE) nécessitent un jeton CSRF, sauf si le point de terminaison est explicitement exempté. Ouitransfer utilise le pattern **double-submit cookie** :

- Le cookie `_csrf` contient un secret posé par le serveur.
- Le client doit envoyer un jeton correspondant dans l'en-tête de requête `X-CSRF-Token`.
- Obtenez le jeton via `GET /csrf-token`.
- Les requêtes GET, HEAD et OPTIONS ne nécessitent pas l'en-tête CSRF.

<Callout type="warn">
  Le jeton CSRF est requis pour **toutes les requêtes POST, PUT, PATCH et DELETE**, même les points de terminaison marqués `Auth: Public` (publics). Les mutations publiques comme les téléchargements de fichiers (`POST /files/download-url`) nécessitent toujours un en-tête `X-CSRF-Token` valide, sauf s'ils sont explicitement listés comme exempts CSRF. Voir la liste des exemptions ci-dessous.
</Callout>

**Points de terminaison exempts CSRF** (mutations publiques ou non authentifiées) : `/auth/login`, `/auth/refresh`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/2fa/login`, `/register-with-invite`, les points de terminaison d'accès par mot de passe aux partages et partages inversés, et tous les points de terminaison publics de téléversement vers les partages inversés.

### Exemple : connexion avec curl

```bash
# 1. Get CSRF token
CSRF=$(curl -s -c cookies.txt http://localhost:3333/csrf-token | jq -r '.token')

# 2. Login
curl -s -b cookies.txt -c cookies.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF" \
  -d '{"emailOrUsername":"admin@example.com","password":"yourpassword"}' \
  http://localhost:3333/auth/login

# 3. Make authenticated requests (cookies are sent automatically)
curl -s -b cookies.txt http://localhost:3333/files
```

## Documentation interactive

Lorsque la documentation API est activée (toujours en développement, optionnelle en production via `ENABLE_API_DOCS=true`), deux interfaces de documentation interactive sont disponibles :

- **Scalar** : `http://localhost:3333/docs`
- **Swagger UI** : `http://localhost:3333/swagger`

Les deux offrent l'exploration des points de terminaison, des constructeurs de requêtes et une visualisation des réponses générée à partir des schémas Zod.

## Référence des points de terminaison

### Authentification

| Méthode | Chemin | Auth | Description |
|---------|--------|------|-------------|
| POST | `/auth/login` | Public | Connexion avec email/nom d'utilisateur et mot de passe |
| POST | `/auth/2fa/login` | Public | Finaliser la connexion avec un code de vérification 2FA |
| POST | `/auth/logout` | Public | Déconnexion et suppression des cookies de session |
| GET | `/auth/me` | Public | Obtenir l'utilisateur authentifié courant (retourne `null` si non connecté) |
| POST | `/auth/forgot-password` | Public | Demander un email de réinitialisation de mot de passe |
| POST | `/auth/reset-password` | Public | Réinitialiser le mot de passe avec le jeton reçu par email |
| POST | `/auth/refresh` | Public | Rafraîchir le jeton d'accès via le cookie de jeton de rafraîchissement (rotation — l'ancien jeton de rafraîchissement est invalidé) |
| GET | `/auth/config` | Public | Obtenir la configuration d'authentification (si l'auth par mot de passe est activée) |
| GET | `/auth/trusted-devices` | User | Lister les appareils 2FA de confiance |
| DELETE | `/auth/trusted-devices/:id` | User | Supprimer un appareil de confiance spécifique |
| DELETE | `/auth/trusted-devices` | User | Supprimer tous les appareils de confiance |
| GET | `/csrf-token` | Public | Obtenir un jeton CSRF (pose le cookie `_csrf`) |

**Remarque sur les points de terminaison à authentification optionnelle :** `/auth/me` retourne l'utilisateur courant si une session valide existe, `null` sinon : aucune authentification n'est requise pour l'appeler. `/auth/logout` efface les cookies de session même sans session valide. Aucun des deux ne retourne de `401` quand il est appelé sans identifiants. Notez que `/auth/logout` nécessite quand même un jeton CSRF (comme tous les points de terminaison POST) même s'il ne requiert pas de session JWT.

**Connexion** retourne l'objet utilisateur en cas de succès. Si le compte a la 2FA activée, il retourne `{ requiresTwoFactor: true, challengeToken: "..." }` : transmettez le jeton de défi et le code TOTP à `/auth/2fa/login` pour compléter l'authentification.

**Limites de débit :** Connexion : 5 tentatives par minute par IP. Mot de passe oublié : 3 par minute par IP. Réinitialisation du mot de passe : 3 par minute par IP. Rafraîchissement du jeton : 10 par minute par IP.

**Verrouillage de compte :** Après 10 échecs de connexion consécutifs en 15 minutes, le compte est temporairement verrouillé et retourne un code d'erreur `ACCOUNT_LOCKED` avec `403 Forbidden`. Le verrouillage expire automatiquement 15 minutes après la plus ancienne tentative échouée — aucune intervention d'un administrateur n'est requise. Une connexion réussie remet à zéro le compteur d'échecs.

| GET | `/shares/:shareId/visits` | User | Lister les visites d'un partage (paginé, filtrable par action et statut d'identification) |

**Accès aux partages :** Pour les partages protégés par mot de passe, le mot de passe doit être envoyé dans le corps de la requête via les points de terminaison `/access` — jamais en paramètre de requête. Les partages sans mot de passe sont accessibles sans authentification.

**Jetons de suivi :** Les points de terminaison d'accès aux partages acceptent un paramètre de requête optionnel `?t=<token>`. Lorsqu'il est présent, le visiteur est automatiquement identifié comme le destinataire propriétaire de ce jeton de suivi. Voir [Partages : Identification des visiteurs](/docs/v1-beta/shares#visitor-identification).

**Visites de partage :** Le point de terminaison `GET /shares/:shareId/visits` retourne des enregistrements de visites paginés. Paramètres de requête : `page` (défaut 1), `limit` (défaut 10), `action` (`access` ou `download`), `identified` (`true` ou `false`). Seul le propriétaire du partage peut accéder à ce point de terminaison.

## Codes de réponse courants

| Code | Signification |
|------|---------------|
| 200 | OK — requête réussie |
| 201 | Created — ressource créée avec succès |
| 302 | Redirect — redirections du flux OAuth/OIDC |
| 400 | Bad Request — échec de validation (schéma Zod) |
| 401 | Unauthorized — non authentifié, jeton invalide ou non-concordance CSRF |
| 403 | Forbidden — authentifié mais permissions insuffisantes |
| 404 | Not Found — la ressource n'existe pas |
| 409 | Conflict — ressource en double ou conflit fichier-dans-partages |
| 410 | Gone — partage ou partage inversé expiré |
| 413 | Payload Too Large — le corps de la requête dépasse la limite de taille de 50 Mo |
| 429 | Too Many Requests — limite de débit dépassée |
| 500 | Internal Server Error |

Toutes les réponses d'erreur suivent une structure JSON cohérente :

```json
{
  "error": "Human-readable description",
  "code": "ERROR_CODE",
  "statusCode": 400,
  "timestamp": "2025-01-15T12:00:00.000Z"
}
```

Le champ `error` contient un message lisible par l'humain, `code` est le code d'erreur lisible par la machine (ex. `VALIDATION_ERROR`, `NOT_FOUND`, `ACCOUNT_LOCKED`), et `timestamp` est une chaîne ISO 8601. Certaines erreurs incluent un objet `details` supplémentaire avec des métadonnées structurées.

## Limitation du débit

Limite de débit globale : **100 requêtes par minute par IP**. Certains points de terminaison peuvent imposer des limites plus strictes :

| Point de terminaison | Limite |
|----------------------|--------|
| `POST /auth/login` | 5 / minute |
| `POST /auth/2fa/login` | 5 / minute |
| `POST /auth/forgot-password` | 3 / minute |
| `POST /auth/reset-password` | 3 / minute |
| `POST /auth/refresh` | 10 / minute |
| `POST /auth/2fa/verify` | 5 / minute |
| `GET /files/presigned-url` | 30 / minute |
| `POST /files/download-url` | 20 / minute |
| `POST /files/download` | 20 / minute |
| `POST /s3/upload-url` | 30 / minute |
| `GET /csrf-token` | 30 / minute |

En cas de dépassement de la limite, le serveur retourne `429 Too Many Requests` avec un champ `retryAfter` indiquant le nombre de secondes avant la réinitialisation de la limite.

<Callout type="info">
  Les réponses d'erreur de limite de débit ont une structure différente des erreurs API standard — elles n'incluent pas les champs `code` ni `timestamp`. Une réponse de limite de débit ressemble à :

  ```json
  { "error": "Too many requests", "message": "Rate limit exceeded. Try again in 15 seconds.", "retryAfter": 15 }
  ```
</Callout>

### Limites de taille des requêtes

L'API impose une limite de taille de corps de **50 Mo** sur les requêtes non-multipart. Les téléversements de fichiers contournent cette limite en utilisant des URLs présignées S3 — le contenu du fichier va directement vers S3, pas via le serveur API.
