When deploying **OUITRANSFER.** behind a reverse proxy (like Traefik, Nginx, or Cloudflare), you need to configure secure cookie settings to ensure proper authentication. This guide covers the `SECURE_SITE` environment variable and related proxy configurations.

## Overview

Reverse proxies terminate SSL/TLS connections and forward requests to OUITRANSFER., which can cause authentication issues if cookies aren't configured properly for HTTPS environments. The `SECURE_SITE` environment variable controls cookie security settings to handle these scenarios.

## The SECURE_SITE Environment Variable

The `SECURE_SITE` variable configures how OUITRANSFER. handles authentication cookies based on your deployment environment:

### Configuration Options

| Value   | Cookie Settings                       | Use Case                            |
| ------- | ------------------------------------- | ----------------------------------- |
| `true`  | `secure: true`, `sameSite: "lax"`     | HTTPS/Production with reverse proxy |
| `false` | `secure: false`, `sameSite: "strict"` | HTTP/Development (default)          |

### When to Use SECURE_SITE=true

Set `SECURE_SITE=true` in the following scenarios:

- ✅ **Reverse Proxy with HTTPS**: Traefik, Nginx, HAProxy with SSL termination
- ✅ **Cloud Providers**: Cloudflare, AWS ALB, Azure Application Gateway
- ✅ **CDN with HTTPS**: Any CDN that terminates SSL
- ✅ **Production Deployments**: When users access via HTTPS

### When to Use SECURE_SITE=false

Keep `SECURE_SITE=false` (default) for:

- ✅ **Local Development**: Running on `http://localhost`
- ✅ **Direct HTTP Access**: No reverse proxy involved
- ✅ **Testing Environments**: When using HTTP
- ✅ **HTTP Reverse Proxy**: Nginx, Apache, etc. without SSL termination

---

## HTTP Reverse Proxy Setup

**Docker Compose for HTTP Nginx:**

```yaml
environment:
  - SECURE_SITE=false # HTTP = false
```

> **⚠️ HTTP Security**: Remember that HTTP transmits data in plain text. Consider using HTTPS in production environments.

## Troubleshooting Authentication Issues

### Common Symptoms

If you experience authentication issues behind a reverse proxy:

- ❌ Login appears successful but redirects to login page
- ❌ "No Authorization was found in request.cookies" errors
- ❌ API requests return 401 Unauthorized
- ❌ User registration fails silently

### Diagnostic Steps

1. **Check Browser Developer Tools**:
   - Look for cookies in Application/Storage tab
   - Verify cookie has `Secure` flag when using HTTPS
   - Check if `SameSite` attribute is appropriate

2. **Verify Environment Variables**:

   ```bash
   docker exec -it ouitransfer-server env | grep SECURE_SITE
   ```

3. **Test Cookie Settings**:
   - With `SECURE_SITE=false`: Should work on HTTP
   - With `SECURE_SITE=true`: Should work on HTTPS

### Common Fixes

**Problem**: Authentication fails with reverse proxy

**Solution**: Set `SECURE_SITE=true` and ensure proper headers:

```yaml
environment:
  - SECURE_SITE=true
```

**Problem**: Mixed content errors

**Solution**: Ensure proxy passes correct headers:

```yaml
# Traefik
- "traefik.http.middlewares.ouitransfer-headers.headers.customrequestheaders.X-Forwarded-Proto=https"

# Nginx
proxy_set_header X-Forwarded-Proto $scheme;
```

**Problem**: Authentication fails with HTTP reverse proxy

**Solution**: Use `SECURE_SITE=false` and ensure proper cookie headers:

```yaml
environment:
  - SECURE_SITE=false # For HTTP proxy
```

```nginx
# Nginx - Add these headers for cookie handling
proxy_set_header Cookie $http_cookie;
proxy_pass_header Set-Cookie;
```

**Problem**: SQLite "readonly database" error with bind mounts

**Solution**: Configure proper UID/GID permissions:

```yaml
environment:
  - OUITRANSFER_UID=1000 # Your host UID (check with: id)
  - OUITRANSFER_GID=1000 # Your host GID

```

> **💡 Note**: Check your host UID/GID with `id` command and use those values. See [UID/GID Configuration](/docs/v1-beta/uid-gid-configuration) for detailed setup.

## Security Considerations

> **⚠️ Important**: Always use HTTPS in production environments. The `SECURE_SITE=true` setting ensures cookies are only sent over encrypted connections.

## Advanced Configuration

### Multiple Domains

If serving OUITRANSFER. on multiple domains, ensure consistent cookie settings:

```yaml
environment:
  - SECURE_SITE=true # Use for all HTTPS domains
```

### Development vs Production

Use environment-specific configurations:

**Development (HTTP):**

```yaml
environment:
  - SECURE_SITE=false
```

**Production (HTTPS):**

```yaml
environment:
  - SECURE_SITE=true
```

### Health Checks

Add health checks to ensure proper proxy configuration. In the 3-container architecture, the health endpoint lives on the **server** container (port 3333), not the web container:

```yaml
services:
  server:
    image: ouitransfer/server:latest
    container_name: ouitransfer-server
    # ... other config
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3333/health"]
      interval: 30s
      timeout: 10s
      retries: 3
```

The health endpoint returns `{ status, timestamp, uptime, checks: { database, storage } }`. It returns HTTP 200 when all subsystems are healthy, or HTTP 503 when degraded.

## Storage and CSP Configuration Behind a Reverse Proxy

When deploying behind a reverse proxy, two additional configuration points are important:

### STORAGE_URL Must Be Externally Reachable

The `STORAGE_URL` environment variable on the **server** service controls the base URL embedded in presigned upload/download URLs. When behind a reverse proxy, this must point to the externally reachable address of the storage service — not an internal Docker hostname.

```yaml
services:
  server:
    environment:
      STORAGE_URL: "https://files.yourdomain.com"  # or http://YOUR_SERVER_IP:9000
```

> **💡 Note:** Browsers must be able to reach port 9000 (or your proxy path for storage) to perform file uploads and downloads. Presigned URLs are generated with this address and sent directly to browsers.

### CSP Configuration for Storage Origin

The web container sets a Content Security Policy (CSP) that restricts which origins browsers can connect to. If your storage service runs on a different domain or port than the web interface, you must add it to the allowed origins using the `CSP_CONNECT_SOURCES` environment variable on the **web** service:

```yaml
services:
  web:
    image: ouitransfer/web:latest
    container_name: ouitransfer-web
    environment:
      API_BASE_URL: "http://server:3333"
      CSP_CONNECT_SOURCES: "https://files.yourdomain.com"  # Add storage origin here
```

Multiple origins can be space-separated: `CSP_CONNECT_SOURCES: "https://files.yourdomain.com https://cdn.yourdomain.com"`.

## Need Help?

If you're still experiencing issues after following this guide:

1. **Check the Logs**: `docker compose logs server` (or `docker compose logs web` for frontend issues)
2. **Verify Headers**: Use browser dev tools or `curl -I`
3. **Test Direct Access**: Try accessing OUITRANSFER. directly (bypassing proxy)
4. **Open an Issue**: [Report bugs on GitHub](https://github.com/burger-cie/ouitransfer/issues)

> **💡 Pro Tip**: When reporting issues, include your reverse proxy configuration and any relevant error messages from both OUITRANSFER. and your proxy logs.
