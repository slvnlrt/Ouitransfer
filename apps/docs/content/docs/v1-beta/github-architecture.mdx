### Server module structure

Each feature lives in `apps/server/src/modules/<feature>/` and follows the same layout:

| File | Role |
|------|------|
| `routes.ts` | Fastify route registration, Zod schema declarations |
| `controller.ts` | Request/response handling, input validation |
| `service.ts` | Business logic, Prisma queries |
| `dto.ts` | Shared Zod schemas and TypeScript types |

Current modules: `admin`, `app`, `audit`, `auth`, `auth-providers`, `background-image`, `config`, `email`, `file`, `folder`, `group`, `health`, `invite`, `ldap`, `quota`, `reverse-share`, `s3-storage`, `share`, `storage`, `two-factor`, `user`.

## Monorepo tooling

| Tool | Role |
|------|------|
| **pnpm 10.6.0** | Package manager + workspace management |
| **pnpm catalogs** | Shared dependency versions across packages (defined in `pnpm-workspace.yaml`) |
| **Turborepo** | Build pipeline orchestration — runs `lint`, `type-check`, `test`, `build` in parallel across packages |
| **Biome** | Unified linter + formatter (replaces ESLint + Prettier). `noExplicitAny` enforced. |
| **Lefthook** | Git hooks — runs checks before every commit and validates commit messages |
| **commitlint** | Enforces [Conventional Commits](https://www.conventionalcommits.org/) on all commit messages |
| **Knip** | Dead code and unused export detection |
| **`just`** | Task runner — run `just --list` for all available recipes |

Common `just` recipes for contributors:

```bash
just setup-dev       # First-time local setup (install + DB init)
just dev             # Start all apps in watch mode
just test            # Run all Vitest tests
just lint            # Run Biome across the monorepo
just validate        # type-check + lint + test (mirrors CI)
just db-generate     # Regenerate Prisma client after schema changes
just db-migrate-dev  # Apply pending migrations
```

### Pre-commit hooks

Lefthook installs two hooks automatically when you run `just setup-dev` (or `pnpm exec lefthook install`):

**`pre-commit`** — runs in parallel on every `git commit`:

| Check | What it does |
|-------|-------------|
| **Biome** | Lints and auto-formats **staged files only** (`--staged`). Fixed files are automatically re-staged — you don't need to `git add` again. |
| **Knip** | Scans for unused exports, dead code, and unresolved imports across the monorepo. Fails the commit if issues are found. |

**`commit-msg`** — validates the commit message format using commitlint.

### Commit message format

Messages must follow the [Conventional Commits](https://www.conventionalcommits.org/) specification with these enforced rules:

```
<type>(<scope>): <description>
```

**Allowed types:**

`feat` `fix` `docs` `style` `refactor` `perf` `test` `build` `ci` `chore` `revert` `security`

**Allowed scopes (required):**

`server` `web` `docs` `infra` `deps` `ci` `monorepo`

Both type and scope are validated at commit time — the commit is rejected if either is missing or not in the allowed list. Subject must not start with an uppercase letter.

**Examples:**

```
feat(server): add per-user quota enforcement
fix(web): correct presigned URL handling on Safari
docs(docs): update reverse proxy configuration guide
chore(deps): upgrade Fastify to 5.3.0
ci(ci): add Lighthouse step to release workflow
```

## CI/CD pipelines

### CI (`ci.yml`) — pull request gate

Triggers on **push to `main`** and **pull requests targeting `main`**. Concurrent runs on the same ref are cancelled automatically.

<Pipeline>
  <PipelineTriggers>
    <PipelineStep variant="trigger" icon={<GitBranch size={14} />}>Push to main</PipelineStep>
    <PipelineStep variant="trigger" icon={<GitPullRequest size={14} />}>Pull Request → main</PipelineStep>
  </PipelineTriggers>
  <PipelineArrow />
  <PipelineStep icon={<PackageCheck size={14} />}>Install dependencies</PipelineStep>
  <PipelineArrow />
  <PipelineStep variant="warn" badge="non-blocking" icon={<ShieldAlert size={14} />}>Security audit</PipelineStep>
  <PipelineArrow />
  <PipelineParallel label="Turborepo · runs in parallel">
    <PipelineParallelItem>Lint</PipelineParallelItem>
    <PipelineParallelItem>Type-check</PipelineParallelItem>
    <PipelineParallelItem>Tests</PipelineParallelItem>
  </PipelineParallel>
  <PipelineArrow />
  <PipelineStep icon={<Hammer size={14} />}>Build all apps</PipelineStep>
  <PipelineArrow />
  <PipelineStep variant="success" icon={<CircleCheck size={14} />}>All checks pass</PipelineStep>
</Pipeline>

**Steps:**

1. **Install** — `pnpm install --frozen-lockfile` (no lock file drift allowed)
2. **Security audit** — `pnpm audit --audit-level=high`. Non-blocking (transitive vulnerabilities from upstream don't gate the build, but surface as warnings).
3. **Lint + Type-check + Test** — `turbo lint type-check test --continue`. Turbo runs all three task types in parallel across all packages. `--continue` ensures all tasks run even if one fails, so you get the full picture in one pass.
4. **Build** — `pnpm build` with a minimal `JWT_SECRET` to satisfy env validation.

This pipeline must pass before any PR can be merged.

### Release Validation (`e2e.yml`) — tag gate + Docker publish

Triggers on **`v*` tags** (releases) and **manual dispatch** (`workflow_dispatch`). Concurrent release runs are cancelled.

<Pipeline>
  <PipelineTriggers>
    <PipelineStep variant="trigger" icon={<Tag size={14} />}>Git tag (v*)</PipelineStep>
    <PipelineStep variant="trigger" icon={<Play size={14} />}>Manual trigger</PipelineStep>
  </PipelineTriggers>
  <PipelineArrow />
  <PipelineStep icon={<PackageCheck size={14} />}>Install dependencies & browsers</PipelineStep>
  <PipelineArrow />
  <PipelineStep icon={<Hammer size={14} />}>Build Docker images</PipelineStep>
  <PipelineArrow />
  <PipelineStep icon={<Layers size={14} />}>Start 3-container stack</PipelineStep>
  <PipelineArrow />
  <PipelineStep icon={<HeartPulse size={14} />}>Health checks · 120s timeout</PipelineStep>
  <PipelineArrow />
  <PipelineStep variant="warn" badge="non-blocking" icon={<Gauge size={14} />}>Lighthouse audit</PipelineStep>
  <PipelineArrow />
  <PipelineStep icon={<Globe size={14} />}>E2E tests (Playwright)</PipelineStep>
  <PipelineArrow />
  <PipelineStep icon={<FileUp size={14} />}>Upload test report</PipelineStep>
  <PipelineArrow />
  <PipelineStep variant="muted" badge="always" icon={<OctagonX size={14} />}>Stop stack</PipelineStep>
  <PipelineArrow />
  <PipelineFork question="Tag push?">
    <PipelineForkBranch label="yes" highlight>
      <PipelineStep icon={<CloudUpload size={14} />}>Publish to GHCR</PipelineStep>
      <PipelineArrow />
      <PipelineStep variant="success" icon={<CircleCheck size={14} />}>Done</PipelineStep>
    </PipelineForkBranch>
    <PipelineForkBranch label="no">
      <PipelineStep variant="success" icon={<CircleCheck size={14} />}>Done</PipelineStep>
    </PipelineForkBranch>
  </PipelineFork>
</Pipeline>

**Steps:**

1. **Build Docker images** — `docker compose build` using `docker-compose.ci.yml` overrides. The git tag name becomes `NEXT_PUBLIC_APP_VERSION` (e.g. `v1.2.3` → `1.2.3`), which is injected at build time into the Next.js bundle.
2. **Start stack** — full 3-container stack (storage + server + web) with CI overrides.
3. **Wait for health** — polls `GET /health` (server) and the web port until both respond, with a 120-second timeout.
4. **Lighthouse CI** — performance audit. Non-blocking.
5. **E2E tests** — full Playwright suite against the live Docker stack. Blocking.
6. **Upload Playwright report** — stored as a GitHub Actions artifact (14-day retention).
7. **Stop stack** — always runs, even on failure.
8. **Publish to GHCR** — only on tag pushes (skipped on `workflow_dispatch`). Pushes `server` and `web` images to `ghcr.io/slvnlrt/ouitransfer-{server,web}` with three tags: `latest`, `1.2.3` (semver), and `1.2` (minor).

<Callout type="info">
**Why two separate workflows?**

CI runs on every PR and must be fast — no Docker builds, no E2E. The release workflow is heavier (Docker build + full E2E) and only runs when cutting a release or triggering manually. This keeps PR feedback loops short.
</Callout>
