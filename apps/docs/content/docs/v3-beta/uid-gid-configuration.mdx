Configure user and group permissions for seamless bind mount compatibility across different host systems, particularly NAS environments.

## Overview

OUITRANSFER. supports runtime UID/GID configuration to resolve permission conflicts when using bind mounts. This eliminates the need for manual permission management on your host system.

**⚠️ Important**: OUITRANSFER uses **UID 1000, GID 1000** by default, which matches the standard Linux convention. However, some systems may use different UID/GID values, which can cause permission issues with bind mounts.

## The Permission Problem

### Why This Happens

- **OUITRANSFER Default**: UID 1000, GID 1000 (container)
- **Linux Standard**: UID 1000, GID 1000 (most host systems)
- **Result**: Usually compatible, but some systems may use different values

### Common Error Scenarios

```bash
# When you see errors like:
EACCES: permission denied, open '/app/server/data/database.db'
```

```bash
# Or when checking permissions:
$ ls -la data/
drwxr-xr-x 2 user user 4096 Jan 15 10:00 data/
# Container tries to write with different UID/GID than directory owner
```

## Quick Fix

### Option 1: Set OUITRANSFER to Use Standard UID/GID (Recommended)

Add these environment variables to the **server** service in your `docker-compose.yaml`:

```yaml
services:
  server:
    image: ouitransfer/server:latest
    container_name: ouitransfer-server
    environment:
      OUITRANSFER_UID: "1000"
      OUITRANSFER_GID: "1000"
      # ... (storage and web services omitted for brevity)
    volumes:
      - ./server-data:/app/server
    restart: unless-stopped
```

### Option 2: Change Host Directory Permissions

If you prefer to keep OUITRANSFER's defaults:

```bash
# Create directory with correct ownership
mkdir -p server-data
chown -R 1001:1001 server-data
```

## Environment Variables

Configure permissions using these optional environment variables on the **server** service:

| Variable    | Description                      | Default | Example |
| ----------- | -------------------------------- | ------- | ------- |
| `OUITRANSFER_UID` | User ID for container processes  | `1001`  | `1000`  |
| `OUITRANSFER_GID` | Group ID for container processes | `1001`  | `1000`  |

## Finding Your Host UID/GID

Determine your host system's user and group IDs:

```bash
# Check current user
id

# Output example
uid=1000(user) gid=1000(group) groups=1000(group),27(sudo)
```

Use the `uid` and `gid` values for your `OUITRANSFER_UID` and `OUITRANSFER_GID` configuration.

## Storage Service Permissions (RustFS)

The RustFS storage image runs as **UID 10001** by default. This affects bind mounts for the storage service:

### Named Volumes (No Action Needed)

Docker named volumes handle permissions automatically. This is the recommended approach.

### Bind Mounts

If you use bind mounts for the storage service, you must set correct ownership:

```bash
mkdir -p storage-data
chown -R 10001:10001 storage-data
```

Then in your `docker-compose.yaml`:

```yaml
services:
  storage:
    image: rustfs/rustfs:latest
    volumes:
      - ./storage-data:/data
    # ...
```

If the directory has wrong ownership, RustFS will fail to start with permission errors.

## Troubleshooting

### Common Permission Errors

**Error**: `EACCES: permission denied`

```bash
# 1. Check your current UID/GID
id

# 2. Check directory ownership
ls -la server-data/

# 3. Fix via environment variables (preferred)
# Add to server service in docker-compose.yaml:
# OUITRANSFER_UID: "1000"
# OUITRANSFER_GID: "1000"

# 4. Or fix via chown (alternative)
chown -R 1001:1001 server-data
```

**Error**: Container starts but files aren't accessible

```bash
# Check container's UID/GID configuration
docker compose logs server | grep -E "🔧|Runtime UID/GID"

# Check file ownership inside container
docker exec ouitransfer-server ls -la /app/server/
```

### Verification Commands

Verify UID/GID settings are applied correctly:

```bash
# View startup logs for UID/GID configuration
docker compose logs server | head -20

# Check file ownership in container
docker exec ouitransfer-server ls -la /app/server/

# Verify process is running with correct UID/GID
docker exec ouitransfer-server ps aux | grep node

# Check environment variables
docker exec ouitransfer-server env | grep OUITRANSFER
```

### Advanced Troubleshooting

**NAS-specific debugging:**

```bash
# Synology - Check mount point ownership
ls -la /volume1/docker/ouitransfer/

# QNAP - Check mount point ownership
ls -la /share/Container/ouitransfer/

# Check NAS user configuration
cat /etc/passwd | grep -v nobody
```

**Docker bind mount issues:**

```bash
# Check if data directory exists and is writable
test -w server-data && echo "data writable" || echo "data NOT writable"

# Create directory with correct permissions
mkdir -p server-data
sudo chown -R $(id -u):$(id -g) server-data
```

## When to Configure

UID/GID configuration is **required** when:

- ✅ Using bind mounts (most common case)
- ✅ Encountering "permission denied" errors
- ✅ Deploying on NAS systems (Synology, QNAP, etc.)
- ✅ Host system uses different default UID/GID values
- ✅ Running multiple containers that need to share files

UID/GID configuration is **optional** when:

- ❌ Using Docker named volumes (Docker manages permissions)
- ❌ Not using bind mounts
- ❌ No permission errors occurring

## Migration Guide

### Existing Installations

To add UID/GID configuration to running installations:

1. **Stop the containers**

   ```bash
   docker compose down
   ```

2. **Backup your data**

   ```bash
   cp -r ./server-data ./server-data-backup
   ```

3. **Check your UID/GID**

   ```bash
   id
   ```

4. **Update configuration**
   Add UID/GID variables to the server service in your `docker-compose.yaml`:

   ```yaml
   environment:
     OUITRANSFER_UID: "1000"
     OUITRANSFER_GID: "1000"
   ```

5. **Restart with new configuration**
   ```bash
   docker compose up -d
   ```

## Implementation Details

The UID/GID configuration process:

1. **Detection** - Environment variables are read during container startup
2. **Ownership Update** - File permissions are adjusted to match target UID/GID
3. **Privilege Drop** - Application runs with specified user permissions via `su-exec`
4. **Logging** - Configuration changes are logged for verification

The server container starts as root to allow runtime UID/GID configuration, then drops privileges to the target user via `su-exec`. The web container runs as non-root (`nextjs` user) by default since it doesn't need UID/GID override.

This approach provides automatic permission management without user creation or system modification.

## Build-Time Configuration

For custom base images with different default values:

```bash
docker build \
  --build-arg OUITRANSFER_UID=2000 \
  --build-arg OUITRANSFER_GID=2000 \
  -t ouitransfer:custom .
```

Runtime environment variables override build-time defaults.

## Summary

For most users experiencing permission issues with bind mounts:

1. **Find your UID/GID**: Run `id` command
2. **Add to docker-compose.yaml** (server service):
   ```yaml
   environment:
     OUITRANSFER_UID: "1000"
     OUITRANSFER_GID: "1000"
   ```
3. **Restart**: `docker compose down && docker compose up -d`

This ensures compatibility between OUITRANSFER's UID/GID and your host system's file ownership.
