# 5.1 — Per-User Storage Quotas

**Status**: Not started
**Depends on**: —
**Blocks**: 5.4 (Groups), 5.3 (LDAP — quota enforcement per group)

---

## Goal

Prevent users from uploading unlimited data. Provide visibility on storage consumption and enforce configurable limits with a per-user override system, forward-compatible with Groups (5.4).

## Existing Infrastructure

The codebase already enforces two **global** limits via `AppConfig`:

| Config Key | Default | Enforced Where |
|-----------|---------|---------------|
| `maxFileSize` | 1 GiB | `file/controller.ts` (registerFile, checkFile), `reverse-share/upload.service.ts` (copyToUserFiles) |
| `maxTotalStoragePerUser` | 10 GiB | `file/controller.ts` (registerFile, checkFile), `reverse-share/upload.service.ts` (copyToUserFiles) |

**What's missing:**
- No per-user override fields on the User model
- `ReverseShareFile.size` is NOT counted in quota calculation (only `File.size`)
- Reverse share incoming uploads are NOT checked against creator's quota
- Frontend quota widget is a non-functional placeholder (hardcoded 0%, "Not configured")
- `GET /storage/disk-space` only returns data for admin users (physical disk), not regular users
- No soft limit warnings, no over-quota banner

## Quota Hierarchy

Two settings follow the same override hierarchy:
- **Max total storage** (`maxTotalStoragePerUser`)
- **Max file size** (`maxFileSize`)

Resolution order (first non-null wins):
1. **Per-user override** — admin sets explicitly on a user (`User.maxTotalStorageOverride`, `User.maxFileSizeOverride`)
2. **Group quota** — user's group has a limit (5.4 — not implemented in 5.1, placeholder in resolution function)
3. **Global default** — `AppConfig` values (`maxTotalStoragePerUser`, `maxFileSize`)

**Special case — Admin users**: If an admin has no override, their effective limit is **unlimited** (0) regardless of the global default. This is hardcoded in the resolution logic. An admin can still be restricted via a per-user override if needed.

### Semantics

| Field value | Meaning |
|------------|---------|
| `null` | No override — use next level in hierarchy |
| `0` (BigInt) | Unlimited — no limit enforced |
| `> 0` (BigInt) | Explicit limit in bytes |

## What Counts Toward Quota

**Total storage = `SUM(File.size WHERE userId = X)` + `SUM(ReverseShareFile.size WHERE ReverseShare.creatorId = X)`**

- Only finalized files in the database count
- Incomplete multipart upload fragments (S3-side) do NOT count — these are an S3 lifecycle concern, not a quota concern
- Shares are views on existing files — no double-counting

## Blocking Behavior

| Action | Over quota? | Behavior |
|--------|------------|----------|
| User uploads a file | Yes | **BLOCKED** — 400 error with clear message |
| User creates a share | Yes | **ALLOWED** — shares don't consume new storage |
| User creates a reverse share | Yes | **ALLOWED** — but show warning that quota is exceeded |
| Third party uploads to user's reverse share | Yes | **ALLOWED** — never block external clients |
| User uploads a file | No | Check `maxFileSize` per-file + `maxTotalStorage` total |

**Rationale for not blocking reverse share incoming uploads**: The creator may be over quota, but blocking uploads from external clients would break the service contract. The creator's next direct upload will be blocked, incentivizing cleanup.

## Race Conditions

**Optimistic check, no locking.** Two concurrent uploads may each pass the quota check individually but exceed the limit combined. This is acceptable — the next upload will be blocked. The slight overage is negligible (file sizes are MB, quotas are GB).

## Resolution Function Design

A single entry point `resolveEffectiveLimits(userId)` returns `{ maxFileSize: bigint, maxTotalStorage: bigint }`.

```
function resolveEffectiveLimits(userId):
  user = getUser(userId)
  
  maxTotalStorage = user.maxTotalStorageOverride    // per-user override
    ?? null                                          // placeholder: group?.maxTotalStorage
    ?? (user.isAdmin ? 0n : getConfigValue("maxTotalStoragePerUser"))
  
  maxFileSize = user.maxFileSizeOverride             // per-user override
    ?? null                                          // placeholder: group?.maxFileSize  
    ?? (user.isAdmin ? 0n : getConfigValue("maxFileSize"))
  
  return { maxFileSize, maxTotalStorage }
```

The `?? null` placeholder line is where group resolution (5.4) will be inserted. The function signature and return type won't change.

A value of `0` means unlimited — callers must check `if (limit > 0n)` before enforcing.

## Schema Changes

### Prisma — User model additions

```prisma
model User {
  // ... existing fields ...
  maxFileSizeOverride     BigInt?   // Per-user max file size override (bytes). null=inherit, 0=unlimited.
  maxTotalStorageOverride BigInt?   // Per-user max total storage override (bytes). null=inherit, 0=unlimited.
}
```

No new models. No new tables. The AppConfig entries `maxFileSize` and `maxTotalStoragePerUser` remain as-is (they become the global defaults in the hierarchy).

## Server Changes

### 1. Quota resolution service (`modules/quota/`)

New module with:
- `service.ts` — `resolveEffectiveLimits(userId)`, `calculateStorageUsed(userId)`, `getQuotaStatus(userId)` (returns usage, limit, percentage, warning level)
- `repository.ts` — queries for storage calculation (aggregate File + ReverseShareFile)

### 2. Refactor existing enforcement

Replace all direct `getConfigValue("maxFileSize")` / `getConfigValue("maxTotalStoragePerUser")` calls in:
- `file/controller.ts` (3 locations: getPresignedUrl, registerFile, checkFile)
- `reverse-share/upload.service.ts` (1 location: copyReverseShareFileToUserFiles)

These will call `resolveEffectiveLimits(userId)` instead.

### 3. Storage calculation fix

Current code: `prisma.file.findMany({ where: { userId } })` then sums in JS.

New code: single aggregate query combining `File.size` + `ReverseShareFile.size` (via ReverseShare.creatorId). This should be a Prisma raw query or two aggregate queries combined, moved to the quota repository.

### 4. Extend disk-space endpoint

`GET /storage/disk-space` already has two code paths:
- **Admin**: returns physical disk info (`statfs()`) — keep as-is
- **Non-admin**: returns logical quota info — currently broken (frontend doesn't call it for regular users)

Refactor the non-admin path to use `resolveEffectiveLimits()` and `calculateStorageUsed()`, and enrich the response:

```json
{
  "diskSizeGB": 10.0,
  "diskUsedGB": 5.0,
  "diskAvailableGB": 5.0,
  "uploadAllowed": true,
  "warningLevel": "none",
  "maxFileSize": 1073741824,
  "percentage": 50
}
```

The existing fields (`diskSizeGB`, `diskUsedGB`, `diskAvailableGB`, `uploadAllowed`) keep backward compatibility with the admin view. New fields (`warningLevel`, `maxFileSize`, `percentage`) are added for the quota widget.

Warning levels: `none` (< 80%), `warning` (80-89%), `critical` (90-99%), `exceeded` (≥ 100%).

Enable the frontend `useSystemStatus` hook to call this endpoint for all authenticated users, not just admins.

### 5. Admin endpoints (extend existing user management)

Follows existing pattern (`/users/:id/activate`, `/users/:id/deactivate`):

- `GET /users/:id/quota` — returns effective limits + current usage + warning level (admin-only)
- `PATCH /users/:id/quota` — set `maxFileSizeOverride` and/or `maxTotalStorageOverride` (admin-only)
  - Accepts `null` (clear override), `0` (unlimited), or positive BigInt (explicit limit)
- Extend `GET /users/:id` response to include `maxFileSizeOverride` and `maxTotalStorageOverride` fields

### 6. Multipart cleanup

Verify if S3/RustFS has `AbortIncompleteMultipartUpload` lifecycle policy. If not, document as a deployment prerequisite. No application code needed — this is an S3 configuration concern.

## Frontend Changes

### 1. Quota widget (dashboard)

Replace the current placeholder in `system-status.tsx` `UserView` component:
- Call `GET /storage/disk-space` for all authenticated users (not just admins)
- Display: progress bar with `usedBytes / limitBytes`, human-readable sizes ("5.0 GB / 10.0 GB")
- Color coding: default → yellow (warning, 80%) → orange (critical, 90%) → red (exceeded, 100%)
- If `limitBytes === 0` (unlimited): show usage only, no progress bar, label "Unlimited"

### 2. Over-quota banner

When `warningLevel === "exceeded"`:
- Persistent banner on dashboard/home page
- Message: "Your storage quota is exceeded. You cannot upload new files until you free up space by deleting existing files or shares."
- Style: red/error variant, not dismissible

When `warningLevel === "warning"` or `"critical"`:
- Dismissible warning banner
- Message: "You're using {percentage}% of your storage quota."

### 3. Upload flow

- Before upload: check quota status, show warning if close to limit
- On upload rejection (400 INSUFFICIENT_STORAGE): display clear error message explaining the quota situation

### 4. Reverse share creation

- If user is over quota: show warning that reverse share uploads will still count toward their quota, but won't be blocked
- No hard block on reverse share creation

### 5. Admin — user quota management

In the admin user management panel:
- Display: current usage, effective limits (resolved), override values
- Edit: `maxFileSizeOverride` and `maxTotalStorageOverride` with the same `FileSizeInput` component used for global settings
- Clear button to reset to "inherit" (null)
- "Unlimited" toggle option (sets to 0)
