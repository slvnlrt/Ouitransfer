# 7.1 — Systemic Error Handling & Dashboard Redesign

## Goal

Overhaul the application's error handling to be consistent, role-aware, and user-friendly across all layers. Redesign the dashboard top section into a unified "System Status" card that adapts content by role. Fix all 6 bugs from `features/BUGS.md` as part of this work.

## Context

Post-6.x testing revealed that while the server has solid error infrastructure (`AppError` hierarchy, `globalErrorHandler`), the frontend has 4-5 inconsistent patterns for parsing and displaying API errors. Some frontend code matches on human-readable error messages (fragile), and the dashboard shows raw/generic errors when services are unavailable. The dashboard also has layout issues and a missed opportunity to show meaningful metrics.

## Scope

Two interconnected workstreams:

1. **Systemic Error Handling** — server-side code registry, frontend unified error parser, role-aware display
2. **Dashboard Redesign** — unified "System Status" card (replaces `SystemHealth` + `StorageUsage`), new admin metrics endpoint

All 6 bugs (B-1 through B-6) are addressed as part of this work.

The frontend additionally defines client-only codes (never sent by server) in `apps/web/src/utils/api-error.ts`:

```ts
export const ClientErrorCodes = {
  NETWORK_ERROR: "NETWORK_ERROR",       // Server didn't respond at all
  UNKNOWN_ERROR: "UNKNOWN_ERROR",       // Unrecognized error shape

```

**Migration:**
- `AppError` subclasses: use `ErrorCodes.X` instead of string literals
- `globalErrorHandler`: use registry for all synthesized codes
- Services: normalize ad-hoc codes (`fileSizeExceeded` → `FILE_SIZE_EXCEEDED`, `insufficientStorage` → `INSUFFICIENT_STORAGE`)
- Convention: `SCREAMING_SNAKE_CASE` for all error codes
- Both `apps/server` and `apps/web` import from `@ouitransfer/shared/error-codes`

### 2. Server: Timestamp in Error Responses

Modify the `ErrorResponse` shape in `globalErrorHandler`:

```ts
interface ErrorResponse {
  error: string;             // Human-readable message (client-safe)
  code: string;              // Machine-readable error code
  statusCode: number;        // HTTP status code
  timestamp: string;         // ISO 8601 timestamp
  details?: Record<string, unknown>; // Optional structured data
}
```

Update `ErrorResponseSchema` (Zod schema used in route definitions) to include `timestamp: z.string()`.

The timestamp is generated at error-handling time (`new Date().toISOString()`).

### 3. Server: Standardize Share Error Codes

Endpoints returning password-related errors for shares currently use human-readable messages. Ensure they return proper codes:

- Share access with missing password: `code: "PASSWORD_REQUIRED"` (in addition to `error: "Password required"`)
- Share access with wrong password: `code: "INVALID_PASSWORD"`
- Expired share access: `code: "SHARE_EXPIRED"` or `GONE`
- Max views reached: `code: "MAX_VIEWS_REACHED"` or `GONE`

### 4. Server: New Endpoints

#### `GET /health/status` (public, no auth)

Lightweight health status for non-admin users:

```ts
{
  status: "healthy" | "degraded" | "unhealthy";
}
```

Runs the same checks as `/health` but returns only the aggregate status. No component details, no uptime.

#### `GET /admin/stats` (admin-only, JWT protected)

Platform-wide metrics for the admin dashboard:

```ts
{
  users: { total: number; active: number };
  files: { total: number };
  shares: { active: number; expired: number };
  reverseShares: { active: number };
}
```

Implementation:
- `users.total`: `prisma.user.count()`
- `users.active`: `prisma.user.count({ where: { isActive: true } })`
- `files.total`: `prisma.file.count()`
- `shares.active`: shares where `(expiration > now OR expiration IS NULL)` — a share is "active" if not expired by date (max views is a per-access check, not a state; shares aren't marked inactive when views are exhausted)
- `shares.expired`: `prisma.share.count({ where: { expiration: { lte: now } } })` — only date-expired shares
- `reverseShares.active`: `prisma.reverseShare.count({ where: { isActive: true, expiration: { gt: now } OR expiration: null } })`

### 5. Frontend: Centralized Error Parser

**File:** `apps/web/src/utils/api-error.ts`

```ts
export interface ApiError {
  code: string;              // Machine-readable code from server, or derived client-side
  message: string;           // Human-readable message
  statusCode: number;        // HTTP status (0 for network errors)
  timestamp: string;         // From server response, or generated client-side
  details?: Record<string, unknown>;
  isNetworkError: boolean;   // True when server didn't respond at all
}

/** Parse any error into a structured ApiError */
export function parseApiError(error: unknown): ApiError;

/** Format for user display: title + optional support reference */
export function formatErrorForDisplay(apiError: ApiError): {
  title: string;       // i18n-resolved message
  description?: string; // Additional context if available
  supportRef: string;  // "{code} • {HH:mm:ss}" for user to report
};
```

**Parsing logic:**
1. `axios.isAxiosError(error)` with `error.response` → extract `{code, error, statusCode, timestamp, details}` from body
2. `axios.isAxiosError(error)` without `error.response` → `{ code: "NETWORK_ERROR", statusCode: 0, isNetworkError: true }`
3. Standard `Error` → `{ code: "UNKNOWN_ERROR", message: error.message }`
4. Anything else → `{ code: "UNKNOWN_ERROR", message: "An unexpected error occurred" }`

**Display logic:**
- `formatErrorForDisplay` uses an i18n mapping: `errors.codes.{code}` → localized message
- Falls back to `apiError.message` if no i18n key exists for the code
- `supportRef` formatted as `"{code} • {HH:mm:ss}"` using the timestamp

**Migration:**
- Delete `apps/web/src/utils/getErrorData.ts` after migrating all callers
- Replace all direct `error.response?.data?.error` / `error.response?.data?.code` access with `parseApiError()`
- Replace message-matching in `use-public-share.ts`, `use-reverse-share-upload.ts` with code-matching

### 7. Frontend: Upload Error Handling (B-3)

In `use-uppy-upload.ts`, the error callbacks (getUploadParameters, signPart, completeMultipart, upload-error event) will:

1. Wrap errors through `parseApiError()` to get structured data
2. For network errors (S3 unreachable): produce `code: "STORAGE_UNREACHABLE"`, clear message
3. For HTTP errors from S3: map status codes to meaningful messages
4. Display via `formatErrorForDisplay()` — no more "Unknown error `{}`"

The `upload-error` Uppy event handler will show a toast with the formatted error instead of the raw object.

### 8. Frontend: Hook Migration

All hooks currently parsing errors manually will be migrated to use `parseApiError()`:

| Hook | Current Pattern | Migration |
|------|----------------|-----------|
| `use-file-upload.ts` | `getErrorData()` | `parseApiError()` |
