# 8.2 — Email Notifications

**Status:** Not started
**Depends on:** — (SMTP settings already exist)

## Summary

Comprehensive email notification system covering account lifecycle, share events,
and configurable user preferences.

## Scope

### Account Lifecycle
- Account creation welcome email
- Password reset email (flow may already exist — verify current state)

### Share Notifications
- **Invite mode** for shares and reverse-shares: instead of just generating a URL,
  optionally specify recipient email(s) / name(s) and send invitation emails
  - Each invitee gets a personal link with unique access credentials
  - Enables download/upload tracking per invitee (see 8.3)
- Share password included in invitation email (when applicable)
- Share expiration reminder (e.g., "your share expires in 24h")

### Activity Notifications (per-share settings)
- Download notification: email when someone downloads from your share
- Upload notification: email when someone uploads to your reverse share
- Inactivity alert: email when nobody has downloaded after N days (configurable)

### Service / Maintenance Emails
- Quota warning: daily reminder when user is near/over quota
- Share expired: notification when a share auto-expires
- Files auto-deleted: notification when cleanup removes old files

### User Preferences
- Global notification preferences (per-account settings page)
- Per-share notification toggle (on the share creation/details modal)
- Email frequency: immediate, daily digest, or disabled

### SMTP Test
- "Send test email" button in Settings > Email (with recipient address input)
- Currently only "Test connection" exists — add actual email delivery test

## Existing MVP — Share Recipient Notifications

A basic "notify recipients" flow is already coded end-to-end, predating this spec.

### What exists

| Layer | Location | What it does |
|-------|----------|--------------|
| Route | `POST /shares/:shareId/notify` (`share/routes.ts:512`) | Authenticated, takes `{ shareLink: string }` |
| Service | `shareService.notifyRecipients()` (`share/service.ts:444`) | Iterates all recipients, calls `emailService.sendShareNotification()` per recipient |
| Email | `emailService.sendShareNotification()` (`email/service.ts:222`) | Sends HTML email (green theme, "Access Shared Files" CTA, sender name, share name) |
| Frontend API | `notifyRecipients()` (`http/endpoints/shares/index.ts:200`) | `POST /api/shares/recipients/notify/:shareId` |
| Proxy | `proxy-routes.ts:393` | Rewrites to `POST /shares/:shareId/notify` |
| UI | `RecipientSelector` (`components/general/recipient-selector.tsx`) | "Notify All", "Notify Selected", per-recipient notify icon |

### How it works

1. User creates a share with an **alias** (required — the notify buttons are hidden without one)
2. User adds recipients via the `RecipientSelector` component
3. User clicks "Notify All" — frontend builds `shareLink` = `window.location.origin/s/{alias}`, calls the API
4. Backend sends one email per recipient via SMTP (must be configured in Settings > Email)

### Known issues

1. **BUG: "Notify Selected" sends to ALL, not just selected.** `handleNotifySelected()` builds `emailsToNotify` from `selectedForAction` but never passes it to the API. The backend route has no `emails` filter parameter — it always notifies every recipient on the share. Same issue for the per-recipient notify icon button.
2. **No selective notify API.** The `POST /shares/:shareId/notify` route doesn't accept an email list. Fixing bug #1 requires adding an optional `emails` field to the request body and filtering server-side.
3. **No notification tracking.** No field records whether a recipient was already notified, so repeated clicks spam the same person.
4. **Hardcoded green theme.** The email template uses `#22B14C` (old green brand color), not the current indigo palette. Should be updated when 8.2 introduces a proper template system.
5. **English-only email.** No i18n — the email subject and body are hardcoded in English regardless of user locale.

### Relationship to 8.2

This MVP covers only the "send share link to recipients" use case. The 8.2 spec is much broader (account lifecycle, activity notifications, digests, preferences, templates). The MVP should be refactored/absorbed into 8.2 rather than extended independently.
