Complete overhaul of the email system: replace the current inline-template, synchronous, English-only email service with a modular, queue-based, i18n-ready notification system. Adds visitor tracking on shares, invite mode with per-recipient tracking tokens, user notification preferences, and comprehensive notification types covering account lifecycle, share events, and system alerts.

2. **Visitor identification & tracking** — know who accesses shares (invite tokens, identification form, audit trail)
3. **User notification preferences** — per-type frequency control (immediate / daily digest / disabled)
4. **Comprehensive notification catalog** — 22 notification types covering all system events
5. **Fix all 5 existing MVP bugs** — selective notify, notification tracking, theme, i18n

## 1. Architecture

Complete refactoring of `apps/server/src/modules/email/` into 5 layers:

```
email/
  service.ts          → EmailService (orchestrator: resolve template + locale + check prefs + enqueue)
  transport.ts        → SmtpTransport (SMTP connection, pooling, raw send)
  queue.ts            → EmailQueueScheduler (poll DB, send, retry, digest hook)
  templates/
    base-layout.ts    → renderLayout({ subtitle, body, cta?, infoBox?, unsubscribeUrl? }) → { html, text }
    share-invitation.ts
    share-accessed.ts
    share-downloaded.ts
    password-reset.ts
    welcome.ts
    ... (one file per notification type)
  i18n/
    loader.ts         → t(locale, key, params) → string
    messages/
      en.json
      fr.json
      ... (23 languages)
```

### Email send flow

1. A business module calls `emailService.send("share_invitation", { to, locale, userId?, data })` — fully type-safe via a discriminated type map (see below).
2. `EmailService` checks if SMTP is enabled. If not, returns silently.
3. For non-critical types: resolves user notification preference (see [Section 6](#6-user-preferences--admin) for cascade logic). If `disabled`, stops.
4. Resolves the template function for the type, applies i18n, generates `LayoutSlots`.
5. Calls `renderLayout()` to produce final HTML + plain text.
6. Inserts an `EmailJob` row in DB:
   - `status: "pending"` for immediate frequency → `htmlBody`/`textBody` pre-rendered, `payload` null
   - `status: "digest_pending"` for daily digest frequency → `payload` stored as JSON, `htmlBody`/`textBody` null (rendered later by digest aggregation)
   - `priority: 1` for critical emails (password reset, welcome, etc.)
7. For `priority: 1` jobs: emits a wake-up signal to the queue scheduler for immediate processing (see [Section 4](#4-queue--scheduler)).
8. Returns immediately — the caller never waits for SMTP.

### Type-safe send API

The `emailService.send()` method uses a TypeScript type map to enforce compile-time correctness:

```typescript
// Type map: notification type → required data shape
type EmailPayloads = {
  share_invitation: ShareInvitationData;
  password_reset: PasswordResetData;
  welcome: WelcomeData;
  share_accessed: ShareAccessedData;
  // ... one entry per notification type
};

// Type-safe send method
async send<T extends keyof EmailPayloads>(
  type: T,
  options: { to: string; locale: string; userId?: string; data: EmailPayloads[T] }
): Promise<void>
```

Passing the wrong data shape for a notification type is a compile-time error. Adding a new notification type requires adding an entry to `EmailPayloads` — the compiler then enforces that all callers provide the correct data.

### Notification catalog as single source of truth

All notification metadata is defined in a single `notificationCatalog` object:

```typescript
const notificationCatalog = {
  share_invitation: {
    render: renderShareInvitation,
    payloadSchema: ShareInvitationDataSchema, // Zod schema for payload validation
    priority: 0,
    isCritical: false,
    defaultFrequency: "immediate" as const,
    configurable: false, // one-shot, not in preferences page
    hasUnsubscribe: false,
    requiredI18nKeys: ["shareInvitation.subject", "shareInvitation.body", ...],
  },
  password_reset: {
    render: renderPasswordReset,
    payloadSchema: PasswordResetDataSchema,
    priority: 1,
    isCritical: true,
    defaultFrequency: "immediate" as const,
    configurable: false,
    hasUnsubscribe: false,
    requiredI18nKeys: ["passwordReset.subject", "passwordReset.body", ...],
  },
  // ... one entry per type
} as const satisfies Record<string, NotificationTypeConfig>;
```

This single object derives:
- The `EmailPayloads` type map (compile-time type safety for `send()`)
- The template registry (queue scheduler looks up `catalog[type].render`)
- The preferences page rows (filter `configurable: true`)
- The i18n key validation at startup (`catalog[type].requiredI18nKeys`)
- The Section 10 catalog table (this spec section is a human-readable view of the code object)

Adding a new notification type = add one entry to `notificationCatalog` + template function + i18n keys. Everything else (type safety, preferences, i18n validation) follows automatically.

**Type derivation (how compile-time safety works):**

```typescript
// 1. Catalog is the single source of truth
const notificationCatalog = { share_invitation: { payloadSchema: ShareInvitationDataSchema, ... }, ... } as const;

// 2. Keys are derived from the catalog
type NotificationKey = keyof typeof notificationCatalog;

// 3. EmailPayloads maps each key to its Zod-inferred type
type EmailPayloads = {
  [K in NotificationKey]: z.infer<(typeof notificationCatalog)[K]["payloadSchema"]>
};

// 4. send() uses the narrowed key
async send<T extends NotificationKey>(type: T, options: { to: string; locale: string; data: EmailPayloads[T] }): Promise<void>
```

The catalog's `as const` preserves literal string keys. `satisfies Record<NotificationKey, NotificationTypeConfig>` ensures each entry has the required shape without widening. `EmailPayloads` is derived, never manually maintained.

The `EmailQueueScheduler` picks up pending jobs and sends them via `SmtpTransport`.

### SmtpTransport

Replaces the current duplicated `createTransporter()` logic (130 lines copy-pasted between `createTransporter` and `testConnection`).

```typescript
class SmtpTransport {
  private transporter: nodemailer.Transporter | null = null;
  private configHash: string | null = null;

  async getTransporter(): Promise<nodemailer.Transporter>
```

## 2. Database Schema

### New model: `EmailJob`

Persistent email queue. ALL emails go through this table, including "immediate" ones.

```prisma
model EmailJob {
  id            String    @id @default(cuid())
  type          String    // notification type key (e.g., "share_invitation")
  to            String    // recipient email address
  subject       String    // rendered subject line
  htmlBody      String    // rendered HTML (stored to avoid re-rendering on retry)
  textBody      String    // rendered plain text
  locale        String    @default("en")
  status        String    @default("pending")
  // Statuses: pending | digest_pending | processing | sent | failed
  priority      Int       @default(0) // 0 = normal, 1 = high (password reset, etc.)
  attempts      Int       @default(0)
  maxAttempts   Int       @default(3)
  nextAttemptAt DateTime  @default(now())
  lastError     String?   // last failure message
  lockedAt      DateTime? // set when status transitions to 'processing' (crash recovery)
  sentAt        DateTime?
  createdAt     DateTime  @default(now())

  // Raw data for digest aggregation
  payload String? // JSON-serialized original data: { v: 1, type: string, data: {...} }.
                  // Versioned so digest aggregation can handle schema changes across cycles.
                  // Filled for digest_pending jobs (htmlBody/textBody are null).
                  // Null for immediate jobs (htmlBody/textBody are pre-rendered).
                  // Validated against the type's payloadSchema (from notificationCatalog) at aggregation time.

  // Headers
  listUnsubscribe String? // List-Unsubscribe header value (for RFC 8058)

  @@index([status, nextAttemptAt]) // for the queue polling query
}
```

**Design decisions:**
- **Immediate jobs:** HTML and text are pre-rendered at enqueue time (`htmlBody`/`textBody` filled, `payload` null). This avoids re-rendering on retry and ensures the email content is frozen at creation.
- **Digest jobs:** Raw data is stored as JSON (`payload` filled, `htmlBody`/`textBody` null). The digest scheduler aggregates multiple payloads into a single summary email and renders at aggregation time.
- `digestGroupKey` enables future digest aggregation: `SELECT * FROM EmailJob WHERE status = 'digest_pending' GROUP BY digestGroupKey`.
- `relatedId` is a free-form string for context — not a foreign key (the related entity might be deleted by the time the job is processed).

### New model: `NotificationPreference`

Per-user, per-type notification settings.

```prisma
model NotificationPreference {
  id        String @id @default(cuid())
  userId    String
  user      User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  type      String // notification type key
  frequency String @default("immediate") // immediate | daily_digest | disabled

  @@unique([userId, type])
}
```

When no preference exists for a user+type, the server-side default for that type is used (see [Section 10](#10-notification-type-catalog) for defaults).

### New model: `ShareVisit`

Tracks every identified or anonymous access to a share.

```prisma
model ShareVisit {
  id           String   @id @default(cuid())
  shareId      String
  share        Share    @relation(fields: [shareId], references: [id], onDelete: Cascade)
  recipientId  String?  // FK to ShareRecipient (if identified via tracking token)
  recipient    ShareRecipient? @relation(fields: [recipientId], references: [id], onDelete: SetNull)
  visitorName  String?  // from identification form
  visitorEmail String?  // from identification form
  ipAddress    String?
  userAgent    String?
  action       String   // "access" | "download"
  fileId       String?  // which file (for downloads). Free-form, no FK — file may be deleted later.
  createdAt    DateTime @default(now())

  @@index([shareId, createdAt]) // for paginated activity log queries
}
```

**Retention:** `ShareVisit` rows are NOT automatically cleaned up in 8.2. For popular public shares, this table may grow large. A `shareVisitRetentionDays` config key and cleanup pass are deferred to 5.2 (which already implements retention schedulers). For 8.2, the table grows unbounded — acceptable for a pre-production app with no existing users.

## 3. Templates & i18n

### Base layout

A single TypeScript function that produces both HTML and plain text:

```typescript
interface LayoutSlots {
  subtitle: string;                      // below app name in header ("Shared Files", etc.)
  body: string;                          // main HTML content
  cta?: { url: string; label: string };  // optional action button
  infoBox?: string;                      // optional "Important:" callout
  unsubscribeUrl?: string;               // absent for critical emails
}

interface LayoutConfig {
  appName: string;
}

function renderLayout(slots: LayoutSlots, config: LayoutConfig): { html: string; text: string }
```

**Visual design:**
- Indigo theme (hue 265), consistent with the 6.3 visual redesign
- Responsive single-column layout, max 600px, all inline styles (Outlook compatibility)
- Header: app name + subtitle on indigo background
- Body: white background, system font stack
- CTA button: indigo background, white text, rounded
- Info box: left indigo border, light gray background
- Footer: "This email was sent by {appName}", "Powered by Ouitransfer" link
- Plain text version auto-generated by stripping HTML tags + formatting (indentation, separators)

**Email headers (when `unsubscribeUrl` is provided):**
- `List-Unsubscribe: <{unsubscribeUrl}>`
- `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058)

### Per-type templates

Each notification type is a pure function:

```typescript
// Example: templates/share-invitation.ts
interface ShareInvitationData {
  senderName: string;
  shareName: string;
  shareLink: string;  // includes tracking token if applicable
  hasPassword: boolean;
  expiresAt?: string; // ISO date
}

function renderShareInvitation(data: ShareInvitationData, t: TranslationFn): LayoutSlots
```

- Receives typed data + translation function
- Returns `LayoutSlots` — the base layout handles final rendering
- Pure function, no side effects — trivially unit-testable

### i18n system

**Files:** `apps/server/src/modules/email/i18n/messages/{locale}.json`

```json
{
  "shareInvitation": {
    "subject": "{appName} - {shareName} shared with you",
    "subtitle": "Shared Files",
    "body": "<strong>{senderName}</strong> has shared <strong>\"{shareName}\"</strong> with you.",
    "cta": "Access Shared Files",
    "info": "This share may have an expiration date or view limit. Access it as soon as possible.",
    "infoPassword": "This share is password-protected. The password was shared with you separately."
  },
  "common": {
    "footer": "This email was sent by <strong>{appName}</strong>",
    "footerIgnore": "If you didn't expect this email, you can safely ignore it.",
    "poweredBy": "Powered by Ouitransfer",
    "unsubscribe": "Unsubscribe from these notifications"
  }
}
```

**Translation function:**

```typescript
function t(locale: string, path: string, params?: Record<string, string>): string
```

- Loads JSON file for the locale (cached in memory after first load)
- Resolves dot-separated path (e.g., `"shareInvitation.subject"`)
- Interpolates `{key}` placeholders with provided params
- **Fallback chain:** requested locale → `en` → throw error (missing key in `en` is a bug)
- **Pluralization:** two-key approach — `"key.one"` / `"key.other"`, selected by the template based on count

**Initial delivery:** `en` and `fr` complete. The 21 other languages ship with `en` content as placeholder, translated in a dedicated i18n pass later.

**Validation at startup:** On server boot, verify that `en.json` has all expected keys. The expected keys are declared in the `notificationCatalog` — each entry has a `requiredI18nKeys` array (see [Section 1](#1-architecture)). This makes the key list co-located with the template that uses them. Fail fast if keys are missing — this catches typos and forgotten translations during development. Template functions must use only constant string keys (no dynamic path construction) to keep the validation accurate.

## 4. Queue & Scheduler

### EmailJob lifecycle

```
pending → processing → sent
                    ↘ failed (retries left?) → pending (with backoff)
                                             ↘ failed (max attempts) → dead (stays in DB)

digest_pending → (daily aggregation, implemented later) → pending (digest email) → ...
```

### EmailQueueScheduler

Same chained `setTimeout` pattern as existing schedulers (audit retention, LDAP sync):

- **Poll interval:** 30 seconds (configurable via `emailQueueIntervalSeconds` config key)
- **Wake-up signal:** When a `priority: 1` job is enqueued, `EmailService` emits an event that triggers an immediate poll cycle. Implementation: simple Node.js `EventEmitter` — the scheduler listens for `"wake"` events and schedules an immediate tick when received. If a batch is currently being processed, the wake signal queues a follow-up tick after the current batch completes. Worst-case latency = current batch processing time (typically < 5s for 10 emails), not 30s.
- **Batch size:** 10 jobs per tick (prevents monopolizing the event loop)
- **Selection query:** `WHERE status = 'pending' AND nextAttemptAt <= now() ORDER BY priority DESC, createdAt ASC LIMIT 10`
- **Concurrency:** Sequential within batch (one email at a time — SQLite doesn't benefit from concurrent writes)
- **Locking:** Job set to `processing` (with `lockedAt` timestamp) before send attempt. On restart, `processing` jobs where `lockedAt` is older than 5 minutes are reset to `pending`.
- **Single-process assumption:** The queue scheduler assumes a single Node.js process. There is no distributed locking. If the app is ever scaled to multiple workers, the scheduler must be limited to a single designated worker (e.g., via an environment flag). This is consistent with all existing schedulers (LDAP sync, audit retention, login attempts cleanup). The wake-up EventEmitter is in-process only — multi-process deployments fall back to polling.
- **Scheduler lifecycle:** The `EmailQueueScheduler` is a singleton initialized at server boot (same pattern as `AuditRetentionScheduler`). The scheduler exposes `start()` / `stop()` methods. `stop()` removes all EventEmitter listeners and clears pending timeouts. Registered with Fastify's `onClose` hook for graceful shutdown. In tests, each test that initializes the app must call `stop()` in teardown to prevent listener leaks.
- **Index:** `@@index([status, nextAttemptAt])` on `EmailJob` to ensure the polling query doesn't degrade as the table grows.

### Retry with exponential backoff

- `maxAttempts`: 3 (configurable via `emailQueueMaxRetries`)
- Delays: 1 min, 5 min, 30 min (exponential)
- `nextAttemptAt` recalculated on each failure
- After max attempts: status set to `failed` permanently, `lastError` populated
- **Render failure vs SMTP failure:** If a job fails during template rendering (missing i18n key, invalid payload), it is marked `failed` immediately with `attempts` forced to `maxAttempts` (no retry — the same render error will recur). Only SMTP failures are retried. The `lastError` field distinguishes: `"render: Missing key shareInvitation.subject in en"` vs `"smtp: Connection refused"`.
- Failed jobs are never deleted (consultable by admin in the queue stats)

### Digest scheduler (design-ready, implementation deferred)

The schema and preference model support digests from day one. What's deferred is:

- The daily aggregation query (`GROUP BY digestGroupKey` on `digest_pending` jobs)
- The digest email template (summary of N events)
- The scheduler hook that runs once daily at configurable hour

**What's built now:**
- `EmailJob.digestEligible`, `digestGroupKey`, and `payload` fields
- `NotificationPreference.frequency` column supports `"daily_digest"` value in DB
- `EmailService.send()` creates jobs with `status: "digest_pending"` and stores raw `payload` (no HTML rendering) when preference is digest
- Config key `emailDigestHour` (default 8) is registered

**What's deferred:**
- Digest template rendering
- Aggregation query and daily scheduler pass

**UI for digest option:** The "Daily digest" frequency option is **not exposed in the UI** until the digest feature is implemented. The preference dropdown only shows "Immediate" and "Disabled" for now. This prevents users from selecting a mode that silently swallows their notifications. When digest is implemented, the option is added to the dropdown — no schema or API changes needed.

**YAGNI justification for digest schema fields:** The `digestEligible`, `digestGroupKey`, and `payload` fields on `EmailJob` are inert in 8.2 — no code path populates them (since the UI doesn't expose `daily_digest`). They are retained because (a) adding columns to a SQLite table later requires a migration on user data, while shipping them now costs nothing (empty defaults), and (b) the `payload` field design (versioned JSON) was validated during brainstorming and influences the pre-rendering decision for immediate jobs — removing it would require re-designing when digests ship. The `NotificationPreference.frequency` column also supports `daily_digest` in its schema, which is a free type-level guarantee. No code in `EmailService.send()` or the queue scheduler handles the `digest_pending` path in 8.2 — it's dead code that doesn't exist yet, not dead code that was written and abandoned.

### Priority emails

Critical emails (`password_reset`, `welcome`, `account_deactivated`, `account_reactivated`, `test_email`):
- `priority: 1` (processed before normal priority)
- Ignore user preferences (always `immediate`)
- No unsubscribe link

### Job cleanup

- Jobs with `status: "sent"` are purged after X days (configurable via `emailJobRetentionDays`, default 30)
- Cleanup runs as a pass within the queue scheduler (once per hour, not every tick)

### Config keys

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| (unsubscribe signing key) | (derived) | — | **Not a separate secret.** Derived at runtime via `crypto.createHmac("sha256", JWT_SECRET).update("unsubscribe").digest()`. This avoids adding yet another env var for self-hosters while still isolating the unsubscribe key space from auth JWTs. No persistence needed — the same derivation produces the same key on every boot as long as `JWT_SECRET` hasn't changed. If `JWT_SECRET` rotates, all unsubscribe links in already-sent emails become invalid (acceptable — worst case: user is re-subscribed until they unsubscribe again via UI). |
| `appUrl` | string | (required, no fallback) | Base URL of the application (e.g., `https://transfer.example.com`). Used for all links in emails (unsubscribe, share links, CTA buttons). This is a **global** `AppConfig` key (not per-module). The existing `LdapConfig.appUrl` should be migrated to use this global key to avoid divergence. Server refuses to send emails if `appUrl` is not configured (logs a warning, marks job as failed with "appUrl not configured"). |
| `emailQueueIntervalSeconds` | int | 30 | Queue poll frequency |
| `emailQueueMaxRetries` | int | 3 | Max send attempts per job |
| `emailDigestHour` | int | 8 | Hour of day for digest emails (0-23) |
| `emailJobRetentionDays` | int | 30 | Days before purging sent jobs |

## 5. Invite Mode & Visitor Tracking

### Three identification mechanisms

Shares support three complementary ways to identify visitors:

#### A. Invite mode (tracking token)

When the share creator sends invitations via email:

1. Each `ShareRecipient` receives a unique `trackingToken` at **creation time** (not at notify time) — generated via `crypto.randomBytes(...).toString("base64url")`, consistent with existing token generation patterns in the codebase (e.g., `auth/refresh-token.service.ts`). Generating at creation ensures tokens survive share updates (the current `updateShare` flow deletes and recreates recipient rows — this must be changed to upsert by `[shareId, email]` to preserve tokens and access stats).
2. The invitation email contains a personalized link: `/s/{alias}?t={TOKEN}`
3. When the visitor clicks:
   - Server resolves the `ShareRecipient` via the token
   - Records a `ShareVisit` with `recipientId` populated
   - Updates `lastAccessedAt` and increments `accessCount` on the recipient
4. The creator sees in share details: "Alice accessed 3 times, last access 2h ago"

**The token does not grant extra access.** If the share has a password, the visitor must still enter it. The token is purely for identification.

**Tracking token limitations:** If Alice forwards her invitation email to Bob, Bob's accesses are recorded as Alice's — the server cannot distinguish forwarded links. "Identified via tracking token" means "accessed through the email-targeted link," not "cryptographically verified identity." This is an inherent limitation of link-based tracking (same as any tracking pixel or UTM parameter). The share creator should understand that tracking shows which invitation link was used, not necessarily who used it.

#### B. Identification form

Like reverse shares, regular shares can require visitor identification:

1. Creator sets `nameFieldRequired` and/or `emailFieldRequired` on the share (HIDDEN / OPTIONAL / REQUIRED)
2. Before accessing content, the visitor sees a form (shown when at least one field is OPTIONAL or REQUIRED)
3. Submitted info is stored in `ShareVisit` (`visitorName`, `visitorEmail`)
4. **OPTIONAL semantics:** The form is displayed but the visitor can submit with empty optional fields. Same behavior as existing reverse share identification form. A visitor who leaves optional fields blank passes through — they appear as "partially identified" in the activity log.
5. **REQUIRED semantics:** The visitor must fill the required fields to proceed. Server validates and rejects empty values.
6. If the visitor has a tracking token, the form is **skipped only if** all REQUIRED fields are satisfied by the `ShareRecipient` record (email is always available via the recipient's email; name is available if `ShareRecipient.name` is set). If the share requires `nameFieldRequired = REQUIRED` and the recipient has no `name`, the form is shown pre-filled with the known email but the name field must be completed. The submitted name is saved to both the `ShareVisit` and the `ShareRecipient.name` for future visits.

#### C. Best-effort (audit)

When neither A nor B applies:
- IP address and User-Agent from the request are stored in `ShareVisit`
- This is the default for public anonymous shares

#### Combination matrix

| Situation | Identification | What's recorded |
|---|---|---|
| Public link, no identification | Anonymous | IP/UA in ShareVisit |
| Public link + identification required | Form | visitorName/Email in ShareVisit |
| Email invitation | Token (automatic) | recipientId in ShareVisit |
| Email invitation + identification required | Token (form skipped) | recipientId in ShareVisit |

### Notification triggers

When events occur on a share:

- **Access** (`share_accessed`): recorded when non-owner calls `GET /shares/alias/:alias` or `POST /shares/alias/:alias/access` (the content-revealing endpoints). **Not** recorded on metadata probes (`/shares/alias/:alias/metadata`) to avoid duplicate visits per page load.
- **Download** (`share_downloaded`): recorded when the frontend requests a presigned download URL via `POST /files/download-url` or a streaming download via `POST /files/download`. Both endpoints are extended with an optional `shareId` field in the request body.

  **How `shareId` propagates from the frontend:**
  - The share page component (`/s/{alias}`) knows its `shareId` from the initial share load.
  - All download buttons/actions on the share page pass `shareId` in the download request body.
  - Downloads from the user's own dashboard (My Files) do NOT pass `shareId` — no tracking needed.
  - If `shareId` is omitted, no `ShareVisit` is created and no notification fires.

  **Server-side validation:**
  - When `shareId` is provided, the server verifies that the file actually belongs to that share (via the `ShareFiles` join table). If the file is not in the claimed share, the `shareId` is silently ignored (no `ShareVisit`, no notification). This prevents inflating another share's activity.
  - The `checkFileAccess()` function already resolves which share(s) contain the file — the validation piggybacks on that lookup.

  **Important limitation:** Ouitransfer uses presigned S3 URLs — the actual byte transfer goes directly from the client to S3/RustFS, bypassing the server. Therefore "download" actually means "download URL requested" (for `POST /files/download-url`) or "streaming download started" (for `POST /files/download`). A presigned URL can be requested without being used, or used multiple times within its TTL. This imprecision is accepted as a reasonable trade-off — the alternative (streaming all downloads through the server) negates the performance benefit of presigned URLs for large file transfers, which is the app's core use case. The `lastDownloadedAt` field on Share is updated on URL issuance/download start. **5.2 dependency note:** The cleanup feature's inactivity detection relies on `lastDownloadedAt`. In normal usage, a presigned URL is consumed immediately after issuance, so the imprecision is negligible. 5.2's inactivity window (days/weeks) is orders of magnitude larger than a presigned URL's TTL (minutes).
- **Owner exclusion:** Only non-owner actions create `ShareVisit` rows and update `lastDownloadedAt`. The owner viewing or downloading their own share does not count as "activity" (this is critical for the inactivity alert feature to work correctly). Owner identification is based on JWT `userId` matching `share.creatorId`. If the owner accesses the share while logged out (no JWT), the server treats them as an anonymous visitor — a `ShareVisit` is created and a notification may fire. This is by design: without authentication, the server cannot know it's the owner.

For each event:
1. A `ShareVisit` row is created (always, regardless of notification preferences)
2. If the share creator has notifications enabled for that type → an `EmailJob` is created
3. The job payload includes the visitor's identity (name, email, or "anonymous")

### Inactivity alert

- Configured per-share: `inactivityAlertDays` (number of days without any download)
- The queue scheduler checks daily: shares where `inactivityAlertDays IS NOT NULL AND inactivityAlertSent = false AND (lastDownloadedAt IS NULL OR lastDownloadedAt < now() - inactivityAlertDays)`
- Sends a `share_no_activity` notification to the creator
- Sets `inactivityAlertSent = true`
- If a non-owner download occurs later, `inactivityAlertSent` is reset to `false` and `lastDownloadedAt` updated (allowing a future alert cycle)
- The `inactivityAlertSent` flag is sufficient to prevent spam: once set, no re-alert fires until real non-owner activity resets it. The owner checking their own share does not reset the flag (owner downloads are excluded from tracking). This means: one alert per inactivity period, no re-alert until genuine external activity occurs.

### Preference resolution cascade

When an event triggers a notification:

```
1. Is the type critical? (password_reset, welcome, account_deactivated, account_reactivated)
   → YES: enqueue with priority 1, skip all preference checks

2. Is SMTP enabled?
   → NO: do nothing, return silently

3. Resolve user preference for this type:
   → User has a NotificationPreference row → use stored frequency
   → No row → use server-side default for this type

4. Is the resolved frequency "disabled"?
   → YES: stop. Do not notify. (Global disabled ALWAYS wins, even over per-share overrides.
     This means an unsubscribe action correctly stops all emails for that type.)

5. Is there a per-share override? (notifyOnDownload on the share)
   → true: use "immediate" (upgrade from default/preference for this specific share)
   → false (default): use the frequency from step 3

6. Enqueue with appropriate status:
   → "immediate" → status: "pending"
   → "daily_digest" → status: "digest_pending"
```

### Unsubscribe (one-click, stateless)

Every non-critical email sent to internal users (with an account) includes an unsubscribe link. One-shot invitations to external recipients (types 5–6) do NOT include an unsubscribe link — they are manually triggered, non-recurring emails.

**Two-step mechanism (prevents email scanner auto-unsubscribe):**

1. Email contains a signed URL: `{appUrl}/api/notifications/unsubscribe?token={JWT}`
2. `GET /api/notifications/unsubscribe?token={JWT}` — **displays a confirmation page** ("Click to confirm you want to unsubscribe from {type} notifications"). This is a simple HTML page with a form containing a POST button. The GET request does NOT perform the unsubscribe — this is critical because email security scanners (Outlook Safe Links, Microsoft Defender, Gmail) automatically prefetch GET links, which would otherwise unsubscribe users without their consent.
3. `POST /api/notifications/unsubscribe` with body `{ token }` — **performs the actual unsubscribe.** Verifies the JWT, upserts `NotificationPreference` for that userId+type to `frequency: "disabled"`. Renders a success page.

**JWT design:**
- Payload: `{ userId, type, iat, exp }` — `exp` set to 90 days after `iat`
- Signed with a derived key: `crypto.createHmac("sha256", JWT_SECRET).update("unsubscribe").digest()`. This isolates the key space from auth JWTs without requiring a separate env var (see [Section 4 config table](#4-queue--scheduler))
- No separate table needed — stateless verification + preference update

**Conformance:** RFC 8058 headers on all non-critical emails sent to internal users:
- `List-Unsubscribe: <{appUrl}/api/notifications/unsubscribe?token={JWT}>`
- `List-Unsubscribe-Post: List-Unsubscribe=One-Click`

**Bounce handling:** Deferred to a future iteration. Not in scope for 8.2.

## 7. Migration of Existing Code

### Methods replaced

| Current method | New notification type | Notes |
|---|---|---|
| `sendPasswordResetEmail()` | `password_reset` | Priority 1, no preferences |
| `sendLdapWelcomeEmail()` | `welcome` | Priority 1, no preferences |
| `sendShareNotification()` | `share_invitation` | With tracking token, i18n, indigo theme |
| `sendReverseShareBatchFileNotification()` | `reverse_share_uploaded` | Respects user preferences |

All callers migrate to `emailService.send(type, { to, locale, userId?, data })`. The old monolithic `EmailService` class is deleted and replaced by the new architecture.

**Batch enqueue error semantics:** When notifying multiple recipients (e.g., `POST /shares/:shareId/notify`), each `EmailJob` insert is independent — not wrapped in a transaction. If one insert fails (unlikely — it's a simple DB write), the others still succeed. The caller logs the failure per-recipient but does not abort the batch. This matches the existing behavior where `sendShareNotification` errors are caught per-recipient.

### Callers to migrate

| File | Current call | Migration |
|---|---|---|
| `auth/service.ts` | `sendPasswordResetEmail()` (1 call) | `emailService.send("password_reset", ...)` |
| `ldap/sync.scheduler.ts` | `sendLdapWelcomeEmail()` (1 call) | `emailService.send("welcome", ...)` |
| `share/service.ts` | `sendShareNotification()` (loop) | `emailService.send("share_invitation", ...)` per recipient |
| `share/routes.ts` | `sendReverseShareBatchFileNotification()` (1 call) | `emailService.send("reverse_share_uploaded", ...)` |

### SmtpTransport refactoring

The current `createTransporter()` logic is duplicated between the regular send path and `testConnection()` (~130 lines of copy-paste). Both are replaced by `SmtpTransport` (see [Section 1](#1-architecture)).

### Recipient update refactoring

The current `updateShare` flow in `share/service.ts` deletes all recipients then recreates them on every share edit. This destroys tracking tokens and access stats. **Changed to a sync/upsert approach:**

1. Load existing recipients for the share (keyed by `[shareId, email]`)
2. Compare with the new list from the request
3. **Remove** recipients whose email is no longer in the list (actual deletion — tokens and stats are lost, which is correct for explicitly removed recipients)
4. **Add** new recipients not in the existing list (with fresh tracking tokens generated at creation)
5. **Keep** existing recipients unchanged (preserving `trackingToken`, `notifiedAt`, `lastAccessedAt`, `accessCount`)

This is possible because of the `@@unique([shareId, email])` constraint on `ShareRecipient`.

### Key behavior change

**Before:** Email sending is synchronous — the HTTP request waits for SMTP delivery (or failure).
**After:** Email sending is asynchronous — the HTTP request inserts an `EmailJob` in DB and returns immediately. The queue scheduler handles delivery.

This means:
- `POST /shares/:shareId/notify` returns instantly (no SMTP wait)
- Password reset returns instantly (the email is queued)
- If SMTP is temporarily down, emails will be retried automatically

### Payload note — expiring notifications

The `share_expiring` and `reverse_share_expiring` payloads include `expiresAt` (absolute ISO datetime) but NOT a computed `daysRemaining` field. The initial plan referenced `daysRemaining` but it was dropped during implementation — the template body uses `expiresAt` directly for unambiguous communication. If relative-time wording is desired ("expires in 3 days"), it can be computed from `expiresAt` in a future template enhancement.

### Expiration notifications (types 9, 14)

The queue scheduler checks daily for shares/reverse shares expiring within a configurable window:
- Config key (existing or new): `autoCleanupNotifyDaysBefore` (default 3)
- Query: shares where `expiration IS NOT NULL AND expiration BETWEEN now() AND now() + notifyDaysBefore`
- Each match creates an `EmailJob` for the share creator
- Two flags on the share model (`notifiedForExpiring` + `notifiedForExpired`) independently track "expiring soon" and "has expired" notifications, preventing duplicates. Both are reset to `false` in the share update handler (`PUT /shares/:id`) when the new `expiration` value is later than the current one (extended). Not reset when expiration is shortened or unchanged. The split into two fields (rather than a single `notifiedForExpiration`) is the correct design — it allows the "expiring" warning to be sent independently of the post-expiration notification.
