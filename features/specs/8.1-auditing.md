# 8.1 — Audit Trail / Activity Log

**Status:** In progress (spec phase)
**Depends on:** — (foundational infrastructure)

## Summary

System-wide audit trail that logs all significant actions performed in the application,
including public access events (share views, downloads, uploads). Provides an admin-facing
view for reviewing activity, and serves as the data layer for downstream features
(download tracking 8.3, email notifications 8.2).

## Decisions

1. **Admin-only visibility.** Audit logs are only visible to admins. No "my activity" view for regular users.
2. **No real-time.** No WebSocket streaming. Simple refresh / pagination.
3. **No sensitive data in metadata.** Passwords, tokens, and secrets are never logged. A runtime denylist of keys (`password`, `token`, `secret`, `bindPassword`, `clientSecret`, `smtpPass`, `twoFactorSecret`, `twoFactorBackupCodes`) is stripped in `logAuditEvent()` itself as a safety net.
4. **Configurable retention.** New admin setting `auditRetentionDays` (default 365, minimum 7, 0 = forever). Daily cleanup scheduler deletes older entries. The admin UI enforces the floor.
5. **Atomic counter for enforcement, audit events for observability.** `Share.views` is kept as an atomic integer counter for race-safe `maxViews` enforcement. `SHARE_ACCESS` audit events are logged in parallel for observability and analytics (8.3). The counter is the source of truth for limits; the events are the source of truth for "who accessed when."
6. **`maxViews` moves from `ShareSecurity` to `Share`.** It is a share-level limit, not a security credential.
7. **Visitor identity only where actually captured.** `visitorEmail`/`visitorName` metadata fields are only populated on events where the visitor actively identifies themselves: `REVERSE_SHARE_UPLOAD` (uploader fields), `SHARE_RECIPIENT_NOTIFY` (recipient email). For anonymous share access, only `ipAddress` and `userAgent` are recorded.
8. **Audit events are not the concurrency control mechanism.** Fire-and-forget is acceptable for all audit writes — they are observability, not enforcement. `Share.views` handles enforcement atomically.
9. **GDPR / data retention.** Audit logs retain `userId` strings after user deletion for forensic/security purposes. This is intentional — audit integrity overrides "right to be forgotten" for security records.
10. **`SHARE_ACCESS` is emitted from the share page load path only** (`getShare`/`getShareByAlias`), not from embed or file download requests. Embed range requests and file downloads emit their own distinct events. This prevents a single video playback from generating dozens of `SHARE_ACCESS` rows.
11. **LDAP audit events reference `LdapSyncLog`**, not duplicate it. The `LDAP_SYNC_COMPLETED` event's `targetId` points to the `LdapSyncLog.id` for details. The audit event provides the unified timeline; the sync log provides structured stats.
12. **Typed target types.** `targetType` is enforced via a `AuditTargetTypeSchema` Zod enum, same pattern as `AuditActionSchema`.
13. **WAL mode required.** The server must verify SQLite is in WAL journal mode on boot (`PRAGMA journal_mode`). Audit events add significant write volume; WAL mode prevents reader/writer contention.
14. **Proxy-aware IP.** `ipAddress` uses Fastify's `request.ip` which respects the `trustProxy` configuration. The spec assumes `trustProxy` is correctly configured for containerized deployments (behind nginx/reverse proxy). `userAgent` is capped at 512 characters in `logAuditEvent()`.
15. **Date filter semantics.** `dateFrom` is inclusive (>= start of day UTC), `dateTo` is inclusive (<= end of day UTC). Both are ISO 8601 date strings.

## Existing State

### What already exists
- **Prisma model:** `AuditLog { id, userId?, action, ipAddress, userAgent?, metadata?, createdAt }` with indexes on `(userId, createdAt)`, `(action, createdAt)`, `(createdAt)`. Table: `audit_logs`.
- **Service:** `logAuditEvent({ userId?, action, ipAddress, userAgent?, metadata? })` + `getAuditLogs({ userId?, action?, limit?, offset? })` in `modules/audit/service.ts`.
- **Route:** `GET /admin/audit-logs` (admin-only, paginated, filterable by userId/action).
- **12 actions covered:** `LOGIN_SUCCESS`, `LOGIN_FAILURE`, `LOGOUT`, `PASSWORD_CHANGE`, `PASSWORD_RESET`, `TWO_FACTOR_ENABLE`, `TWO_FACTOR_DISABLE`, `ADMIN_CONFIG_CHANGE`, `USER_CREATE`, `USER_DELETE`, `ACCOUNT_LOCKED`, `LOGIN_LOCKED`.
- **Callers:** `auth/routes.ts` (6 calls), `user/routes.ts` (3), `two-factor/routes.ts` (2), `app/routes.ts` (2), `login-attempts.service.ts` (1).
- **`Share.views`:** atomic Int counter, incremented in `getShare()`, skipped for share creator.
- **`ShareSecurity.maxViews`:** optional Int, enforced in `getShare()` and embed route (atomic `updateMany` guard).
- **`LdapSyncLog`:** structured sync log model with `startedAt`, `completedAt`, `status`, `trigger`, user/group stats, `details`. Already exists and is the detailed source for sync results.

### What changes
- `Share.views` — kept, but `maxViews` moves from `ShareSecurity` to `Share`.
- `ShareSecurity.maxViews` — removed from `ShareSecurity`.
- Share service — `getShare()` still increments `views` atomically AND emits `SHARE_ACCESS` audit event.
- Embed route — still uses atomic `updateMany` guard for `maxViews`, AND emits `FILE_EMBED_ACCESS` event (not `SHARE_ACCESS`).
- `AuditLog` model — enriched with `targetType` and `targetId` fields.

## Schema Changes

### Enrich `AuditLog` model

```prisma
model AuditLog {
  id         String   @id @default(cuid())
  userId     String?            // Authenticated actor (null for public/system)
  action     String
  ipAddress  String
  userAgent  String?            // Capped at 512 chars by service layer
  metadata   String?            // JSON — runtime denylist strips sensitive keys
  targetType String?            // Typed enum: share, reverse_share, file, folder, user, group, etc.
  targetId   String?            // Entity ID
  createdAt  DateTime @default(now())

  @@index([userId, createdAt])
  @@index([action, createdAt])
  @@index([createdAt])
  @@index([targetType, targetId, action, createdAt])
  @@map("audit_logs")
}
```

Note: the composite index `(targetType, targetId, action, createdAt)` replaces the simpler `(targetType, targetId, createdAt)` — it covers the `countAuditEvents` query pattern and all target-scoped filter queries.

### Move `maxViews` from `ShareSecurity` to `Share`

```diff
 model Share {
   id          String    @id @default(cuid())
   name        String?
   views       Int       @default(0)
+  maxViews    Int?
   expiration  DateTime?
   ...
 }

 model ShareSecurity {
   id        String   @id @default(cuid())
   password  String?
-  maxViews  Int?
   ...
 }
```

This is a reset migration — existing `maxViews` settings on dev databases are discarded. No data migration script needed.

### New admin setting

`auditRetentionDays` — type `number`, group `general`, default `365`. Value `0` = keep forever. Minimum value `7` enforced by the admin UI and API validation.

## Service Layer Changes

### `logAuditEvent()` — enriched signature with safety guards

```typescript
/** Keys stripped from metadata before persistence. */
const METADATA_DENYLIST = new Set([
  "password", "token", "secret", "bindPassword", "clientSecret",
  "smtpPass", "twoFactorSecret", "twoFactorBackupCodes",
  "currentPassword", "newPassword", "confirmPassword",
]);

export async function logAuditEvent(params: {
  userId?: string;
  action: AuditAction;
  ipAddress: string;
  userAgent?: string;       // Capped at 512 chars
  metadata?: Record<string, unknown>;
  targetType?: AuditTargetType;
  targetId?: string;
}): Promise<void> {
  // 1. Cap userAgent
  // 2. Strip denylist keys from metadata
  // 3. Validate targetType against enum
  // 4. prisma.auditLog.create(...)
}
```

All calls are fire-and-forget (no `await` at call sites). Audit events are observability — enforcement uses atomic counters.

### `getAuditLogs()` — enriched filters

```typescript
export async function getAuditLogs(params: {
  userId?: string;
  action?: AuditAction;
  targetType?: AuditTargetType;
  targetId?: string;
  dateFrom?: Date;          // Inclusive, start of day UTC
  dateTo?: Date;            // Inclusive, end of day UTC
  search?: string;          // Searches ipAddress, action (LIKE %term%) — NOT metadata
  limit?: number;           // Default 50, max 100
  offset?: number;
}): Promise<{ logs: AuditLogEntry[]; total: number }>
```

**Search restriction:** `search` queries structured fields (`ipAddress`, `action`) via `LIKE %term%`, not the `metadata` JSON blob. This avoids full table scans on the largest table. Metadata is viewable in the detail view but not searchable.

### `exportAuditLogs()` — streaming with ceiling

```typescript
export async function exportAuditLogs(params: {
  format: "csv" | "json";
  userId?: string;
  action?: AuditAction;
  targetType?: AuditTargetType;
  targetId?: string;
  dateFrom?: Date;          // Required for export
  dateTo?: Date;            // Required for export
  search?: string;
}): AsyncGenerator<string>  // Yields chunks for streaming
```

- `dateFrom` and `dateTo` are **required** for export (prevents unbounded queries).
- Hard ceiling of 100,000 rows. If exceeded, the response includes a warning header and truncates.
- Implementation uses cursor-based pagination internally (`findMany({ take: 1000, cursor })`) and yields chunks — never buffers the full result set.
- Route handler pipes the async generator to `reply.raw` with appropriate `Content-Type` and `Content-Disposition` headers.

### Retention scheduler

- Uses **chained `setTimeout`** pattern (matching LDAP sync scheduler), not `setInterval`.
- `initAuditRetentionScheduler()` called on server boot, same pattern as `initSchedulerOnBoot` for LDAP.
- Reads `auditRetentionDays` from `AppConfig` on each cycle (picks up config changes without restart).
- If retention > 0, deletes `AuditLog` records where `createdAt < now() - retentionDays` in batches (1000 at a time to avoid long-held locks).
- Logs `AUDIT_RETENTION_CLEANUP` event with `{ deletedCount, olderThan }`.
- Deletes are idempotent — no crash recovery needed beyond normal re-execution on next boot.

### WAL mode verification

On server boot, before registering routes, execute `PRAGMA journal_mode` and log a warning if not `wal`. This is a check, not an auto-set — the migration or deployment config should handle WAL mode.
