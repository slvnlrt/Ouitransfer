# 5.3 — LDAP / Active Directory Synchronization

**Status**: Spec
**Depends on**: 5.4 (Groups — done)
**Blocks**: —

---

## Goal

Import and synchronize user accounts from a corporate Active Directory into Ouitransfer. AD is the source of truth for identity and group membership of LDAP-managed users. Authentication remains local (app-specific passwords).

## Decisions

| Question | Decision | Rationale |
|----------|----------|-----------|
| Target directory | Active Directory only (no OpenLDAP/FreeIPA for V1) | Scope control |
| Auth approach | **Option B — LDAP as import source** | Server in DMZ — bind would expose AD credentials in app memory. App passwords isolate blast radius. See "Auth Approach" below. |
| Onboarding | Auto invite email + admin override + self-service reset | Email on first sync, admin can set password manually, users can reset via forgot-password flow |
| Self-service password reset | Enabled for LDAP users | Resets app password only, no security concern, reduces admin burden |
| Group sync strategy | Sync group (filter) + quota group mapping via `ldapDn` on Group model | Single group per user, first match wins |
| Nested AD groups | Direct membership only | KISS. Recursive (`memberOf:1.2.840.113556.1.4.1941:=`) can be added later if needed |
| Conflict (email collision) | Skip (non-blocking) in sync log | Expected case (e.g., pre-existing admin account). Not an error. |
| AD = source of truth | Local overrides allowed but reset on next sync | Manage LDAP users in AD, not in app |
| Deactivation vs deletion | Deactivate only (`isActive = false`), never delete | Files/shares preserved. Reactivation auto if user reappears in sync group. |
| Config storage | Dedicated `LdapConfig` table | Cohesive config block with sensitive data (bind password) |
| LDAP library | `ldapts` | TypeScript-native, promise-based, actively maintained |
| Scheduling | `node-cron` in-process | Configurable interval, re-entrance guard |
| UI | Dedicated admin page `/admin/ldap` | Too complex for settings page (config, test, sync, logs, group mapping) |

## Auth Approach — Why Option B

LDAP bind (Option A) means the application server acts as a credential proxy: AD passwords transit **in cleartext through app memory** at every login. In a DMZ deployment:

- If the server is compromised, an attacker can silently intercept domain credentials during normal logins
- AD passwords grant access to email, file shares, VPN, etc. — disproportionate blast radius
- This is the same reason the industry migrated from LDAP bind to SAML/OIDC

Option B (import + app passwords):
- The server **never sees** AD passwords — only a read-only service account connects to AD for sync
- Compromise yields bcrypt hashes of app-specific passwords — near-zero value
- Existing auth infrastructure (bcrypt, JWT, 2FA, lockout) is reused as-is
- Works even if AD is temporarily unreachable

The "extra password" cost is a **feature** (credential isolation), not a bug.

## Schema Changes

### New table: `LdapConfig`

| Field | Type | Notes |
|-------|------|-------|
| `id` | String (cuid) | PK |
| `enabled` | Boolean | Global on/off, default `false` |
| `serverUrl` | String | e.g., `ldaps://ad.corp.local:636` |
| `bindDn` | String | Service account DN |
| `bindPassword` | String | **Encrypted** (AES-256-GCM, key from `ENCRYPTION_SECRET` env var) |
| `searchBase` | String | e.g., `DC=corp,DC=local` |

| `emailAttribute` | String | Default `mail` |
| `displayNameAttribute` | String | Default `displayName` |
| `syncIntervalMinutes` | Int | Default `360` (6 hours) |
| `useTls` | Boolean | `true` = LDAPS, `false` = STARTTLS |
| `createdAt` | DateTime | |
| `updatedAt` | DateTime | |

### User model change

```prisma
model User {
  // ... existing fields
  ldapDn    String?   @unique   // DN in AD — null = local account
}
```

- `ldapDn != null` → LDAP-managed user (sync overwrites name, email, group)
- `ldapDn == null` → local account (unchanged behavior)
- No separate `isLdapUser` boolean — `ldapDn` serves as both identifier and marker

### Group model (existing)

The `ldapDn` field on `Group` (added in 5.4) is used for quota group mapping:

```prisma
model Group {
  // ... existing fields
  ldapDn    String?   // DN of the corresponding AD group — null = no AD mapping
}
```

## Server Architecture

### Module structure

```
apps/server/src/modules/ldap/
  config.repository.ts    — CRUD for LdapConfig (single row, upsert pattern)
  sync.repository.ts      — CRUD for LdapSyncLog
  ldap.client.ts          — ldapts wrapper (connect, bind, search, disconnect)
  sync.service.ts         — sync engine (diff, create/update/deactivate/skip logic)
  sync.scheduler.ts       — node-cron scheduling, re-entrance guard
  encryption.ts           — AES-256-GCM encrypt/decrypt for bind password
  controller.ts           — admin endpoint handlers
  routes.ts               — Fastify route definitions with Zod schemas
  dto.ts                  — Zod schemas for config, sync, test
```

### API Endpoints (admin-only)

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/admin/ldap/config` | Read config (bind password masked) |
| `PUT` | `/admin/ldap/config` | Create or update config (upsert) |
| `POST` | `/admin/ldap/test` | Test AD connection (bind + search sync group) |
| `POST` | `/admin/ldap/sync` | Trigger manual sync |
| `GET` | `/admin/ldap/sync/logs` | List sync history (paginated) |
| `GET` | `/admin/ldap/sync/logs/:id` | Get sync log detail (with skip/error details) |
| `GET` | `/admin/ldap/status` | Quick status: enabled, last sync result, next scheduled sync |

### Sync Cycle

```
1. Bind to AD with service account credentials
2. Search: members of syncGroupDn (direct membership)
3. For each AD user:
   a. Read attributes (username, email, displayName) via configured attribute mapping
   b. Read AD groups (memberOf attribute, direct only)
   c. Match first AD group whose DN matches an Ouitransfer group's ldapDn
4. Compare with local LDAP users (ldapDn IS NOT NULL):
   a. New (DN not in local DB)     → create account + send invite email
   b. Existing (DN matches)        → update name, email, group if changed
   c. Gone (local DN not in AD)    → deactivate (isActive = false)
   d. Returning (deactivated + back in AD) → reactivate (isActive = true)
5. Conflict (email used by a non-LDAP account) → skip, log with details
6. Write LdapSyncLog (stats + details)
```

### Scheduling

- `node-cron` expression derived from `syncIntervalMinutes`
- Starts on server boot if `enabled = true`
- Reloads dynamically when config is updated via `PUT /admin/ldap/config`
- **Re-entrance guard**: in-memory mutex. If a sync is already running, scheduled/manual triggers are rejected with "sync already in progress"

### Encryption

- `ENCRYPTION_SECRET` environment variable (required when LDAP is enabled)
- AES-256-GCM: random IV per encryption, stored alongside ciphertext
- Used for `bindPassword` in `LdapConfig`
- `GET /admin/ldap/config` returns `bindPassword: "••••••••"` (never the real value)
- `PUT /admin/ldap/config` with `bindPassword: ""` or omitted → keep existing password

## Frontend

### Page: `/admin/ldap`

Single admin page with three sections:

**1. Configuration**
- Form: server URL, TLS toggle, bind DN, bind password, search base, sync group DN
- Attribute mapping fields (username, email, displayName) with defaults pre-filled
- Sync interval (minutes)
- Enabled/disabled toggle
- "Test connection" button → calls `POST /admin/ldap/test`, shows structured result inline (bind OK, group found, N members)
- "Save" button

**2. Group Mapping Summary**
- Read-only table: Ouitransfer groups that have a `ldapDn` set (name → AD DN)
- Link to `/groups-management` for editing
- If no groups have `ldapDn`: informational message ("No mapping configured — set LDAP DNs in group management")

**3. Sync Operations**
- "Sync now" button (disabled if sync in progress)
- Next scheduled sync indicator
- History table: date, trigger, duration, stats (created/updated/deactivated/reactivated/skipped/errors), status badge
- Click row → detail view with skip/error messages

### Page: User Management (existing, enhanced)

When LDAP is configured and enabled:
- **Header indicator**: last sync status (date + summary, e.g., "Last sync: 2h ago — 3 created, 1 updated")
- **"Sync LDAP" button** next to the indicator (triggers `POST /admin/ldap/sync`, toast feedback)
- **"LDAP" badge** on each synced user in the list (`ldapDn != null`)

### Settings page (existing, enhanced)

In the "Authentication Providers" section:
- If LDAP configured + enabled: info banner "LDAP/AD sync active — [Configure]" (link to `/admin/ldap`)
- If LDAP configured but disabled: "LDAP/AD sync disabled — [Configure]"
- If not configured: nothing shown

### Navigation

- Admin dropdown in navbar: add "LDAP" link (alongside Groups, Users, Settings)

## Security

| Concern | Mitigation |
|---------|------------|
| Bind password storage | AES-256-GCM encrypted in DB, never returned by API |
| Service account privileges | Read-only: read group members, user attributes. No write access to AD. |
| Admin-only access | All `/admin/ldap/*` routes require admin JWT |
| Sync concurrency | In-memory mutex prevents parallel syncs |
| User deactivation | Deactivate only, never delete — files/shares preserved |
| Config validation | `POST /admin/ldap/test` verifies bind, group existence, member readability before enabling |
| LDAP injection | DN values used in search filters are escaped via `ldapts` built-in escaping |
