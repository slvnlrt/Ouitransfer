# 8.3 — Download Tracking

**Status:** Spec finalized — scope reduced after audit (most delivered by 8.2)
**Depends on:** 8.1 Auditing (event logging infrastructure), 8.2 Email Notifications (invite mode for identified recipients)

## Summary

Track who downloads shared files and when, with per-invitee visibility.
Builds on 8.1 audit infrastructure for event logging and 8.2 invite mode
to identify individual recipients.

**Important :** ce spec a été écrit *avant* l'implémentation de 8.2, qui a finalement
couvert la majorité du scope initial. Un audit complet du codebase (juin 2026) a établi
l'écart exact entre l'existant et la cible. Ce spec reflète désormais cet état des lieux :
il ne reste que 5 lots à implémenter (A, B, C, D, F). Le lot E (mot de passe par invité)
a été explicitement sorti du scope.

### Reste à implémenter — 5 lots

| Lot | Description | Effort |
|-----|-------------|--------|
| **A** | Badge explicite « Téléchargé / En attente » par destinataire dans la liste (UI). Dérivé des données existantes (`ShareVisit` action=download lié au `recipientId`), pas seulement `accessCount`. | Faible |
| **B** | Relance **manuelle** des non-téléchargeurs : bouton « Relancer les non-téléchargeurs » → nouvel email de rappel uniquement aux destinataires sans download. Template + endpoint + UI. **Pas de scheduler.** | Moyen |
| **C** | Auto-lier le visiteur identifié **par cookie** (sans token) à un `ShareRecipient` existant via matching email → renseigner `ShareVisit.recipientId` au lieu de NULL. | Faible-moyen |
| **D** | Reverse share : suivi d'upload **par destinataire**. Ajouter `uploadedAt` (+ compteur) sur `ReverseShareRecipient`, lier les uploads au destinataire, exposer le statut « a uploadé / pas encore » dans l'UI (symétrie avec les shares). | Moyen |
| **F** | Émettre un événement **AuditLog** par téléchargement de fichier individuel (aujourd'hui seuls les accès share-level sont audités) + ajouter la mention RGPD dans le formulaire d'identification. | Faible |

### ❌ Hors scope (décidé)

- **Mot de passe auto-généré par invité** (ancien lot E) — tokens personnels + identification couvrent déjà le besoin. Bénéfice sécurité marginal pour un coût élevé (schéma + service + flux download + UI). Non retenu ; à reverser en TD si un besoin concret émerge.

## Scope détaillé

### Core Tracking
- Chaque téléchargement est déjà loggé en `ShareVisit` (action=download) avec timestamp,
  `fileId`, identité visiteur, `recipientId`. **(F)** ajoute en plus un événement `AuditLog`.
- Partages anonymes (lien public) : compteur `views` + `lastDownloadedAt` — **déjà fait**.
- Partages en mode invitation : statut par invité **téléchargé / en attente** dérivé des
  `ShareVisit` action=download → exposé via badge **(A)**.

### Invite Mode (livré par 8.2)
- Ajout d'invités (nom + email), liens personnels uniques, emails d'invitation — **déjà fait**.
- Pas de mot de passe par invité (hors scope).

### Share Tracking View
- Vue « Download Activity » sur les détails du partage — **déjà fait** (Share Activity section).
- Ajouts : badge statut **(A)**, bouton relance non-téléchargeurs **(B)**.
- Renvoi d'invitation — **déjà fait**.

### Reverse Share Tracking **(D)**
- Suivi d'upload par destinataire : `uploadedAt`/compteur sur `ReverseShareRecipient`,
  liaison upload → destinataire, statut UI « a uploadé / pas encore ».

## Decisions (juin 2026)

| # | Question | Décision |
|---|----------|----------|
| Scope-E | Mot de passe auto-généré par invité | **Hors scope.** Tokens perso + identification suffisent. TD si besoin futur. |
| Scope-B | Niveau de relance des non-téléchargeurs | **Manuel uniquement** (bouton propriétaire). Pas de scheduler automatique. |
| Scope-D | Reverse share upload tracking par destinataire | **Dans le scope.** Symétrie avec les shares. |
| Q4 | Schéma de tracking | **Étendre `ShareVisit`** (action=download, recipientId, fileId déjà présents). Pas de modèle `DownloadEvent` dédié — il dupliquerait `ShareVisit`. |
| Q1 | Rétention des logs de download | **Liée à la durée du partage** — suppression en cascade FK (comportement actuel). Pas de TTL indépendant. |
| Q2 | Visibilité non-admin | **Oui** — le créateur voit le tracking de **ses propres** partages (déjà le cas dans l'UI). Les admins voient tout via l'audit trail global. |
| Q3 | Information RGPD des invités | **Oui** — courte mention i18n sous le formulaire d'identification visiteur (« vos accès peuvent être visibles par l'expéditeur »). Intégrée au lot **F**. |
| Q-F | Audit log des downloads individuels | **Oui** — émettre un événement audit par download de fichier (cohérent avec 8.1). Lot **F**. |
