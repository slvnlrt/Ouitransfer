# 5.2 — Lifecycle Management & Automatic Cleanup

**Status**: Phase A.1 implemented (2026-06-03) — explicit two-phase lifecycle (deactivate → delete) + manual pause/resume; `maxViewsCleanupDays` retired. Phase B not started. Decisions recorded 2026-06-02.
**Depends on**: 8.2 (Email Notifications — template engine, queue, preferences) ✓
**Blocks**: —

---

## Goal

Comprehensive lifecycle management for all content and accounts: expired content cleanup, quota enforcement policies, orphan detection, and account deactivation/deletion cascades.

## Scope (expanded from brainstorming session 13, 2026-05-28)

This feature goes well beyond simple expiration cleanup. It covers:

### 1. Expired Content Cleanup
- Shares past `expiration` date + configurable grace period → delete from DB + S3
- Reverse shares past expiration + grace period → delete uploaded files from DB + S3
- Shares that hit `maxViews` → cleanup after X days of inactivity (configurable)
- Email owner before cleanup (uses 8.2 notification system)
- Audit log entries for all automated deletions

### 2. Quota Overage Policy
- Admin-configurable enforcement policy:
  - **Grace period**: When user exceeds quota, tolerance period + alerts for X days
  - **Smart deletion order**: After grace period, auto-delete oldest files:
    1. First: files uploaded but NOT used in any share (orphan uploads)
    2. Then: files in shares with no activity for X days
    3. If no safe candidates (everything in active shares): block upload, don't delete
  - **Threshold warnings**: Admin-configurable (e.g., at 80%, 90% of quota → email alert)
  - Admin configures notification frequency for quota alerts

### 3. Reverse Share Quota Tolerance
- **Current state**: No tolerance — at 100% quota, upload is refused (`used < limit`)
- **New behavior**: Reverse share uploads get soft enforcement:
  - Don't block client uploads on reverse shares even if user quota is exceeded
  - Block only at extreme overage (e.g., 3x quota, with absolute cap like 75GB)
  - Alert the reverse share owner to regularize their situation
- **Direct uploads**: Keep hard enforcement (block at quota limit, possibly with small tolerance)

### 4. Orphan Cleanup
- **Incomplete uploads**: Files registered in DB (pre-signed URL generated) but never finalized in S3
- **S3 ↔ DB consistency**: Objects in S3 without DB records, or DB records pointing to missing S3 objects (related to TD-25)
- **Reverse share file orphans**: Files uploaded to expired reverse shares still in S3

### 5. Account Deactivation Cleanup
- **On deactivation**: Immediately deactivate all user's shares (block access)
- **After X days**: Delete all user's files from S3 + DB
- **Current gap**: Deactivation only invalidates sessions — shares remain active and accessible

### 6. Account Deletion Cascade
- **On user deletion**: Complete cascade — delete ALL user data (files, shares, reverse shares, S3 objects)
- **Current state**: Shares get `creatorId: null` (Prisma SetNull) but files may be orphaned
- Resources without owner should be cleaned up, not left dangling

### 7. Empty Shares / Reverse Shares
- **Decision: Do NOT auto-delete** — users may be preparing shares and uploading files in stages
- Reverse shares can legitimately stay empty while waiting for uploads
- These are not considered orphans

## Design Requirements

- Server-side scheduled task (chained `setTimeout` pattern, matching existing schedulers)
- Cleanup service: query expired/overage items, cascade-delete S3 + DB
- Notification service: uses 8.2 email system for all alerts
- Admin-configurable policies via settings page
- Audit log entries for all automated actions

## Decisions (2026-06-02)

Resolved with the project owner before implementation. These are binding.

### Product decisions (owner)

1. **Phased delivery.** The 7-axis scope is split into **Phase A** (safe, mostly
   non-destructive-by-default lifecycle management) and **Phase B** (aggressive
   quota-overage policy). Phase A ships and is validated before Phase B starts.
2. **Auto-deletion is opt-in, off by default.** Any operation that destroys content
   the user may still want (scheduled cleanup of expired content, time-delayed deletion
   of a deactivated account's files, quota-overage smart deletion) is gated behind an
   admin toggle that defaults to **disabled**. The product never deletes user content
   automatically until an admin consciously enables it.
3. **Conservative defaults.** Long grace periods, warn-before-delete, never delete
   content that is still inside an active share. Data safety beats storage economy.

### Technical decisions (implementer)

4. **In-process scheduler**, chained `setTimeout`, modeled on
   `modules/audit/retention.scheduler.ts` (boot init, `onClose` stop hook,
   registration in `server.ts`). No separate worker process — matches every other
   scheduler in the codebase and keeps deployment single-container-simple.
5. **Admin UI = a section in the existing settings page** (a new `cleanup` config
   group), consistent with how `security`/`email`/`storage` groups already render.
   No dedicated page.
6. **Reuse 8.1 audit + 8.2 email** infrastructure. All automated deletions emit audit
   events; all warnings/notices go through the existing notification catalog + queue +
   per-user preferences + cooldown.
7. **Explicit admin actions always do the right thing, ungated.** Deleting a user
   (admin action) performs a *full* cascade including S3 cleanup — that is a
   correctness fix, not a scheduled destructive policy, so it is never behind a flag.
   Blocking a deactivated user's shares is reversible (re-derived from `creator.isActive`
   at read time) and therefore also ungated.

| A4 | `maxViews`-reached shares → delete the **share link** after N inactive days (same scope as A2). | link only | `autoCleanupEnabled` |
| A5 | "Will be permanently deleted in N days" warning email before A2–A4 | no | `autoCleanupEnabled` |
| A6 | Account **deactivation** → immediately block the user's shares (read-time `creator.isActive` gate, auto-reverses on reactivation) | no (reversible) | **ungated** (correct default behavior) |

| A9 | Orphan sweep, both directions: DB row → missing S3 object, and S3 object → no DB row (absorbs **TD-17**, **TD-25**) | yes | `autoCleanupOrphansEnabled` (default **off**) + min-age guard |
| A10 | Admin settings UI for the `cleanup` group + i18n (23 locales) + server-side validation | — | — |

### Data-model clarification (critical — corrects the original "delete DB + S3" framing)

The original Scope §1 said expired shares should be deleted "from DB + S3". That reflects a
WeTransfer transfer-centric model that **does not match this app's data model**:

- A `File` belongs to a `User` (`File.userId`, `onDelete: Cascade`), lives in the user's
  **file manager** (folders), and is linked to shares **many-to-many** (`ShareFiles`). One
  file can be in several shares and exists independently of any share.
- Therefore **expired/maxViews regular-share cleanup deletes only the share link**, never the
  owner's `File`/`Folder` rows or their S3 objects — deleting them would be data loss in the
  user's file manager and could break other shares referencing the same file.
- A `ReverseShareFile` belongs to its `ReverseShare` (`onDelete: Cascade`), is uploaded by an
  external party, and has **no independent existence** — so expired reverse-share cleanup
  **does** delete those files + their S3 objects (this is the storage-reclaiming path).
- Storage reclamation for regular shares is handled instead by account
  deletion/deactivation cleanup (A7/A8), the orphan sweep (A9), and Phase B's opt-in
  quota smart-deletion of unshared "orphan upload" files.

### Schema changes (Phase A)

One migration (`prisma migrate dev`), additive only:

- `User.deactivatedAt DateTime?` — set in `deactivateUser`, cleared in `activateUser`; drives
  the A7 delay window.
- `Share.notifiedForPendingDeletion Boolean @default(false)` — idempotency flag for the A5
  warning; reset when `expiration`/`maxViews` is extended (alongside the existing
  `notifiedForExpiring`/`notifiedForExpired`/`notifiedForMaxViews` resets).
- `ReverseShare.notifiedForPendingDeletion Boolean @default(false)` — same, for reverse shares.

No `isActive` field is added to `Share`: A6 blocking is derived at read time from
`creator.isActive`, which auto-reverses on reactivation and needs no migration or backfill.

### Phase A.1 — Unified explicit share/reverse-share lifecycle (decided 2026-06-03)

**Owner decision**: replace Phase A's implicit "expired/maxViews → 410 at read time → hard-delete
after grace" with an **explicit, persisted, two-phase lifecycle** that is uniform across triggers
and adds a manual pause/resume capability. Grace is measured uniformly from `deactivatedAt`.

This **reworks** the Phase A share/reverse-share cleanup (it does not throw it away — the delete
helpers and notifications are reused). It is implemented as a distinct slice on top of Phase A.

#### Model

Every share and reverse share has an explicit lifecycle state:

```
active  ──(expiration reached | maxViews reached | manual pause)──▶  deactivated  ──(grace)──▶  deleted
   ▲                                                                      │
   └──────────────── reactivate / renew (manual, or extend) ─────────────┘   (only auto reasons are deletable)
```

- **`Share.isActive Boolean @default(true)`**, **`Share.deactivatedAt DateTime?`**,
  **`Share.deactivationReason String?`** (`"expired" | "max_views" | "manual"`). ReverseShare
  already has `isActive`; add `deactivatedAt` + `deactivationReason` to it too.
- **Phase 1 — Deactivated** (persisted, accessible = false, reversible):
  - Set automatically when `expiration` passes (reason `expired`, `deactivatedAt` = the expiration
    instant) or when `maxViews` is hit (reason `max_views`, `deactivatedAt` = the moment it is hit,
    set at read time where the atomic increment already happens), or manually (reason `manual`).
  - The scheduler's **deactivation sweep** is the backstop that persists `expired` deactivation for
    shares that are never read again, and sends the deactivation notice (`share_expired` /
    `share_max_views_reached` / `reverse_share_expired` — reuse existing types).
  - Read-time access gates on `isActive` first (plus defensive expiry/maxViews checks so a share
    that expires between sweeps is still blocked immediately), returning the reason.
- **Phase 2 — Deleted** (after a single uniform grace from `deactivatedAt`):
  - The **deletion sweep** deletes shares/reverse shares where `isActive = false` AND
    `deactivationReason ∈ {expired, max_views}` AND `deactivatedAt < now - autoCleanupGracePeriodDays`.
  - **Manual pauses are never auto-deleted** (reason `manual` is excluded). If a manually-paused
    share later also expires, the deactivation sweep upgrades its reason to `expired`, making it
    deletable.
  - Warn (`share_pending_deletion` / `reverse_share_pending_deletion`) `autoCleanupNotifyDaysBefore`
    days before; delete + `share_auto_deleted` / `reverse_share_auto_deleted` + audit.

#### Reactivation

- Manual **resume** (`isActive=true`, clear `deactivatedAt`/`reason`, reset
  `notifiedForPendingDeletion`). Extending `expiration` / raising `maxViews` likewise reactivates and
  clears the deactivation fields. A still-expired share cannot be resumed without also extending it
  (read-time stays blocked).

#### Config change

- **Retire `maxViewsCleanupDays`** — superseded by the single uniform `autoCleanupGracePeriodDays`
  measured from `deactivatedAt`. (No prod/back-compat; remove the seed key + its validation/UI/i18n.)
- `autoCleanupGracePeriodDays` (7) now means "days after **deactivation** before permanent deletion".

#### New surface

- Audit actions: `SHARE_DEACTIVATED`, `SHARE_REACTIVATED`, `REVERSE_SHARE_DEACTIVATED`,
  `REVERSE_SHARE_REACTIVATED` (reason in metadata). `*_AUTO_DELETED` reused for phase 2.
- Manual pause/resume endpoint for shares (reverse shares already toggle `isActive`; align it to set
  `deactivatedAt`/`reason`).
- Frontend: deactivated/paused state + reason badge + resume (and renew/extend) action + manual
  pause toggle on the share card/list, mirroring the existing reverse-share toggle.

#### What Phase A code is reworked

`cleanupExpiredShares` + `cleanupMaxViewsShares` → split into `deactivateEndedShares` (phase 1) +
`deleteDeactivatedShares` (phase 2). `cleanupExpiredReverseShares` → likewise. `deleteShareLink` /
`deleteReverseShareWithStorage` and all notification types are reused unchanged. The scheduler calls
the two sweeps instead of the three old cleanup functions.

### Phase B — Aggressive quota-overage policy (future, separate spec slice)

- Quota grace period + threshold warnings (§2 of Scope)
- Smart deletion order (orphan uploads → inactive-share files → block) — opt-in
- Reverse share quota tolerance / soft enforcement (§3 of Scope)
- These reuse the Phase A scheduler + notification + audit plumbing.

Empty shares / reverse shares are **never** auto-deleted (already decided, §7 of Scope).

## Config Keys (Phase A — finalized, conservative defaults)

All keys live in the new `cleanup` config group, seeded in `prisma/seed.js`, validated in
`modules/config/config-validation.ts`, and labeled in the 23 locale files.

| Key | Type | Default | Meaning / validation |
|-----|------|--------:|----------------------|
| `autoCleanupEnabled` | boolean | `false` | Master toggle for the scheduled cleanup of expired content (A2–A5) and orphans. |
| `autoCleanupIntervalHours` | number | `24` | Scheduler run frequency. Integer ≥ 1. |
| `autoCleanupGracePeriodDays` | number | `7` | Days **after deactivation** (`deactivatedAt`) before a share/reverse-share is deleted. Single uniform grace for every automatic reason (expired / max_views); manual pauses are never deleted. Integer ≥ 0. |
| `autoCleanupNotifyDaysBefore` | number | `3` | Send the "pending permanent deletion" warning this many days before deletion. Integer ≥ 0 (0 = no warning). Must be ≤ grace period (else no warning fires). |
| `accountDeactivationCleanupEnabled` | boolean | `false` | Opt-in: delete a deactivated user's files after the delay below. |
| `accountDeactivationCleanupDays` | number | `30` | Days after deactivation before the user's files are deleted. Integer ≥ 1. |
| `autoCleanupOrphansEnabled` | boolean | `false` | Opt-in: run the bi-directional S3↔DB orphan sweep. |
| `autoCleanupOrphanMinAgeHours` | number | `24` | Only consider S3 objects / DB rows older than this in the orphan sweep (protects in-flight uploads). Integer ≥ 1. |

## Audit actions (Phase A)

Add to the audit action enum (`modules/audit/service.ts`), following the existing
`AUDIT_RETENTION_CLEANUP` precedent:

- `SHARE_AUTO_DELETED`, `REVERSE_SHARE_AUTO_DELETED` (expired/maxViews/orphan cleanup)
- `ACCOUNT_FILES_CLEANED` (A7 — deactivated account file deletion)
- `ORPHAN_S3_DELETED`, `ORPHAN_DB_DELETED` (A9 — sweep)
- The full user-deletion cascade (A8) reuses the existing `USER_DELETE` action, enriched
  with metadata (counts of files/shares/S3 objects removed).
