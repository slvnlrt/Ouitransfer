# 8.2 Re-Review — Server Core

**Reviewer**: AI Agent (principal-engineer review mode)
**Date**: 2026-05-29
**Scope**: `apps/server/src/modules/email/{service,transport,queue,catalog,notification.scheduler,i18n/loader,templates/base-layout}.ts` + tests + `prisma/schema.prisma` + `app/service.ts` cache invalidation.

## Summary

The email module is well-structured: a clean 5-layer architecture (transport → i18n → templates → catalog → queue) with reasonable separation, type-safe payload schemas, idempotent schedulers, and competent test coverage. The hand-rolled HMAC unsubscribe JWT and the SmtpTransport hash-based config caching are both sound implementations.

That said, several real defects are present. The most user-visible is a rendering bug in the welcome subtitle (literal `{appName}` ships to users) and a more general HTML-rendering issue where `\n` newlines in `body` translations collapse silently, breaking the layout of welcome/account-deactivated/admin emails. Concurrency in the wake event handler is partially correct but can suppress its own purpose. There are also smaller security and robustness issues around header injection, cache-poisoning during partial configuration, and missing test coverage of HTML escaping at the integration level.

Overall: solid engineering work, but with a handful of findings that must be fixed before this is shippable.

## Findings

### Critical

#### C-1: HTML body paragraphs collapse — `\n` is not converted to `<br>` or `<p>`
- **File**: `apps/server/src/modules/email/templates/base-layout.ts:113-114` + `apps/server/src/modules/email/i18n/messages/en.json` (e.g. lines 11, 24, 31, 132, 137, 144)
- **Description**: Several body translations rely on `\n\n` to separate paragraphs, e.g.
  - `welcome.body`: `"Hello {firstName},\n\nWelcome to {appName}!..."`
  - `accountDeactivated.body`: `"Hello {firstName},\n\nYour account has been deactivated..."`
  - `accountReactivated.body`: `"Hello {firstName},\n\nGreat news!..."`
  - `adminUserRegistered.body`: `"A new user has registered...\n\nName: ...\nEmail: ...\nRegistration method: ..."`
  - `adminQuotaAlert.body`: same pattern.
  - `testEmail.bodyCustom`: same pattern.

  The HTML renderer puts the body directly inside `<div style="font-size:15px;line-height:1.7;...">${slots.body}</div>` with no `white-space: pre-line` and no replacement of `\n` → `<br>` or `<p>...</p>`. Browsers collapse whitespace, so every newline becomes a single space.
- **Impact**: User-facing visual bug — the welcome email reads `"Hello John, Welcome to TestApp! Your account..."` as a single run-on line. The admin-registration email shows `"...registered on TestApp. Name: Dave Email: dave@test.com Registration method: email"` with no separation between fields. This is the very first email new users see.

  The plain-text version is correct (newlines preserved), so the bug is invisible in plain-text-only mail clients and unit tests, which is why it slipped through.
- **Suggested fix**: Either (a) convert `\n` to `<br>` in the body before rendering (post-translation, pre-layout), OR (b) update `renderHtml` to wrap `slots.body` in a container with `white-space: pre-line`. Option (a) is more email-client-safe (Outlook handles `<br>` correctly; `white-space` rules are inconsistently honored). Add a small `toHtmlBody(text: string)` helper that escapes nothing (template strings are trusted) and replaces `\n` with `<br>`, then call it in the catalog `render` adapter or in `base-layout.renderHtml`. Add a regression test asserting `<br>` appears in HTML output when the body contains `\n`.

#### C-2: `welcome.subtitle` ships unresolved `{appName}` placeholder to users
- **File**: `apps/server/src/modules/email/templates/welcome.ts:11` + `apps/server/src/modules/email/i18n/messages/en.json:10`
- **Description**: `en.json` defines `"welcome.subtitle": "Welcome to {appName}"` but `welcome.ts` calls `t("welcome.subtitle")` with **no params**. The `interpolate()` function (`loader.ts:259`) returns the template unchanged when params is missing or empty, so the literal text `Welcome to {appName}` is emitted into the email header.

  Other subtitles in `en.json` are static strings (no placeholders), so this is the only template currently affected — but the `t()` API silently fails open, which means the same mistake will recur. Note the `validateAllI18nKeys()` boot-check only verifies key existence, not placeholder satisfaction.
- **Impact**: First email a new user receives shows `"Welcome to {appName}"` in the indigo header banner. Embarrassing user-visible bug.
- **Suggested fix**:
  1. Immediate: change `welcome.ts:11` to `subtitle: t("welcome.subtitle", { appName })` — but `appName` is not in the data payload. It must be threaded through the `TranslationFn` or injected differently. The cleanest fix is to make `appName` available to template renders the same way it's available to `renderLayout` — e.g. add a `t` that closes over `{appName}` as a default param, OR augment the `LayoutSlots` so the subtitle becomes a `(t, ctx) => string` callable resolved later.
  2. Longer term: make `interpolate()` strict by default. Detect unsubstituted `{xxx}` placeholders after interpolation and either throw or return them surrounded with a marker (`__UNRESOLVED_xxx__`) so tests catch it. Add a new assertion to `validateAllI18nKeys` that for every required key, scans the en.json string for `{placeholder}` tokens that are not in a hardcoded `KNOWN_PLACEHOLDERS` allowlist passed by the catalog entry.

### Important

#### I-1: Wake signal can be dropped if it arrives during an in-flight tick
- **File**: `apps/server/src/modules/email/queue.ts:271-319`
- **Description**: The wake-event flow has a partial race:
  1. Tick 1 starts; `currentTimeout = handle1`, `isProcessing = true`.
  2. `wake` fires → `onWake()`: `clearTimeout(handle1)` (no-op since it has already fired), creates `handle2` at 0ms, sets `currentTimeout = handle2`.
  3. Tick 1's body finishes and checks `if (currentTimeout === handle1) scheduleNext()`. Since `currentTimeout === handle2`, no chaining occurs.
  4. `handle2` fires, runs `processTick()` → `processBatch()` sees `isProcessing === false` (just cleared in finally), but this is OK so far. Then `if (currentTimeout === handle2) scheduleNext()` — yes, chains the next normal poll.

  Most of the time this works. The problem is the race window between the `isProcessing = false` assignment in the previous tick's finally block and the `handle2` callback executing. If `processBatch()` is in the middle of an `await prisma.emailJob.findMany` when wake fires, the wake-scheduled `handle2` will fire shortly, see `isProcessing === true`, return immediately from `processBatch()`, and then re-schedule a normal `scheduleNext()` 30s later. The priority email therefore waits up to one full polling interval after the in-progress tick finishes — defeating the purpose of the wake signal in exactly the busy-queue scenario where wake matters most.

  Note also that `processTick()` does not check `currentTimeout` after its `processBatch()` returns — if a tick was superseded by a wake while it was running, the superseded tick's `processBatch()` already ran and may have processed the priority job; the subsequent `handle2` is then redundant but harmless. That part is fine.
- **Impact**: Priority-1 emails (password reset, welcome, 2FA, account state changes) may be delayed by up to `emailQueueIntervalSeconds` (default 30s, configurable up to anything). The whole point of the wake event is to send these instantly.
- **Suggested fix**: Two options:
  - **Re-queue the wake** if `processBatch()` finds `isProcessing === true`: instead of returning silently, schedule another 0ms tick. (Risk: tight loop if `isProcessing` stays true; bound the retry to e.g. 100ms.)
  - **Move the in-progress check into the wake handler**: when wake fires while `isProcessing === true`, set a `wakePending = true` flag. In `processBatch()`'s `finally` block, if `wakePending` is set, clear it and immediately schedule a 0ms tick. This is race-free because the flag/timer manipulation all happens on the main thread between awaits.

  Either fix needs a test that simulates wake arriving while a long-running send is in-flight. Currently `queue.test.ts` does not cover the wake handler behaviour at all (it only checks listener registration/removal).

#### I-2: Cooldown query uses post-filter on `status` — recently-failed jobs do not gate
- **File**: `apps/server/src/modules/email/service.ts:140-148`
- **Description**: The cooldown query filters out `status: { notIn: ["failed", "processing"] }`. A job that exhausted its retries and is now `failed` does NOT count for cooldown. Consequence: if `share_accessed` fails to send (e.g. recipient mailbox full, SMTP rejects), then 100ms later the queue marks the job `failed` after 3 attempts; another visit triggers a new `send()`; the cooldown query finds no recent non-failed job; a new `share_accessed` job is enqueued — and it will probably fail too. Cooldown is a backpressure mechanism; failed jobs should still consume backpressure.

  Even worse, `processing` is excluded — so if a job is currently being sent (locked), the cooldown sees nothing. The window is small but real.
- **Impact**: Potential email flood for downloads/access events when SMTP is intermittently failing. Each retry-then-fail-then-flood cycle generates more failed jobs. Not a security issue, but a noise/cost issue.
- **Suggested fix**: Cooldown should count ANY recent enqueued job (regardless of final status):
  ```ts
  const recent = await prisma.emailJob.findFirst({
    where: { type, to: options.to, relatedId: options.shareId ?? null, createdAt: { gt: cutoff } },
  });
  ```
  Drop the status filter entirely. The presence of a recent EmailJob (whether sent, pending, processing, failed, or digest_pending) means "we already produced one of these recently; suppress."

#### I-3: `share_downloaded` cooldown granularity is per-share, not per-file
- **File**: `apps/server/src/modules/email/service.ts:140-153` + `apps/server/src/modules/email/catalog.ts:330-345`
- **Description**: The cooldown query uses `relatedId: options.shareId ?? null`. For `share_downloaded`, `relatedId` is the share ID. But the payload contains `fileName` — meaning if a recipient downloads file A then file B from the same share within 15 minutes, only the first triggers a notification. That may be intentional ("one notification per share per cooldown window") but it's not documented anywhere, and it diverges from the `share_accessed` semantics (which also dedups by share).

  If "one notification per file per cooldown" is the intent, the cooldown key needs to include `fileName` (or better, the file ID). If the current behaviour IS the intent, document it in the catalog entry's JSDoc.

  Note: this is partially academic because there is currently **no production caller** for `share_downloaded` (only `share_accessed` is wired up via `share/service.ts:332`). The Zod payload and template exist, but no controller fires them. That itself is worth flagging — see M-2.
- **Impact**: Behavioural ambiguity that will become visible once `share_downloaded` is wired up. Without a deliberate decision, the first wire-up may surprise the user.
- **Suggested fix**: Decide explicitly (spec-level) whether `share_downloaded` cooldown is per-share or per-file. If per-file, add an optional `cooldownKey?: (data) => string` to `NotificationTypeConfig` and use it when building the cooldown query.

#### I-4: HTML render output is not HTML-escaped against the `body` slot — but template authors call `tr()` which IS escaped. Consistency hazard.
- **File**: `apps/server/src/modules/email/templates/base-layout.ts:114` + `apps/server/src/modules/email/i18n/loader.ts:69-75`
- **Description**: `renderHtml` interpolates `${slots.body}` directly into the HTML (`<div>${slots.body}</div>`). This is intentional — the body is already "HTML" (escapable values escaped by `tHtml`, template HTML markup preserved). It works as long as every template author uses the HTML-escaping `tr` returned from `createTranslationFn`. The catalog's `asRender` adapter casts to `(data, t) => LayoutSlots` and the body of `service.ts:177-185` passes the HTML-escaping `tr`.

  The hazard: a future template author might call `tHtml` directly with their own concatenation, or build `body` by string-joining payload data without going through `tr`. Today, `share-accessed.ts:18` does `visitorName: data.visitorName ?? data.visitorEmail ?? ""` — the value flows through `tr` which escapes it, so we're fine.

  But there is no mechanism enforcing that `slots.body` is "safe HTML". It's just convention. The type system says `body: string`, indistinguishable from any other string.
- **Impact**: Latent XSS risk. Today the code is safe, but the pattern relies on every contributor knowing the rule.
- **Suggested fix**: Either (a) introduce a branded type `HtmlSafe & string` and require templates to return `HtmlSafe` bodies (constructed by going through a `tr` that returns `HtmlSafe`), OR (b) add a defensive sanitization pass on `slots.body` in `renderHtml` (e.g. strip `<script>` and event handlers — but DOM-purify is overkill for emails), OR (c) at minimum, add a test that verifies `renderShareInvitation` with a `senderName: '<script>...'` payload does not leak `<script>` into the rendered HTML when called through `service.send()`. Currently only `i18n-loader.test.ts:171-181` and `base-layout.test.ts:264-279` directly exercise escaping; the full pipeline (service.send → tr → render → layout) is not asserted XSS-safe.

#### I-5: SMTP `from` header is built by string concatenation — header injection vector if `smtpFromName` contains `"` or CR/LF
- **File**: `apps/server/src/modules/email/transport.ts:116-118`
- **Description**: `from = \`"${fromName}" <${fromEmail}>\`` is built by string interpolation. If an admin sets `smtpFromName` to e.g. `Acme" <evil@attacker.com>, "Real Name` — the resulting header is malformed and may allow a second `from` or other header injection depending on nodemailer's parser.

  Nodemailer's mail composer does validate addresses, so a fully malformed header is likely rejected — but the admin-configurable `smtpFromName` should be sanitized at the source. The same applies to `smtpFromEmail` (less risk because it must look like an email).

  This is admin-only input (only admins can change config), so it's not an RCE-by-anonymous, but it's a hardening gap.
- **Impact**: Admin can corrupt outgoing email headers, potentially spoof the `from` field for downstream relays.
- **Suggested fix**: Either use nodemailer's structured form: `from: { name: fromName, address: fromEmail }` (nodemailer will properly encode), OR strip CR/LF and `"` from `fromName` in `loadConfig()`. Add a validation Zod schema at the admin-config update path that rejects names containing `"`, `<`, `>`, `,`, `\r`, `\n`.

#### I-6: Hand-rolled JWT lacks `alg` and `typ` verification on decode
- **File**: `apps/server/src/modules/notification/service.ts:123-170` (cross-module concern noted because email/service.ts signs these tokens)
- **Description**: `verifyUnsubscribeToken` decodes only the body and verifies the HMAC signature, but does NOT verify the JWT header. A token signed with `alg: "none"` (no signature, empty third part) would fail the length check (`parts.length !== 3` returns false only if the token has 3 dot-separated parts — `header.body.` has 3 parts, with empty signature). Then `Buffer.from("", "base64url")` = empty buffer, `expectedBuffer.length` is 32 bytes, lengths differ, → rejected. OK, `alg: none` is implicitly rejected.

  However, the verifier doesn't reject tokens with a *different* HMAC algorithm in the header. Since the signature is recomputed with HS256 unconditionally, a token with `alg: HS512` and a correct HS256 signature would still validate. That's not an attack — but it does mean the header is decorative, not validated.

  More importantly, the signing module (`email/service.ts:53-71`) and the verifying module (`notification/service.ts:123-170`) duplicate the `UNSUBSCRIBE_KEY_LABEL` constant via comment-only coordination ("Must match UNSUBSCRIBE_KEY_LABEL in email/service.ts"). One change in one file silently desynchronizes the system.
- **Impact**: Minor cryptographic hardening gap. The unsubscribe endpoint is low-stakes (worst case: an attacker disables a user's notifications for one type), but the constant duplication is a maintenance trap.
- **Suggested fix**:
  1. Extract `UNSUBSCRIBE_KEY_LABEL` and the `deriveKey`/sign/verify functions into a single shared module (e.g. `apps/server/src/modules/email/unsubscribe-token.ts`) consumed by both email/service.ts and notification/service.ts.
  2. In the verifier, also check that `JSON.parse(header).alg === "HS256"` before trusting it.

#### I-7: `notification.scheduler` uses fixed 24h interval starting from boot — drifts over time and can fire at user-hostile times
- **File**: `apps/server/src/modules/email/notification.scheduler.ts:317-334`
- **Description**: The scheduler runs `runAllChecks()` at boot and then every exactly 24h via chained `setTimeout`. The next run time depends on `boot time + N × 24h`. If the server restarts daily for deploys, the run anchor drifts; if the server runs for a long time, the anchor drift accumulates (Node's setTimeout isn't wall-clock-aligned and skews under CPU load).

  Operationally: if the server boots at 3am (when the admin deploys after-hours), all expiration alerts will be sent at 3am every day. The scheduler comment at line 365 acknowledges this: "Wall-clock alignment to a specific hour (e.g. `emailDigestHour`) is a future enhancement." But the comment understates: this is also a timezone issue — there is no per-user timezone consideration.
- **Impact**: Users may receive expiration alerts at 3am local time. Not catastrophic but unpleasant.
- **Suggested fix**: Either compute `next run = next occurrence of (configured hour, server local time)` and `setTimeout` the delta, OR run more frequently (e.g. every 1h) and gate each check by "have we already run today?" via a DB row or `lastRunAt` config key. The latter is more robust to clock drift and missed runs.

#### I-8: `processBatch` does not handle Prisma errors during the lock-update — error propagates out and prevents subsequent jobs in the same batch
- **File**: `apps/server/src/modules/email/queue.ts:151-230`
- **Description**: The `for (const job of jobs)` loop locks each job (`prisma.emailJob.update` to set `status: "processing"`), then `try` sends, then `catch` records failure. The lock-update at lines 153-159 is OUTSIDE the try/catch. If Prisma throws here (e.g. lost DB connection, lock conflict, sqlite_busy), the error escapes the `for` loop and propagates up to `processTick` which logs it. But then the remaining `jobs` in the batch are abandoned — they were `findMany`-fetched but never locked or processed, so they'll be picked up on the next tick. That's actually OK, but:

  Worse, if the *lock* succeeds but the subsequent `try` block fails because the `prisma.emailJob.update` for `status: "sent"` (line 183) or for status: "pending" (retry, line 218) throws, the job remains in `processing` status with `lockedAt` set. It's then a stuck job, only recoverable by `recoverStuckJobs()` which runs every 60 minutes (`CLEANUP_EVERY_N_TICKS = 120` × `30s` = 1 hour). For the affected job, that's a 1h+ delay before re-attempt.
- **Impact**: A transient DB error during a status update can leave a job stuck for up to 1h. Low-severity in steady state, but during DB hiccups the queue can stall.
- **Suggested fix**:
  - Wrap the lock-update in the same try/catch and treat lock failure as "skip this job, continue the batch".
  - For the final status updates (sent/failed/retry), use a short retry loop (e.g. retry once after 100ms) since these are critical for queue progress.
  - Consider lowering the `STUCK_JOB_TIMEOUT_MS` (5 min) recovery cadence — currently recovery only runs every hour at the periodic cleanup tick, not every minute.

  At minimum, run `recoverStuckJobs` on every tick (it's a single indexed UPDATE — cheap), not every 120 ticks.

#### I-9: `EmailJob` schema's `@@index([status, nextAttemptAt])` does not cover the priority-ordered scan
- **File**: `apps/server/prisma/schema.prisma:199` + `apps/server/src/modules/email/queue.ts:132-149`
- **Description**: The query is `WHERE status = 'pending' AND nextAttemptAt <= now ORDER BY priority DESC, createdAt ASC LIMIT 10`. The current index `(status, nextAttemptAt)` lets SQLite filter quickly but the `ORDER BY priority DESC, createdAt ASC` requires a sort step. With a small queue this is irrelevant; under load (thousands of pending jobs), it's an unindexed sort.
- **Impact**: Throughput degradation under high queue depth. Not a blocker for current usage scale but a known scaling cliff.
- **Suggested fix**: Either add `@@index([status, priority, nextAttemptAt])` (helps filter + partial-order) or accept the cost and document. For SQLite the index choice trade-offs differ from Postgres; benchmark with realistic load before deciding.

#### I-10: `subject` is rendered using `t()` (non-escaping) with user-controlled data — header-injection vector via subject
- **File**: `apps/server/src/modules/email/service.ts:212-223`
- **Description**: `subject = await t(options.locale, ${prefix}.subject, { appName, ...dataParams })`. `t()` does NOT HTML-escape (correct for plain-text subjects), but it also does NOT sanitize for CR/LF, which is the SMTP header-injection vector. If `dataParams` contains a value with `\r\n`, the resulting `subject` will contain CR/LF which, when passed to `nodemailer.sendMail({ subject })`, may inject additional headers.

  Nodemailer's MailComposer encodes subjects with RFC 2047 encoded-words if they contain non-ASCII or special characters — which neutralizes most attacks — but this is a defense provided by the library, not by our code. If the payload's `senderName`, `shareName`, etc. contains `\r\n`, we shouldn't rely solely on nodemailer.

  Payload values come from user-controlled fields (e.g. share name, file name, sender's first/last name from a registration form). The Zod schemas don't reject `\r\n`.
- **Impact**: Possible SMTP header injection if nodemailer's encoding fails or is bypassed. Low likelihood, high impact if exploited.
- **Suggested fix**: In `service.ts`, before interpolation, strip `\r` and `\n` from `dataParams` values. Or add a global Zod refinement `.refine(v => !/[\r\n]/.test(v))` to every string payload field. Add a unit test that `send()` rejects (or sanitizes) a payload with newlines in user-controlled fields.

#### I-11: `loadLocale` caches missing-file as ABSENT but `inFlight.delete` is reached before assertion — minor cache-coherency gap
- **File**: `apps/server/src/modules/email/i18n/loader.ts:186-217`
- **Description**: When `fs.promises.access` rejects, the function returns `null` and removes the in-flight promise — but does NOT cache the result. So every subsequent call for a missing locale re-runs `fs.access` (which on hot path costs ~milliseconds per request). The docstring at line 203 actually says "cache a sentinel so we don't retry every call" but the implementation does not do that.

  Impact is small (each email send triggers one `loadLocale("en")` and one `loadLocale(options.locale)` — both async, both cache after first call). But missing locales (e.g. `loadLocale("xx-YY")`) would be repeatedly checked on disk.
- **Impact**: Minor perf hit for unknown locales. Bigger problem: comment lies about behaviour.
- **Suggested fix**: Either (a) cache `null` as a sentinel by using a separate `missing: Set<string>` or by storing `null` in `cache` (but that conflicts with the `Map<string, Record<string, unknown>>` type) or (b) update the comment to reflect actual behaviour.

#### I-12: `appUrl` cache is process-local; multi-instance deploys will see stale values until restart
- **File**: `apps/server/src/modules/email/url-builder.ts:5-25` + `apps/server/src/modules/app/service.ts:87-89, 126-128`
- **Description**: `cachedAppUrl` is a module-level variable. `invalidateAppUrlCache()` is called from `app/service.updateConfig` — which only runs in the process where the admin's request lands. If the deployment ever scales to multiple Node instances (which the project says it doesn't today, but it's worth flagging), other instances will continue using their stale cached value until they restart.

  Same applies to the SMTP config hash-cache in `transport.ts:57-71`: each instance has its own hash, and if the admin changes config on instance A, instance B keeps using the old transporter.
- **Impact**: For single-instance deploys (current state per CLAUDE.md), no impact. Flagged for completeness so it doesn't get forgotten when the architecture is ever scaled.
- **Suggested fix**: Document this assumption. Or move toward a TTL-based cache (e.g. 30s) so other instances eventually pick up changes. Or use a pub/sub channel.

#### M-8: Hand-rolled JWT — long-term maintenance debt
- **File**: `apps/server/src/modules/email/service.ts:53-71`
- **Description**: The implementation comment already flags this. Acknowledged tech debt; library migration (`jose`) is justified if any of the following materialize: key rotation, RS256 support, audience checks, or token revocation by `jti`.

#### M-9: `share-no-activity` filter does not pre-filter via SQL — `findMany` returns ALL shares with `inactivityAlertDays` set
- **File**: `apps/server/src/modules/email/notification.scheduler.ts:126-177`
- **Description**: The Prisma query fetches all shares with `inactivityAlertDays != null` and `inactivityAlertSent = false`. The inactivity threshold check happens in JS (`isInactive` line 147). For a deployment with thousands of shares having inactivity alerts configured, this fetches all of them daily. Not a critical perf issue at current scale but should be SQL-filtered when share count grows. Hard to do in Prisma when the threshold is a per-row computation (`lastDownloadedAt < now - inactivityAlertDays * day`), but `prisma.$queryRaw` could.

#### M-10: `processBatch` retries are sequential — no parallelism within a batch
- **File**: `apps/server/src/modules/email/queue.ts:151-230`
- **Description**: The code comment at line 122-124 says SQLite doesn't benefit from parallelism. True for writes. But SMTP sends are I/O-bound and could overlap. For a batch of 10 emails where each takes 1s, sequential processing means 10s per batch; with `Promise.all` (or `Promise.allSettled`), 1s. Trade-off: parallel sends increase memory/connection pressure and complicate error handling. Acceptable for current scale; document the decision.

#### M-12: `EmailJob.status` is a free-form string — no enum at the Prisma/TypeScript level

#### M-16: `interpolate` silently ignores unknown placeholder keys
- **File**: `apps/server/src/modules/email/i18n/loader.ts:264`
- **Description**: `if (!(key in params)) return match;` — unknown placeholders are left as literal `{xxx}` in the output. This is what enables the C-2 bug. Add a dev-mode assertion (NODE_ENV !== 'production') that warns/throws when an unsubstituted placeholder remains after interpolation.

## Positive Observations

- **`SmtpTransport` hash-based config caching is well-designed**: only the connection-relevant fields are included in the hash (correctly excluding `smtpFromName`/`smtpFromEmail`), and `testConnection` properly supports draft-config overrides. The `close()` flow correctly invalidates the cache.
- **Catalog → renderLayout → transport separation is clean** and lets each layer be tested in isolation. The `asRender` adapter is a pragmatic way to bridge typed renders to the untyped catalog without compromising payload-time Zod validation.
- **Stateless unsubscribe JWT with derived key per purpose** (`UNSUBSCRIBE_KEY_LABEL`) is a sound design — it prevents a leaked auth JWT from being used as an unsubscribe token. The 90-day expiry is reasonable.
- **`createTranslationFn` pre-loads both target locale AND English** so the synchronous TranslationFn returned to templates is guaranteed I/O-free during render. Smart design that avoids `async` plumbing through every template.
- **Idempotency via per-share flags** (`notifiedForExpiring`, `notifiedForExpired`, `inactivityAlertSent`) makes the boot-time scheduler run safe to repeat — a critical property for crash recovery.
- **Test coverage of the i18n loader's XSS-escape behaviour** is direct and convincing (`i18n-loader.test.ts:171-204`). The catalog smoke test that asserts no `{x.y}` placeholders remain in render output (`catalog.test.ts:373-376`) is a nice regression net for missing translation keys (though it doesn't catch the welcome.subtitle case because there's no dot in `{appName}`).
- **`stopEmailQueueScheduler()` is idempotent and properly removes the wake listener** — addressed a common bug class (listener leaks across restarts).
- **The `digest_pending` status** is reserved for future digest implementation; the type-level distinction between `pending` and `digest_pending` makes the future implementation straightforward.
- **Per-admin send loop in `sendToAdmins`** correctly applies per-admin preferences and locale — not a fan-out to a single mailing list.
