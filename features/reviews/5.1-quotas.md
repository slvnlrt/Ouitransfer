## Strengths

- **Clean module boundary.** The new `modules/quota/` directory has a single, well-defined responsibility. Repository, service, controller, routes, DTO are decomposed cleanly. The service is ~100 lines, the controller ~75 lines — no bloat.
- **Resolution hierarchy correctly designed.** `resolveEffectiveLimits` uses `??` (nullish coalescing) which correctly preserves `0n` as "unlimited" while treating `null` as "inherit". The unit tests explicitly verify both semantics. The group placeholder for 5.4 is in place and clearly commented.
- **Refactor of duplicated enforcement points is faithful.** The 3 call sites in `file/controller.ts` and the 1 in `reverse-share/upload.service.ts` all delegate to the same service. The "skip if unlimited" pattern (`if (limit > 0n)`) is applied consistently.
- **BigInt serialization at the user controller is centralized.** The `serializeUser` helper in `user/controller.ts` is applied to every send path — defensible against accidental BigInt leaks for the user-management endpoints.
- **Storage calculation is correctly delegated to SQL aggregates.** `prisma.file.aggregate` + `prisma.reverseShareFile.aggregate` is the right approach (no full table scan into JS). The relation filter `{ reverseShare: { creatorId: userId } }` correctly attributes ReverseShareFile bytes to the share creator.
- **Tests cover the core paths.** Unit tests exhaustively cover hierarchy permutations (admin/user × override/no-override × null/0/positive). Integration tests cover the request lifecycle for enforcement, admin endpoints, and the disk-space endpoint.
- **Forward-compat for Groups (5.4) is real, not theoretical.** The placeholder is a single line in the service, with no signature change needed when groups land.

## Issues

### Critical (Must Fix)

_None._ No data loss risks, no security holes, no broken functionality in the happy path. The feature works as specified.

### Important (Should Fix)

- [x] **[Important] Admin user-form-modal has two save buttons; quota changes are lost if the user clicks the main "Save"** — `apps/web/src/app/users-management/components/user-form-modal.tsx:262-273` and `:283-286`. The quota section has its own `quotaMutation` triggered by a separate button labelled with `t("users.form.quota.title")` ("Storage Quotas"). The main form submit handler does NOT send `maxFileSizeOverride` / `maxTotalStorageOverride`. A user who changes both name and quota, then clicks the main Save, gets only the name persisted. Worse, the small Save-button label is the section title, not an action verb, so users won't realize they need to click both.
  **Fix:** Merge quota fields into the main form schema and submit them in one request. Either extend `UpdateUserBody` server-side or call `updateUserQuota` from inside the parent `onSubmit` before/after `updateUser`. Single save action.

- [x] **[Important] `quotaOverrideField` transform produces 500 (not 400) on invalid input** — `apps/server/src/modules/quota/dto.ts:8-13`. The transform calls `BigInt(val)` unguarded — passing `"abc"`, `"1.5"`, or `1.5` causes `SyntaxError` / `RangeError` to bubble up as an uncaught error → 500 Internal Server Error instead of 400 Bad Request. The `throw new Error("...non-negative")` is also not a Zod issue, so the message doesn't get the standard validation-error envelope.
  **Fix:** Use the contextual transform signature and `ctx.addIssue`:
  ```ts
  const quotaOverrideField = z.union([z.number(), z.string(), z.null()]).transform((val, ctx) => {
    if (val === null) return null;
    try {
      const n = BigInt(val);
      if (n < 0n) {
        ctx.addIssue({ code: z.ZodIssueCode.custom, message: "Quota value must be non-negative" });
        return z.NEVER;
      }
      return n;
    } catch {
      ctx.addIssue({ code: z.ZodIssueCode.custom, message: "Quota value must be an integer in bytes" });
      return z.NEVER;
    }
  });
  ```

- [x] **[Important] Route-level body schema bypasses the `quotaOverrideField` transform** — `apps/server/src/modules/quota/routes.ts:59-68`. The PATCH body schema declares `maxFileSizeOverride: z.union([z.number(), z.string(), z.null()]).optional()` inline, NOT `UpdateQuotaSchema`. Fastify+Zod validates the body against this looser schema first, then the controller calls `UpdateQuotaSchema.parse(...)` which has the strict transform. This is exactly the Rule-9 anti-pattern called out in `CLAUDE.md` ("keep route-level and controller-level schemas in sync"). Currently it's a redundant duplication that will drift; combined with the bug above it's the path that produces 500s.
  **Fix:** Reference `UpdateQuotaSchema` directly in the route schema: `body: UpdateQuotaSchema`. Single source of truth.

- [x] **[Important] Admin quota UI doesn't display the user's effective limits or current usage — spec §Frontend Changes §5 not met.** The spec says: *"Display: current usage, effective limits (resolved), override values"*. The implementation only renders the override values (the three-mode Select inherit/unlimited/custom). The `getUserQuota` API function is defined (`apps/web/src/http/endpoints/users/index.ts:123-128`) and the proxy route exists (`apps/web/src/lib/proxy-routes.ts:395`), but nothing in the UI calls it. An admin sets `null` (inherit) and has no way to see what the user's effective quota actually is or how much they've used.
  **Fix:** Fetch `GET /users/:id/quota` when the modal opens in edit mode, render the resolved `maxFileSize`/`maxTotalStorage`/`used`/`percentage` as read-only display rows alongside the override inputs.

- [x] **[Important] BigInt → percentage truncation can under-report the warning level near boundaries** — `apps/server/src/modules/quota/service.ts:78`. `Math.round(Number((used * 100n) / limits.maxTotalStorage))` truncates the BigInt division before the rounding. Example: used = 8.9 GiB of 10 GiB → real percentage 89.0%, but `(8589934592 * 100n) / 10737418240n` = `80n` (integer division of `953674823 * 100 / 1073741824`... actually need recomputation, but in general the truncation can lose 1% near boundaries). For the `critical` threshold (90%) and `warning` threshold (80%) this means transitions occur slightly later than displayed. The over-quota detection itself is unaffected because `used >= limit` is the source of truth for `exceeded`.
  **Fix:** Compute on Number after a safe down-cast: `Math.round(Number(used) / Number(limits.maxTotalStorage) * 100)`. For all realistic quotas (< 2^53 bytes ≈ 9 PB) Number can hold the operands without loss. Or use `(used * 10000n) / limit` and divide by 100 to keep two decimal precision.

- [x] **[Important] Non-English locale files were not actually translated — 22 locale files contain English placeholders for the quota strings.** Confirmed via diff: `fr-FR.json`, etc., have `"unlimited": "Unlimited"`, `"used": "{used} of {total} used"`, `"banner": "Your storage quota is exceeded..."`. The plan Task 15 Step 2 explicitly says *"the translations can be improved later — the important thing is that the keys exist"*, but the codebase standard (per `features/SESSIONS.md` and the recent translation work in commits `bfd5276`/`eb78fe2`) is to translate all keys at the time of feature merge. This regresses i18n quality.
   **Fix:** Translate the new keys in all 22 non-English locales. The pattern is well-established — quota strings are small and self-contained.

- [x] **[Important] `auth/me`, `/auth/login`, `/auth/2fa/login` response schemas omit the new quota fields, but the frontend `User` type declares them as if they were returned.** `apps/web/src/http/endpoints/auth/types.ts:17-18` declares `maxFileSizeOverride?: string | null` on the `User` interface used by `GetCurrentUser200`. The server schema at `apps/server/src/modules/auth/routes.ts:64-74` (login), `:108-118` (2fa login), and `:213-224` (/auth/me) does not include these fields, so the Zod serializer strips them. The frontend will see `undefined` from these endpoints even though the type allows `string | null`. Not a runtime crash (Zod stripping is graceful), but it's a contract mismatch hidden by optional `?:`. Either remove the fields from the frontend `User` type and require admin endpoints to deliver quota info separately, or extend the three response schemas to include the fields and route the responses through `serializeUser`. Otherwise this will silently cause bugs when downstream code reads `user.maxFileSizeOverride` from auth responses.
  **Fix:** Decide on the contract. Simplest: include the two fields in `/auth/me`, `/auth/login`, and `/auth/2fa/login` response schemas as `z.string().nullable()`, and apply `serializeUser` in the three auth controller paths (`reply.send({ user })` at controller.ts lines 102, 160, 241).

- [x] **[Important] `QuotaController.getUserQuota` performs a redundant `prisma.user.findUnique`** — `apps/server/src/modules/quota/controller.ts:14-20` then `:26` (`getQuotaStatus` → `resolveEffectiveLimits` → another `findUnique`). Two DB roundtrips per request for the same user. Move the override read into `getQuotaStatus`, or have `resolveEffectiveLimits` return the raw overrides alongside the effective values.
  **Fix:** Extend `QuotaService.getQuotaStatus` (or add a new method `getQuotaStatusWithOverrides`) to return `overrides: { maxFileSizeOverride, maxTotalStorageOverride }` from the same `user.findUnique` already done inside `resolveEffectiveLimits`. Then drop the controller-level lookup.

- [x] **[Important] No integration test for PATCH endpoint rejection by non-admin.** `apps/server/src/__tests__/quota.integration.test.ts:593-612` tests that a regular user gets 403 on `GET /users/:id/quota`, but never tests PATCH. The two routes share `preValidation`, but Rule 9 (Fastify+Zod) says "service-layer tests are not sufficient" and Rule 11 calls out that security-critical flows need integration tests for each. PATCH is the mutation — it deserves its own 403 assertion.
  **Fix:** Add a test that signs a non-admin token and PATCHes `/users/:id/quota`, asserting `statusCode === 403`.

### Minor (Nice to Have)

- [ ] **[Minor] `private maxFileSize?: number; percentage?: number;` in `getDiskSpace` return type lets admins inherit those as `undefined`** — `apps/server/src/modules/storage/service.ts:96-107`. Optional fields create a typing escape hatch: callers that don't narrow `isAdmin` first may try to read `maxFileSize` and get `undefined`. Consider a discriminated union `{ kind: "admin", ... } | { kind: "user", warningLevel, maxFileSize, percentage, ... }` to make the variants explicit. Low-impact since the existing callers handle it.

- [x] **[Minor] `Number.MAX_SAFE_INTEGER` returned as `diskAvailableGB` when unlimited (in `storage/service.ts:142`) is then overridden to `-1` two lines later (line 148).** The intermediate `Number.MAX_SAFE_INTEGER` value is unreachable code. Just inline: `const availableStorageGB = isUnlimited ? 0 : ...` and use the `-1` ternary directly in the response. Cleaner.

- [x] **[Minor] No upper-bound validation on quota override values.** A user could submit `9999999999999999999` (greater than `Number.MAX_SAFE_INTEGER`) and store a number Prisma can hold but the frontend can't round-trip safely through `Number()`. Consider capping at e.g. `1 PB` (`1n << 50n`) or `Number.MAX_SAFE_INTEGER` to prevent surprises in downstream MB/GB conversions which use `Number(limit) / (1024*1024)`.

- [x] **[Minor] `QuotaService` is instantiated multiple times across the codebase** — each of `FileController`, `ReverseShareUploadService`, `StorageService`, `QuotaController` creates its own instance with its own `QuotaRepository`. Inexpensive but inconsistent with the singleton-ish pattern used elsewhere (e.g., service classes typically reused). Not worth changing now, but a constructor-injected dependency would be cleaner if/when DI is introduced.

- [x] **[Minor] `quotaOverrideField` accepts arbitrary unbounded strings like `"0x1234"` or `"1e10"`.** `BigInt("0x1234")` returns 4660n (hex parsing); `BigInt("1e10")` throws. The mixed behavior is surprising. Restrict the string variant with a regex: `z.string().regex(/^-?\d+$/)` before transforming.

- [x] **[Minor] Integration test `getCsrf` helper returns `{ csrfToken, csrfCookie: string | undefined }`** — `apps/server/src/__tests__/quota.integration.test.ts:143-148`. The `undefined` case isn't asserted; if `_csrf` cookie isn't present the test silently sends `cookie: token=...; _csrf=undefined`, which fails the CSRF check and yields a confusing 403 instead of a test-fixture error.
  **Fix:** Throw if `csrfCookie === undefined` in the helper.

- [x] **[Minor] `formatStorageSize` is reused for both quota display and disk space, but assumes GB input.** When `diskSpace.diskUsedGB` is computed from BigInt bytes via `Number(...) / (1024^3)`, small file counts produce e.g. `0.00 MB` rendered as "0.00 MB" via the helper's MB branch. For a brand-new user with no files, the QuotaDisplay shows "0.00 KB used" or similar — fine, but a tiny UI polish would be to show "0 B" when empty.

- [x] **[Minor] Admin-only widget restriction means an admin who has been restricted via an override sees no quota info.** Admins are routed to `AdminView` which shows physical disk space, not their personal quota. A restricted admin will hit the upload error without any visual warning beforehand. Edge case — admins restricting themselves is rare. Could be addressed by adding the QuotaDisplay to AdminView too when their effective limit > 0.

- [x] **[Minor] `getInitialMode` in user-form-modal.tsx mutates `fileSizeValue` to `"0"` when the override is `null`** — `apps/web/src/app/users-management/components/user-form-modal.tsx:66, 69`. If the user toggles from "inherit" to "custom" the `FileSizeInput` starts at "0" rather than preserving any previous custom value. Minor UX inconvenience.

- [x] **[Minor] Quota mutation only invalidates `queryKeys.users.all`, not the specific user query.** `apps/web/src/app/users-management/components/user-form-modal.tsx:95`. The modal's `selectedUser` becomes stale until parent refetches. Minor — the user list invalidation will eventually trigger a refetch, but if the modal stays open the UI doesn't reflect the saved override.

- [x] **[Minor] No `_count` is asserted in the QuotaRepository test for `prisma.file.aggregate` — only `_sum: { size: true }` is verified.** `apps/server/src/modules/quota/__tests__/service.test.ts:61-68`. If a future refactor adds `_count` to the aggregate query (e.g., to also display file count), the test won't catch over-fetching. Low priority — a tiny call-shape assertion is sufficient.

- [x] **[Minor] The `useSystemStatus` hook enables `diskSpaceQuery` for all users (line 74), including unauthenticated visitors during the brief moment before `useAuth` resolves.** If the hook mounts before auth completes, the query runs and gets a 401 → parsed as `server_error`. Minor — the dashboard route already requires auth, so this won't normally happen.

- [x] **[Minor] `UpdateQuotaResponseSchema` has a 200 status code but no `404` documented in `UpdateQuotaSchema`'s zod object — only added at the route level.** Not actually a bug since the route declares 404, but the DTO file would be a more natural single source of truth for response shapes per status.

## Recommendations

1. **Spec coverage matters as much as code coverage.** The "current usage and effective limits" display (spec §5) is missing from the admin UI. When you fix the two-save-button issue (Important #1), bring the effective limits along — they're already fetched on the server, just need to be displayed.

2. **Use Fastify+Zod's response schema as a forcing function for `serializeUser`.** Today, three auth-controller paths leak the BigInt-bearing Prisma object through `reply.send` — they work only because the Zod schema silently strips. Either explicitly include the quota fields and call `serializeUser`, or remove the field declarations from the frontend `User` type to match reality.

3. **Consolidate the route+DTO schema duplication.** The PATCH body is declared twice with different strictness — exactly the kind of drift CLAUDE.md Rule 9 warns about. Reference `UpdateQuotaSchema` in the route.

4. **Add a single integration test for quota-overage on reverse-share copy.** The 4th refactored enforcement point (`reverse-share/upload.service.ts:299-324`) has zero integration coverage — only unit-level expectations via the QuotaService unit tests. Given the criticality of "user copying a reverse-share file to their own files while over quota", a single `app.inject()` test is warranted.

5. **Consider extracting the duplicated quota-check block** from `FileController.registerFile` (lines 127-152) and `FileController.checkFile` (lines 208-233). They are identical 24-line blocks. A helper method `private async enforceQuota(userId, fileSize)` on QuotaService would reduce the duplication and centralize the error messages (currently the messages are duplicated in 3 places — `MB available`, `maxSizeMB`).
