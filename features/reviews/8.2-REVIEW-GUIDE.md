# 8.2 Email Notifications — Review & Remediation Guide

Guide opérationnel pour les phases de review de la feature 8.2. Ce document est le résultat de 5 passes de review (dont de nombreuses erreurs). Lis-le intégralement avant de lancer quoi que ce soit.

---

## Contexte

La feature 8.2 (Email Notifications) a traversé 5 passes de review. Les review files sont dans `features/reviews/8.2-review-*`. La spec est `features/specs/8.2-email-notifications.md`, le plan est `features/plans/8.2-email-notifications.md`.

Les passes précédentes ont trouvé et corrigé ~230 findings au total. Chaque passe trouve moins de critiques, mais certaines erreurs de process ont été commises. Ce guide documente les leçons apprises.

---

## Phase 1 : Lancer la review

### Scopes

On dispatche **3 agents reviewer séquentiellement** (jamais en parallèle — CLAUDE.md l'interdit) :

1. **Server Core** — `apps/server/src/modules/email/` + `apps/server/src/modules/notification/` + modèle Prisma
2. **Server Integration** — `apps/server/src/modules/share/`, `file/`, `reverse-share/`, `user/`, `auth/`, `ldap/` — comment le système email s'intègre au reste
3. **Frontend** — `apps/web/` — composants, hooks, types, i18n

### Prompt pour les agents reviewer

Chaque agent reçoit :
- La spec et le plan comme référence (PAS les review files précédentes)
- Son scope (quels fichiers/modules lire)
- Le format de sortie attendu (fichier markdown avec Critical/Important/Minor)
- L'instruction de vérifier chaque finding contre le code réel avant de le reporter

**Ne PAS dire aux agents** :
- Le numéro de la passe ("c'est la passe 6") — ça les biaise
- Les findings des passes précédentes — ils doivent regarder le code dans son état actuel
- Quoi que ce soit sur les phases précédentes

**Nommage des fichiers** : `features/reviews/8.2-review-{N}-{scope}.md` où N est le numéro de passe et scope est `server-core`, `server-integration`, ou `frontend`.

### Format des findings

```markdown
# 8.2 Email Notifications — {Scope} Review (Pass {N})

**Date**: YYYY-MM-DD
**Reviewer**: Agent ({Scope})
**Scope**: [description]

## Critical
### C-N: [Title]
- **File(s)**: [path:line]
- **Description**: [what's wrong]
- **Expected**: [what the spec/plan says]
- **Fix**: [concrete fix suggestion]

## Important
### I-N: [Title]
(same format)

## Minor
### M-N: [Title]
(same format)

## Positive Observations
- [things done well]
```

### Après les 3 reviews

1. Commit les 3 fichiers : `docs: add pass {N} review files for 8.2 email notifications`
2. Lire les 3 fichiers en entier pour comprendre tous les findings
3. Planifier les batches de remédiation

## Phase 2 : Remédiation (fixer les findings)

### Organisation en batches

Ordre de priorité :
1. **Batch 1** : Tous les Criticals (les 3 scopes combinés)
2. **Batch 2** : Server Importants
3. **Batch 3** : Frontend Importants (+ Integration Importants restants)
4. **Batch 4** : Tous les Minors (les 3 scopes combinés)
5. **Final** : Cocher les findings dans les review files

### Dispatching des agents de fix

- **Un seul agent à la fois** (séquentiel, jamais parallèle)
- Agent type : `worker-smart` pour les criticals/importants, `worker` pour les minors
- Chaque agent doit :
  - Implémenter le fix
  - Ajouter/mettre à jour les tests
  - Vérifier type-check + test suite
  - Commiter avec un message clair

### CE QU'IL NE FAUT JAMAIS FAIRE

#### 1. NE JAMAIS transformer un finding en commentaire/TODO

C'est l'erreur #1 des passes précédentes. Un reviewer signale un problème réel → l'orchestrateur écrit dans le prompt du fix agent "ajoute un commentaire" ou "ajoute un TODO" au lieu de demander un vrai fix.

**Exemples de ce qui a été fait (et qui est INTERDIT)** :
```
### M-8: share_downloaded loses visitor identity
Fix: No code change. Add a comment in file/routes.ts noting this is a known gap.

### M-9: getShare by ID doesn't parse visitor cookie  
Fix: Add a comment noting this route doesn't support cookies.

### M-5: Audit metadata stores plaintext emails
Fix: Add a TODO comment.
```

**Ce qu'il faut faire à la place** :
- Si le fix est réalisable dans le scope de 8.2 → **le faire**
- Si le fix est vraiment hors scope (nécessite un nouveau modèle de données, une feature entière, etc.) → **le tracker dans `features/TECHNICAL-DEBT.md` ou `features/BUGS.md`** avec une description complète, le contexte, et le fix attendu. NE PAS mettre un commentaire dans le code.
- En cas de doute → demander à l'utilisateur, ne pas décider seul

#### 2. NE JAMAIS ignorer un bug pré-existant trouvé par un agent

CLAUDE.md dit : "Fix pre-existing issues encountered along the way — not just items explicitly in scope."

Un agent a trouvé un bug dans `updateShare` qui efface l'expiration quand elle n'est pas dans le payload. Il a écrit "Not a 8.2 finding. Skip." dans ses notes. L'orchestrateur n'a rien fait. Le bug existe toujours.

**Ce qu'il faut faire** :
- Si le fix est simple → le fixer dans le même batch ou un batch dédié
- Si le fix est complexe → le tracker dans `features/BUGS.md` avec numéro B-XX
- **Ne JAMAIS juste "skip"**

#### 3. NE JAMAIS toucher au working tree après un agent timeout/empty output

CLAUDE.md : "HARD STOP on empty subagent output. Your ONLY action is to inform the user and STOP."

Ça veut dire :
- Pas de `git status`
- Pas de `git log`
- Pas de `git checkout`
- Pas de `git diff`
- Pas de lecture de fichiers
- Pas de lancement de tests
- RIEN. Informer l'utilisateur et attendre.

Un `git checkout` sur des fichiers non-commités peut **détruire le travail de l'agent**.

#### 4. NE JAMAIS supprimer des fichiers/dossiers sans permission explicite de l'utilisateur

Même si un fichier semble "pas à nous" (ex: `memory-bank/` créé par un agent). Demander d'abord.

#### 5. NE JAMAIS décider seul qu'un finding est "hors scope"

Seul l'utilisateur peut décider qu'un item est hors scope. L'orchestrateur ne fait que proposer.

### Vérification des outputs d'agents

Après chaque agent de fix :
1. **Lire l'output en entier** — pas juste "X tests pass, done"
2. **Chercher les mots-clés** : "skip", "defer", "no action", "no code change", "comment added", "TODO added", "out of scope", "acceptable", "trade-off"
3. **Pour chaque item trouvé** : est-ce que c'est un vrai fix ou un contournement ? Si c'est un contournement, le tracker.
4. **Vérifier les déviations** : l'agent a-t-il fait exactement ce qui était demandé ? A-t-il ajouté/modifié des fichiers inattendus ?

### Vérification des tests

Après chaque batch :
- `pnpm --filter ouitransfer-api run type-check`
- `pnpm --filter ouitransfer-api test`
- `pnpm --filter ouitransfer-web run type-check`
- `pnpm --filter ouitransfer-web test`
- `pnpm --filter @ouitransfer/shared test` (si le package shared a été touché)

Si l'agent a déjà vérifié et commité, ces vérifications sont redondantes mais pas interdites (contrairement au cas du timeout/empty output où elles SONT interdites).

## Phase 3 : Check-off

Après tous les fix batches, utiliser le script PowerShell dédié — **ne pas dispatcher d'agent** pour ça :

```powershell
# Depuis la racine du projet
pwsh features\reviews\check-off-review.ps1 "features\reviews\8.2-review-{N}-*.md"
```

Le script transforme `### C-1: Titre` → `### ~~C-1~~ [x]: Titre` (et `####` également).
Il est idempotent — on peut le relancer sans casser les fichiers déjà cochés.

Puis commiter : `docs: check off all pass {N} review findings for 8.2`

---

## Phase 4 : Décision

Après le check-off, regarder les résultats :
- **0 critiques trouvées dans cette passe** → la feature peut être déclarée Done
- **Des critiques trouvées** → relancer une nouvelle passe de review (retour à Phase 1)

Le critère d'arrêt est : **0 critiques dans une passe complète**.

---

## Checklist de pré-lancement d'une passe

- [ ] Les fix de la passe précédente sont tous commités
- [ ] Les tests passent (server + web + shared)
- [ ] Les type-checks passent
- [ ] Les review files de la passe précédente sont cochées
- [ ] Le contexte est compressé (les détails des passes précédentes ne sont plus nécessaires)

## Checklist post-remédiation

- [ ] Chaque finding a un vrai fix OU est tracké dans BUGS.md/TECHNICAL-DEBT.md (pas un commentaire)
- [ ] Les outputs de tous les agents ont été lus et vérifiés pour les skip/defer/TODO
- [ ] Les bugs pré-existants trouvés par les agents sont trackés
- [ ] Les tests passent
- [ ] Les type-checks passent
- [ ] Les findings sont cochés dans les review files
- [ ] `features/TODO-2026-05-30.md` a été vérifié (items restants ?)
