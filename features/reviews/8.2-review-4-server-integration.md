# 8.2 Email Notifications — Server Integration Review (Pass 4)

**Date**: 2026-05-29
**Reviewer**: Principal-level code review (Codebase MCP + manual verification)
**Scope**: Share / File / ReverseShare / Notification / Auth routes & services — email integration points
**Reference**: `features/specs/8.2-email-notifications.md`, `features/plans/8.2-email-notifications.md`

---

## Summary

The email **plumbing** (SmtpTransport, queue, catalog, templates, i18n, EmailService orchestrator, NotificationPreference cascade, unsubscribe, admin endpoints) is in good shape and largely matches the spec. Migration of the 4 legacy callers (auth, ldap, share/notify, reverse-share/upload) is correctly done, the 5 MVP bugs are fixed, recipient upsert preserves tracking tokens, and visitor tracking + identification gate behave per spec.

However, the **business-side trigger coverage is incomplete vs. the spec's in-scope catalog** (Section 12: "triggers for types 1-15 and 20-22"). Five in-scope notification types are defined in the catalog but never fired from anywhere in the codebase: `account_deactivated`, `account_reactivated`, `reverse_share_invitation`, `share_max_views_reached`, `admin_user_registered`. The catalog also exhibits a preference-cascade semantic that makes the per-share `notifyOnDownload` toggle a silent no-op for the most common user state. And `notifyRecipients` records `notifiedAt = now()` even when SMTP is disabled, so the UI lies to the operator.

The visitor-identification cookie is scoped to `path: "/api"`, which works in production behind the Next.js proxy but would silently fail if the API were ever accessed directly without the proxy rewrite — a hidden coupling worth documenting in the cookie handler.

Most other items are minor (rate limit on `/notify`, the share-folder gap in download tracking, lack of runtime Zod validation of payloads at send time).

## Critical

### C-1: Per-share `notifyOnDownload=true` is a silent no-op for users with no preference row

- **Files**:
  - `apps/server/src/modules/email/service.ts:251-281` (`resolveFrequency`)
  - `apps/server/src/modules/share/dto.ts:27` / `repository.ts` (the per-share field)
  - `apps/server/src/modules/file/routes.ts:192-204` (the call site)
- **Issue**: The cascade in `resolveFrequency()` reads:
  ```ts
  const baseFrequency = pref ? pref.frequency : (catalogEntry?.defaultFrequency ?? "immediate");
  if (baseFrequency === "disabled") return "disabled";
  // per-share override only checked AFTER the early return
  ```
  Because `share_downloaded` has `defaultFrequency: "disabled"` (catalog.ts:353) and a brand-new user has no `NotificationPreference` row, `baseFrequency === "disabled"` and the function returns *before* the `notifyOnDownload` check. Practical consequence: a user who toggles **"Notify me on each download"** on a specific share gets **no notifications** unless they *also* go to the global preferences page and switch `share_downloaded` to "immediate" — at which point the per-share toggle becomes redundant.
  This is a real UX/spec-intent bug, not a hypothetical edge case. The whole point of the per-share toggle (spec §6, "Per-share overrides") is "I want download notifications for *this* share even though my global default is off."
  The existing test `email-service.test.ts:580-592` ("disabled wins over notifyOnDownload=true") only covers the case where the user has *explicitly* chosen `disabled` — that case should indeed lose to user choice. There is no test for `no preference row + notifyOnDownload=true`, so the regression has slipped through.
- **Fix**: Distinguish between *explicit* user-disabled and *implicit* catalog-default-disabled. One clean shape:
  ```ts
  const explicitFrequency = pref?.frequency; // user-set
  const defaultFrequency = catalogEntry?.defaultFrequency ?? "immediate";

  // 1. Explicit "disabled" always wins
  if (explicitFrequency === "disabled") return "disabled";

  // 2. Per-share override only when relevant
  if (shareId && type === "share_downloaded") {
    const share = await prisma.share.findUnique({ where: { id: shareId }, select: { notifyOnDownload: true } });
    if (share?.notifyOnDownload) return "immediate";
  }

  // 3. Otherwise fall back to explicit pref or catalog default
  return (explicitFrequency ?? defaultFrequency) as "immediate" | "daily_digest" | "disabled";
  ```
  And add the missing test: "no preference + notifyOnDownload=true → immediate" + "no preference + notifyOnDownload=false → disabled".

### C-2: `notifyRecipients` sets `notifiedAt` even when SMTP is disabled — UI lies to the operator

- **File**: `apps/server/src/modules/share/service.ts:712-734`
- **Issue**: `emailService.send()` returns silently (without throwing) when `smtpEnabled !== "true"` or `appUrl` is not configured (`email/service.ts:67-86`). `notifyRecipients` treats a non-throwing `send()` as success and immediately writes:
  ```ts
  await emailService.send("share_invitation", { ... });   // ← silent no-op when SMTP is off
  await prisma.shareRecipient.update({ data: { notifiedAt: new Date() } });
  notifiedRecipients.push(recipient.email);
  ```
  So the route returns `{ notifiedRecipients: [...] }`, the UI shows a check icon on each recipient, the audit log records `SHARE_RECIPIENT_NOTIFY`, but **no email was actually sent and none will ever be sent** (no job was enqueued either). This is dangerous in real use: an admin disables SMTP during a maintenance window, users click "Notify", everything looks fine.
- **Fix**: Either
  (a) Have `emailService.send()` return a discriminated result (`{ enqueued: true } | { enqueued: false, reason: "smtp_disabled" | "appUrl_missing" | "preference_disabled" | "cooldown" }`) so callers can act on it. The cooldown/preference cases should *not* prevent `notifiedAt` for invitations (preferences don't apply to `share_invitation`), but `smtp_disabled` / `appUrl_missing` should.
  (b) Cheaper interim: in `notifyRecipients`, peek at SMTP/appUrl state *before* the loop and refuse the whole call with a clear `ServiceUnavailable` error if either is off — the operator immediately understands. The "fire-and-forget" notifications elsewhere (`share_accessed`, `share_downloaded`, scheduler) are fine to stay silent; user-initiated `/notify` is the only path where the user expects feedback.
  Also add an integration test: `POST /shares/:shareId/notify` with `smtpEnabled=false` should not set `notifiedAt`.

### C-3: Five in-scope notification types defined but never triggered

- **Files**: catalog and templates exist (`apps/server/src/modules/email/catalog.ts:247-278, 302-320, 399-413, 550-563`) and `email/templates/{account-deactivated,account-reactivated,reverse-share-invitation,share-max-views-reached,admin-user-registered}.ts`.
- **Issue**: Spec §12 says 8.2 ships "triggers for types 1-15 and 20-22". Grep across `apps/server/src` confirms that no business module calls `emailService.send()` for the following in-scope types:
  - `account_deactivated` (type 3) — should fire when admin deactivates a user. The user PATCH/deactivate route does not call `emailService.send("account_deactivated", …)`.
  - `account_reactivated` (type 4) — same, for reactivation.
  - `reverse_share_invitation` (type 6) — no `notify` endpoint exists on `reverse-share/routes.ts`; the catalog entry, schema, i18n keys and template are pure dead code in 8.2.
  - `share_max_views_reached` (type 11) — `share/service.ts:288-294` throws `MAX_VIEWS_REACHED` when the atomic increment fails, but does not call `emailService.send("share_max_views_reached", …)` for the creator. The spec catalog explicitly lists this as in-scope.
  - `admin_user_registered` (type 20) — `emailService.sendToAdmins()` is implemented and tested, but no caller (LDAP sync, invite acceptance, OAuth first-login) actually invokes it.
- **Fix**: Add the trigger code paths. They are small additions:
  - In the user admin update flow, when `isActive` flips false → send `account_deactivated`. When true ← false → send `account_reactivated`. Fire-and-forget with try/catch + logger.error.
  - Add `POST /reverse-shares/:id/notify` mirroring the share notify route (with `ShareRecipient` equivalent on reverse-share — though reverse-shares don't have recipients today, so this might also require a schema addition; if so, downgrade to Important and re-defer with an explicit note).
  - In `share/service.ts:288-294`, when `incremented === false` and `share.maxViews !== null && share.creatorId && share.creator?.email`, dispatch a fire-and-forget `emailService.send("share_max_views_reached", …)` before throwing — gated by `notifiedForMaxViews` Boolean on Share (new field) to avoid spamming the creator on every subsequent attempt. Without such a flag this would fire on every refused access.
  - In whichever flow currently creates a User from LDAP sync / invite acceptance, call `emailService.sendToAdmins("admin_user_registered", { ... })`.
  Alternative (acceptable but should be explicit): downgrade the spec to defer these triggers, document them as deferred in `features/specs/8.2-email-notifications.md` §12, and convert the catalog entries to clearly-marked dead-code TODO stubs with a tracking issue. **What is unacceptable is the current state**, where the spec says these are shipped but no code path exercises them — that masks the omission from anyone reading only the spec.

## Important

### I-1: `/shares/:shareId/notify` has no rate limit — recipient-spam vector

- **File**: `apps/server/src/modules/share/routes.ts:709-769`
- **Issue**: A logged-in user owning a share can call `POST /shares/:shareId/notify` arbitrarily often. `share_invitation` has no `cooldownSeconds` in the catalog (intentional — re-notify is a feature), so each call enqueues fresh `EmailJob`s for every selected recipient. The global rate limit is 100/min/IP, which still lets one user enqueue several hundred external emails per minute through a single share, and the audit row makes the spam attributable.
- **Fix**: Add a route-level rate limit on `/shares/:shareId/notify` (e.g., `max: 10, timeWindow: "10 minutes"` keyed on `shareId + userId`). Mirrors the protection on `/shares/alias/:alias/identify`.

### I-2: Share download tracking misses files reached via shared folders

- **File**: `apps/server/src/modules/file/routes.ts:144-206` (`trackShareDownload`)
- **Issue**: The membership check is `prisma.share.findFirst({ where: { id: shareId, files: { some: { id: fileRecord.id } } } })`. Shares can also expose files through `folders` (the `ShareFolders` relation in `schema.prisma`). A visitor downloading a file from a shared folder will be silently filtered out: no `ShareVisit` row, no `lastDownloadedAt` update, no `share_downloaded` notification. The same blind spot breaks `share_no_activity` for any share whose entire content is folder-based — `lastDownloadedAt` stays NULL and the inactivity scheduler triggers on `createdAt < threshold` (notification.scheduler.ts:161-165), causing false inactivity alerts on perfectly active folder-shares.
- **Fix**: Extend the validation query to also accept files whose `folderId` (or any ancestor folder) is connected to the share via `folders`. Pseudo:
  ```ts
  const shareWithFile = await prisma.share.findFirst({
    where: {
      id: shareId,
      OR: [
        { files: { some: { id: fileRecord.id } } },
        { folders: { some: { files: { some: { id: fileRecord.id } } } } },
        // and recursively through nested folders if FolderService exposes that
      ],
    },
    include: { creator: { select: { email: true, locale: true } } },
  });
  ```
  Since the folder structure can be nested, the cleanest implementation is to reuse `FolderService.getAllFilesInFolder` (already used elsewhere in `file/routes.ts:81`) to compute the full file set per shared folder and check membership. A small `shareContainsFile(shareId, fileId)` helper would belong in `share/service.ts` and be reused.

### I-3: Visitor identification cookie `path` couples server to Next.js proxy

- **Files**:
  - `apps/server/src/modules/share/routes.ts:867-874` (Set-Cookie)
  - `apps/server/src/modules/share/routes.ts:39-62` (`parseVisitorCookie`)
- **Issue**: `reply.setCookie(\`sv_${alias}\`, payload, { path: "/api", ... })`. The Fastify backend serves `/shares/...` directly (no `/api` prefix in `server.ts` route registration); the `/api` prefix only exists in the Next.js proxy layer. In production this works because requests transit `/api/shares/...` (browser → Next → rewritten). But:
  - Anyone running the backend directly (CI, local debugging without the web app, integration test that calls `/shares/...` without a proxy) will silently get cookie-less follow-up requests. The integration test `visitor-identification.test.ts:597-604` re-attaches the cookie manually via `cookies: { ... }`, which bypasses path matching and therefore *can't catch this misconfiguration*.
  - If anyone ever changes the proxy prefix, the auth cookie will silently break and only manual testing will catch it.
- **Fix**: Either scope to `path: "/"` (simplest, the cookie name `sv_{alias}` is already namespaced and httpOnly+signed, leakage risk is negligible), or read the prefix from an env var so both layers stay in sync. Add an explicit comment near the Set-Cookie call documenting the coupling. Also worth adding an integration test that uses `cookies: undefined` and reads the actual Set-Cookie path from the response — currently no test asserts the cookie path.

### I-4: Notify route ignores recipient name from request body

- **Files**:
  - `apps/server/src/modules/share/routes.ts:721-731` (`emails: z.array(...).optional()`)
  - `apps/server/src/modules/share/service.ts:691-694` (sender resolution)
- **Issue**: The route schema for `POST /shares/:shareId/notify` only accepts `emails: string[]`. There is no path to pass per-recipient *names* — but the `ShareRecipient` model now has a `name` column and the spec talks about per-recipient name. To actually populate `recipient.name`, the user must hit `POST /shares/:shareId/recipients` (which accepts `recipients: [{ email, name }]`) first, then `/notify`. The frontend can manage this two-step dance, but the API ergonomics invite mistakes — a frontend developer using just `/notify` will lose the recipient name.
  Also `notifyRecipients` does not validate that the requested `emails` are owned by the share creator (already gated by `share.creatorId === userId` check, OK) but it does silently lower-case input on both sides for matching — good (matches the dto-level transform). One small concern: when none of `selectedEmails` match, the service throws `"None of the selected emails match..."` (service.ts:677-679). The error message leaks the recipient set state to the caller; since the caller is authenticated as the share owner, that's acceptable.
- **Fix**: Either document explicitly in the route description that `/notify` requires recipients to already exist on the share (good current behavior, but make it obvious), or accept a richer body like `{ recipients?: Array<{ email, name? }> }` that *upserts then notifies* in one call to match the `addRecipients` shape. Decision belongs to product, but the asymmetry between `addRecipients` (accepts `{ email, name }`) and `notify` (only `email`) should at least be called out in route descriptions.

### I-5: `share_accessed` triggered on every non-owner access regardless of `share.creator.isActive`

- **File**: `apps/server/src/modules/share/service.ts:344-359`
- **Issue**: The fire-and-forget `share_accessed` send only checks `share.creatorId && share.creator?.email`. The scheduler notifications (notification.scheduler.ts:39, 93, 149, 210, 257) all filter on `creator: { isActive: true }`. The inline triggers don't. Result: a deactivated user (or admin-disabled account) continues to receive `share_accessed` and `share_downloaded` notifications for their old shares. This both contradicts the schedulers' policy and may violate the spec intent for `account_deactivated` (an inactive account shouldn't receive further app emails except critical lifecycle ones).
  The cascade in `emailService.send()` does not check `isActive` either — it checks SMTP + preferences only. So nothing else catches this.
- **Fix**: Two options:
  (a) Add `creator: { isActive: true }` (or fetch `creator.isActive` and short-circuit) at the call sites in `share/service.ts:344` and `file/routes.ts:191`.
  (b) Or, more general, add an active-user filter inside `EmailService.send()` when `options.userId` is provided and the type is non-critical. (b) is more invasive but eliminates the failure mode forever and aligns with the scheduler's behavior. Either way, add a regression test.

### I-6: No runtime validation of `data` against `payloadSchema` at send time

- **Files**: `apps/server/src/modules/email/catalog.ts:41-60` (catalog), `apps/server/src/modules/email/service.ts:43-240` (send)
- **Issue**: The catalog defines `payloadSchema: z.ZodType` for every type and `asRender` casts the typed render fn to `(unknown, t) => LayoutSlots`. But `send()` never calls `entry.payloadSchema.parse(options.data)`. TypeScript catches most mistakes at compile time, *but only at the call site* — anything that loses precise typing on the way in (e.g., a refactor where `data` is built dynamically from a `Record<string, unknown>`, the upcoming digest path which the spec already mandates "Validated against the type's payloadSchema… at aggregation time") will pass through and either crash inside the template or render a corrupted email.
- **Fix**: Add a single line near the top of `send()`:
  ```ts
  const parsed = entry.payloadSchema.safeParse(options.data);
  if (!parsed.success) {
    log.error({ type, issues: parsed.error.issues }, "Invalid email payload — refusing to send");
    // Treat the same way as a render failure: persist a `failed` job with the error
    await prisma.emailJob.create({ data: { type, to: options.to, subject: type, ..., status: "failed", lastError: `payload: ${parsed.error.message}` } });
    return;
  }
  ```
  Cost is one Zod parse per email enqueue, negligible. Buys you defense in depth and lays the foundation the spec already declared for digest aggregation.

## Minor

### M-1: Hard-coded `locale: "en"` for `share_invitation`

- **File**: `apps/server/src/modules/share/service.ts:718`
- **Issue**: The notify path forces every recipient to English regardless of their UI locale. The comment justifies this ("external recipients have no profile"), which is fair, but the *sender's* locale is a strictly better default — the sender often communicates with recipients in a known shared language, and shipping the email in the sender's locale matches every other "I send X to Y" UX in the app.
- **Fix**: Either default to `user.locale ?? "en"` (the sender's locale, already fetched at line 690), or expose a `locale` field on `ShareRecipient` for explicit override. The former is one trivial change with no schema impact.

### M-2: `notify` route stores plaintext recipient emails in `audit` metadata

- **File**: `apps/server/src/modules/share/routes.ts:755-767`
- **Issue**: Already commented in the code ("Recipient emails are stored in the audit log for forensics. PII retention follows auditRetentionDays..."). This is a conscious choice but worth flagging in a security review pass. For GDPR-style data subject requests, you'd need to redact `metadata.emails` from audit rows on user deletion — the deletion handler probably doesn't do this today.
- **Fix**: Document the PII handling in the security section of the spec / docs. Optional: hash the emails before storing in metadata (lose forensics value), or accept the current trade-off explicitly.

### M-3: `share_accessed` cooldown key uses raw `shareId`, no per-visitor segregation

- **File**: `apps/server/src/modules/email/service.ts:106-125`
- **Issue**: The cooldown query is `WHERE type='share_accessed' AND to=creator.email AND relatedId=shareId AND createdAt > cutoff`. Within a 15-minute window the *first* visitor of any kind suppresses notifications for *all* subsequent visitors on the same share. For a creator who actually opted in to download notifications, the second visitor in a 14-min window is silently dropped. That matches the spec ("cooldown 15 min per (type, to, relatedId)") but means the notification is essentially "I had at least one visitor in the last 15 minutes," not "Visitor X accessed your share." Worth being explicit in the template body or in user docs.
- **Fix**: Either accept and document, or add an aggregation: when the cooldown is active, append the visitor info to a `digest_pending` payload that fires once the cooldown elapses. Out of 8.2 scope — note as follow-up.

### M-4: Unsubscribe page is English-only

- **File**: `apps/server/src/modules/notification/routes.ts:41-106`
- **Issue**: Already commented (`LIMITATION: Unsubscribe confirmation pages are English-only`). The fix is small once `notification/service.ts` learns to fetch the user's locale after token verification. Not a blocker for 8.2.
- **Fix**: After `verifyUnsubscribeToken(token)` returns `{ userId, type }`, fetch `prisma.user.findUnique({ where: { id: userId }, select: { locale: true } })` and pass the locale into `renderConfirmPage` / `renderSuccessPage`, which would then look up i18n strings via the existing `t()` loader for the matching keys (`common.unsubscribeTitle`, etc.).

### M-5: `parseVisitorCookie` treats `{name: "", email: ""}` as "absent" but a malformed `JSON.parse` is also "absent" with no log

- **File**: `apps/server/src/modules/share/routes.ts:39-62`
- **Issue**: A signed cookie whose unsigned value is not valid JSON is silently treated as missing (`catch { return undefined; }`). If the signing secret rotates or a downstream proxy mangles the cookie, the visitor is silently re-prompted and the operator has no signal. Low-impact, but a single `request.log.debug({ alias }, "Visitor cookie was unsigned-valid but JSON-malformed — re-prompting")` in the catch would be cheap and useful for diagnostics.
- **Fix**: Add a debug-level log in the catch, not error/warn — this is an expected case during secret rotation, not a bug.

### M-6: `formatShareResponse` ignores `notifyOnDownload` override even for the owner

The strip-for-non-owner block at service.ts:114-124 correctly hides `notifyOnDownload` from anonymous responses. The owner sees it. Good. But there's no test that asserts the owner *does* see `notifyOnDownload: true` (the symmetric test for the non-owner strip exists). Worth adding for completeness.

- **Fix**: Add an `it("owner sees notifyOnDownload")` to the visitor-tracking integration suite.

### M-7: `share_invitation` carries no `userId`/`relatedId`, so admin queue stats can't attribute it to a sender

- **File**: `apps/server/src/modules/share/service.ts:713-726`
- **Issue**: `share_invitation` is enqueued without `userId` or `relatedId`. The admin email stats and the queue dashboard show "X invitations sent" but cannot answer "by whom, for which share." `relatedId: share.id` would give the latter at zero cost (and would enable per-share invitation history queries in the admin UI later). `userId: share.creatorId` doesn't make semantic sense for an invitation *to* the recipient, but `relatedId: share.id` clearly does.
- **Fix**: Pass `relatedId: share.id` in the `emailService.send("share_invitation", …)` call. No schema change required.

### M-8: `share_downloaded` doesn't pass visitor identity even when a tracking token / cookie is present

- **File**: `apps/server/src/modules/file/routes.ts:144-205`
- **Issue**: The download endpoint receives `objectName + shareId` only — no `t=` query, no visitor cookie consultation. Therefore `share_downloaded` notifications are always "anonymous visitor" even when the download is part of an invited flow whose identity the server *could* know from the same tracking token used to access the share moments earlier. This is a reasonable scoping decision (the alternative is wiring the visitor cookie through every download endpoint), but the spec's example template (`share-downloaded.ts` with `bodyIdentified`/`bodyAnonymous` variants) suggests identified-download notifications were intended. Worth either implementing or explicitly deferring.
- **Fix**: Either (a) read `sv_{alias}` cookie when the download passes a `shareId` whose share has an alias, and pass `visitorName/visitorEmail` to the notification; or (b) document the deferral in the spec/notes near the template. The cookie path is only available because cookies scope to `path: "/api"` and downloads happen under `/api/files/...` — confirms the cookie *is* sent on download endpoints in production, so wiring is genuinely cheap.

## Positive Observations

- **Recipient upsert in `updateShare` (service.ts:384-409)** is a substantive improvement over the legacy delete+recreate: it correctly preserves `trackingToken`, `notifiedAt`, `lastAccessedAt`, `accessCount` for surviving recipients, with the explicit transaction and email normalization for matching. The migration test covers the key scenarios.
- **`formatShareResponse` strip-for-non-owner** (service.ts:104-125) is exactly what the security-conscious thing to do — recipients (including `trackingToken`), `creatorId`, and the new owner-only fields are nulled/emptied for anonymous responses, and the regression test in `visitor-identification.test.ts:462-495` is well-targeted.
- **Tracking-token cross-share check** (service.ts:256-263, also tested) closes what would otherwise be a trivial enumeration bypass — a token from share A cannot grant identification on share B.
- **Cookie re-validation against current share requirements** (service.ts:266-285, FIX 3 in the comments) is genuinely thoughtful: a cookie set when the form was OPTIONAL is correctly rejected after the owner promotes the field to REQUIRED. The two regression tests for `cookie name=null` and `cookie email=null` lock this in.
- **Atomic max-views increment** (`incrementViewsAtomic` in repository.ts) is the right design — no TOCTOU window between read and increment, and the count is conditionally bumped via `updateMany` with `views: { lt: maxViews }`.
- **Audit logging on every relevant share action** (create, update, delete, password update, items add/remove, recipients add/remove, notify, alias create, password-failed during access) is comprehensive and includes IP + UA — solid forensic surface.
- **CSRF exemption is per-route via `config.csrfExempt`** (e.g., the public access endpoints, the identify endpoint, the unsubscribe POST) — type-safe and co-located with the route definition; tracking this in code review is straightforward.
- **Notification scheduler** (`notification.scheduler.ts`) is clean: filters on `creator.isActive`, chains setTimeout to prevent overlap, runs an immediate boot-time pass for catch-up, and the test suite covers all five check functions.
- **Migration of the 4 legacy callers is correctly typed** through `EmailPayloads[T]`, and each migration site fetches `user.locale ?? "en"` (the exception being `share_invitation`, noted in M-1).
- **Recipient email normalization** (`.trim().toLowerCase()`) is consistently applied in DTO transforms, in `addRecipients`, in `removeRecipients`, and in `notifyRecipients`'s selectedEmails matching — no accidental case-sensitivity bugs.
- **Empty `selectedEmails` and no-match cases are validation errors** (service.ts:666-679) rather than silent successes, which is the right ergonomic choice.
- **`GET /shares/:shareId/visits` correctly strips `ipAddress` and `userAgent`** from the response (routes.ts:974) — these are stored for audit but never exposed to the share creator. The privacy test (visitor-tracking.test.ts:656-657) locks this in.
