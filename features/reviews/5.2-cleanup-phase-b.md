## Summary

Phase B implements the quota-overage policy in three slices: B1 event-driven
threshold warnings + exceeded transition, B2 opt-in (off-by-default) smart
deletion with a safe orphan-then-inactive order, and B3 reverse-share soft
enforcement (default on) with a relative factor + absolute cap. The
implementation closely follows the binding spec and the plan. Code quality is
high: no `any`/`@ts-ignore` in the new server code, server `type-check` passes,
the full server suite (1453 tests) and web suite (321 tests) are green, the 7
config keys are seeded + validated on both single and bulk paths with web-side
mirrors, and all 23 locales have `title`+`description` for the 7 fields plus the
`QUOTA_FILES_DELETED` audit label.

The destructive B2 path was scrutinized hardest. The never-delete-active-share
invariant **is** expressed in the Prisma predicates themselves (not only in the
picker), the sweep is correctly gated behind `quotaSmartDeletionEnabled` (default
false), it deletes nothing and counts `blocked` when no safe candidate exists,
DB-before-S3 ordering is failure-tolerant, and `quotaExceededSince` is cleared
through the centralized path. The unit + service tests cover the all-active⇒
blocked path, grace boundary, candidate ordering, and S3-failure tolerance.

**Verdict**: Approve with follow-ups. No Critical findings. One Important
(missing DB-level tests for the safety-critical repository predicates) and a few
Minor items. The Important finding is a test-coverage gap on the most dangerous
code path, not a logic defect — the predicate logic itself reads correct.

## Confirmed-clean dimensions

- **Never-delete-active-share invariant (B2 — critical).** The invariant lives
  in the Prisma `where` clauses in `apps/server/src/modules/quota/repository.ts`,
  not merely in the picker. A share is "recent/active" iff:
  ```
  recentShare = { OR: [
    { lastDownloadedAt: { gte: inactiveBefore } },
    { lastDownloadedAt: null, updatedAt: { gte: inactiveBefore } },
  ] }
  ```
  `findInactiveShareFiles` requires a file to be referenced (`OR: [{ shares: { some: {} } }, { folder: { shares: { some: {} } } }]`),
  to have **no** recent direct share (`shares: { none: recentShare }`), AND **no**
  recent folder share (`AND: [{ OR: [{ folderId: null }, { folder: { shares: { none: recentShare } } }] }]`).
  I traced the adversarial cases: a file in a folder-share that is still active is
  excluded via the folder branch; a file in two shares where one is active is
  excluded by the direct-`none` clause; the `folderId: null` arm correctly avoids
  a relational `none` wrongly excluding folder-less files. `findOrphanFiles`
  (`shares: { none: {} }` + folder has no shares) and `findInactiveShareFiles`
  (≥1 share reference) are mutually exclusive, so no file is double-counted.
- **B2 gating.** `quotaSmartDeletionEnabled` is seeded `false`
  (`prisma/seed.js:305`) and the sweep only runs inside the
  `if (await getBoolConfig("quotaSmartDeletionEnabled"))` block in
  `cleanup.scheduler.ts:194`, using `quotaGracePeriodDays`/`quotaInactiveShareDays`.
- **B2 sweep safety.** `enforceQuotaOverage` (`cleanup/service.ts:980`) selects
  only users with `quotaExceededSince < now - grace`; clears a stale clock for
  unlimited/under-limit users via the centralized `evaluateAndNotifyQuota`;
  `blocked++` with no deletion and no destructive audit when candidates are empty;
  deletes DB-before-S3 (`deleteUserFileWithStorage:925`), counting S3 failures
  without aborting; emits `QUOTA_FILES_DELETED` + `files_auto_deleted` only after
  real deletions; emptied shares are left as-is (§7).
- **B1 boundary math.** `highestCrossedThreshold` uses bigint boundaries, is
  upward-only (`boundary > oldUsed && newUsed >= boundary`), treats `>=100` as the
  limit, returns null for unlimited; `quota_exceeded` fires on the 100% transition
  independent of configured thresholds (`evaluateAndNotifyQuota:402-418`,
  test `service.test.ts:863`); dedup via `quotaLastWarnedThreshold`, re-arm on drop
  below the lowest boundary; `quotaExceededSince` set-once / clear-when-under;
  fully wrapped in try/catch (fire-and-forget, never throws into the upload path).
- **B3 enforcement.** `isReverseUploadAllowed` (unlimited⇒true; `used+size` within
  `limit*factor` and the absolute cap) is applied to external reverse uploads
  by-id AND by-alias when soft enforcement is on, hard block when off
  (`upload.service.ts:403-440`). The owner's own direct uploads keep the hard
  block (`file/routes.ts:451`, unchanged), confirmed by the parameterized
  integration test (`direct-quota.integration.test.ts:181`, soft=true/false).
  `assertOwnerActive` (A6) is still called on every reverse path. Multipart only
  presigns/completes S3; the DB `ReverseShareFile` is created via
  `registerFileUpload*`, which carries B3 — so multipart does not bypass it.
- **Config/validation.** All 7 keys seeded in the `storage` group with the spec
  defaults; `validateConfigValue` is invoked on both `updateConfig` and
  `bulkUpdateConfigs` (`app/service.ts:62,92`). Validators: CSV thresholds 1–99
  non-empty, `intMin` ints, factor `intMin(...,1)`, `bigintMin(...,0n)` parsed via
  native `BigInt` (exact). Web mirrors all of these, including a BigInt-safe
  `isValidNonNegativeBigint`.
- **Hygiene/i18n.** No stale "pending-trigger" notes in the email catalog; no
  dead exports (every helper is wired); 23-locale parity verified for the 7
  settings fields + `audit.actions.QUOTA_FILES_DELETED`.

### Important

- [x] **[Important] No DB-level tests for the safety-critical repository predicates** — `apps/server/src/modules/quota/repository.ts:41` (`findOrphanFiles`) and `:70` (`findInactiveShareFiles`) — The never-delete-active-share invariant is enforced entirely by these two Prisma `where` clauses, yet they are never exercised against a real database. The only tests that touch them (`quota/__tests__/service.test.ts:659-660`) **mock** the repo via `vi.spyOn(QuotaRepository.prototype, ...)`, so `pickDeletionCandidates` is validated against a stubbed return value, not against the actual query. CLAUDE.md Rules 10/11 call out exactly this: service-layer/mocked tests do not catch query-shape regressions, and this is the most destructive path in the feature. A subtle future edit to the folder-share `OR`/`AND` arms (e.g. dropping the `folderId: null` guard, or flipping a `none`/`some`) would silently start returning active-share files for deletion with no failing test. **Fix**: add integration tests that seed a real DB with (a) a pure orphan, (b) a file in an active direct share, (c) a file in an inactive direct share, (d) a file in an active *folder* share, (e) a file in an inactive folder share, and (f) a file in two shares where one is active, then assert `findOrphanFiles`/`findInactiveShareFiles` (or `pickDeletionCandidates` without mocking the repo) return exactly the safe set. This converts the invariant from "reads correct" to "proven".
  - **Resolved**: added `apps/server/src/modules/quota/__tests__/repository.integration.test.ts` — a real-DB suite (schema bootstrapped via `prisma db push --accept-data-loss` in `beforeAll`, mirroring `__tests__/prisma-v7.integration.test.ts`; prisma NOT mocked). Seeds all six scenarios (a)–(f) and asserts `findOrphanFiles` → only (a); `findInactiveShareFiles` → exactly (c)+(e) oldest-first and NEVER (b)/(d)/(f); `pickDeletionCandidates` (repo unmocked) → `[a, c, e]` with the active-share files excluded end-to-end. 9 tests, all green.

### Minor

- [x] **[Minor] Warning dedup / exceeded transition are only unit-tested, not integration-tested** — `file/__tests__/direct-quota.integration.test.ts:68` and `reverse-share/__tests__/quota-enforcement.integration.test.ts:100` — Both `app.inject()` suites **mock** `evaluateAndNotifyQuota`, so they assert the hook is invoked with the correct `{ oldUsed, newUsed }` transition (good wiring proof) but never drive the real warning/exceeded notification through the request lifecycle. The plan (Batch 2) explicitly asked for integration coverage of "warning crossing + dedup (no re-spam), exceeded set/clear." The dedup/exceeded logic itself is thoroughly unit-tested (`quota/__tests__/service.test.ts:736-929`, including dedup, re-arm, exceeded-independent-of-thresholds, admin-alert-once, deactivated-owner, no-throw), so the end-to-end risk is low. **Fix** (optional but matches the bar): one `app.inject()` test that registers two uploads crossing 80% then staying in-band and asserts a single `quota_warning` enqueue, plus one crossing 100% asserting `quota_exceeded` + `quotaExceededSince` set.
  - **Resolved**: added `apps/server/src/modules/file/__tests__/direct-quota-warning.integration.test.ts` — `app.inject()` direct-upload suite driving the REAL `evaluateAndNotifyQuota` (quota service NOT mocked); only the transport/queue boundary (`emailService.send`/`sendToAdmins`) and the prisma state store are mocked. Test 1: two uploads cross 80% then stay in-band → exactly one `quota_warning` enqueued (dedup proven, asserting on `emailService.send` calls, not on the hook). Test 2: one upload crosses 100% → `quota_exceeded` enqueued + `admin_quota_alert` + persisted `quotaExceededSince`. 2 tests, green.

- [x] **[Minor] `reverseShareAbsoluteMaxBytes` reuses the Number-based FileSizeInput widget (>~9PB precision loss)** — `apps/web/src/app/settings/components/settings-input.tsx:93` → `file-size-input.tsx:30,58,63` — The field is rendered with `FileSizeInput`, which round-trips through `parseInt`/`parseFloat`/`Math.floor` (Number), so a cap above `Number.MAX_SAFE_INTEGER` (~9PB) would be displayed/saved imprecisely even though the schema validation (`isValidNonNegativeBigint`) is BigInt-exact. This is a **pre-existing** limitation already shared by `maxFileSize` and `maxTotalStoragePerUser` (same widget), and the realistic cap range (e.g. 75 GB, and the `0` = no-cap default) is unaffected. Flagged for completeness per the Batch-4 note; judged a real-but-negligible nit, not a Phase-B regression. **Fix** (if ever needed): make `FileSizeInput` operate on BigInt internally, fixing all three bigint byte fields at once.
  - **Resolved (clean fix taken)**: reworked `FileSizeInput` to operate on BigInt internally — byte↔human conversion now uses `BigInt` multipliers and constructor-form math (ES2017 target precludes `n` literals). Whole-number sizes prefer the largest exactly-dividing unit and round-trip exactly at any magnitude; fractional sizes use scaled-integer math. Fixes all three bigint byte fields at once (`maxFileSize`, `maxTotalStoragePerUser`, `reverseShareAbsoluteMaxBytes`). The duplicated reverse-share widget copy was kept in sync. Added `file-size-input.test.ts` (9 tests) covering >2^53 exact round-trips and preserved small-value behavior.

- [x] **[Minor] Spec says `reverseShareMaxOverageFactor` is a "number ≥ 1"; implementation constrains it to an integer** — `config-validation.ts:205` (`intMin(..., 1)`) — The factor is validated as an integer, and `isReverseUploadAllowed` computes `limit * BigInt(factor)` (`quota/service.ts:254`), which would throw on a fractional factor. The integer constraint is actually the *safer* choice (it makes `BigInt(factor)` total) and the default `3` satisfies it, so this is a deliberate, defensible deviation rather than a defect — noted only so the spec wording and code agree. **Fix** (optional): update the spec table to say "integer ≥ 1", or, if fractional factors are ever desired, switch the helper to scaled-integer math (e.g. `limit * BigInt(round(factor*100)) / 100n`).
  - **Resolved**: kept the integer constraint (the safer choice) and aligned the docs — `features/specs/5.2-cleanup.md` Phase B config table + B3 prose now say "integer" (with a note that the helper computes `limit × BigInt(factor)`, requiring an integer), and `features/plans/5.2-cleanup-phase-b.md` says "integer ≥ 1".
