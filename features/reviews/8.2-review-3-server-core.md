## Summary

The implementation is broadly faithful to the spec and well-structured: the 5-layer architecture is in
place, the catalog acts as a single source of truth, the queue scheduler is non-trivial but solid, the
templates are pure functions with a tidy base layout, the i18n loader has proper fallback and async/sync
modes, the JWT unsubscribe path is hand-rolled but uses a derived HMAC sub-key and `timingSafeEqual`,
and the SMTP transport correctly factors out the duplicated config logic from the legacy service.
Test coverage is broad — service, queue, transport, templates, i18n, catalog and scheduler are all
exercised — and includes good XSS regression coverage via the real en.json render path.

That said, several real defects affect production behavior. The most important is a **spec deviation**
that breaks the inactivity-alert lifecycle (`inactivityAlertSent` is never reset on real download
activity, so each share gets exactly one inactivity alert *forever*). There's a **boot-time crash
vector**: `initEmailQueueOnBoot()` awaits `validateAllI18nKeys()` outside any try/catch and is invoked
as `void initEmailQueueOnBoot()` in `server.ts`, so a missing key in `en.json` turns into an
unhandled promise rejection and silently disables the queue. Several smaller correctness issues
(per-share cooldown collapsing to a "global" cooldown when no `shareId` is supplied, `share_invitation`
losing the expiry info if the share also has a password, weakening of HTML escaping on CTA URLs to
text-only — no scheme validation, the share-update reset path not handling null↔value transitions)
deserve attention.

Overall: this is solid, ship-shape work with one important spec-compliance miss and a small handful
of defensive-engineering gaps. Nothing here is a "Critical" production-incident risk on its own, but
C-1 below (inactivity-alert lifecycle) is a clear spec-vs-behavior bug.

## Findings

### Critical

#### ~~C-1~~ [x]: `inactivityAlertSent` is never reset → inactivity alerts fire only once, ever (spec deviation)
- **File**: `apps/server/src/modules/file/routes.ts:184-190`, `apps/server/src/modules/email/notification.scheduler.ts:122-185`
- **Description**: The spec (Section 5, lines 589–590) explicitly says: *"If a non-owner download occurs later, `inactivityAlertSent` is reset to `false` and `lastDownloadedAt` updated (allowing a future alert cycle)"*. The implementation only updates `lastDownloadedAt`:
  ```typescript
  // file/routes.ts line 185-190
  prisma.share
    .update({
      where: { id: shareId },
      data: { lastDownloadedAt: new Date() },  // ← missing: inactivityAlertSent: false
    })
  ```
  Worse, the doc comment in `notification.scheduler.ts:126-128` retcons this as intentional:
  > *"One-shot alert: once inactivityAlertSent=true, no second alert fires for this share even if activity resumes then stops again. This is by design — a single nudge per share lifecycle."*
  This contradicts the spec. With the current code, every share gets exactly one inactivity alert per lifetime, which makes the per-share `inactivityAlertDays` configuration useless for any share that has ever gone inactive once.
- **Impact**: Permanent behavioral divergence from the spec. Once an inactivity alert fires, the share owner can never receive another one even if activity resumes and goes quiet for months. This is a silent failure — neither the user nor an admin will notice that "the second alert never came."
- **Suggested fix**: In `trackShareDownload()` (and the non-owner branch of `POST /shares/alias/:alias/access` if reverse-share semantics need it), update the share with `{ lastDownloadedAt: new Date(), inactivityAlertSent: false }` whenever the requester is not the owner. Remove the misleading comment in `notification.scheduler.ts:126-128`. Add a regression test that drives the cycle: alert fires → reset on download → alert re-fires on subsequent inactivity.

#### ~~C-2~~ [x]: `initEmailQueueOnBoot()` boot-time validation can become an unhandled promise rejection
- **File**: `apps/server/src/modules/email/queue.ts:433-444`, `apps/server/src/server.ts:118` (`void initEmailQueueOnBoot()`)
- **Description**: `initEmailQueueOnBoot()` calls `await validateAllI18nKeys()` *outside* the surrounding `try/catch`:
  ```typescript
  export async function initEmailQueueOnBoot(): Promise<void> {
    await validateAllI18nKeys();         // ← can throw; NOT wrapped
    try {
      await recoverStuckJobs();
    } catch (error) { ... }
    startEmailQueueScheduler();
  }
  ```
  And it is invoked as a fire-and-forget in `server.ts:118`:
  ```typescript
  // Initialize email queue scheduler (fire-and-forget - has internal try/catch)
  void initEmailQueueOnBoot();
  ```
  The comment in `server.ts` is wrong. If `en.json` is missing a key referenced by the catalog (e.g. after a typo in a new template's `requiredI18nKeys`), the validator throws, the promise rejects unhandled, the queue scheduler never starts, AND the rest of the server keeps running — producing the worst-of-both-worlds: SMTP is "enabled" but `EmailJob` rows pile up forever and nothing sends them.
- **Impact**: A silent regression where the email subsystem stops working completely with no visible error to the operator. Unhandled rejections in Node 24 also default to crashing the process under some flag configurations (and Fastify's logger doesn't catch them either).
- **Suggested fix**: Wrap `validateAllI18nKeys()` in its own try/catch with an explicit `getLogger().fatal({ err }, "i18n validation failed — email subsystem disabled")` and either (a) re-throw to crash boot deterministically (preferred — fail fast), or (b) skip starting the scheduler and surface the error in `/admin/email/stats`. Option (a) is consistent with the spec's "Fail fast — this catches typos and forgotten translations during development" (Section 3, line 424).

### Important

#### ~~I-1~~ [x]: Cooldown collapses to global per-(type, to) when `shareId` is absent → `reverse_share_uploaded` floods become possible
- **File**: `apps/server/src/modules/email/service.ts:98-112`
- **Description**: The cooldown check uses `relatedId: options.shareId ?? null`. For `reverse_share_uploaded` (which has `cooldownSeconds: 300` per `catalog.ts:431`), no `shareId` is passed by the caller (reverse shares don't go through a `Share`), so the query becomes `findFirst({ where: { type, to, relatedId: null, createdAt: { gt: cutoff } } })`. That means the cooldown is enforced *per recipient*, not per reverse-share — so if user X owns two reverse shares and both receive a batch of uploads within 5 minutes, the second notification is silently swallowed.
  Conversely, for `share_accessed`/`share_downloaded` the `shareId` *is* expected and the cooldown correctly scopes per-share. The implementation never asserts this — a caller that forgets the `shareId` silently degrades to a global cooldown.
- **Impact**: Lost notifications for reverse-share users with multiple active reverse shares; subtle correctness bug that only shows up under specific timing.
- **Suggested fix**: Either (a) pass a `relatedId` for reverse-share uploads (e.g., `reverseShareId`) and rename the service's `shareId` option to a more generic `relatedId`, or (b) at minimum log a warning when the cooldown engages with `relatedId: null` for types that aren't naturally global (most of them). Option (a) is the principled fix and only costs a parameter rename. The schema is already free-form (`EmailJob.relatedId: String?`), so this is a code-level change.

#### ~~I-2~~ [x]: `share_invitation` info box swallows expiry info when password is set
- **File**: `apps/server/src/modules/email/templates/share-invitation.ts:20-24`
- **Description**:
  ```typescript
  infoBox: data.hasPassword
    ? t("shareInvitation.infoPassword")
    : data.expiresAt
      ? t("shareInvitation.infoExpires", { expiresAt: data.expiresAt })
      : t("shareInvitation.info"),
  ```
  Three mutually exclusive states. A share that has both a password **and** an expiry shows only the password info — the recipient loses the "this link expires on X" message. That's a real loss of information: it's the user's first contact with this share, the spec puts both as legitimate states, and the `shareInvitation.info` / `infoPassword` / `infoExpires` keys exist precisely to communicate this.
- **Impact**: Recipients don't see expiry warnings when the share also has a password — they may try to use the link after expiration.
- **Suggested fix**: Concatenate (or render both as separate info blocks). Simplest: build a list of relevant info strings and join them with `<br><br>` (or pass an `infoBox` array — would require a tiny `LayoutSlots` shape change). Adding a new `infoBox?: string | string[]` field to `LayoutSlots` keeps backward compat. Alternatively, add a combined i18n key `shareInvitation.infoPasswordExpires` for the both-set case.

#### ~~I-3~~ [x]: Per-share expiration-flag reset doesn't handle null↔value transitions
- **File**: `apps/server/src/modules/share/service.ts:419-425`
- **Description**:
  ```typescript
  if (shareData.expiration && share.expiration) {
    const newExp = new Date(shareData.expiration);
    if (newExp > share.expiration) {
      updateData.notifiedForExpiring = false;
      updateData.notifiedForExpired = false;
    }
  }
  ```
  Only resets when both old and new expirations are non-null. Concrete edge cases that bite users:
  1. Share previously had an expiration that already fired (`notifiedForExpired=true`). User clears the expiration (`shareData.expiration = null`), then later sets a new future expiration. The `notifiedForExpired` flag is still `true` → the new expiration will never produce an `expired` notification.
  2. Similar with `notifiedForExpiring` if user clears, then re-adds a soon-to-expire share.
- **Impact**: Silent loss of legitimate expiration notifications after an "edit cycle" that touches the expiration field.
- **Suggested fix**:
  ```typescript
  const newExp = shareData.expiration ? new Date(shareData.expiration) : null;
  const oldExp = share.expiration;
  // Reset when expiration is added or extended (anything that creates a new "future window")
  if (newExp && (!oldExp || newExp > oldExp)) {
    updateData.notifiedForExpiring = false;
    updateData.notifiedForExpired = false;
  }
  ```

#### ~~I-4~~ [x]: CTA URL escaping does not validate scheme — `javascript:` etc. pass through
- **File**: `apps/server/src/modules/email/templates/base-layout.ts:158-165`, `apps/server/src/utils/escape-html.ts`
- **Description**: `renderCtaHtml` does `const safeUrl = escapeHtml(cta.url); ... <a href="${safeUrl}">`. `escapeHtml` only replaces `& < > " '`. It does not validate the URL scheme. While in practice the CTA URLs come from server-controlled builders (`buildShareLink`, `buildResetPasswordUrl`), this is defense-in-depth on a security-relevant surface, and the contract for "data flows into an email template" should not assume callers vet the URL. Most modern email clients ignore `javascript:` in `href`, but a few render it as a clickable link in their HTML preview pane, and downstream forwarding/copy-paste loses the email-client protection.
- **Impact**: A future caller (e.g., a callsite that builds the share-link from a partially-user-controlled subdomain) could introduce a phishing/XSS vector without any code-level guardrail.
- **Suggested fix**: In `renderCtaHtml` (and `renderUnsubscribeHtml`), validate the scheme: reject anything that doesn't start with `https://`, `http://`, or `mailto:`. Easiest:
  ```typescript
  function safeHref(url: string): string {
    try {
      const u = new URL(url);
      if (!["http:", "https:", "mailto:"].includes(u.protocol)) return "#";
      return escapeHtml(url);
    } catch {
      return "#";
    }
  }
  ```
  Apply to `cta.url` and `unsubscribeUrl`.

#### ~~I-5~~ [x]: Cached `appUrl` never invalidates → admin SMTP config change requires server restart
- **File**: `apps/server/src/modules/email/url-builder.ts:8-28`
- **Description**: `cachedAppUrl` is set on first read and never cleared except via `invalidateAppUrlCache()`. The function is exported, but there is no caller wired into the AppConfig update path (see `apps/server/src/modules/config/service.ts` — `getConfigValue` doesn't notify subscribers). After an admin updates the `appUrl` in the admin UI, all queued and future emails still use the stale value until the server restarts. The same applies to the SMTP transport's hash cache, *except* there the hash is recomputed on every `getTransporter()` call, so it self-heals. `appUrl` does not self-heal.
- **Impact**: Operational footgun. An admin updates `appUrl`, sends a test email, and the test email contains the *old* URL. Failure mode is confusing because everything else (subjects, content) seems updated.
- **Suggested fix**: Either (a) re-read on every call (`getAppUrl` is already async and `getConfigValue` is fast — a per-call DB read is negligible at queue throughput), or (b) wire `invalidateAppUrlCache()` into the config update path. Option (a) is simpler and consistent with the queue's behavior of re-reading `emailQueueIntervalSeconds` on every tick.

#### ~~I-6~~ [x]: i18n loader's missing-locale set never repopulates a locale once a file appears
- **File**: `apps/server/src/modules/email/i18n/loader.ts:25-26, 236-238`
- **Description**: `missingLocales.add(locale)` is set when a locale file is absent at the first read attempt. There's no expiry. If an operator adds a translation file to the running server (e.g., `de.json`) the loader will never pick it up until restart. This is unlikely to matter much because translations are baked at build time, but the comment / behavior contract should be clear, and the test `clearLocaleCache()` correctly clears both — so this is mostly a documentation/operational gap.
- **Impact**: Minor — installer/operator surprise. Adding a translation requires a restart even though everything else is hot-reloadable.
- **Suggested fix**: Either document this clearly in `loader.ts` or add a "TTL on negative lookups" (e.g., re-check after 60s). Since the messages dir is shipped with the build, the documentation route is fine.

#### ~~I-7~~ [x]: `email-service.test.ts` mocks `createTranslationFn` away → service tests never exercise the real `tr` contract
- **File**: `apps/server/src/modules/email/__tests__/email-service.test.ts:67-69, 122-123`
- **Description**: The mocked `createTranslationFn` returns a fn that always returns the literal string `"translated"`. As a result, `EmailService.send()` is never tested with a translation function that interpolates `appName` or any payload fields. The only thing the test verifies is "service called renderLayout and emailJob.create with something." Subject building, unsubscribe URL composition, and slot construction all go through the real codepath in production but are not exercised here. The catalog test (`catalog.test.ts:320-432`) does run the templates against the real `en.json`, which catches missing-key bugs — that test is good — but the service-level test is shallow.
  Also note: line 124-128, when the **subject** path goes through `t(locale, ...)` (NOT the curried `tr`), `mockT` is set to reject for ALL keys, which exercises only the fallback path. The "happy path" of "subject was correctly built from i18n + payload data" is never tested.
- **Impact**: Real bugs in the subject build (e.g., a payload field being non-stringifiable, an XSS payload reaching the subject) would not be caught at the service layer.
- **Suggested fix**: Add at least one test that wires the real `t()` and `createTranslationFn` against a fixture en.json, asserts the subject contains the appName/payload substring (verbatim), and verifies the unsubscribe URL is appended to `slots.unsubscribeUrl`. Or convert most of the existing tests to use an integration setup (`app.inject()`) so that the real chain is exercised end-to-end.

#### ~~I-8~~ [x]: `share_invitation` template silently drops expiry when `expiresAt` is an arbitrary string
- **File**: `apps/server/src/modules/email/templates/share-invitation.ts:20-24`, `catalog.ts:90-96`
- **Description**: The Zod schema declares `expiresAt: z.string().optional()` — no date validation. The template feeds this string straight into `t("shareInvitation.infoExpires", { expiresAt: data.expiresAt })`. The current callers happen to pass ISO strings, but the contract is loose — a caller passing a `Date` object (which `String(date)` would turn into `"Wed May 29 2026..."`) or a malformed string is silently accepted, with no validation error, no logging. Same pattern in many other templates (`share_expired.expiredAt`, `share_expiring.expiresAt`, …).
- **Impact**: Malformed expiry strings leak into emails as user-facing dates. Hard to debug.
- **Suggested fix**: Use `z.string().datetime()` (or `z.string().refine(s => !Number.isNaN(Date.parse(s)), ...)`) on date fields. Catches bad callers at the type/service boundary, costs nothing at runtime since Zod already validates the schema.

#### ~~I-9~~ [x]: `notification.scheduler` calls `prisma.share.findMany` then iterates with N+1 `prisma.share.update`s and N `buildShareManageUrl` calls
- **File**: `apps/server/src/modules/email/notification.scheduler.ts:30-71, 134-185`
- **Description**: For each share, a sequential `await buildShareManageUrl(share.id)` is called (which reads `cachedAppUrl` — fast after first call, fine) and then `await prisma.share.update`. Sequentially this is O(N) DB calls in the daily run. For the current scale this is acceptable, but on a hypothetical 10k-share installation with most shares about to expire in some batch, this is a serial 10k-update loop in the daily tick that holds the event loop until done.
- **Impact**: Scalability cliff. Acceptable today, predictable problem later.
- **Suggested fix**: Use `prisma.share.updateMany({ where: { id: { in: ids } }, data: { notifiedForExpiring: true } })` after a successful batch, or chunk processing to N=100 and yield between chunks. Not required for shipping; flag as TODO with a sensible threshold.

#### M-2: `EmailJob.payload`/digest path is dead code with no test coverage
- **File**: `apps/server/prisma/schema.prisma:194`, `apps/server/src/modules/email/service.ts:194-198`
- **Description**: The `digest_pending` status branch in `send()` runs (line 196-198) but no caller exercises it (digest UI is intentionally deferred per spec, `frequency` enum only exposes `immediate`/`disabled`). However, the test `email-service.test.ts:488-509` *does* set up a `daily_digest` preference and verifies `status === "digest_pending"`. So the branch is tested. OK — withdrawn as a coverage concern. Keeping the note as: there's no test that the `payload` field is *populated* on digest_pending jobs (spec Section 2 line 215-219 says it should be). - **Impact**: When digest is eventually implemented, the digest aggregator will find `digest_pending` rows with no raw payload to render — they'd have to fall back to the pre-rendered htmlBody/textBody, which defeats the whole point of digest aggregation. - **Suggested fix**: When `status === "digest_pending"`, also store `payload: JSON.stringify({ v: 1, type, data: options.data })` and **do not** pre-render `htmlBody`/`textBody`. Spec line 230 is explicit: *"Digest jobs: Raw data is stored as JSON (`payload` filled, `htmlBody`/`textBody` null)."* Promoting to Important if the digest spec is considered binding for 8.2.

#### M-3: `queue.ts` exponential-backoff clamp is silent
- **File**: `apps/server/src/modules/email/queue.ts:256-258`
- **Description**: `BACKOFF_SECONDS[newAttempts - 1] ?? BACKOFF_SECONDS[BACKOFF_SECONDS.length - 1]`. If an admin raises `emailQueueMaxRetries` to 10, attempts 4–10 all retry with the same 30-minute backoff. Spec doesn't explicitly cover this, but the silent clamp is unexpected.
- **Suggested fix**: Either compute a doubling schedule (`min(3600, 60 * 2^(n-1))`) or log a one-time warning at boot if `maxRetries > BACKOFF_SECONDS.length`.

## Positive Observations

- **`catalog.ts` is a clean, principled single source of truth.** The `as const satisfies Record<string, NotificationTypeConfig>` pattern is exactly right and the `EmailPayloads` type derivation gives compile-time safety with no manual maintenance. The `asRender` adapter (`catalog.ts:61-66`) is a tiny, well-commented bridge that explains its single `any` usage.

- **`unsubscribe-token.ts` is well-defended.** It validates the `alg` header to block algorithm-confusion attacks (`unsubscribe-token.ts:82-84`), uses `timingSafeEqual` with length check (`unsubscribe-token.ts:97-103`), and derives a purpose-isolated HMAC sub-key from `JWT_SECRET` (`unsubscribe-token.ts:21-23`). All catch-and-throw paths use a generic "Invalid unsubscribe token" message that doesn't leak internal state.

- **The queue's wake-event handling correctly preserves single-thread semantics.** The `isProcessing`/`wakePending` interaction in `queue.ts:166-294, 361-391` is subtle but sound. The "handle === currentTimeout" guard prevents superseded timers from chaining additional ticks. The deferred-wake re-tick in the `finally` block (`queue.ts:275-293`) is the right way to avoid losing a wake during a batch.

- **`transport.ts` config-hash detection** (`transport.ts:62-75, 249-264`) is a clean fix for the legacy duplication and explicitly excludes display-only fields (`smtpFromName`, `smtpFromEmail`) from the hash so cosmetic config changes don't churn the SMTP pool.

- **i18n test coverage via real `en.json`** in `catalog.test.ts:320-432` is excellent — it validates every catalog entry against its actual i18n keys with sample payloads, and asserts that no raw `{x.y}` keys leak into rendered output. This catches the entire class of "forgot to add an i18n key" bugs in one test.
