# 8.1 Audit Trail — Spec Compliance Review

Scope of this review: verify the 8.1 implementation against `features/specs/8.1-auditing.md`. Code was read directly for every claim. Findings are rated Critical / Important / Minor.

Overall: the core infrastructure (schema, service, retention scheduler, routes, integration tests, admin page skeleton, all 23 i18n files) is in place and matches the spec's structural requirements. The defects below are mostly on event payload details (`metadata`, `targetId`), missing UI polish items, and one Critical data-leak in invite-token logging.

---

## Critical

- [x] **C-1: Invite token value (not its DB id) is stored as `targetId` in audit logs** — `apps/server/src/modules/invite/routes.ts:45,108`
  Both `INVITE_TOKEN_CREATE` and `INVITE_TOKEN_USED` pass `targetId: token` where `token` is the raw secret invite token string. The spec example explicitly uses `targetId: token.id`. The `InviteToken` model has `id` (cuid) and `token` (secret) as separate fields. This persists the active invite token in plaintext to the audit log table. Even though `/admin/audit-logs` is admin-only, this:
  1. Lengthens the period during which the token is recoverable (it survives past use because `INVITE_TOKEN_USED` also stores it).
  2. Couples the audit log with secret material — any future feature that surfaces audit logs (export, debug dumps, replication, backups, downstream 8.2 notifications) leaks tokens.
  3. Violates spec decision 3 ("No sensitive data in metadata") in spirit — tokens are also on the denylist for `metadata`, but here the secret is in `targetId`, bypassing the denylist.
  Fix: change both calls to use `targetId: inviteToken.id`. That requires `inviteService.generateInviteToken` to return the row id (it currently returns `{ token, expiresAt }`), and `registerWithInvite` to surface the matched `InviteToken.id` to the route.

## Important

- [x] **I-1: Concurrency test for `maxViews` enforcement is missing** — `apps/server/src/__tests__/share-audit.integration.test.ts`
  Spec §Testing / Concurrency test (line 458) requires: "10 parallel requests with `maxViews=5` must result in exactly 5 successes (atomic counter, not event counting). This validates that the enforcement mechanism is race-safe." No such test exists in the share-audit integration file or anywhere else (`grep maxViews apps/server/src/__tests__` only finds the test fixture). This is the test that justifies spec decision 5 ("Atomic counter for enforcement").
  Note: looking at `share/service.ts:177-179`, the share-page enforcement is in fact **not atomic** — the check `if (share.maxViews && share.views >= share.maxViews)` is followed by a non-atomic `incrementViews(shareId)` in `repository.ts`. Only the embed route (`file/routes.ts:1058-1066`) uses the atomic `updateMany` guard. So the concurrency test would currently **fail** for the share page path — and writing it would expose that gap, which is precisely the point of the requirement.

- [x] **I-2: Audit page omits user resolution and target navigation that the spec explicitly requires** — `apps/web/src/app/admin/audit/components/audit-log-table.tsx:128-156`
  Spec §Frontend / AuditLogTable (line 396) requires:
  - "User (avatar + name, or 'System' / 'Anonymous')" — implementation shows only a truncated `log.userId.slice(0, 8)…`, no avatar, no user name lookup.
  - "Action (badge, color-coded by category)" — implementation uses a single `<Badge variant="secondary">` for every action. No category-based coloring (the `audit.actionCategories` i18n keys exist but are unused).
  - "Target (type icon + link to entity if applicable)" — implementation shows the type label and a truncated `targetId.slice(0, 8)…` with no icon and no link.
  These are visible UX gaps for the primary view of the feature.

- [x] **I-3: Audit page is not responsive — IP and Details are not hidden on mobile** — `apps/web/src/app/admin/audit/components/audit-log-table.tsx:96-173`
  Spec line 397: "Responsive: hides IP and Details columns on mobile". No `hidden md:table-cell` (or equivalent) classes are applied to any column. All six columns render on mobile, which will overflow on narrow viewports.

- [x] **I-4: `REVERSE_SHARE_FILE_DOWNLOAD` writes the file id into `targetId` while keeping `targetType: "reverse_share"`** — `apps/server/src/modules/reverse-share/routes.ts:707-715`
  `targetType: "reverse_share"` paired with `targetId: request.params.fileId`. The corresponding `targetType` should be `"file"` (or the parent reverse-share's id should be used as `targetId`, matching the sibling `REVERSE_SHARE_FILE_DELETE` at line 754 which correctly uses `file.reverseShareId`). As written, target lookups by `targetType+targetId` will return mismatched rows — a feature that the new composite index `(targetType, targetId, action, createdAt)` is designed to support.

- [x] **I-5: `AUTH_PROVIDER_LOGIN` uses provider **name** instead of provider **id** for `targetId` and omits `providerType` metadata** — `apps/server/src/modules/auth-providers/routes.ts:595-603`
  The spec (line 144) requires `metadata: { providerType, providerName }` and the example pairs `targetId: provider.id`. Implementation:
  - `targetId: providerName` (e.g., `"google"`) — not a cuid, breaks consistency with `AUTH_PROVIDER_CREATE/UPDATE/DELETE` which use `provider.id`.
  - `metadata: { providerName }` — `providerType` is missing.
  Cross-event analytics keyed on `targetId` (e.g., "all events touching auth_provider X") will lose `AUTH_PROVIDER_LOGIN` rows.

- [x] **I-6: `SHARE_RECIPIENT_ADD/REMOVE/NOTIFY` lose the recipient identities — spec required `emails: [...]`** — `apps/server/src/modules/share/routes.ts:447,494,646`
  Spec lines 178-179 specify:
  - `SHARE_RECIPIENT_ADD` metadata `{ emails: [...] }` — impl emits `{ count }`.
  - `SHARE_RECIPIENT_REMOVE` metadata `{ emails: [...] }` — impl emits `{ count }`.
  - `SHARE_RECIPIENT_NOTIFY` metadata `{ recipientCount, emails: [...] }` — impl emits only `{ recipientCount }`.
  Recipient emails are an essential forensic detail for a "who got notified" audit — replacing them with a count makes the trail unusable for that purpose. Note: 8.2 (Email Notifications) lists 8.1 as a data source; downstream notification analytics will lack the recipient list.

- [x] **I-7: `SHARE_UPDATE` has no `metadata: { fields: [...] }`** — `apps/server/src/modules/share/routes.ts:206-213`
  Spec line 171: `SHARE_UPDATE | share | { fields: [...] }`. Implementation passes no metadata at all. The same omission applies to `REVERSE_SHARE_UPDATE` (`reverse-share/routes.ts:165-172`) — no `fields` metadata — and `GROUP_UPDATE` (`group/routes.ts:178-186`) — also no metadata. `USER_UPDATE` does pass `changedFields` (`user/routes.ts:266`), which is the spec's intent under a slightly different key.

- [x] **I-8: `REVERSE_SHARE_CREATE` is missing `hasPassword` and `expiration` metadata** — `apps/server/src/modules/reverse-share/routes.ts:65-68`
  Spec line 207: `{ maxFiles, maxFileSize, hasPassword, expiration }`. Implementation persists only `maxFiles` and `maxFileSize`. Combined with the `password` denylist, recovering "was this reverse share password-protected at creation time?" from the audit trail is no longer possible.

- [x] **I-9: `SHARE_PASSWORD_FAILED` audit is emitted before the no-password "PASSWORD_REQUIRED" path** — `apps/server/src/modules/share/service.ts:181-198`
  When a password-protected share is accessed via `GET /shares/:shareId` (without a password), the service throws `PASSWORD_REQUIRED` at line 182 — that path emits no audit event. Only when a password is provided AND wrong does `SHARE_PASSWORD_FAILED` fire. That matches the literal spec (spec calls it "Failed password entry"), but in practice every brute-force attempt that doesn't supply a password is invisible. Consider whether the missing-password path also deserves an audit signal (probably yes, for rate-limit observability). Either way: spec decision 10 says SHARE_ACCESS is emitted "from the share page load path only" — that page-load includes the no-password rejection.
  Verdict: behaviour is consistent with the literal spec text but contradicts decision 10's intent. Document or fix.

- [x] **I-10: Aliased reverse-share password failure uses the alias string as `targetId`** — `apps/server/src/modules/reverse-share/routes.ts:447-452`
  When `getReverseShareForUploadByAlias` throws `INVALID_PASSWORD`, the catch logs `targetId: request.params.alias`. The successful path on the same route logs `targetId: reverseShare.id` (line 441). Within the same event type (`REVERSE_SHARE_PASSWORD_FAILED`), `targetId` will sometimes be a cuid, sometimes an alias slug. The simple fix is to resolve the reverse share id by alias up-front (before the password check) and use it on both paths.

## Minor

- [x] **M-1: `auditRetentionDays` seeded into `security` group while spec says `general`** — `apps/server/prisma/seed.js:104-108`, `features/specs/8.1-auditing.md:100`
  Spec §"New admin setting" says `group: "general"`. Seed file uses `group: "security"`. Plan task 1 step 3 also says "Security Configurations section" — internally consistent within the plan, but inconsistent with the spec text. Choose one and align.

- [x] **M-2: i18n metadata catalog does not match the keys the server actually emits** — `apps/web/messages/en-US.json:899-937`
  Several metadata keys present in audit calls have no i18n entry (the `AuditMetadataDisplay` falls back to a camelCase auto-formatter, so this is cosmetic, not broken):
  - `oldMaxFileSize`, `newMaxFileSize`, `oldMaxTotalStorage`, `newMaxTotalStorage` (quota route uses these instead of the spec's `oldQuota`/`newQuota`).
  - `changedFields` (user update — spec used `fields`).
  - `unassignedCount` (group delete).
  - `previousGroupId`, `memberId` (group member add/remove — spec used `userId`/`username`).
  - `parentId`, `targetFolderId` (folder/file move).
  - `extension`, `size` (file upload — spec used `fileSize`).
  - `enabled` (LDAP config update), `passwordCleared` (share password update).
  - `trigger`, `status`, `usersCreated`, `usersUpdated`, `usersDeactivated`, `usersReactivated`, `usersSkipped` (LDAP sync completed/error).
  - `createdUserId`, `deletedUserId` (user create/delete).
  - `emailOrUsername` (login failure), `remainingMinutes` (account locked), `keys` (bulk config change), `type` (auth provider create).
  Either align field names with the spec, or add the i18n keys for what is actually emitted.

- [x] **M-3: `BACKGROUND_IMAGE_DELETE` does not include `fileName` metadata** — `apps/server/src/modules/background-image/routes.ts:169-176`
  Spec line 269: `{ fileName }`. Implementation passes no metadata. (The `service.delete(id)` call doesn't return the deleted row, so the implementer would need to fetch first; minor lift.)

- [x] **M-4: `SMTP_TEST` does not capture a recipient identity in metadata** — `apps/server/src/modules/app/routes.ts:259-264`
  Spec line 262: `metadata: { recipientEmail }`. The current `POST /app/test-smtp` body has no `recipientEmail` field, which is why the metadata is empty — that means the spec hint and the route shape disagree. Either expose a `recipientEmail` body field and record it, or update the spec.

- [x] **M-5: CSV export is fragile against userAgent quotes/newlines** — `apps/server/src/modules/audit/service.ts:301-302`
  Each row is built by string concatenation with only one transformation: `(log.userAgent ?? "").replace(/,/g, " ")`. Quotes and newlines inside user-agent strings are not escaped or quoted. The `metadata` column is properly quoted/escaped but the others rely on the assumption that the source fields cannot contain commas — true for cuid()/enum values, false for arbitrary user-agent strings (which can contain commas, quotes, parentheses, etc.). Real-world UA strings have commas (e.g., `"Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36, like Gecko"`). Replacing the writer with a tiny CSV-encoding helper that wraps every field in quotes and doubles internal quotes would remove the foot-gun. The `metadata` quoting pattern at line 301 already shows the helper logic — applying it uniformly is two lines.

- [x] **M-6: Hard-coded English in pagination summary** — `apps/web/src/app/admin/audit/components/audit-log-table.tsx:190`
  `{total} {total === 1 ? "result" : "results"}` is not internationalised, despite the rest of the page being fully translated and 23 locales being updated. Use `useTranslations` with an ICU plural.

- [x] **M-7: `LDAP_SYNC_COMPLETED`/`LDAP_SYNC_ERROR` use `ipAddress: "127.0.0.1"` instead of `"system"`** — `apps/server/src/modules/ldap/sync.service.ts:112,146`
  The retention scheduler uses `ipAddress: "system"` (`retention.scheduler.ts:35`). The LDAP scheduler events use the literal IP `127.0.0.1`, which will be indistinguishable from real loopback requests in queries. Standardise on `"system"` for all internally-originating events.

- [x] **M-8: `Share.maxViews` enforcement on the share-page path is not atomic — pre-existing race, not introduced by 8.1, but spec decision 5 declares it the source of truth** — `apps/server/src/modules/share/service.ts:177-210`, `apps/server/src/modules/share/repository.ts` (`incrementViews`)
  The check at line 177 reads from a stale `share` and the increment at line 210 is a regular `update`, not an `updateMany`-with-guard. Only the embed route uses the atomic pattern (`file/routes.ts:1058-1066`). Mention is here because spec decision 5 names the counter as the enforcement mechanism — but it only is for embeds. If 8.1 is intended to "validate" the spec, the share-page increment should also be made atomic (the I-1 concurrency test would exercise this).

- [x] **M-9: `FILE_EMBED_ACCESS` fires on every range request — documented but worth confirming the volume implication** — `apps/server/src/modules/file/routes.ts:1088-1095`
  Spec decision 10 acknowledges this: "FILE_EMBED_ACCESS … can be many per share view (range requests)". With `audit_logs` being one of the heaviest write paths in the system, a single video playback can generate dozens of audit rows. This is consistent with the spec but worth verifying against the WAL warning logic — and considering whether the 365-day default retention will keep the table manageable on a busy instance. Not a defect; an operational note.
