## Important

### I-1: Dates rendered as raw ISO strings in email bodies (date formatting helper only applies to subjects)

- **File(s)**:
  - `apps/server/src/modules/email/service.ts:44-67` (`formatDateIfApplicable`)
  - `apps/server/src/modules/email/service.ts:185-200` (build `dataParams`, then `entry.render(validatedData, tr)`)
  - `apps/server/src/modules/email/templates/share-expiring.ts:13-16`
  - `apps/server/src/modules/email/templates/share-accessed.ts:16-23`
  - `apps/server/src/modules/email/templates/share-invitation.ts:20-27`
  - `apps/server/src/modules/email/i18n/messages/en.json:42,48-49,54-55,60,66`
- **Description**: `send()` builds a `dataParams` record where date-shaped values
  (keys ending in `At` or matching the ISO regex) are converted to human-readable
  form via `Intl.DateTimeFormat` (lines 185-193). **However, `dataParams` is used
  only for the email subject** (line 242). The template body is rendered by
  `entry.render(validatedData, tr)` at line 200, which receives the **raw validated
  payload** — the un-formatted ISO strings. Every template that interpolates a date
  into the body (`share_expiring`, `share_expired`, `share_accessed`,
  `share_downloaded`, `share_invitation` infoBox, `share_max_views`, reverse-share
  expiry, etc.) passes the raw `data.expiresAt` / `data.accessedAt` / `data.downloadedAt`
  directly to the translation function. The recipient therefore sees
  `2026-12-31T00:00:00.000Z` in the email body instead of `December 31, 2026 at 12:00 AM`.
- **Expected**: Spec Section 3 describes human-readable email content; the
  `formatDateIfApplicable` helper was clearly written to produce localized dates.
  The intent is that dates display human-readable in the rendered email.
- **Fix**: Apply the same date formatting to the params the template receives, not
  just the subject. The cleanest fix is to format dates once and pass the formatted
  values into the render path. Option A: have `send()` build a formatted-params object
  and pass it to templates (requires changing the render signature to accept params).
  Option B (less invasive): move date formatting into the `createTranslationFn`
  interpolation layer so any date-shaped value is formatted at interpolation time.
  Option C: format dates inside each template before calling `t()`. Whatever the
  approach, add a service-level or template-level test that asserts the rendered
  `htmlBody` contains a formatted date (not the raw ISO string) — the current
  `templates.test.ts` uses an echo `mockT` and `email-service.test.ts` mocks Prisma,
  so neither exercises real date rendering.

### I-2: `notifyOnDownload` ("notify me on each download") is silently throttled by the 900s cooldown

- **File(s)**:
  - `apps/server/src/modules/email/service.ts:154-173` (cooldown check)
  - `apps/server/src/modules/email/service.ts:331-338` (`notifyOnDownload` → "immediate")
  - `apps/server/src/modules/email/catalog.ts:366` (`share_downloaded` `cooldownSeconds: 900`)
  - `apps/server/src/modules/share/service.ts:464-465` (comment acknowledging this)
- **Description**: The per-share `notifyOnDownload` toggle is documented in the UI/spec
  as "Notify me on **each** download" (spec Section 6 / Section 8). In code, it upgrades
  the resolved frequency from `disabled` to `immediate` (`resolveFrequency` step 3). But
  `share_downloaded` carries `cooldownSeconds: 900`, and the cooldown check in `send()`
  runs **after** frequency resolution, unconditionally for any type with a cooldown.
  Result: even with `notifyOnDownload = true`, the owner receives at most one
  download notification per 15 minutes per share — not one per download. A user who
  explicitly opted into per-download notifications will silently miss most of them.
  The comment at `share/service.ts:464-465` confirms the behavior is known, but it
  directly contradicts the feature's stated purpose.
- **Expected**: Spec Section 6: "Notify me on each download — toggle (overrides global
  `share_downloaded` preference for this share)." A per-download override should bypass
  (or at least not be defeated by) the anti-flood cooldown.
- **Fix**: When the per-share override is active, skip the cooldown for that send (the
  override is an explicit opt-in to high-volume notifications). Plumb a flag from
  `resolveFrequency` (e.g. return `{ frequency, overridden }`) into `send()` and skip
  the cooldown block when `overridden === true`. Alternatively, document the cooldown
  explicitly in the UI label ("Notify me on downloads (max once per 15 min)") so the
  promise matches behavior — but the code fix is preferable since the spec wording is
  unambiguous.

### I-3: `share_accessed` / `share_downloaded` notifications are sent before the `ShareVisit` row is durably written, and visitor identity can be lost

- **File(s)**:
  - `apps/server/src/modules/share/service.ts:330-367` (visit create fire-and-forget, then notification)
  - `apps/server/src/modules/file/routes.ts:186-239`
- **Description**: In `getShare`, the `ShareVisit` insert (lines 330-342) and the
  `share_accessed` notification (lines 347-366) are two independent fire-and-forget
  async operations. They are not ordered and not transactional. If the `ShareVisit`
  insert fails (the `.catch` only logs), the owner still receives an "X accessed your
  share" email for a visit that was never recorded — the activity log and the
  notification disagree. This is a data-integrity inconsistency: the notification
  asserts an event the audit trail does not contain. The same pattern exists in
  `trackShareDownload` (`file/routes.ts:187-239`).
- **Expected**: Spec Section 5: "For each event: 1. A `ShareVisit` row is created
  (always, regardless of notification preferences) 2. If the share creator has
  notifications enabled → an `EmailJob` is created." The ordering implies the visit is
  the source of truth and the notification is downstream.
- **Fix**: Await the `ShareVisit` create before enqueuing the notification (or make the
  notification depend on the visit insert succeeding). Since both are already off the
  hot response path conceptually, awaiting the visit insert inside the existing
  fire-and-forget IIFE is low-cost and removes the divergence. At minimum, do not send
  the notification if the visit insert rejected.

## Minor

### M-1: `validateI18nKeys` only checks key existence, not placeholder consistency — translation typos still reach production

- **File(s)**:
  - `apps/server/src/modules/email/i18n/loader.ts:125-138`
  - `apps/server/src/modules/email/i18n/loader.ts:293-322` (interpolate throws only when `NODE_ENV !== "production"`)
- **Description**: Boot-time `validateAllI18nKeys()` verifies every required key exists
  in `en.json`, but does not verify that the placeholders inside each translation match
  what the template passes. A locale file with a missing `{shareName}` placeholder (or a
  typo like `{shareNam}`) passes validation. At render time, `interpolate()` throws on
  unresolved placeholders **only when `NODE_ENV !== "production"`** (line 311). In
  production, an unresolved `{placeholder}` is left verbatim in the email, and a template
  that references a param the locale string doesn't use silently drops it. The 21
  placeholder-only locale files (shipping `en` content) are lower risk, but `fr.json` is
  hand-translated and could drift.
- **Expected**: Spec Section 3: "Fail fast if keys are missing — this catches typos and
  forgotten translations during development."
- **Fix**: Extend the i18n validation (or a test) to render every catalog type with a
  representative payload in `en` and `fr` and assert no unresolved `{...}` placeholders
  remain. This would have also surfaced I-1.

### M-2: `notificationCheckHour` config key is read but never seeded

- **File(s)**:
  - `apps/server/src/modules/notification/notification.scheduler.ts:350-372`
  - `apps/server/prisma/seed.js` (only `emailDigestHour` is seeded, line ~217)
- **Description**: `getNotificationCheckHourUtc()` reads `notificationCheckHour` as the
  "dedicated config key" first, then falls back to `emailDigestHour`. `notificationCheckHour`
  is never seeded, so the dedicated key is always absent and the code always uses the
  fallback. This works, but the "dedicated key" is dead configuration surface: an admin
  cannot actually set it via the seeded config, and the fallback comment implies a
  migration that never happened. Either seed it or remove the dead lookup.
- **Expected**: Config keys referenced by schedulers should be seeded (consistent with
  the other email config keys in Batch 1 Step 7).
- **Fix**: Add `notificationCheckHour` to `seed.js` (default 8, group "email"), or remove
  the first lookup and rename the fallback to be the canonical key.

### M-3: `EmailJob.payload` digest path is inert dead surface, but the cooldown query counts `digest_pending`

- **File(s)**:
  - `apps/server/src/modules/email/service.ts:258-285` (digest branch)
  - `apps/server/src/modules/email/service.ts:163` (cooldown `status: { in: [..., "digest_pending"] }`)
- **Description**: This is mostly a spec-acknowledged deferral (digest aggregation is
  Post-8.2). Worth noting for completeness: since the API/UI never allow selecting
  `daily_digest`, no `digest_pending` job is ever created in 8.2, so the `digest_pending`
  branch (lines 260-277) and its inclusion in the cooldown query (line 163) are unreachable
  today. Not a bug — flagging only so a future reviewer doesn't mistake the unreachable
  branch for tested behavior. No change required for 8.2.

### M-4: Unsubscribe POST accepts `.passthrough()` body and ignores everything but `token`

- **File(s)**: `apps/server/src/modules/notification/routes.ts:324, 330-352`
- **Description**: The POST `/notifications/unsubscribe` body schema is
  `z.object({ token: z.string().optional() }).passthrough().optional()`. `.passthrough()`
  is intentional (RFC 8058 one-click POSTs `List-Unsubscribe=One-Click` in the body), and
  the handler only ever reads `token`, so this is safe. Minor note: the permissiveness is
  correct but undocumented at the schema level beyond the inline comment — fine as-is, no
  action needed unless stricter validation is desired.

## Positive Observations

- **SMTP header injection is properly mitigated**: `sanitizeForSubject` (service.ts:25-31)
  strips CR/LF from all interpolated subject params, and `appName` is included in the
  sanitized set. The interpolation layer HTML-escapes body values via `tHtml`/`escapeHtml`.
- **Unsubscribe token security is solid**: `verifyUnsubscribeToken` validates the `alg`
  header (algorithm-confusion defense), uses a purpose-derived HMAC key
  (`deriveKey("unsubscribe")`) isolated from auth JWTs, uses constant-time comparison
  with a length pre-check, and only trusts `exp`. The two-step GET-confirm / POST-perform
  flow correctly prevents email-scanner auto-unsubscribe.
- **Defense-in-depth on unsubscribe**: `unsubscribeUser` silently no-ops for unknown,
  critical, or non-configurable types — a crafted/replayed token can never disable
  `password_reset` or `welcome`.
- **Queue job locking is race-safe**: `processBatch` uses `updateMany` with a
  `status: "pending"` guard and checks `lockResult.count === 1` before sending, so a
  hypothetical second worker cannot double-send a job. Stuck-job recovery treats recovery
  as a failed attempt with exponential backoff and respects `maxAttempts`.
- **Owner exclusion is correctly enforced** at the earliest point: `getShare` returns
  before any visit tracking or notification when `isOwner` (service.ts:204-206), and
  `trackShareDownload` returns early when `isOwner` (file/routes.ts:171).
- **Render-failure vs SMTP-failure distinction is implemented**: render failures create a
  `failed` job with `maxAttempts: 0` (no retry), SMTP failures retry with exponential
  backoff — matching the spec.
- **Visits endpoint correctly strips PII**: `GET /shares/:shareId/visits` removes
  `ipAddress`/`userAgent` from the response and verifies share creator ownership; the
  `share_accessed`/`share_downloaded` payloads omit `ipAddress` as the privacy note requires.
- **Recipient upsert preserves tracking tokens**: `updateShare` syncs recipients by
  `[shareId, email]` (add/remove/keep) inside a transaction, preserving `trackingToken`,
  `notifiedAt`, and access stats for unchanged recipients — exactly as the migration spec
  requires.
- **Catalog-as-source-of-truth is faithfully implemented**: `EmailPayloads` is derived
  from the Zod schemas, `send()` validates payloads before render, and all 22 types are
  present with correct `isCritical`/`configurable`/`hasUnsubscribe` invariants.
