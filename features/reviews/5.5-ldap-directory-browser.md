## Important

- [x] **`distinguishedName` empty-array coercion yields an empty `dn` on non-AD servers** — `apps/server/src/modules/ldap/ldap.client.ts:338` and `:340` (and the pre-existing `:186` in `searchSyncGroupMembers`). `searchGroups` requests the `distinguishedName` attribute and maps with `String(entry.distinguishedName || entry.dn)`. ldapts' `SearchEntry.toObject` (`ldapts@8.1.8`, `index.mjs:2344`) sets **any requested-but-absent attribute to `[]`**, not `undefined`. `distinguishedName` is an AD-specific operational attribute — OpenLDAP / 389-DS / FreeIPA do **not** return it, so `entry.distinguishedName` is `[]`. Since `[]` is truthy in JS, `entry.distinguishedName || entry.dn` evaluates to `[]`, and `String([])` is `""`. Result: on every non-AD server (which the spec explicitly supports, I-1) the returned group `dn` is an **empty string**, so selecting a group sets `syncGroupDn = ""`. The C-1/mapping tests never catch this because every fixture includes a populated `distinguishedName`.
  **Fix:** stop requesting/preferring `distinguishedName` and rely on `entry.dn` (which `toObject` always sets to the entry's real DN — `index.mjs:2345`, `result = { dn: this.name }`). i.e. drop `"distinguishedName"` from the `attributes` array (`ldap.client.ts:315`) and map `dn: String(entry.dn)` / name fallback `String(entry.dn)`. This matches what `browseContainers` already does (`:269` uses `entry.dn` only) and is correct for both AD and non-AD. Add a fixture **without** `distinguishedName` to `ldap.client.directory.test.ts` proving the dn is the real DN, not `""`. (Recommend fixing the same latent pattern at `:186` for consistency, but at minimum the new `searchGroups` path must be correct.)

## Minor

- [x] **Spec deviation: `searchGroups` requests `["cn","name","distinguishedName"]`, spec says `["cn","name"]`** — `apps/server/src/modules/ldap/ldap.client.ts:315`; spec line 89 / plan Task 1.2 specify `attributes: ["cn","name"]`. The extra `distinguishedName` is the root cause of the Important finding above. Once that is fixed by dropping it, the code re-aligns with the spec. Listed separately so the spec/code divergence is explicitly reconciled (either fix the code or amend the spec decision — fixing the code is correct here).

- [x] **`getEntryAttribute` returns a comma-joined string for multi-valued attributes** — `apps/server/src/modules/ldap/ldap.client.ts:68-76`. `String(entry[key] || "")` on an array of length ≥2 yields `"a,b"`. In practice `ou`/`cn`/`name` are single-valued (ldapts returns the scalar, `toObject` `index.mjs:2358`), so the realistic blast radius is nil, but the helper is not array-safe by contract and the new `browseContainers`/`searchGroups` name derivation depends on it. Low risk; consider taking `[0]` of the multi-value form (reuse `getEntryAttributeValues(...)[0] ?? ""`) so the helper can't silently concatenate. Pre-existing helper — flagged because the new methods rely on it for `name`.

- [x] **No test asserts `disconnect()` is reached when `resolveBindPassword` throws before `connect()`** — `apps/server/src/modules/ldap/__tests__/directory-routes.test.ts:298-327`. The two resolver-error tests assert `connectMock` was not called but do **not** assert `disconnectMock` was called. The route's `finally` does run `disconnect()` on that path (it is a no-op on the real client since `this.client` is still `null`), so there is no defect — but the "disconnect always in finally" guarantee on the *pre-connect throw* branch is untested. Add `expect(disconnectMock).toHaveBeenCalledTimes(1)` to both the `LDAP_BIND_PASSWORD_REQUIRED` and `LDAP_ENCRYPTION_UNAVAILABLE` cases to lock it in.

- [x] **`truncated` is a conservative false-positive when the directory holds *exactly* `GROUP_SEARCH_SIZE_LIMIT` matches** (accepted — documented with an explicit comment at `ldap.client.ts`) — `apps/server/src/modules/ldap/ldap.client.ts:329`. With `searchEntries.length >= GROUP_SEARCH_SIZE_LIMIT`, a result set of exactly 50 reports `truncated: true` even if those were the only matches (server returned `Success`, not `SizeLimitExceeded`). This is intentional and safe (the UI hint is "refine your search" — harmless over-prompt) and a precise count is not recoverable from `searchEntries` alone without inspecting the LDAP result code, which ldapts swallows when `sizeLimit` is set (`index.mjs:3554`). Acceptable as-is; documenting so the behavior is a deliberate, reviewed choice rather than an unnoticed edge. No code change strictly required — leave a one-line comment noting the off-by-one is intentional, or mark this checkbox as accepted.

## Verified correct (no action)

- **C-1 filter injection — fully mitigated and proven.** `searchGroups` composes the query **only** as `new SubstringFilter({ attribute, any: [query] })` inside `AndFilter`/`OrFilter` objects (`ldap.client.ts:297-307`); the query is never concatenated into a filter string anywhere. ldapts only parses *string* filters via `FilterParser.parseString` (`index.mjs:3429-3431`); a filter **object** is BER-encoded, so `* ( ) \` in the query are data. The C-1 test (`ldap.client.directory.test.ts:298-322`) asserts `options.filter` is **not** a string, is an `AndFilter` instance, and that the raw `"*()\\"` query is carried verbatim as the `SubstringFilter.any` value on both `cn` and `sAMAccountName` branches. `browseContainers` and `readRootDse` use only `EqualityFilter`/`OrFilter`/`PresenceFilter` objects — no string-built filters in the module. DTO `baseDn`/`searchBase` are search bases (not filter values) and are still Zod-validated to DN shape.
- **Every connection path routes through `connect()` → `assertLdapTargetAllowed`.** Both routes call `new LdapClient()` then `client.connect(...)` (`routes.ts:273-279`, `:325-331`); `connect()` calls `assertLdapTargetAllowed` before constructing the `Client`/binding (`ldap.client.ts:129-140`). No bypass; no new egress path.
- **Error genericization (`toClientSafeLdapError`, `routes.ts:57-70`).** Surfaces only `AppError` with a `LDAP_*` code; everything else is logged server-side (`err.message` only) and replaced with a generic `LDAP_CONNECTION_FAILED` message. No host/IP/port/server-string leak. Integration tests assert the generic path does not contain `ECONNREFUSED`, `10.0.0.5`, or `internal-dc` (`directory-routes.test.ts:335-349`, `:425-439`) and that genuine `LDAP_*` config errors pass through verbatim (`:351-366`). Mirrors `testConnection` discipline exactly.
- **`disconnect()` in `finally` on both routes** (`routes.ts:298-300`, `:337-339`); `disconnect()` is null-safe (`ldap.client.ts:387-396`), so a throw inside `resolveBindPassword` (before connect) is handled.
- **`sizeLimit` enforced on every bounded search:** `browseContainers` passes `BROWSE_SIZE_LIMIT` (`ldap.client.ts:258`), `searchGroups` passes `GROUP_SEARCH_SIZE_LIMIT` (`:316`). `readRootDse` is a `scope:"base"` single-entry read — no cap needed (correct).
- **SizeLimitExceeded handling matches ldapts@8.1.8 behavior.** With `sizeLimit` set, ldapts returns the partial result (does **not** throw) — `_sendSearch` special-cases `MessageResponseStatus.SizeLimitExceeded && searchRequest.sizeLimit` (`index.mjs:3554`). So the primary `length >= cap` detection (`ldap.client.ts:329`) is the live path; the `SizeLimitExceededError` catch (`:323`) is genuine defense-in-depth for servers/versions that surface it as an error, and it returns `{ groups: [], truncated: true }` without leaking the raw error. Both the partial-result and thrown-error paths are unit-tested (`ldap.client.directory.test.ts:271-295`).
- **Masked-password resolver (`bind-password.ts`).** Empty/masked → stored decrypt; no stored config → `LDAP_BIND_PASSWORD_REQUIRED`; decrypt failure → `LDAP_ENCRYPTION_UNAVAILABLE` (`:28-47`). The `try/catch` wraps **only** `decrypt(config.bindPassword)` (`:38-46`), so it cannot swallow an unrelated error from `configRepository.get()` (that is awaited outside the try). Decrypt-failure is correctly distinguished from a wrong-password (wrong password is never detected here — that surfaces later as a generic bind failure, which is correct). Plaintext password is returned but **never logged**. Unit-tested for all four branches (`bind-password.test.ts`) plus full-lifecycle integration coverage incl. ENCRYPTION_SECRET-unset (`directory-routes.test.ts:281-327`).
- **`readRootDse` correctness:** base `""`, `scope:"base"`, `PresenceFilter(objectClass)`, attrs `["namingContexts","defaultNamingContext"]` (`ldap.client.ts:211-215`); empty-string naming contexts filtered out (`:219-221`); `defaultNamingContext` is `null` when absent — uses `getEntryAttributeValues` so AD scalar vs array and absent (`[]`) are all handled (`:222-228`); empty-RootDSE response handled without throwing (test `:129-136`).
