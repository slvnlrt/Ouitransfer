## End-to-end identity/source thread (highest value — B1+B2+B3) — VERIFIED

Traced the full coherent thread and confirmed every hop:

1. **Token arrival → cookie write (server-side only).** Access resolves the
   token recipient at `share/service.ts:333-341` (re-checked `candidate.shareId === share.id`),
   stamps `identificationSource = "token"`, and sets `context.out.recipientIdForCookie`
   **only** in the token branch (`service.ts:416-418`). The cookie is then written
   by `refreshVisitorCookieWithRecipient` (`share/routes.ts:71-90`), which sources
   `recipientId` **exclusively** from `recipientIdForCookie`. The identification
   form endpoint (`/identify`, `routes.ts:1089-1095`) **never** sets `recipientId`
   — confirmed it calls `buildVisitorCookiePayload` without it. So the cookie
   `recipientId` can only ever vouch for a token-verified recipient. ✓
2. **Cookie is tamper-resistant.** `parseVisitorCookie` (`visitor-cookie.ts:37-38`)
   calls `request.unsignCookie` and bails on `!unsigned.valid`. Cookie options
   (`routes.ts:55-64`) are `signed: true, httpOnly, sameSite: strict`. ✓
3. **Download reads cookie → links recipient.** `trackShareDownload`
   (`file/routes.ts:200-250`) parses the cookie and calls the shared
   `resolveDownloadRecipient`. Counter bump is atomic (`{ increment: 1 }`) and
   fire-and-forget (`.catch`), so it can never break the download. ✓
4. **Source labeling is honest end to end.** `resolveDownloadRecipient`
   (`recipient-resolution.ts:36-73`): `cookie.recipientId` → re-verifies it
   belongs to `shareId` → `"token"`; else `cookie.email` → `shareId_email` match →
   `"self_declared"`; else null. A self-declared (form-typed) email is **never**
   labeled `token` — pinned by the spoof test (`visitor-tracking.test.ts:726`,
   "anonymous visitor typing a known recipient's email is 'self_declared', never
   'token'"). ✓
5. **`/visits` mapping.** `routes.ts:1218-1231`: stored `"token"`→`"tracking_token"`,
   stored `"self_declared"`→`"cookie"`; the `recipientId`-heuristic branch fires
   **only** for null (pre-8.3) rows. This is the 5728bdb fix and it is correct —
   lot C's self-declared linkage can no longer be mislabeled as a verified token. ✓
6. **Badge + reminder consistency.** Badge keys off `lastDownloadedAt != null`
   (`recipient-selector.tsx:418`); "Pending" = `notifiedAt != null && !downloaded`
   (`:419`). The server reminder filter is **identical**
   (`service.ts:1095-1097`) and is enforced server-side regardless of the
   `emails` subset (intersected, `:1100-1103`). UI `pendingCount` matches
   (`recipient-selector.tsx:248-250`). ✓

**No place** labels a self-declared email as verified (checked cookie, access
visit, download visit, `FILE_DOWNLOAD` audit metadata, `/visits` response, and
both UI surfaces).

### Minor

- [x] **[Minor] Download path resolves the recipient twice (one extra share-scoped query per download).** `apps/server/src/modules/file/routes.ts:1080-1082` and `:1205-1207` call `resolveDownloadRecipientFromRequest` to enrich the `FILE_DOWNLOAD` audit, then `trackShareDownload` (`:200-216`) parses the cookie and calls `resolveDownloadRecipient` again — two independent resolver round-trips (each does an alias lookup + recipient lookup) for the same download. Functionally correct and both are best-effort, so this is purely a micro-efficiency note, not a bug. If ever consolidated, resolve once in the handler and pass the result into `trackShareDownload`. **Resolution:** tracked in TD-52 (item 3) — micro-efficiency on a fire-and-forget hot path; not refactored at close-out to avoid an unreviewed hot-path change. No code change for Done.

- [x] **[Minor] `downloadCount` / `uploadCount` are serialized but never surfaced in the UI.** `ShareRecipient.downloadCount` and `ReverseShareRecipient.uploadCount` flow through the DTO + web types but the badges are derived purely from `lastDownloadedAt` / `uploadedAt` (booleans). The counters are API-only. **Resolution:** already tracked as TD-52 (item 1); symmetric on both sides; acceptable as designed (R-6 documents `downloadCount` = files fetched). Logged, not silently dropped.

- [x] **[Minor] No live-DB integration test for the atomic reverse-upload counter / conditional first-stamp.** Coverage is `app.inject()` with a mocked Prisma (matched / absent / second-upload / spoofed asserted), which verifies the *call shape* (`updateMany({ where: { uploadedAt: null } })` and `{ increment: 1 }`) but not the real DB's atomicity under concurrency. Same pattern as the share-side counter. **Resolution:** already tracked as TD-52 (item 2). Nice-to-have, non-blocking; the call-shape assertions are a reasonable proxy.
