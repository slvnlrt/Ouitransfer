# 8.1 Audit Trail — Code Quality Review

Scope: code-quality review of the 8.1 implementation across the 75 changed files in `843b790..bfb7a71`. Every finding below was verified against the actual code (file:line referenced). For findings already captured in `features/reviews/8.1-auditing-spec.md`, I either flag them as confirmed and reference that file, or skip them. The focus here is on bugs, type safety, error handling, race conditions, and production-readiness — not spec compliance.

A short note on what is well done is included at the end.

## Critical

- [ ] **C-1: Date-range filter is broken end-to-end — UI sends `YYYY-MM-DD`, server rejects with 400** — `apps/web/src/app/admin/audit/components/audit-log-filters.tsx:85-111`, `apps/server/src/modules/audit/routes.ts:29-30,89-90`
  `AuditLogFilters` uses `<Input type="date">`, which produces values of the form `2026-01-31`. The hook forwards them verbatim through `useAuditLogs` → `getAuditLogs` → axios query params. The server schema requires `z.string().datetime()` for both `dateFrom` and `dateTo`. `z.string().datetime()` only accepts ISO-8601 with a time component:
  ```
  > z.string().datetime().parse("2026-01-01") // throws
  > z.string().datetime().parse("2026-01-01T00:00:00Z") // OK
  ```
  Consequence: as soon as the user picks any date in the UI, the list call returns `400` and the page silently shows an empty result; the export button is enabled but every click 400s. The integration tests pass because they hand-craft full ISO strings (`audit-logs.integration.test.ts:244,290`) — they do not exercise the front-end behavior.
  Fix: in the hook (or the filters component) convert `dateFrom` to `${value}T00:00:00.000Z` and `dateTo` to `${value}T23:59:59.999Z` before sending, OR relax the server schema to accept `z.union([z.string().datetime(), z.string().date()])` and normalize inside the handler. The first option is cleaner because it also matches the spec's "inclusive end of day" requirement.

- [ ] **C-2: Invite token value is stored as `targetId` in audit logs (confirmed)** — `apps/server/src/modules/invite/routes.ts:45,108`
  Already raised as C-1 in `features/reviews/8.1-auditing-spec.md`. Including here because it is a code-quality and security concern that must be fixed before merge. Both `INVITE_TOKEN_CREATE` and `INVITE_TOKEN_USED` write the raw 64-hex-char invite secret into the `audit_logs.targetId` column. Anyone with audit-read access (admin only today, but the column will leak into every future export/notification/replication path) recovers a usable, valid token. Trivially fixable by returning the row id from `inviteService` and writing `targetId: inviteToken.id`.

- [ ] **C-3: `deleteOldAuditLogs` "batch loop" is a lie — and tested behavior is impossible** — `apps/server/src/modules/audit/service.ts:347-361`, `apps/server/src/modules/audit/__tests__/service.test.ts:259-269`
  ```ts
  do {
    const result = await prisma.auditLog.deleteMany({ where: { createdAt: { lt: olderThan } } });
    batchDeleted = result.count;
    totalDeleted += batchDeleted;
  } while (batchDeleted >= DELETE_BATCH_SIZE);
  ```
  Prisma's `deleteMany` issues a single SQL `DELETE` with no `LIMIT` clause (SQLite + Prisma does not support `LIMIT` on `deleteMany`). So the first call deletes **everything** matching the predicate and returns the total. The second call deletes zero. The loop therefore always exits after at most two iterations — there is no batching. The "DELETE_BATCH_SIZE = 1000" constant is dead. Real-world consequence on a multi-million-row table: a single multi-second / multi-minute transaction holding the SQLite writer lock; the very thing batching was meant to avoid.
  Worse: the existing test (`service.test.ts:260-268`) mocks two successive returns of 1000 and 500 and asserts `totalDeleted === 1500`. That sequence cannot happen in production — a true `deleteMany` call would return 1500 once then 0. The test gives false confidence that batching works.
  Fix: drop the loop and rename the function (one shot), OR implement real batching with `prisma.$queryRaw` (`DELETE FROM audit_logs WHERE id IN (SELECT id FROM audit_logs WHERE createdAt < ? LIMIT 1000)`) and a true batch test with a real SQLite fixture. Either way the misleading test must be reworked.

- [ ] **C-4: Retention scheduler never runs for the first 24 hours after process start** — `apps/server/src/modules/audit/retention.scheduler.ts:14-56,61-65`
  `startAuditRetentionScheduler()` calls `scheduleNext()`, which schedules the first cleanup `ONE_DAY_MS` (24h) later. There is no initial run, no on-boot pass, no "if last_cleanup older than X then run now" logic. On any deployment that restarts the server more often than its retention interval (CI/CD daily deploys, container restarts, blue/green rollouts, crashes), retention **never executes**. The LDAP scheduler has the same chained-setTimeout shape but is given an initial-delay parameter; this one is hard-coded to 24h.
  Fix: either invoke `deleteOldAuditLogs` once during `initAuditRetentionOnBoot` (after the WAL check), or persist `lastCleanupAt` and compute the next-run delay from that timestamp.

## Important

- [ ] **I-1: User-related actions are missing from the action filter dropdown** — `apps/web/src/app/admin/audit/types/index.ts:1-78`
  The `ACTION_CATEGORIES` constant — which drives the `AuditLogFilters` `<Select>` — does **not** include any of the seven `USER_*` actions emitted by the server: `USER_CREATE`, `USER_UPDATE`, `USER_DELETE`, `USER_ROLE_CHANGE`, `USER_QUOTA_CHANGE`, `USER_ACTIVATE`, `USER_DEACTIVATE`. The server emits them, the i18n catalogue has entries for them, the table renders them — but the admin cannot filter for them from the UI. There is no "user" category at all in the dropdown.
  Fix: add a `user` category to `ACTION_CATEGORIES` (and an `actionCategories.user` i18n key in all 23 locales — currently 4 of them already have `actionCategories.user` defined and unused).

- [ ] **I-2: Frontend metadata special-case for quota change uses wrong keys — the server never produces them** — `apps/web/src/app/admin/audit/components/audit-metadata-display.tsx:37-48` vs `apps/server/src/modules/quota/routes.ts:104-109`
  `AuditMetadataDisplay` checks `metadata.oldQuota !== undefined && metadata.newQuota !== undefined` and renders a nice "1.0 GB → 2.0 GB" view. The server writes:
  ```
  metadata: { oldMaxFileSize, newMaxFileSize, oldMaxTotalStorage, newMaxTotalStorage }
  ```
  Neither `oldQuota` nor `newQuota` exists. The special-case branch is dead code; every `USER_QUOTA_CHANGE` falls through to the generic key-value renderer that prints raw byte strings.
  Worse: the test at `audit-page.test.tsx:342-369` "validates" the dead branch by hand-crafting metadata with `oldQuota`/`newQuota` keys. Like C-3, this gives false confidence.
  Fix: pick a side. Either rename the server-side metadata to `oldQuota`/`newQuota` (simpler; matches the spec, but loses the file-vs-storage distinction), or change the front-end to detect either of the four real keys and render two bytes-arrows for the two limits. Add a real test using server-shaped fixtures.

- [ ] **I-3: Hardcoded English strings inside the audit page** — `apps/web/src/app/admin/audit/components/audit-log-table.tsx:190`, `apps/web/src/app/admin/audit/components/audit-metadata-display.tsx:59`
  Two places hard-code English in a feature that is otherwise fully internationalized across 23 locales:
  - `audit-log-table.tsx:190`: `{total} {total === 1 ? "result" : "results"}` — ASCII English plural, not ICU. Should be `t("table.resultCount", { count: total })`.
  - `audit-metadata-display.tsx:59`: `value ? "Yes" : "No"` for boolean metadata values. Should use translated `audit.common.yes`/`audit.common.no` keys.
  Minor on its own, but a regression of the "fully translated UI" guarantee the project advertises. The 23 locale files would also need the new keys.

- [ ] **I-4: CSV export streaming has no error handling — partial responses on failure** — `apps/server/src/modules/audit/routes.ts:111-127`, `apps/server/src/modules/audit/service.ts:287-342`
  The handler writes Content-Type / Content-Disposition headers, then iterates `for await (const chunk of generator) reply.raw.write(chunk)`. If any of the chunks (a Prisma findMany failure, a JSON.parse error inside the JSON branch at line 328, a network hiccup) throws, headers and a partial body have already been sent — Fastify cannot turn that into a JSON error response. The client receives a truncated CSV/JSON file that looks valid; the audit operator silently gets incomplete data.
  Several specific failure modes to consider:
  - `JSON.parse(log.metadata)` at service.ts:328 throws if a previously stored metadata blob is malformed.
  - Backpressure: `reply.raw.write()` returns a boolean; here it is ignored. Under network slowness, the generator keeps pumping into the kernel buffer until either OOM or the socket buffer fills.
  Fix: wrap the loop in try/catch; on error call `reply.raw.destroy(err)` (terminates the connection with a TCP RST so the client knows the file is incomplete) and `getLogger().error(...)`. Add an `await new Promise(resolve => reply.raw.once("drain", resolve))` when `write()` returns false.

- [ ] **I-5: Export cursor pagination can skip or duplicate rows when `createdAt` ties exist** — `apps/server/src/modules/audit/service.ts:290-309, 315-340`
  ```ts
  orderBy: { createdAt: "desc" },
  ...(cursor ? { skip: 1, cursor: { id: cursor } } : {}),
  ```
  The cursor field (`id`) is not the ordering field (`createdAt`). Prisma supports this only when the cursor row is uniquely positionable in the order — fine when timestamps are unique. SQLite's `DateTime` has millisecond resolution. Under burst writes (which audit logs are highly prone to — login storms, batch operations, the audit-retention cleanup itself), multiple rows share the same `createdAt`. Two failure modes:
  1. Rows with the same `createdAt` as the cursor row can be silently skipped (the `skip: 1` jumps past one of them but the next page does not pick up the rest).
  2. Conversely, if the database internally reorders ties differently across page calls, the same row can appear in two consecutive pages.
  Fix: use a compound order `[{ createdAt: "desc" }, { id: "desc" }]` and a compound cursor `{ createdAt_id: { createdAt, id } }` (after adding a corresponding `@@unique([createdAt, id])` to the schema, OR simply emulate the ordering manually with `where: { OR: [{ createdAt: { lt: lastCreatedAt } }, { createdAt: lastCreatedAt, id: { lt: lastId } }] }` and an offset-style approach). This is a real-data-loss bug in an export, not just theoretical.

- [ ] **I-6: CSV writer destroys data instead of quoting fields** — `apps/server/src/modules/audit/service.ts:300-303`
  Each row is concatenated with one transformation: `(log.userAgent ?? "").replace(/,/g, " ")`. That:
  - Replaces commas inside the User-Agent with spaces — irreversibly corrupting the field. (Many real-world UAs do contain commas: `Mozilla/5.0 (Linux; Android 14; SM-S918B Build/UP1A.231005.007, wv) AppleWebKit/...`).
  - Does nothing about double-quotes or CR/LF inside any field — those will break parsing in Excel/LibreOffice.
  - Does nothing for action/ipAddress/targetId/etc. — fine today because they are enum/cuid/IP literals, but it relies on the assumption that no future code ever writes a comma to those columns.
  - The `metadata` column uses correct quote-escaping at line 301 (`metadataStr = log.metadata ? "\"${log.metadata.replace(/"/g, '""')}\""`) — apply that pattern uniformly. Five lines of work.
  This was already noted as M-5 in the spec review; bumping to Important because real exports will silently corrupt UA strings.

- [ ] **I-7: REVERSE_SHARE alias path uses the alias slug as `targetId` (confirmed)** — `apps/server/src/modules/reverse-share/routes.ts:447-452`
  Already noted as I-10 in the spec review. Within the same event type (`REVERSE_SHARE_PASSWORD_FAILED`), success writes `targetId: reverseShare.id` (line 441) but failure writes `targetId: request.params.alias` (line 451). The new composite index `(targetType, targetId, action, createdAt)` is rendered partially useless for analytics — joining all events for a given reverse share will miss the alias-failure rows. Resolve the reverse-share id by alias before the password check, then use a single consistent `targetId` on both paths.

- [ ] **I-8: REVERSE_SHARE_PASSWORD_FAILED check uses string literal `"INVALID_PASSWORD"` instead of the `ErrorCodes` constant** — `apps/server/src/modules/reverse-share/routes.ts:349,445`
  ```ts
  if (err instanceof AppError && err.code === "INVALID_PASSWORD") { ... }
  ```
  Should be `err.code === ErrorCodes.INVALID_PASSWORD` (imported from `@ouitransfer/shared/error-codes`, as done in `auth/routes.ts:107`). If the constant value ever changes, this string-compare silently breaks. Confirmed: `ErrorCodes` is not imported in this file.

- [ ] **I-9: Metadata denylist only checks top-level keys** — `apps/server/src/modules/audit/service.ts:146-155`
  ```ts
  for (const [key, value] of Object.entries(metadata)) {
    if (!METADATA_DENYLIST.has(key)) sanitized[key] = value;
  }
  ```
  No recursion. Today no call site nests, so it is harmless — but the function is the security boundary for "no secrets in audit", and the next person to write `metadata: { config: { smtpPass: "..." } }` will leak silently. Either deep-walk the object and strip any matching key at any depth, or assert flat metadata with a runtime check and a Zod-validated `metadata: z.record(z.string(), z.unknown())` shape.

- [ ] **I-10: USER_CREATE on first-user self-registration is attributed to the new user themselves** — `apps/server/src/modules/user/routes.ts:124-133`
  ```ts
  logAuditEvent({
    userId: request.user?.userId ?? user.id,  // ← falls back to the just-created user
    action: "USER_CREATE",
    metadata: { via: "admin", createdUserId: user.id, email: user.email },
  ...
  ```
  For the first-user setup flow (no admin yet, no JWT, `request.user` is undefined), this writes an audit row claiming the new user created themselves and tags it `via: "admin"`. The `via: "admin"` is also factually wrong for the setup path. Either suppress the audit on the bootstrap path, or distinguish: `via: request.user?.userId ? "admin" : "self_setup"` and leave `userId: undefined` when there is no actor.

- [ ] **I-11: No tests cover the retention scheduler at all** — `apps/server/src/modules/audit/retention.scheduler.ts`, `apps/server/src/modules/audit/__tests__/`
  98 lines of timer-driven code with chained setTimeout, WAL check, error handling, mutex-style `currentTimeout !== handle` guard, "skip if zero deleted" branch — zero tests. This is the second piece of timer-based infrastructure in the project (the first is the LDAP scheduler) and it deserves the same treatment as LDAP's scheduler tests: stub timers with `vi.useFakeTimers()`, advance, assert. Especially important given C-3 and C-4.

- [ ] **I-12: i18n key files outside `en-US`/`fr-FR` contain English strings copy-pasted, not translations** — `apps/web/messages/de-DE.json`, `ja-JP.json`, `zh-CN.json`, and others — for example the `audit.*` block in `de-DE.json:799-979`
  Spot-checking `de-DE.json` audit block: every value is in English (`"oldQuota": "Old quota"`). Same for `ja-JP`, `zh-CN`, `ko-KR`, etc. Only `fr-FR` has actual French translations (and `en-US` is the source). 23 locale files were "updated" by adding the English strings as placeholders — the audit feature is, in practice, English-only for 21 languages. The commit message ("feat(web): add audit i18n keys to all locale files") obscures the fact that the strings were not translated. ## Minor

- [ ] **M-1: Type casts on `params` in `useAuditLogs` are unnecessary and unsafe** — `apps/web/src/app/admin/audit/hooks/use-audit-logs.ts:17`
  `queryKey: queryKeys.admin.audit.logs(params as Record<string, unknown>)` — `AuditLogsParams` is already an interface with `string`/`number` fields; the cast loses type safety in the query key. Change the signature of `queryKeys.admin.audit.logs` to accept `AuditLogsParams` (or a generic) and drop the cast.

- [ ] **M-2: Response schema declares `targetType`/`targetId` as `.nullable().optional()` but they are always present** — `apps/server/src/modules/audit/routes.ts:45-46`
  Service returns these fields always (default `null`). Marking them `.optional()` means clients cannot rely on the keys existing. Either drop `.optional()` or guarantee at the service level that they may be undefined.

- [ ] **M-3: `cleanupInterval` and `refreshCleanupInterval` use unguarded `setInterval` without exit-skip** — `apps/server/src/server.ts:119-146`
  Pre-existing pattern, but worth noting: if the previous tick is still running when the next interval fires, the calls can stack. The retention scheduler intentionally uses chained `setTimeout` to avoid that; the login-attempts/refresh-token cleanups use `setInterval` and have no guard. Not introduced by 8.1, but relevant in the same neighbourhood.

- [ ] **M-4: CSV export has no UTF-8 BOM — Excel will mis-render non-ASCII characters** — `apps/server/src/modules/audit/service.ts:287-288`
  Audit logs include user agents, names, file names, error messages with accented characters. Excel on Windows will display them as mojibake without a `\uFEFF` BOM. One-line fix: emit `\uFEFF` before the CSV header line. (CSV viewer in macOS Numbers / LibreOffice handles UTF-8 without BOM, so it's only a Windows-Excel problem.)

- [ ] **M-5: `Array.isArray` boolean rendering uses `.join(", ")` with no localized separator** — `apps/web/src/app/admin/audit/components/audit-metadata-display.tsx:55-56`
  Joining recipient arrays with `", "` is fine for English/Latin scripts, awkward for CJK ("、" is the Japanese serial comma) and RTL languages. Use `new Intl.ListFormat(locale, { style: "long" }).format(value)`.

- [ ] **M-6: `safeTranslate` swallows every error including programmer errors** — `apps/web/src/app/admin/audit/components/audit-log-table.tsx:38-48`, `audit-metadata-display.tsx:23-29`
  ```ts
  function safeTranslate(t, key, fallback) {
    try { return t(key as never); } catch { return fallback; }
  }
  ```
  This is used to handle "unknown action key", which is reasonable. But it masks every error including `next-intl` configuration problems and React errors thrown from within the translation function. Prefer next-intl's first-class missing-message handling (which renders the key by default and emits a console warning) over a try/catch.

- [ ] **M-7: `request.user?.userId` redundant double-read in DELETE trusted device routes** — `apps/server/src/modules/auth/routes.ts:496-504,540-548`
  ```ts
  const userId = request.user?.userId;
  if (!userId) throw new UnauthorizedError(...);
  await authService.removeTrustedDevice(userId, request.params.id);
  logAuditEvent({
    ...
  ```

  Use the local `userId` variable to keep behavior identical even if the request object mutates.

- [ ] **M-8: PASSWORD_RESET_REQUEST audits the email even when no account exists** — `apps/server/src/modules/auth/routes.ts:311-316`
  ```ts
  logAuditEvent({
    action: "PASSWORD_RESET_REQUEST",
    ...
    metadata: { email: request.body.email },
  })
  ```
  No userId (correct — preserves the "do not confirm user existence" property at the API surface). But the audit log writes the requested email regardless of existence; an attacker scraping audit logs could enumerate which emails reset-was-attempted-for. With admin-only audit access this risk is low, but combined with the lack of validation that the email exists, the audit becomes a brute-force enumeration aid. Consider hashing the email before audit, or only audit when the user exists.

- [ ] **M-9: `getAuditLogs` typescript return type narrows incorrectly when JSON.parse throws** — `apps/server/src/modules/audit/service.ts:233-243`
  ```ts
  try { return { ...log, metadata: JSON.parse(log.metadata) as unknown }; }
  catch { return { ...log, metadata: log.metadata }; }  // ← string, but typed as `unknown`
  ```
  The catch returns the raw string. The return type is `metadata: unknown` so this is type-safe, but the route serializer at routes.ts:44 declares `metadata: z.unknown().nullable()` and there is no schema-level catch. A malformed metadata in DB → JSON.parse throws → raw string forwarded → frontend's `AuditMetadataDisplay` calls `Object.keys(metadata)` on a string → `Object.keys("foo")` returns array indices and renders character-by-character. Either reject malformed metadata at write time (Zod-validate in `sanitizeMetadata`), or normalize to `null` on parse error and log a warning.

- [ ] **M-10: `await new Promise(setTimeout)` test wait in share-audit integration test is racy** — `apps/server/src/__tests__/share-audit.integration.test.ts:132,169,199`
  Pattern:
  ```ts
  await new Promise((resolve) => setTimeout(resolve, 50));
  expect(mockAuditCreate).toHaveBeenCalledWith(...);
  ```
  Sleeping 50ms is a CI flake recipe. The audit log is fire-and-forget — the test cannot deterministically wait for it without a hook. Either replace the audit module mock with a `vi.fn().mockImplementation(...)` that resolves a deferred promise and `await` that promise, or restructure the route to expose a "done" hook in test mode. A 50ms sleep on a loaded CI agent regularly fails.

- [ ] **M-11: Magic constant `EXPORT_MAX_ROWS = 100_000` is not configurable and not surfaced to the operator** — `apps/server/src/modules/audit/service.ts:250`
  The 100k cap is hard-coded and silently truncates exports above that without a warning to the client. Refine your date range to export more.") so the operator knows. Today the file just ends.

- [ ] **M-12: `ipAddress: "127.0.0.1"` in LDAP scheduler events conflicts with retention scheduler's `"system"` (confirmed)** — `apps/server/src/modules/ldap/sync.service.ts:112,146` vs `apps/server/src/modules/audit/retention.scheduler.ts:35`

- [ ] **M-13: `findShareById` is called twice on every share access for non-creators** — `apps/server/src/modules/share/service.ts:163,222`
  Reads the share once at the start, runs the password/expiration/view checks, increments views via repository, and then calls `findShareById` a second time to get the fresh state. Two DB round-trips per share view in a hot path (and audit-write). Either merge the increment into a single transaction that returns the updated state, or read once and apply the +1 in memory for the response.

## Strengths

A few things are well done and worth keeping:

- The composite index `@@index([targetType, targetId, action, createdAt])` on `AuditLog` (`schema.prisma:411`) is the right shape for "all events touching entity X" analytics queries — those are exactly the use cases 8.2 (notifications) needs.
- The fire-and-forget pattern `logAuditEvent({...}).catch((err) => getLogger().error({err}, "..."))` is used consistently across every audit call site — audit failures cannot break the user request. Good discipline.
- Service- and route-level integration tests (`audit-logs.integration.test.ts`) exercise the actual `app.inject()` request pipeline, including the JWT/cookie/admin-validation stack — the file's comments about "Item 6: do NOT mock validateTokenVersion" demonstrate awareness that mocked auth tests give false confidence.
- The metadata denylist (`service.ts:130-142`) is in the right place and covers the obvious sensitive keys. Combined with the integration test that asserts every key is stripped (`service.test.ts:61-90`), this is solid.
- The decision to make `userId` on `AuditLog` nullable (no FK) is correct — audit logs must survive user deletion. Documenting that in the schema with a `// no FK by design` comment would help future readers.
- WAL-mode check at boot (`retention.scheduler.ts:84-92`) with a clear warning if the journal mode is wrong is exactly the right safety net for the audit write volume.
- Streaming the export with an async generator (rather than buffering 100k rows in memory) is the right architectural choice; the implementation details (cursor pagination, CSV escaping, error handling) are what need fixing.

## Assessment

**Ready to merge?** **No — fixes required.**

**Reasoning:**
- **C-1 (date filter)** breaks the most-used UI feature of the entire 8.1 page. The user-facing audit filtering and the user-facing export are both unusable today.
- **C-2 (invite token leak)** is a security defect that survives token use (the token stays in the audit log for ≥365 days). The fix is mechanical but unambiguous.
- **C-3 (fake batching)** misleads operators and reviewers — the test passes; the production behavior is "one giant DELETE under the writer lock." It needs to be fixed or the abstraction removed; the test that asserts impossible behavior needs to go either way.
- **C-4 (no first-run)** means retention silently does not work on any host that restarts more than daily. For a self-hosted product that is the modal deployment.

The Important findings are mostly fixable in an afternoon and are mostly self-contained (filter category, hardcoded English, CSV escaping, scheduler tests, denylist nesting). The Minor findings are polish that can land in a follow-up. None of the audit events themselves are wrong in their write path — the schema, the service, the routes, and the fire-and-forget pattern are sound. The defects are concentrated in: (1) the export path, (2) the retention scheduler, (3) the front-end filter wiring, and (4) one secret-handling regression.

Recommendation: address C-1 through C-4 and I-1 (user filter category) and I-12 (i18n truth-in-advertising) before merging. The rest can be a fast follow-up PR.
