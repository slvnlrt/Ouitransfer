# 8.2 Review — Server Integration Layer

**Reviewer:** Code quality agent
**Date:** 2026-05-28
**Scope:** Share/file/notification routes, migration, schema, integration tests
**Git range:** `12a11a0..830f35a`

## Strengths

- **Visitor tracking is fire-and-forget** (`share/service.ts:299-311`, `file/routes.ts:933-955`) — `prisma.shareVisit.create()` is not awaited, so it does not block the response. Same for `lastDownloadedAt` updates and `share_accessed` / `share_downloaded` email sends. Good.
- **Recipient upsert in `updateShare()` is wrapped in a `$transaction`** (`share/service.ts:355-377`) and correctly preserves `trackingToken`, `notifiedAt`, `lastAccessedAt`, `accessCount` for existing recipients. Tests in `migration.test.ts` cover this.
- **Identification rate-limiting** (`share/routes.ts:771-776`) — 30/hr per `ip:alias`, matches spec.
- **`@@unique([shareId, email])` on `ShareRecipient`** (`schema.prisma:160`) is in place, making the upsert sound.
- **Owner exclusion is correctly implemented** — both in `share/service.ts:184-188` (early return before view increment/tracking) and `file/routes.ts:929,1091` (`isOwner` check via `request.jwtVerify()` inside the tracking branch).
- **`shareId` validation in download tracking** (`file/routes.ts:910-918`, `1072-1080`) verifies via `files: { some: { id: fileRecord.id } }` that the file actually belongs to the claimed share. The test `"does NOT create ShareVisit when shareId is provided but file does not belong to share"` (`visitor-tracking.test.ts:554-576`) confirms this.
- **Tracking token visit recording correctly checks `recipient.shareId === share.id`** (`share/service.ts:280`) — a token from another share will NOT credit a visit. Test at `visitor-tracking.test.ts:332-370` covers this.
- **Unsubscribe POST is CSRF-exempt** (`notification/routes.ts:208`) — required for the RFC 8058 List-Unsubscribe-Post flow. Test verifies (`routes.test.ts:544-558`).
- **`notifiedForExpiration` is reset only when expiration is extended** (`share/service.ts:386-391`), not when shortened. Three dedicated tests in `share-update-expiration.test.ts` confirm.
- **Type-safe payloads** flow through `emailService.send()` (catalog-derived `EmailPayloads`). The four migrated callers (`auth/service.ts:193`, `ldap/sync.service.ts:384`, `reverse-share/upload.service.ts:466`, `share/service.ts:658`, plus `file/routes.ts` for downloads) all use the new API and the old `EmailService` class is gone.
- **23 integration tests in `notification/__tests__/routes.test.ts`** exercise the full Fastify lifecycle including CSRF, JWT, admin checks, idempotency, and error pages.

## Issues

### Critical

- [x] **C-1: Tracking tokens leaked to anonymous visitors via share response** — `share/dto.ts:142`, `share/service.ts:104-110`
  `ShareResponseSchema.recipients[].trackingToken` is exposed unconditionally. `formatShareResponse()` returns ALL recipient fields, including `trackingToken`, in the response sent by `GET /shares/:shareId`, `GET /shares/alias/:alias`, and `POST /shares/alias/:alias/access`. These endpoints are public — any anonymous visitor who knows a share alias gets ALL recipient emails AND all their tracking tokens. With a tracking token, the visitor can then access the share as that recipient (registered as such in `ShareVisit`, recipient `accessCount` incremented). This is a recipient PII leak (emails) plus identity-spoofing in the activity log.
  **Fix:** Strip `recipients` (or at minimum `trackingToken` and `email`) from `formatShareResponse()` when `userId !== share.creatorId`. Two response shapes (public vs owner) keep the schema explicit.

- [x] **C-2: Identification gate bypassed by tracking token from a DIFFERENT share** — `share/service.ts:240-246`
  ```ts
  const recipient = await prisma.shareRecipient.findUnique({
    where: { trackingToken: context!.trackingToken },
  });
  tokenSatisfiesRequirements =
    (share.nameFieldRequired !== "REQUIRED" || !!recipient?.name) &&
    (share.emailFieldRequired !== "REQUIRED" || !!recipient?.email);
  ```
  No check that `recipient.shareId === share.id`. Any tracking token from any share — possibly one the visitor was legitimately invited to elsewhere — passes the `IDENTIFICATION_REQUIRED` gate on a share that has `nameFieldRequired = REQUIRED` or `emailFieldRequired = REQUIRED`. The visit-recording path on line 280 correctly checks `shareId`, but the gate does not. The integration test at `visitor-identification.test.ts:371-393` only validates same-share tokens; no cross-share negative test exists.
  **Fix:** Add `&& recipient?.shareId === share.id` to the `tokenSatisfiesRequirements` predicate, and add a regression test.

- [x] **C-3: Visitor identification cookie not re-validated against current share requirements** — `share/routes.ts:31-46`, `share/service.ts:236, 248`
  `parseVisitorCookie()` returns `{ alias, name?, email? }` and the gate at line 248 only checks `!!context?.visitorCookie`, not whether the cookie's content satisfies the CURRENT `nameFieldRequired`/`emailFieldRequired`. Concrete attack: creator publishes share with `nameFieldRequired = OPTIONAL`. Visitor calls `/identify` with empty body → gets a cookie with `name = null`. Creator later tightens to `nameFieldRequired = REQUIRED`. Old cookie still bypasses the gate, even though the visitor never provided a name.
  **Fix:** In the gate, require that `visitorCookie.name` is non-null/empty when `nameFieldRequired === "REQUIRED"`, and same for email. Cookie content must match current share requirements, not just exist.

- [x] **C-4: `share_expired` and `share_expiring` are mutually exclusive via a single flag** — `email/notification.scheduler.ts:62-65, 85, 110-113`
  Both `checkExpiringShares()` and `checkExpiredShares()` set `notifiedForExpiration: true` after sending, and `checkExpiredShares` selects `where: { notifiedForExpiration: false }` (line 85). Consequence: once a share has been notified as "expiring," it can never be notified as "expired." The user gets the warning but never the actual expiration. If `EXPIRY_WARN_DAYS = 3` is bypassed (e.g., share created with `expiration < now + 3 days`), the share goes straight from `notifiedForExpiration=false` to `share_expired` and the user never gets the warning either — but that's the expected case. The bug is the *first* path: expiring → expired transition is broken.
  Additionally, `Share.notifiedForExpiration` is reset in `updateShare` only when `newExp > share.expiration` (extension). So a share that was warned ("expiring") will never re-fire "expired" even after it actually expires.
  **Fix:** Either two flags (`notifiedForExpiring`, `notifiedForExpired`) or a single state enum (`"none" | "warned" | "notified-expired"`). Update the scheduler queries accordingly.

- [x] **C-5: `reverse_share_expired` re-sends forever on every scheduler tick** — `email/notification.scheduler.ts:223-258`
  `checkExpiredReverseShares` queries `expiration: { not: null, lt: now }` with NO `notifiedFor*` predicate, no per-job cooldown gate (the catalog `cooldownSeconds` covers same-recipient + same-shareId, but `shareId` isn't passed in the reverse-share send call at line 202/242 — only `userId`). Every scheduler tick (default 30s? or however the notification scheduler is wired) hits every expired reverse share and queues another email. For a workspace with N expired reverse shares, the user gets ⌈N/30s⌉ emails per second forever. Same problem in a milder form for `checkExpiringReverseShares` (which doesn't update any flag either).
  **Fix:** Add `notifiedForExpiration` (or equivalent) to the `ReverseShare` schema, mirror the Share scheduler logic, and reset on `expiration` extension. (Note: notification scheduler interval is not visible in this scope, but `runAllChecks` is presumably called at least daily; even hourly polling produces a flood.)

### Important

- [x] **I-1: `notifyOnDownload` flag upgrades `share_accessed` notifications, not just downloads** — `email/service.ts:271-279`
  `resolveFrequency()` upgrades ANY non-critical type to `"immediate"` if `share.notifyOnDownload === true` and a `shareId` is passed. The `share_accessed` notification (`share/service.ts:315-330`) passes `shareId`, so a share with `notifyOnDownload=true` AND a user preference of `disabled` for `share_accessed` will *also* upgrade `share_accessed` to immediate. The field is named after a download, but it overrides access notifications too. UI users will be surprised: "I enabled notifications on download, why am I getting emails every time someone *views* my share?"
  **Fix:** Scope the upgrade to `type === "share_downloaded"` only. If broader per-share overrides are desired, add a separate flag (`notifyOnActivity`) — but YAGNI says start narrow.

- [x] **I-2: HTML pages in unsubscribe routes lack escaping of interpolated values** — `notification/routes.ts:42-103`
  `renderConfirmPage(token, type)` interpolates both `token` and `type` raw into HTML:
  ```ts
  <div class="type-badge">${type}</div>
  <input type="hidden" name="token" value="${token}" />
  ```
  Today both come from a JWT verified by HMAC — `type` is whatever the email service put in the payload, `token` is a base64url JWT. Currently safe. But:
  1. Defense-in-depth: nothing prevents a future caller from passing a `type` with `"` or `<` in it (e.g., a malicious test_email path). If someone adds a notification type that includes user input, this becomes stored XSS.
  2. The form's hidden input value is constructed by string concatenation: if `token` were ever to contain `"`, the form breaks. Currently base64url is `[A-Za-z0-9_-]` only, but the assumption is implicit.
  **Fix:** Use a simple `escapeHtml()` helper or a template literal that escapes. Also missing `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` on these responses — these are admin-trusted pages but it costs nothing to harden them.

- [x] **I-3: Heavy code duplication between `/files/download-url` and `/files/download` download-tracking blocks** — `file/routes.ts:907-977` vs `1069-1139`
  ~70 lines of identical logic: shareWithFile lookup, isOwner check via `request.jwtVerify`, ShareVisit create, share update, emailService send. Two divergent copies = two places to update for future changes (e.g., adding `userAgent` truncation, capturing referer, switching to async). DRY says: extract `trackShareDownload(request, fileRecord, shareId)` into a helper next to `checkFileAccess()`. The fact that I had to verify both copies line-by-line to confirm consistency is the smell.
  **Fix:** Extract a helper. Keep it module-private (not exported).

- [x] **I-4: `notifyRecipients()` is not transactional and can leave partial state** — `share/service.ts:645-683`
  For each recipient: backfill `trackingToken` (DB write), `emailService.send` (DB write — creates EmailJob), set `notifiedAt` (DB write). All three are awaited sequentially per recipient. If `send()` throws after the trackingToken update, the recipient now has a token but no `notifiedAt`. If `notifiedAt` update throws after `send()` succeeds, the email is queued and will be sent, but the UI will show the recipient as "not notified" (since `notifiedAt` is the source of truth for the "notified" indicator — spec section 5, bug fix #3). The test at `migration.test.ts:332-355` covers "continues to next recipient on failure" but not partial-state-per-recipient.
  Also: the loop awaits each recipient sequentially. For a share with 50 recipients, this is 50× (token write + EmailJob insert + notifiedAt write) sequentially. Slow.
  **Fix:** Per-recipient transaction wrapping the three writes, or accept the race as documented behavior. Parallelize via `Promise.allSettled()` if SQLite contention isn't prohibitive (it might be — single-writer DB).

- [x] **I-5: `shareLink` is naively concatenated with `?t={trackingToken}`** — `share/service.ts:656`
  ```ts
  const personalizedLink = `${shareLink}?t=${trackingToken}`;
  ```
  If `shareLink` already contains a query string (e.g., `https://example.com/s/foo?lang=fr`), this produces `https://example.com/s/foo?lang=fr?t=token` — a single malformed URL where `?t=` is part of the path/query value, not a separate param. The route schema requires `z.string().url()` but does not constrain that there is no query string. Today's frontend doesn't add query params, but a future feature might. Also: no URL-encoding of `trackingToken` (which is `base64url`, no need to encode — but the next dev might change token format).
  **Fix:**
  ```ts
  const url = new URL(shareLink);
  url.searchParams.set("t", trackingToken);
  const personalizedLink = url.toString();
  ```

- [x] **I-6: `POST /admin/email/test` hardcodes `locale: "en"`** — `notification/routes.ts:295`
  ```ts
  await emailService.send("test_email", { to, locale: "en", data: {} });
  ```
  The admin sending the test has a `request.user.userId` available; their preferred locale could be loaded. More importantly: admins in non-English deployments testing SMTP would expect to see the email in their language. Minor functional gap, easy to fix.
  **Fix:** Resolve the calling admin's `locale` from the DB (already cached on the User model) and pass that.

- [x] **I-7: `metadata` endpoint exposes `nameFieldRequired` and `emailFieldRequired` to anonymous visitors** — `share/routes.ts:736-764`, `share/service.ts:704-714`
  Not a critical leak, but the metadata endpoint is intended for OG previews and is unauthenticated. Exposing `nameFieldRequired/emailFieldRequired` is harmless info, but conceptually these are share-configuration internals that probably shouldn't leak through the OG endpoint. The frontend identification form, however, *needs* to know whether to show the form before access — currently it must call the heavier `GET /shares/alias/:alias` and parse the 403. Decision needed: either keep the metadata exposure (and document why), or move this to a dedicated `/shares/alias/:alias/access-requirements` endpoint.
  **Note:** this isn't a bug per se, but the metadata endpoint's scope is becoming muddled.

### Minor

- [x] **M-1: `payload.alias === alias` check in `parseVisitorCookie` is the ONLY scoping** — `share/routes.ts:31-46`
  The cookie name itself (`sv_${alias}`) is already alias-scoped, and the cookie path is `/api`. The redundant alias-in-payload check exists. Fine. But `parseVisitorCookie` is invoked only on `GET /shares/alias/:alias` and `POST /shares/alias/:alias/access` — NOT on `GET /shares/:shareId` or `POST /shares/:shareId/access` (the by-ID routes). Identification via cookie works only for alias routes. Not a bug because by-ID routes are typically used by the owner (who is exempt from identification), but worth a comment in the code clarifying the asymmetry.

- [x] **M-2: `share-audit.integration.test.ts` mock is incomplete for new schema fields** — `apps/server/src/__tests__/share-audit.integration.test.ts` (the diff adds `nameFieldRequired`, `creator`, etc., but the new fields are added inline in `makeShare`)
  This is a maintenance hazard: every new field on the `Share` model requires touching this test's `makeShare` helper. The pattern of "manually replicate Prisma model defaults in test mocks" is fragile. Not 8.2-specific, but 8.2 introduces 7 new Share fields and 5 new ShareRecipient fields, each of which had to be added to test mocks individually.
  **Fix (long-term):** A shared `makeShare` / `makeRecipient` factory in `__tests__/fixtures/` that derives defaults from the Prisma schema, plus per-test overrides. Out of scope for 8.2 but worth tracking.

- [x] **M-3: Seed type field uses `"int"` for new keys but existing config keys use `"number"`** — `prisma/seed.js:202-229` vs `:86-95, 98-101, 104-107`
  ```js
  // Existing:
  { key: "maxLoginAttempts", value: "5", type: "number", group: "security" }
  // New:
  { key: "emailQueueIntervalSeconds", value: "30", type: "int", group: "email", isSystem: true }
  ```
  The `AppConfig.type` field is not parsed anywhere — values are always read as strings. So this is purely cosmetic. But inconsistency creates confusion. Either standardize on `"number"` (matches existing) or, if `"int"` is intentional to distinguish from float, update the existing entries too.
  **Fix:** Use `"number"` for all five new keys to match existing conventions.

- [x] **M-4: No test of "valid sv_{alias} cookie bypasses identification gate"** — `share/__tests__/visitor-identification.test.ts`
  Tests cover: 403 with no cookie/token, 403 with token but recipient lacks required name, 200 with token + recipient has name. Missing: the happy path of identify-then-access, where the cookie set by `/identify` is sent back and the gate passes. Easy to add: extract the `set-cookie` from the identify response, re-inject on the GET, expect 200.

- [x] **M-5: `notification/routes.ts` admin stats endpoint doesn't include `digest_pending` jobs** — `notification/routes.ts:236-267`
  Three counters: pending, sentLast24h, failed. Catalog includes `digest_pending` status (per spec section 4 + schema status field comment). Currently always zero (digest not implemented), but if/when digest is enabled, admin stats will silently underreport queue depth. Trivial future-proofing.
  **Fix:** Add `digestPending` counter, or include `digest_pending` in the `pending` counter with a clear semantic.

- [x] **M-6: `POST /notifications/unsubscribe` has no rate limit** — `notification/routes.ts:205-231`
  An attacker who somehow obtains a valid unsubscribe token can POST it repeatedly — each call is an `upsert` to `frequency: "disabled"` (idempotent), so no state corruption, but DB write storm is possible. Unlikely scenario but trivial to harden. Same goes for the GET endpoint, which doesn't write but does HMAC-verify (CPU cost is negligible per request, but...).
  **Fix:** Apply the same rate limit pattern used on `/identify` (`max: 30, timeWindow: "1 hour"`, key on IP).

- [x] **M-7: `findShareByAlias` repository method omits `alias` in include but `findShareById` includes it** — `share/repository.ts:185-224` vs `:121-155`
  Inconsistency. Currently masked because `getShareByAlias` in the service first resolves the alias-to-shareId, then calls `getShare(shareId)` which goes through `findShareById` (with alias included). But `findShareByAlias` returns a partial shape that doesn't match the type returned by `findShareById` (the IShareRepository interface declares the alias-less return type for `findShareByAlias` on line 45-54, but most callers expect alias). Minor type smell.
  **Fix:** Add `alias: true` to the include in `findShareByAlias`, and update the interface return type to match.

- [x] **M-8: Anonymous owner of share treated as visitor** — `share/service.ts:184-188`
  Spec section 5 acknowledges this: "If the owner accesses the share while logged out, the server treats them as an anonymous visitor." This is intentional per spec, but worth flagging in code (a comment near the `isOwner` check) so future maintainers don't try to "fix" it via cookie/fingerprint inference.

- [x] **M-9: `share_accessed` notification's `visitorName`/`visitorEmail` payload can be undefined** — `share/service.ts:323-325`
  The schema (Zod) for `share_accessed` payload should declare these as optional. If they're not optional, runtime emails for anonymous visitors will fail render. I haven't read `templates/share-accessed.ts` so this may already be handled — flagging for verification.

## Assessment

**Not ready to merge — fix C-1 through C-5 before shipping.**

The integration layer is largely correct and well-tested (notably: visit recording, owner exclusion, recipient upsert, identification flow). However, two of the five Critical findings (C-1 leaking tokens, C-2 cross-share token bypass) are direct security regressions introduced by this batch, and the test suite does not cover them. C-3 (cookie not re-validated) is a logical hole in the identification gate. C-4/C-5 (notification flag mismanagement) will produce either silent missing emails (C-4) or email floods (C-5) in production — both visible to users.

The Important findings (notifyOnDownload bleeding across types, HTML escaping, code duplication, partial-state in notifyRecipients, URL concatenation) are real issues that should be fixed in this PR rather than deferred. None blocks compile or test pass, but each is a known foot-gun the team is currently agreeing to step on.

The Minor findings are polish — fix during the cleanup pass or defer with explicit acknowledgment.

The most concerning observation is methodological: the test for "tracking token from a different share" exists for the *visit-recording* path (`visitor-tracking.test.ts:332-370`) but the analogous test for the *identification-gate* path is absent. The two code paths read the same `findUnique({ trackingToken })` lookup; only one of them validates `shareId`. A reviewer who only tested same-share scenarios would miss it. This suggests the test was written from the "happy path + obvious negative" template, not from a security-threat-model template. Recommend a regression-testing pass focused specifically on "untrusted input passes one check but bypasses another."
