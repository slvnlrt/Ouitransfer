# 8.2 Email Notifications — Server Integration Review (Pass 7)

**Date**: 2026-05-31
**Reviewer**: Agent (Server Integration)
**Scope**: apps/server/src/modules/share/, file/, reverse-share/, user/, auth/, ldap/

This review focuses exclusively on how business modules call the email/notification
system (`emailService.send` / `emailService.sendToAdmins`): payload correctness,
guard logic, notification triggers, and error handling. The internal email module
(queue, catalog mechanics, templates, i18n) is out of scope — it is covered by the
Server Core review.

Every finding below was checked against the actual source lines. Several candidate
findings were investigated and **discarded as false** after reading the code (noted
at the end for transparency).

---

## Critical

None.

The core integration is sound. Payload shapes match the catalog Zod schemas, owner
exclusion and deactivated-user guards are consistently applied, fire-and-forget
patterns catch errors, and the `notifyOnDownload` per-share override resolves
correctly (creator-facing callers pass `relatedId: shareId`, which `send()` forwards
to `resolveFrequency(type, userId, shareId)`).

## Minor

### ~~M-1~~ [x]: `reverse_share_uploaded` second-batch notifications are silently dropped by the 300s cooldown

- **File(s)**: `apps/server/src/modules/reverse-share/upload.service.ts:447-528`,
  `apps/server/src/modules/email/catalog.ts:456-460`
- **Description**: The upload service debounces notifications over a 5-second window
  (`addFileToUploadSession`, `setTimeout(..., 5000)` at line 519) and batches all files
  from a session into a single `reverse_share_uploaded` send. The catalog independently
  sets `cooldownSeconds: 300` on this type. Combined: if a second, distinct upload
  session lands between 5 seconds and 5 minutes after the first, its batched
  notification is suppressed by the cooldown in `send()` and the creator is **never**
  told about those later files (there is no flag/reset/retry mechanism, unlike
  `share_expiring` etc., and the files are not folded into a later digest). The
  `ReverseShareFile` rows are still created, so the data is visible in the dashboard;
  only the email is lost. This is documented as an intentional anti-flood tradeoff in
  the catalog comment (lines 456-459), so it is flagged as Minor / awareness rather than
  a defect. The spec (Section 10, type 13) describes the trigger simply as "Files
  uploaded to reverse share" without noting the rapid-successive-session drop.
- **Expected**: Either the creator is eventually notified of all uploaded files, or the
  drop is an accepted, documented product decision (currently documented only in code
  comments).
- **Fix**: If undesirable, accumulate pending file names across the cooldown window
  rather than per-debounce-session, or rely on the 5s debounce alone and drop the 300s
  cooldown. Otherwise, surface the limitation in the spec so it is not mistaken for a
  regression later.

### ~~M-2~~ [x]: `share_downloaded` / `share_accessed` cooldown is per-share, suppressing notifications about *different* visitors

- **File(s)**: `apps/server/src/modules/file/routes.ts:226-239`,
  `apps/server/src/modules/share/service.ts:382-388`,
  `apps/server/src/modules/email/service.ts:179-198`
- **Description**: Both triggers pass `relatedId: shareId`. The cooldown in `send()` is
  keyed by `(type, to, relatedId)` — per-share, not per-visitor. So if visitor A
  downloads at T0 and visitor B downloads at T0+5min, the owner is notified about A but
  **not** about B (B's notification, carrying B's identity, is suppressed). The
  `notifyOnDownload` per-share override bypasses the cooldown (`skipCooldown` when
  `overridden`), so owners who opted into "notify on each download" still receive every
  one — but the user-preference `immediate` path (without the per-share toggle) is
  subject to this. The `ShareVisit` row is still recorded for B (tracking is
  independent of notifications), so the activity log is complete. This is explicitly
  documented as intentional in `service.ts:173-178`. Flagged as Minor for awareness.
- **Expected**: Acceptable per the documented design; no change required unless
  per-visitor notification granularity is later desired.
- **Fix**: None required. If per-visitor segregation is wanted, include the visitor
  identity (e.g. `visitorEmail`/`recipientId`) in the cooldown scope, at the cost of
  more emails.

## Positive Observations

- **Consistent owner/deactivation guards**: Every creator-facing trigger
  (`share_accessed`, `share_downloaded`, `share_max_views_reached`, all five scheduler
  notifications, and `reverse_share_uploaded`) checks
  `creatorId && creator.email && isActive !== false` before sending. The
  `notifyShareCreator` helper (`share/service.ts:137-160`) centralizes this for the
  share paths; `file/routes.ts:218-222`, `reverse-share/upload.service.ts:466-472`, and
  the scheduler's `creator: { isActive: true }` WHERE clauses
  (`notification.scheduler.ts:42, 98, 156, 219, 268`) mirror it. Deactivated owners
  correctly receive no activity emails.

- **Owner exclusion is correct and JWT-based**: Both the access path
  (`share/service.ts:230`) and the download path (`file/routes.ts:169-171`) exclude the
  owner via `requestUserId === creatorId`, matching the spec's "owner exclusion" rule
  (Section 5). `trackShareDownload` is only invoked when `shareId` is supplied
  (`file/routes.ts:1020-1024, 1117-1121`) and bails early for owners — so no
  `ShareVisit`, no `lastDownloadedAt` update, and no notification for owner
  self-downloads. This is exactly what the inactivity-alert feature requires.

- **Flag-after-enqueue with compare-and-set**: `share_max_views_reached`
  (`share/service.ts:394-413`) only flips `notifiedForMaxViews` *after*
  `result.enqueued === true`, using `updateMany({ where: { …, notifiedForMaxViews:
  false } })` compare-and-set. The scheduler flags
  (`notifiedForExpiring`/`notifiedForExpired`/`inactivityAlertSent`) follow the same
  enqueue-then-flag pattern (`notification.scheduler.ts:71-76, 123-128, 188-193,
  240-245, 289-294`). This correctly prevents both duplicate sends and the inverse bug
  of marking-as-notified when SMTP is disabled (`send()` returns `enqueued: false`).

- **Visit-before-notify ordering**: Both access and download paths await the
  `ShareVisit` insert and `return` early if it fails, so the owner is never notified
  about an activity that was never recorded (`share/service.ts:363-379`,
  `file/routes.ts:189-205`). Correct ordering discipline.

- **Payload/schema conformance verified**: All `data` objects passed to `send()` match
  their catalog Zod schemas, including the strict `isoDateString` fields — every date is
  passed via `.toISOString()` (`accessedAt`, `downloadedAt`, `expiresAt`, `expiredAt`),
  which satisfies `z.string().datetime({ offset: true })`. Numeric fields (`maxViews`,
  `inactivityDays`, `fileCount`) and `fileNames` (non-empty array, schema `.min(1)`) are
  correctly typed at the call sites. The `test_email` send
  (`notification/routes.ts:424-428`) passes `data: {}`, which satisfies `testEmailSchema`
  (`testMessage` optional).

- **External-invitation locale/userId handling is deliberate and correct**:
  `share_invitation` (`share/service.ts:789-807`) intentionally omits `userId` (external
  recipients have no account / preference row) and uses the sender's locale as the best
  available signal, with a clear explanatory comment. `notifiedAt` is set only when
  `result.enqueued` is true (lines 809-814), so the UI "notified" indicator never lies
  about a send that was skipped (SMTP off) or rejected (invalid payload).

- **Password reset correctly bypasses preferences and preserves anti-enumeration**:
  `auth/service.ts:192-209` omits `userId` for the critical `password_reset` type and
  wraps the send in try/catch with an explicit comment that throwing would leak account
  existence — so a send failure does not change the 200 response.

- **LDAP path is consistent with the rest**: `ldap/sync.service.ts:381-407` fans out
  `admin_user_registered` via `sendToAdmins` (each admin's preference checked
  individually) and sends the `welcome` email with `locale: newUser.locale ?? "en"` and
  a robust `userName` fallback (`… || newUser.username`). Both are wrapped to be
  non-fatal so a notification failure never aborts the sync.

- **Scheduler `userId` is always passed for creator notifications**, enabling the
  preference cascade and unsubscribe-link generation for the configurable lifecycle
  types (`share_expiring`/`share_expired`/`share_no_activity`/`reverse_share_*`). The
  reverse-share scheduler correctly passes `userId: rs.creatorId`
  (`notification.scheduler.ts:234, 283`).

- **Account lifecycle payloads are correct**: `account_reactivated`
  (`user/service.ts:126-136, 172-182`) passes `{ firstName, loginUrl }` and
  `account_deactivated` (`user/service.ts:142-151, 197-206`) passes `{ firstName }`,
  both matching their schemas. `firstName`/`lastName` are guaranteed non-empty by
  `RegisterUserSchema` (`.min(1)`), so the `admin_user_registered` `userName` build in
  the local path (`user/service.ts:66`) cannot produce an empty/malformed name.

## Investigated and Discarded (False Positives Avoided)

For transparency, these candidate findings were checked against the source and found
to be **non-issues**:

- *LDAP welcome email ignores locale* — FALSE. `sync.service.ts:401` uses
  `locale: newUser.locale ?? "en"`.
- *LDAP admin notification drops `lastName`* — FALSE. `sync.service.ts:383-384`
  includes both names with a `username` fallback.
- *Dead `result2` placeholder in admin test-email handler* — FALSE. No such code exists;
  the handler (`notification/routes.ts:418-436`) is clean and returns the real result.
- *Unused `resolveAppName()` in UserService* — FALSE. No such method exists; `appName`
  resolution is correctly centralized inside `emailService.send()`.
- *Local-registration `admin_user_registered` produces empty/double-spaced `userName`* —
  FALSE. `RegisterUserSchema` requires non-empty `firstName` and `lastName`
  (`user/dto.ts:4-5`), so the simple template join is always well-formed.
