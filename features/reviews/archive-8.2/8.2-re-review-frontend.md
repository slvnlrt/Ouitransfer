# 8.2 Re-Review — Frontend

**Reviewer**: AI Agent (principal-level pass)
**Date**: 2026-05-29
**Scope**: Share modals, identification, notification preferences, activity section, recipient selector, types, download cache, settings integration
**Baseline**: First-pass review `8.2-review-frontend.md` (all C/I/M items marked checked) — this pass re-verifies fixes and looks for issues missed the first time.

## Summary

Most of the first-pass findings landed correctly. **C-1** (password + identification combo) and **C-2** (download cache key) are real fixes — verified by reading `use-public-share.ts:70-73, 110-116` and `download-url-cache.ts:21-29` respectively. The locale BOMs are gone (all 23 files start with `7B 0A 20`). The duplicated privacy section is extracted (`share-privacy-section.tsx`). The identification form has validation, an actual `<form>` element, and a loader while metadata loads. ICU plural is applied for `recipientSelector.views`. Activity uses `next-intl` `useFormatter().relativeTime`. The notification preferences page surfaces errors and a Save spinner. The email admin section is gated by `smtpEnabled && !collapsedGroups["email"]`.

That said, this pass uncovered a handful of new issues — most importantly:
- **`IdentifyVisitor200` type contract drift** that the first review missed (server returns `{ success: boolean }`, client declares `{ message: string }`).
- **Dead loader branch in `share-details-modal.tsx`** caused by an early `if (!share) return null;` that short-circuits the JSX path supposed to render a `Loader`.
- **`identification-form` infinite loader when `metadataQuery` fails** — no error state is surfaced, so the form stays a spinner forever.
- **Empty-password protection footgun in `share-item-modal`** — toggling password protection without typing a password silently creates a share with no password (server treats `""` as falsy in `service.ts:157`). The bulk modal has this check, the single modal doesn’t.
- **Rate-limit error from the visitor-identification endpoint is not surfaced** — after 30 attempts/hour, all submissions show the same generic toast.

None are show-stoppers, but the first three meaningfully degrade UX and the fourth is a small but real security/UX regression versus the bulk modal. Overall the second-pass fixes are good; the remaining issues are confined to error-path UX, one new type drift, and a couple of i18n/state-cleanup loose ends.

## Findings

### Critical

None found.

The two original Critical items (C-1 password+identification stuck loop, C-2 download cache `shareId` leak) are correctly fixed:

- `use-public-share.ts:110-116, 70-73` — on a password-mutation error with code `IDENTIFICATION_REQUIRED`, the hook now stores the accepted password (state + ref) and invalidates the query; the derived `isIdentificationModalOpen` flips on (`acceptedPassword !== null && isPasswordRequired(shareQuery.error)` is the defensive OR, and the refetch will normally surface `IDENTIFICATION_REQUIRED` directly so the primary branch fires). Verified the password ref pattern avoids the stale-closure trap during refetch.
- `download-url-cache.ts:21-29` — `shareId` is now part of `getCacheKey`. Cross-share leakage and missing audit/notification rows are fixed.

### Important

#### I-1: `IdentifyVisitor200` type drift — server returns `{ success: boolean }`, client declares `{ message: string }`
- **File**: `apps/web/src/http/endpoints/shares/types.ts:241-243` vs `apps/server/src/modules/share/routes.ts:795-798`
- **Description**: Server response schema for `POST /shares/alias/:alias/identify` is `z.object({ success: z.boolean() })`. The client type declares `interface IdentifyVisitor200 { message: string }`. Today nothing reads the response body (`use-public-share.ts:131` awaits but discards it), so this is silent — but it is a type-contract lie of exactly the same shape the first review's I-3 table called out.
- **Impact**: Any future caller that reads `response.data.message` will get `undefined` at runtime. Static analysis will not catch it.
- **Suggested fix**: Change client interface to `{ success: boolean }`. The first review's "drift summary" table should be amended to include this row.

#### I-2: `share-details-modal.tsx` dead loader branch — modal never appears while data is loading
- **File**: `apps/web/src/components/modals/share-details-modal.tsx:192` and `209-212`
- **Description**: `if (!share) return null;` at line 192 short-circuits rendering whenever `shareQuery.data` is undefined. The branch at lines 209-212 (`{isLoading ? <Loader/> : ...}`) is unreachable — when `isLoading` is true, `share` is null and we already returned null at line 192. Result: a parent component that sets `shareId` sees nothing at all until the network round-trip completes, then the modal appears abruptly with content already filled in. No skeleton, no perceived responsiveness.
- **Impact**: Visible UX regression on slower networks; the early-return also defeats the test at line 110-120 in spirit (test passes only because it `waitFor`s the resolved state). Pre-existing pattern but in scope for 8.2 because the activity section was added alongside.
- **Suggested fix**: Replace the early return with a controlled-Dialog pattern:
  ```tsx
  if (!shareId) return null;
  return (
    <Dialog open={!!shareId} onOpenChange={() => onClose()}>
      <DialogContent>…
        {isLoading || !share ? <Loader … /> : <…content…/>}
  ```
  Then guard each `share.foo` access. Alternatively, hoist the "share required" sections behind `{share && (…)}` blocks.

#### I-3: `identification-form.tsx` shows an infinite spinner when `metadataQuery` errors
- **File**: `apps/web/src/app/(shares)/s/[alias]/components/identification-form.tsx:88-91` and `use-public-share.ts:76-84`
- **Description**: The form renders `{!metadata ? <Loader/> : <form…/>}`. If `getShareMetadata(alias)` fails (network drop, server 5xx, even a 404 if the alias was just rotated), `metadata` never transitions away from `null` and the modal is stuck showing a spinner with no feedback or recovery. The hook itself does not surface `metadataQuery.error` to the page either.
- **Impact**: The user is trapped on the identification step with no way to retry or understand what happened. The rate-limited identify endpoint (30/h per IP+alias) plus this stuck state is a particularly bad combination on flaky networks.
- **Suggested fix**: Pass `metadataError`/`metadataIsError` through the hook, surface a toast + "Retry" button in the form when fetch fails, and consider prefetching metadata up-front (it’s a public, cacheable endpoint) so the modal opens populated and avoids the error window entirely.

#### I-4: `share-item-modal.tsx` allows empty password to bypass protection — security/UX footgun
- **File**: `apps/web/src/components/modals/share-item-modal.tsx:411, 148` vs `share-multiple-items-modal.tsx:499-504, 178`
- **Description**: The single-item modal's Create button only checks `!formData.name.trim()`. If the user toggles "Password protection" on but leaves the password field blank, the modal submits `password: formData.isPasswordProtected ? formData.password : undefined` → `password: ""`. The server's `createShare` then evaluates `password ? await bcrypt.hash(...) : null` (`apps/server/src/modules/share/service.ts:157`) → `null`, **silently producing a share with no password while the UI led the user to believe it was protected**. The bulk modal correctly guards against this with `(formData.isPasswordProtected && !formData.password.trim())`.
- **Impact**: A user creates a "protected" share, sends the link to a recipient, expects to communicate the password out-of-band — but the share is in fact unauthenticated. This is precisely the kind of expectation gap that surfaces as a real security incident on the user side. Low-effort fix, high impact.
- **Suggested fix**: Mirror the bulk modal's button-disabled rule in the single modal at line 411:
  ```tsx
  disabled={
    isLoading ||
    !formData.name.trim() ||
    (formData.isPasswordProtected && !formData.password.trim())
  }
  ```
  Also worth adding `aria-invalid` + helper text on the password input to make the requirement obvious.

#### I-5: Identification rate-limit error surfaces as a generic "failed to submit" toast
- **File**: `apps/web/src/app/(shares)/s/[alias]/hooks/use-public-share.ts:138-144` and `apps/server/src/modules/share/routes.ts:773-781`
- **Description**: The identify endpoint applies `rateLimit: { max: 30, timeWindow: "1 hour", keyGenerator: ip+alias }`. After the limit is hit, the server returns 429, which the hook treats as a generic identification error: `toast.error(t("share.identification.error"))`. There is no path for the user to understand they are throttled, no retry-after hint, and combined with the no-dismiss dialog (`onOpenChange={() => {}}`) the user is in a no-exit state.
- **Impact**: A confused visitor making typos in the email field can lock themselves out of the share for an hour with no diagnostic message. Less severe than I-4 but a real dead-end.
- **Suggested fix**: Branch on the error: if it's a 429 (`parseApiError(error).code === ErrorCodes.RATE_LIMITED` or status === 429), toast a specific message ("Too many attempts, please try again later"). Also consider relaxing the keyGenerator (per-IP regardless of alias) or wiring a per-form throttle on the client side to prevent rapid resubmits.

#### I-6: `ShareDetailsActivitySection` silently swallows query errors
- **File**: `apps/web/src/components/modals/share-details/share-details-activity-section.tsx:87-120`
- **Description**: Same pattern as the first-pass I-8 for notification preferences: `visitsQuery.error` is never read. A failure (e.g. user is not the share creator → 403 from `routes.ts:901`, or DB hiccup → 500) renders the "no activity recorded yet" empty-state. The user assumes there is no activity instead of seeing a failure.
- **Impact**: Hides real failures, including 403 / share ownership bugs. Also breaks the audit-trail UX promise of feature 8.2.
- **Suggested fix**: Add an `error && !visitsQuery.data` branch with a destructive-toned message and a Retry button (same shape as the fix in `notification-preferences-table.tsx:194-200`). Bonus: use `placeholderData: keepPreviousData` so paging doesn't blank the list.

#### I-7: `share-item-modal` / `share-multiple-items-modal` leak `isLoading=true` across reopen
- **File**: `apps/web/src/components/modals/share-item-modal.tsx:70-90, 221-240` and `share-multiple-items-modal.tsx:80-117, 239-258`
- **Description**: Neither the `useEffect` on `isOpen` nor `handleClose` resets `isLoading` to `false`. If the user clicks Cancel while `createShare` is in-flight (e.g. slow network), `isLoading` stays `true` after the modal closes. On the next open, the form is rendered but the submit button stays disabled and the spinner glyph displays until the orphaned request resolves — which may not match the current form state at all (the orphaned request will overwrite `shareId`/`step` from the previous attempt).
- **Impact**: Two issues: (a) stuck spinner / disabled submit on reopen; (b) cross-instance state pollution from an orphaned in-flight request finishing after the user has already opened the modal a second time for a different item.
- **Suggested fix**:
  1. Reset `isLoading` in both `useEffect` (on open) and `handleClose`.
  2. Better: convert `createShare` into a `useMutation` and call `mutation.reset()` on close — TanStack Query already handles the lifecycle cleanly.

#### I-8: `truncateIp` leaves most compressed IPv6 addresses fully exposed
- **File**: `apps/web/src/components/modals/share-details/share-details-activity-section.tsx:20-38`
- **Description**: The function only truncates IPv6 when the address has exactly 8 colon-separated groups (full, uncompressed form). Real-world IPv6 addresses almost always contain `::` compression — `2001:db8::1`, `fe80::1`, `2001:db8:abcd:1234::1` all split to fewer than 8 groups and are returned **verbatim**, fully identifying the visitor.
- **Impact**: The visible privacy promise of the activity panel (masking IPs to first-two octets for v4) is broken for any v6 visitor. Public residential IPv6 addresses are a strong PII signal.
- **Suggested fix**: Normalise first. Either expand `::` to full form before truncating, or — simpler — for any `ip.includes(":")` mask everything after the third group:
  ```ts
  if (ip.includes(":")) {
    const groups = ip.split(":");
    const head = groups.slice(0, 3).filter(Boolean).join(":");
    return `${head}::…`;
  }
  ```
  Also unit-test this with `::1`, `fe80::1`, `2001:db8::1`, `2001:db8:1234:5678::abcd`.

#### I-9: Multi-item modal default name and footer summary are hard-coded English
- **File**: `apps/web/src/components/modals/share-multiple-items-modal.tsx:93-98, 437-439`
- **Description**: Two un-i18n'd strings remain after the previous review's M-13:
  - Lines 93-98 build a default share name with literal `"files"`, `"folders"`, `" and "`, `" shared"`. Triggered every time the modal opens with >1 item, in every locale.
  - Line 438-439 appends `({filesList.length} files, {foldersList.length} folders)` to the i18n'd total-size string — half-translated.
- **Impact**: Non-English users see English fragments inside otherwise translated UI. M-13 from the first review only fixed the `Total size:` literal.
- **Suggested fix**: Add ICU plural keys (`shareMultipleFiles.defaultName`, `shareMultipleFiles.itemsBreakdown`) and use them. The hard-coded "Someone" fallback in the server's `notifyRecipients` (`service.ts:658`) is a similar but server-side issue out of scope here.

### Minor

#### M-1: Activity page-end state shows misleading "no activity" when `page > 1` returns empty
- **File**: `share-details-activity-section.tsx:110-114, 122-126`
- **Description**: If `total > 0` but the current `page`'s slice is empty (e.g. items deleted between fetches), the section renders both the "No activity recorded yet" message and "Showing 0 of N". Internally inconsistent.
- **Suggested fix**: When `visits.length === 0 && page > 1`, render a "Page is empty, go back" message and reset to page 1 (or hide the empty-state and just show the pager).

#### M-2: `recipient-selector` duplicate/email validation runs on un-trimmed input
- **File**: `apps/web/src/components/general/recipient-selector.tsx:47-72`
- **Description**: `isValidEmail(newRecipient)` and `recipients.some((r) => r.email === newRecipient)` operate on the raw input. A user typing `"john@example.com "` (with trailing space) gets through the regex check (regex matches even with trailing space? actually `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` rejects whitespace at the end — let me double-check: the final char-class is `[^\s@]+$`, so a trailing space fails. Good.) But on the API call, `emails: [newRecipient]` sends the raw value. If the server doesn't trim, a "ghost" email with whitespace is stored. The "duplicate" check at line 55 also compares raw vs canonical.
- **Suggested fix**: `const trimmed = newRecipient.trim(); …` and use `trimmed` throughout. Same for the email input in `email-admin-section.tsx:31-35` (already trims, good — keep symmetric).

#### M-3: `share-multiple-items-modal` does not reset `formData` on success
- **File**: `share-multiple-items-modal.tsx:155-201` vs `share-item-modal.tsx:128-184`
- **Description**: The single-item modal resets `formData` after a successful create (lines 172-183 in `share-item-modal`). The bulk modal omits this reset. The `handleClose` does clean state but it runs only when the user explicitly closes. Between create-success and close, the form retains the just-submitted values — visible if the user navigates back from the link step.
- **Suggested fix**: Either mirror the reset in the bulk modal, or remove it from the single modal and rely on `useEffect` reset on `isOpen=true`. Pick one; they should match.

#### M-4: `notifyRecipients` server result (`notifiedRecipients`) is discarded by the client
- **File**: `recipient-selector.tsx:107-133` and `apps/server/src/modules/share/service.ts:660-711`
- **Description**: The server returns `{ message, notifiedRecipients: string[] }`. The client only toasts the count of *requested* emails (`emails.length`). If some recipients failed silently inside the server's `for` loop (logged but not propagated), the user thinks "all 5 were notified" when in fact only 3 were.
- **Suggested fix**: Compare `response.data.notifiedRecipients.length` to the requested count and warn when they differ (e.g. "3 of 5 recipients notified, check email logs").

#### M-5: `share-multiple-items-modal` opens with `password: ""` placeholder coupled to switch but no input clear on toggle-off
- **File**: `share-multiple-items-modal.tsx:371-387`
- **Description**: Toggling the password switch off correctly sets `password: ""`. But toggling back on shows the empty field — fine. The bulk modal also has the disable-if-no-password guard (good), but the single-item modal does not (see I-4). Just noting the asymmetry exists across both fields (password validity, name validity, etc.) and should be consolidated when `SharePrivacySection` graduates into a `useShareFormState()` hook (first review's I-1 suggestion).

#### M-6: `getShareByAlias` in `use-public-share.ts:97` resends the password as a body param even on the second invalidation roundtrip
- **File**: `use-public-share.ts:57-66, 95-99`
- **Description**: After the IDENTIFICATION_REQUIRED branch, every refetch of `shareQuery` re-sends the (correct) password to `POST /shares/alias/:alias/access`. Server-side this is fine (it just re-validates), but it does mean we hash the password on every navigation/refetch. Not a bug, but a noticeable round-trip cost on every `invalidateQueries`.
- **Suggested fix**: After a successful password+identification handshake, persist the share data via `setQueryData` rather than re-fetching. Or rely on a stable session-cookie pattern server-side (same `sv_<alias>` cookie now used for identification could also gate password re-entry).

#### M-7: `share-details-modal.tsx` early `if (!share) return null` also masks the `isLoading` test contract
- **File**: `share-details-modal.tsx:192, 209`
- **Description**: Related to I-2 — the existing test `renders share content once the query resolves` passes because of `waitFor`, but there is no test asserting a loader appears during the in-flight window. After fixing I-2, add a test that asserts the loader is visible while the query is pending.

#### M-8: `IdentificationForm.tsx` submit button is disabled on first attempt only after click
- **File**: `identification-form.tsx:152-157`
- **Description**: `disabled={!metadata || isSubmitting || (attempted && !canSubmit)}`. The `attempted &&` guard means on the first click with empty required fields, the button *is* clickable and the validation appears only afterwards. That's intentional (allows users to discover what's required), but for keyboard users hitting Enter it produces a small but real delay because the form's submit handler runs validation server-side anyway (via the dialog form). Consider showing inline asterisks on required labels too so the requirement is visible before submit.

#### M-9: `share-details-modal.tsx` invalidates `queryKeys.shares.all` on every save — broader than needed
- **File**: `share-details-modal.tsx:82-85`
- **Description**: `invalidateShare` calls both `detail(shareId)` and `all`. Invalidating `all` refetches the entire share list, the by-alias queries, the visits query, etc. After every name/description edit. Probably overkill — the list view only needs to update name/description for one row.
- **Suggested fix**: Invalidate `detail(shareId)` and `list()` only. Or use `setQueryData` to surgically patch the list entry.

#### M-10: BOM regression check has no lint guard
- **File**: `apps/web/messages/*.json`
- **Description**: I-6 from the first review was fixed by stripping BOMs, but nothing prevents recurrence on the next Windows-side `Set-Content` typo. Worth adding a quick pre-commit or CI step that asserts the first three bytes of every JSON file are not `EF BB BF`.

#### M-11: `EmailAdminSection` and `notification-preferences-table` use different error-state idioms
- **File**: `email-admin-section.tsx:54-89` (shows `—` on missing data, no explicit error UI) vs `notification-preferences-table.tsx:194-200` (explicit error block with Retry button)
- **Description**: Both are valid, but inconsistent. The stats card showing `—` for both "loading" and "errored" is ambiguous — a user can't tell whether the queue is empty or the API is down.
- **Suggested fix**: Pick one pattern and apply consistently. For stats, a small `(unavailable)` label or a retry icon when `emailStatsQuery.isError` would help.

## Positive Observations

- **`download-url-cache` test surface is the right shape now.** Adding `shareId` to the cache key both fixes the cross-share leak and makes the cache participate correctly in the audit/notification flow. The previous review's recommendation for a unit test is worth following up on if not already done.
- **`SharePrivacySection` extraction is clean.** The `switchIdSuffix` parameter neatly avoids duplicate IDs between the two callers, the Collapsible wrapper is idiomatic Radix, and the type for `SharePrivacyFormData` is exported so any third caller can typecheck against it. This is the kind of extraction CLAUDE.md's DRY-at-second-occurrence rule was written for.
- **Identification form validation is good.** It has actual `<form>` semantics (Enter submits, required attribute works, browser autofill recognizes), client-side validation on required fields, an email regex that matches the recipient-selector regex (consistent), and inline error messages tied to `aria-invalid`. The "attempted" gate is a reasonable UX pattern.
- **Activity section uses `next-intl`'s `useFormatter().relativeTime` correctly.** Locale-aware and handles plurals natively — much better than the original string-template approach.
- **Notification preferences page has proper error + loader states and a Save spinner with `Loader2`.** Matches the email-admin-section's submit pattern.
- **The `acceptedPassword` state + ref pair in `use-public-share.ts`** is a legitimate solution to the stale-closure-during-refetch problem. The inline comment at line 57-58 makes the intent explicit, which is the right call for non-obvious code.
- **Type drift cleanup mostly landed.** `Share.creatorId`, `ShareFolder` (now includes `objectName`, `userId`), and `ShareVisit` (now includes `shareId`, `fileId`, `recipient`) all match the server schemas in `dto.ts`. The new `IdentifyVisitor200` drift (I-1 above) is a regression worth catching next time.
- **The dialog modals correctly use Radix `modal` + `onOpenChange={() => {}}`** to prevent dismissal during forced-identification — accessibility primitives are intact (`aria-modal`, focus trap), only Escape is suppressed.
