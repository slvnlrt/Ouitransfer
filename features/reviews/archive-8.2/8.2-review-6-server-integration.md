# 8.2 Email Notifications — Server Integration Review (Pass 6)

**Date**: 2026-05-30
**Reviewer**: Agent (Server Integration)
**Scope**: apps/server/src/modules/share/, file/, reverse-share/, user/, auth/, ldap/ — integration with email/notification system

Each finding below was verified against the actual code at the cited lines.

## Critical

No findings.

The integration points are sound on the security-critical paths: the identification gate (`getShare`, service.ts:267-287) re-validates cookie content against current share requirements; tracking tokens are bound to the share via `candidate.shareId === share.id` (service.ts:261); `download-url`/`download` validate `shareId` against actual file membership in `trackShareDownload` (file/routes.ts:152-166); visitor cookies are signed and alias-bound (`parseVisitorCookie`, visitor-cookie.ts:37). No auth-bypass or email-injection vector was found (subjects are CR/LF sanitized in service.ts:25-31).

## Important

### ~~I-1~~ [x]: `notifyOnDownload` ("notify me on each download") is silently defeated by the 15-minute cooldown
- **File(s)**: `apps/server/src/modules/email/service.ts:154-173` (cooldown), `apps/server/src/modules/email/service.ts:331-338` (override), `apps/server/src/modules/email/catalog.ts:358-374` (`share_downloaded` has `cooldownSeconds: 900`)
- **Description**: When a share owner enables the per-share `notifyOnDownload` toggle, `resolveFrequency()` correctly upgrades the frequency to `"immediate"`. However, the cooldown check in `send()` runs **unconditionally** for any type with `cooldownSeconds` set, *after* and *independent of* frequency resolution. Because `share_downloaded` has `cooldownSeconds: 900`, only one download notification per share is delivered per 15-minute window — even when the owner explicitly asked to be notified on **each** download.
- **Expected**: Spec Section 6 — "**Notify me on each download** — toggle (overrides global `share_downloaded` preference for this share)." Section 10 also documents the cooldown as a defensive anti-flood measure. The two intents collide and the code resolves it in favor of the cooldown, breaking the user-facing promise of the toggle.
- **Fix**: When the per-share override applies (`notifyOnDownload === true`), bypass the cooldown for `share_downloaded`. Concretely: have `resolveFrequency()` (or a parallel signal) return whether the override forced `immediate`, and skip the cooldown branch when it did. Alternatively, the spec should be amended to state that the cooldown always wins and the toggle merely flips the type from `disabled`→`immediate` (still bounded by 15 min). Either way, code and spec must agree — today they don't.

### ~~I-2~~ [x]: `reverse_share_uploaded` does not skip deactivated creators — inconsistent with all other share notifications
- **File(s)**: `apps/server/src/modules/reverse-share/upload.service.ts:447-484` (`sendBatchFileUploadNotification`, selects `id, email, locale` only)
- **Description**: Every other creator-targeted notification guards against deactivated accounts: `share_accessed` (share/service.ts:346 `share.creator?.isActive !== false`), `share_downloaded` (file/routes.ts:212-216), `share_max_views_reached` (share/service.ts:377-378), and the scheduler queries (`creator: { isActive: true }`). The reverse-share upload notification omits this check entirely — a deactivated creator still receives upload emails. `emailService.send()` itself does **not** check `isActive` (it only runs the preference cascade), so the guard must live in the caller, which it does everywhere except here.
- **Expected**: Consistent behavior — the inline comment in the share path explicitly states "Skip notification when creator account is deactivated (consistent with scheduler checks)". Reverse share should match.
- **Fix**: Add `isActive: true` to the `select` in upload.service.ts:454-457 and return early when `creator.isActive === false` (mirroring file/routes.ts:212-216).

### ~~I-3~~ [x]: `admin_user_registered` is not fired for OIDC/SSO auto-registration or invite-based registration
- **File(s)**: fired only in `apps/server/src/modules/user/service.ts:64-71` (password registration) and `apps/server/src/modules/ldap/sync.service.ts:382` (LDAP). NOT fired in `apps/server/src/modules/auth-providers/user-linking.service.ts:150` (OIDC/SSO user creation) or `apps/server/src/modules/invite/service.ts:85` (invite acceptance).
- **Description**: Two real user-creation code paths create `User` rows without notifying admins. The catalog/spec defines type 20 (`admin_user_registered`) with trigger "New user created/synced" (spec Section 10, row 20). The implementation only covers two of the (at least) four creation paths, so an admin who relies on this notification will miss SSO and invite registrations.
- **Expected**: Spec Section 10 describes a general "user created/synced" trigger; the catalog entry is `configurable`/fan-out to all admins. Coverage should be uniform across creation paths.
- **Fix**: Call `emailService.sendToAdmins("admin_user_registered", { ... })` (fire-and-forget, with the same first-user guard) at the OIDC user-creation site (`user-linking.service.ts`) and the invite-acceptance site (`invite/service.ts`). If these paths are deliberately out of 8.2 scope, document that explicitly in the spec's "OUT of scope" table — currently they are silently uncovered.

## Minor

### ~~M-1~~ [x]: An uploader literally named "Someone" is anonymized in `reverse_share_uploaded`
- **File(s)**: `apps/server/src/modules/reverse-share/upload.service.ts:492` (`uploaderName = fileData.uploaderName || "Someone"`) and `:477` (`uploaderName !== "Someone" ? uploaderName : undefined`)
- **Description**: The sentinel string `"Someone"` is used both as the default-when-absent and as the "treat as anonymous" marker. A real uploader who types "Someone" in the identification form is collapsed into the anonymous branch and rendered with the `bodyAnonymous` template.
- **Fix**: Track presence with a discrete boolean or `undefined` rather than overloading the `"Someone"` string. e.g. keep `uploaderName: fileData.uploaderName ?? null` in the session and branch on `session.uploaderName != null`.

### ~~M-2~~ [x]: Folder-nested files cannot actually trigger `share_downloaded` for anonymous visitors
- **File(s)**: `apps/server/src/modules/file/routes.ts:95-134` (`checkFileAccess`, only `files: { some: { id: fileId } }`, no folder traversal) vs. `:152-164` (`trackShareDownload`, which *does* traverse `folders → files`)
- **Description**: `trackShareDownload` is written to handle files nested in a shared folder (line 157), but `checkFileAccess` — which gates the download before tracking runs — only recognizes files directly attached to a share, not folder-nested ones. For an anonymous visitor downloading a folder-only file, access is denied at `checkFileAccess` (download-url:993 / download:1095) before tracking is ever reached, so the folder branch in `trackShareDownload` is effectively dead for the anonymous case. This is a pre-existing access-model inconsistency surfaced (not introduced) by 8.2's tracking code.
- **Fix**: Out of strict 8.2 scope, but worth a tracked debt item: either extend `checkFileAccess` to recognize folder-nested files, or drop the unreachable folder branch in `trackShareDownload` to avoid implying support that doesn't exist.

### ~~M-3~~ [x]: `share_accessed` notification block is large and inline in `getShare`; duplicated pattern with `share_max_views_reached`
- **File(s)**: `apps/server/src/modules/share/service.ts:344-405`
- **Description**: Two near-identical fire-and-forget IIFE blocks (`share_accessed` and `share_max_views_reached`) each rebuild `shareManageUrl`, repeat the `creatorId && creator?.email && isActive !== false` guard, and log on failure. Not a defect, but the repetition invites drift (e.g. the `isActive` guard already drifted out of the reverse-share path — see I-2).
- **Fix**: Extract a small private helper `notifyCreator(type, share, data)` that centralizes the guard, URL build, and error logging. Reduces the chance of the I-2 class of inconsistency recurring.

### ~~M-4~~ [x]: Stale comment in `getShare`
- **File(s)**: `apps/server/src/modules/share/service.ts:323` — `// Or from identification cookie (Batch 9 will wire this)`
- **Description**: The comment says Batch 9 "will wire" the cookie, but the cookie is already wired (routes.ts:156, 208, 623, 674 → context.visitorCookie) and consumed here. Misleading for future maintainers.
- **Fix**: Remove the "Batch 9 will wire this" qualifier.

## Positive Observations

- **Server-built share links (anti-phishing)**: `notifyRecipients` no longer trusts a client-supplied `shareLink`; it derives the link from the share's own alias via `buildShareLink` (share/service.ts:750-755). This closes the phishing vector from the old MVP API and is a genuine improvement.
- **`notifiedAt` gated on actual enqueue**: `notifyRecipients` only sets `notifiedAt` when `result.enqueued` is true (share/service.ts:801-809), so SMTP-disabled environments don't show false "notified" state. Same discipline applied to all scheduler flag-flips (`notifiedForExpiring`/`notifiedForExpired`/`inactivityAlertSent`) and to `notifiedForMaxViews` with a compare-and-set `updateMany` (share/service.ts:394-399) to prevent duplicate sends under races.
- **Recipient upsert preserves tracking state**: `updateShare` correctly diffs by normalized email and only removes/adds, leaving existing recipients (and their `trackingToken`, `notifiedAt`, `accessCount`) untouched (share/service.ts:430-462) — exactly the spec Section 7 sync semantics, replacing the destructive delete-and-recreate.
- **Owner exclusion and anonymous-owner handling**: `getShare` returns early for the authenticated owner before any visit/notification logic (service.ts:204-206), and the logged-out-owner-as-anonymous behavior is documented and intentional (service.ts:200-202), matching spec Section 5.
- **IP/UA correctly stripped from the visits API**: `GET /shares/:shareId/visits` destructures out `ipAddress`/`userAgent` before serializing (routes.ts:968) and the `share_accessed`/`share_downloaded` payload schemas omit `ipAddress` entirely (catalog.ts:117-132), honoring the spec's privacy note (Section 10).
- **Payload validation at the boundary**: `emailService.send()` validates every payload against the catalog's Zod schema before doing any work (service.ts:97-101), returning `{ enqueued: false, reason: "invalid_payload" }` rather than enqueuing garbage — and render failures produce a permanently-`failed` job with `maxAttempts: 0` instead of retry loops (service.ts:210-231).
- **Graceful shutdown for debounced reverse-share notifications**: `flushPendingNotifications` IS wired to Fastify `onClose` in reverse-share/routes.ts:33-36, so in-flight 5s-debounced upload notifications are not lost on shutdown.
- **No-user-enumeration contract preserved**: `requestPasswordReset` swallows email-send failures (auth/service.ts:203-209) so a misconfigured `appUrl` can't be used to distinguish registered from unregistered emails.
