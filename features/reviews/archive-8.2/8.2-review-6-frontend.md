## Important

### ~~I-1~~ [x]: Activity identity filter is client-side over a single page while pagination uses the server total — broken filter UX and spurious page reset
- **File(s)**: `apps/web/src/components/modals/share-details/share-details-activity-section.tsx:108-126` (and `:117-118`, `:187-189`)
- **Description**: The `action` filter is applied server-side (passed as `actionParam` into `getShareVisits`), but the `identityFilter` ("identified" / "anonymous") is applied **client-side** over `rawVisits`, which is only the current page (`PAGE_LIMIT = 10`). Meanwhile `total` (line 117), `hasMore` (line 118), the "Showing X of Y" counter (lines 187-189), and the auto-reset effect (lines 122-126) all derive from the server's **unfiltered** total. Consequences when `identityFilter !== "all"`:
  - "Showing {shown} of {total}" is misleading — e.g. "Showing 0 of 50" when the current page happens to contain no matching visitors.
  - A page that legitimately contains only anonymous visits (while filtering for "identified") makes `visits.length === 0`; combined with the auto-reset effect at lines 122-126 (`visits.length === 0 && page > 1`), the user is yanked back to page 1, losing their place — even though more matching results may exist on later pages.
  - "Load more" can advance to pages that render empty under the active identity filter.
- **Expected**: Spec Section 8 lists "Filters: by action (access / download), by identified / anonymous" and "Pagination (visits can accumulate)" as a coherent feature. A filter that only inspects the current page is not a working filter once data spans multiple pages.
- **Fix**: Push the identity filter to the server (add an `identified=true|false` query param to `GET /shares/:shareId/visits`, derived server-side from `recipientId || visitorEmail || visitorName`) so `total`/`hasMore`/pagination stay consistent. If a server change is undesirable, at minimum (a) compute `total`/`hasMore`/`showingCount` from the filtered set and (b) remove or guard the auto-reset effect so it cannot fire purely because the active client-side filter emptied the current page.

### ~~I-2~~ [x]: Activity section is rendered unconditionally, not gated by `isOwner` like every other section
- **File(s)**: `apps/web/src/components/modals/share-details-modal.tsx:358` (compare with `:258-259`, `:278`, `:285`, `:292`, `:300`)
- **Description**: Every other editable/owner-only section in `ShareDetailsModal` is gated on `isOwner` (computed at line 208: `!!(user && share?.creatorId && user.id === share.creatorId)`). `ShareDetailsActivitySection` at line 358 is rendered with no gate. The server endpoint `GET /shares/:shareId/visits` returns **403 Forbidden** for non-creators (`apps/server/src/modules/share/routes.ts:942-944`). So whenever this modal is shown for a share the current user does not own (admin viewing another user's share, or any future non-owner entry point), the activity panel issues a request that 403s and renders the `loadError` block with a retry button that will keep failing.
- **Expected**: The activity tab is "visible to creator only" (spec Section 8, item 3). Gating should be consistent with the rest of the modal.
- **Fix**: Wrap the render in the existing owner guard: `{isOwner && <ShareDetailsActivitySection shareId={share.id} />}`.

## Minor

### ~~M-1~~ [x]: Save mutation discards edits made while a save is in flight
- **File(s)**: `apps/web/src/app/notifications/components/notification-preferences-table.tsx:137-141` (with `:259-270`, `:287-290`)
- **Description**: `saveMutation.onSuccess` calls `setLocalChanges({})` unconditionally, clearing the entire pending-changes map. The Save button is disabled during `saveMutation.isPending` (line 289), but the frequency `<Select>` controls are **not** disabled (lines 259-270). A user can change a dropdown while the save request is in flight; that new change lands in `localChanges` and is then silently wiped by `onSuccess` without ever being persisted.
- **Expected**: No silent loss of user input.
- **Fix**: Either disable the `<Select>` controls while `saveMutation.isPending`, or on success remove only the keys that were actually submitted (e.g. capture the submitted change set and `setLocalChanges(prev => omit(prev, submittedKeys))`).

### ~~M-2~~ [x]: `beforeunload` guard omits `returnValue`, so the unsaved-changes prompt is unreliable
- **File(s)**: `apps/web/src/app/notifications/components/notification-preferences-table.tsx:112-119`
- **Description**: The handler only calls `e.preventDefault()`. Several browsers (notably older Chrome/Safari behaviors) require `e.returnValue = ""` to actually trigger the native "leave site?" confirmation. As written, the dialog may not appear, undermining the intended unsaved-changes protection.
- **Expected**: A reliable unsaved-changes prompt across browsers.
- **Fix**: Add `e.returnValue = "";` inside the handler alongside `e.preventDefault()`.

### ~~M-3~~ [x]: Frequency `<Select>` cannot represent a `daily_digest` value returned by the server
- **File(s)**: `apps/web/src/app/notifications/components/notification-preferences-table.tsx:184-186`, `:266-269`
- **Description**: `getFrequency` returns the raw stored frequency, but the `<Select>` only offers `immediate` and `disabled`. Per spec Section 4/6 the DB column supports `daily_digest` (the API rejects it on write for now, but it is a valid stored value and the GET response type is `frequency: string`). If a `daily_digest` row ever exists, the trigger renders with no selected label and any unrelated save would not correct it. This is latent today (no code path writes `daily_digest`), but the component has no defensive handling.
- **Expected**: The UI should degrade gracefully for any frequency the API can return.
- **Fix**: When `getFrequency(pref)` is not one of the rendered options, coerce the display value to a safe default (e.g. fall back to `defaultFrequency` or show a disabled placeholder), so the control never renders blank.

No `any` casts in the notification/share client code; the one `as Parameters<typeof t>[0]` at table line 256 is a reasonable typed-key narrowing.
- **i18n completeness**: all keys referenced by the new components exist in `en-US.json` (`notificationPreferences.*` incl. `types.*`/`categories.*`, `shareDetails.activity.*`, `settings.emailAdmin.*`, `share.identification.*`, `createShare` privacy keys, `recipientSelector` notify keys). The 22 other locale files carry the new `createShare`/share keys (verified across `fr-FR`, `de-DE`, `ja-JP`, etc.), consistent with the "English placeholder" delivery plan.
- **Identification form a11y**: `identification-form.tsx` uses real `<form>` submit semantics, `aria-invalid`, required-field markers with screen-reader-friendly optional labels, single-fire autofocus via `hasFocusedRef`, and intentionally non-dismissible modal (`onOpenChange={() => {}}`) — a correct UX for a hard identification gate. Client-side validation mirrors the server Zod rules (name/email required logic + email regex).
- **Bug-fix #1 (selective notify) is correctly implemented**: `recipient-selector.tsx` routes all three call sites (selected / all / single) through one `notify(emails?)` helper, passing `{ emails }` for selected/single and `undefined` for "all", with per-email in-flight tracking to prevent double-sends and partial-success toasts. The "notified" check icon (`notifiedAt`) and access-count display fulfil bug-fix #3.
- **SMTP-aware controls**: notify controls correctly hide when SMTP is disabled and show a loading state via `useSecureConfigValue("smtpEnabled")` (`recipient-selector.tsx:200-202`).
- **Download tracking propagation**: `share?.id` is threaded into every `getCachedDownloadUrl` call in `use-public-share-download.ts`, and the cache key (`download-url-cache.ts:23-31`) includes `shareId`, so share downloads are correctly attributed (within the documented presigned-URL caching trade-off).
- **Password + identification interplay**: `use-public-share.ts` handles the awkward "password accepted but identification still required" sequence via a ref + state combination to avoid stale closures in the query function — a genuinely tricky case handled deliberately, with metadata fetched lazily only when the identification modal is open.
- **Admin email section** is properly admin/SMTP-gated (rendered only inside the email settings group when `smtpEnabled`), polls at a sensible 60s interval, and renders per-counter loading/error/empty states.
