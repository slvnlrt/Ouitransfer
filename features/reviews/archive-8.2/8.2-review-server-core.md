# 8.2 Review — Server Email Core

**Reviewer:** Code quality agent
**Date:** 2026-05-28
**Scope:** Email module infrastructure (transport, i18n, templates, catalog, service, queue, scheduler)
**Git range:** 12a11a0..830f35a

---

## Strengths

- **Clean separation of concerns.** Transport, queue, service, catalog, templates, i18n, and URL building each live in their own module with sensible boundaries. The `events.ts` indirection neatly breaks the cycle between service (producer) and queue (consumer).
- **Type-safe send API.** The `notificationCatalog` + `EmailPayloads` mapped type does exactly what the spec promised: adding a notification type at one place propagates compile-time constraints to all callers. The `satisfies Record<…>` is used correctly.
- **Zod validation behind the unknown-data bridge.** Casting strongly-typed render fns to `(data: unknown) => …` and validating via `payloadSchema` is a reasonable compromise — the catalog is the single source of truth, and the lone `any` cast is well-scoped and commented.
- **Render-vs-SMTP failure distinction.** Marking render failures as `failed` with `maxAttempts: 0` (so the queue won't retry) is the right call — same i18n bug will recur on every attempt.
- **Stuck-job recovery on boot.** `recoverStuckJobs()` covers crash recovery cleanly; tied into `initEmailQueueOnBoot()`.
- **Wake-up via in-process EventEmitter.** Cheap, correct for the single-process assumption that the spec acknowledges.
- **Cooldown deduplication for noisy types.** `share_accessed` / `share_downloaded` have a 900s cooldown enforced in `service.ts`. Good safety net against share-burst spam.
- **Test coverage for the happy paths is solid.** Lifecycle, retry/backoff, priority ordering, stuck recovery, cleanup, wake-listener registration are all exercised in `queue.test.ts`.

## Issues

### Critical

- [x] **C-1: `List-Unsubscribe` header is silently dropped — RFC 8058 broken**
  `apps/server/src/modules/email/queue.ts:163–173` builds `sendOptions.listUnsubscribeHeader` and passes it to `smtpTransport.sendMail`. But `SmtpTransport.sendMail` (`transport.ts:103–116`) only accepts `Omit<SendMailOptions, "from"> & { from?: string }` and forwards `options` directly to nodemailer. Nodemailer does not recognize `listUnsubscribeHeader` — the value is silently discarded, and no `List-Unsubscribe` / `List-Unsubscribe-Post` headers are ever set on outgoing emails.
  Consequence: all non-critical emails (share lifecycle, quotas, admin alerts) ship without RFC 8058 headers → Gmail/Outlook one-click unsubscribe broken, deliverability hit, spec requirement (Section 6 “Conformance”) unmet.
  The queue test (`queue.test.ts:204–230`) only inspects the mock-call shape, so it doesn't catch the divergence between queue and transport contracts.
  Fix: transport.sendMail must translate `listUnsubscribeHeader` into nodemailer's `headers: { "List-Unsubscribe": value, "List-Unsubscribe-Post": "List-Unsubscribe=One-Click" }`. Add an end-to-end test that inspects the actual `transporter.sendMail` argument.

- [x] **C-2: XSS — user-controlled strings interpolated unescaped into HTML body**
  The i18n templates use HTML markup intentionally (e.g. `"<strong>{senderName}</strong>"` in `en.json:37, 46, 52, 58, 64, 70, 76, 91`). `interpolate()` in `i18n/loader.ts:142–144` substitutes `{key}` literally with no escaping. The rendered body is then injected raw at `base-layout.ts:93` (`${slots.body}`), `:96` (`${slots.infoBox}`).
  All of the following data flows from user input to recipients’ inboxes with **zero escaping**:
  - `senderName` (built from `user.firstName/lastName/username` in `share/service.ts:639–641`) — attacker registers with HTML in their name → all recipients get an HTML/JS payload.
  - `shareName`, `fileName`, `visitorName`, `uploaderName`, `reverseShareName`, `userName`, `userEmail`, the file-list comma-join in `reverse-share-uploaded.ts:17`, `testMessage`, `reason`, etc.
  Email clients aren’t script engines, but: inline `<a href="…">`, `<img src=x onerror=…>` in Gmail web/Apple Mail can still load remote content, leak IPs, and (for some clients) execute event handlers. At minimum it allows hyperlink injection / phishing inside a legitimate-looking template.
  The only XSS test (`base-layout.test.ts:184–201`) covers `appName` and `subtitle` (which **are** escaped), not body/infoBox.
  Fix: switch to a “HTML in template, escape in interpolation” pattern. Either escape every `params` value inside `interpolate()`, or split i18n keys into `subject` / `bodyText` (plain) + a separate set of HTML-fragment keys with no user data. The current design — HTML markup in the locale + raw substitution — is fundamentally unsafe.

- [x] **C-3: Reverse-share expiration scheduler re-sends every single day forever**
  `notification.scheduler.ts:181–218` (`checkExpiringReverseShares`) and `:223–258` (`checkExpiredReverseShares`) query `prisma.reverseShare.findMany` with **no `notifiedForExpiration` filter and no update afterwards**. The `ReverseShare` Prisma model (`schema.prisma:320–346`) doesn’t even have a `notifiedForExpiration` column.
  Every daily tick (or every server boot, which always runs `runAllChecks()` immediately — `:351`) re-sends the same `reverse_share_expiring` / `reverse_share_expired` mail to the creator. Spam loop. Restart the server twice → two extra emails per matching reverse share.
  Fix: add `notifiedForExpiration Boolean @default(false)` to `ReverseShare`, mirror the Share-side filter + `update({ data: { notifiedForExpiration: true } })`. Reset the flag in the reverse-share update handler when the expiration is extended (analogous to the share handler).

- [x] **C-4: `share_expired` notification is suppressed by the prior `share_expiring` send**
  `checkExpiringShares` (`notification.scheduler.ts:62–65`) sets `notifiedForExpiration = true` after sending. `checkExpiredShares` (`:79–93`) filters `notifiedForExpiration: false`. Therefore a share that was warned (type 9) will never receive the “has expired” mail (type 10) — even though the spec catalog (Section 10) lists them as **separate** notifications that should both fire.
  Conversely, a share whose expiration is in the past at creation/import time gets `share_expired` (good), but then `notifiedForExpiration` is set, so if the creator extends the expiration later (the share update handler is supposed to reset the flag) the user can get an `expiring` notification but not a second `expired` if it lapses again — depending on the reset logic, the cascade is incoherent.
  Fix: separate flags (`notifiedForExpiring`, `notifiedForExpired`) or, simpler, use the existing flag exclusively for the warning, and use `expiration < now() AND notifiedForExpired = false` for the expired notification (new column).

### Important

- [x] **I-1: `{appName}` is left unsubstituted in every email body, subtitle, and CTA label**
  The locale files use `{appName}` in many non-subject keys: `welcome.subtitle`, `welcome.body`, `welcome.cta`, `adminUserRegistered.body`, `testEmail.body`, `testEmail.bodyCustom` (see `en.json:10–12, 132, 143–144`). The corresponding templates (`templates/welcome.ts:11–14`, `templates/admin-user-registered.ts`, `templates/test-email.ts`) pass only the type-specific payload params (e.g. `firstName`) — `appName` is never injected.
  Because `interpolate()` leaves unknown placeholders as-is (`loader.ts:143`), users will literally see “Welcome to {appName}” and “Sign in to {appName}” buttons. Same for the admin/registration body and the SMTP test email — the customer-facing branding token never lands.
  Fix: either pass `appName` from `EmailService.send` down to the translation function (e.g. via a contextual second translation fn `tWithDefaults`) or have every template explicitly fetch and pass `{ appName }`. The cleanest fix is to centralize: `createTranslationFn(locale, defaults)` injects `appName` (and possibly `appUrl`) into every interpolation by default.

- [x] **I-2: Subjects with dynamic params show literal `{senderName}` to recipients**
  `service.ts:198–199` resolves the subject as `t(locale, "${prefix}.subject", { appName })`. But `shareInvitation.subject` is `"{appName} - {senderName} shared files with you"` and `reverseShareInvitation.subject` is `"{appName} - {senderName} is requesting files from you"`. The `{senderName}` placeholder is never provided, so the subject reads `"TestApp - {senderName} shared files with you"` — literally, braces included — in every share invitation inbox.
  Fix: the catalog needs to declare which payload fields feed the subject, or the template should expose a `subject(data, t)` function alongside `render(data, t)`. The current “type → fixed prefix → only appName” shortcut is too rigid.

- [x] **I-3: `EmailService.send` resolves the user preference twice — same DB query, possibility of split-brain**
  In `service.ts`, `resolveFrequency` is called at line 116 (for the “disabled?” short-circuit) and again at line 215 (to decide `pending` vs `digest_pending`). Two `notificationPreference.findUnique` + two `share.findUnique` per send. More worryingly, between the two calls the user could change their preference; the job could end up with status `pending` while the first check already passed “not disabled”, or vice-versa.
  Fix: call once, store the result, reuse it. Same for `generateUnsubscribeUrl` (called at `:151` and `:208`) — each call produces a different JWT because `iat`/`exp` are minted per call. Today the two tokens differ; nothing depends on them being identical, but it’s wasteful crypto work and inconsistent (the URL in the HTML body is not the same JWT as the one in the `List-Unsubscribe` header).

- [x] **I-4: Nodemailer connection pooling claimed but not actually enabled**
  `transport.ts:34` docstring says “Pooled, config-hash-aware SMTP transport.” The transport builder (`buildTransportOptions`, `:170–213`) never sets `pool: true`. Each `sendMail` call therefore opens a fresh TCP/TLS connection — defeating the whole point of caching the transporter. With the queue processing 10 jobs per tick this matters; with priority bursts it matters more.
  Fix: add `pool: true` (and consider `maxConnections`, `maxMessages`) to the transport options. Update the test asserting the option is set.

- [x] **I-5: `getAppUrl` cache is never invalidated when admin updates `appUrl`**
  `url-builder.ts:5–17` caches `appUrl` on first read and never refreshes. `invalidateAppUrlCache()` exists (`:23–25`) but a `git grep` shows it’s called from **nothing in production code** — only the cache’s own unit test imports it. If the admin changes `appUrl` (e.g. via Settings → General), the queue keeps minting URLs with the old base until the server restarts. Same problem for the `smtpTransport` config hash, but at least that one re-checks on every `getTransporter()` call; here we just freeze the value.
  Fix: wire `invalidateAppUrlCache()` into the config-update path (config service’s `setConfigValue` for the `appUrl` key), or drop the cache (a single DB read on send is negligible — the queue is async anyway).

- [x] **I-6: Notification scheduler interval ≠ daily; first runs are at boot + (boot + 24h)**
  `notification.scheduler.ts` uses `ONE_DAY_MS` chained `setTimeout` (`:303–320`). The “daily” cycle is actually “every 24h since the last tick” — there’s no alignment to a configured digest hour (the spec defines `emailDigestHour` for this, Section 4 config table). A server that restarts twice a day will check at random clock times; servers that never restart will drift relative to wall-clock “morning”.
  More importantly: `runAllChecks()` is invoked **immediately** in `initNotificationSchedulerOnBoot` (`:351`). Combined with C-3, this means a daily restart loop produces N extra `reverse_share_expired` emails per restart.
  Fix: schedule against a target hour (`emailDigestHour` once it exists, or hardcode 06:00 UTC for now). Boot-time first run is fine in theory, but only after C-3/C-4 are fixed; until then it’s an active spam source.

- [x] **I-7: `EmailQueue.processBatch` lock is not atomic — concurrent process races possible**
  Even with the single-process assumption, the lock pattern is:
  1. `findMany({ status: "pending" })` (`queue.ts:127`)
  2. for each job: `update({ where: { id }, data: { status: "processing" } })` (`:148`)
  Between (1) and (2), a wake event can fire `onWake → processTick → processBatch` again on the same tick if `currentTimeout` happens to match (it does after the wake’s own scheduling). Same job picked twice → sent twice. Today this is rare because the wake handler clears `currentTimeout` before scheduling the new timer, but `processBatch` is `async`; the `await processTick()` inside the wake handler runs concurrently with a still-running prior tick on the await boundary.
  Fix: use an atomic transition (`updateMany({ where: { id, status: "pending" }, data: { status: "processing" } })` and skip if `count === 0`), or guard with a simple module-level `isProcessing` boolean so wake events don’t reenter a running batch.

- [x] **I-8: `<html lang="en">` is hardcoded — emails render in the wrong language metadata**
  `base-layout.ts:68`: `<html lang="en">`. Even when the email body is French (or any other locale), the HTML doctype claims English. Affects screen readers and a few client heuristics. Trivial fix: thread the locale through `renderLayout`.

- [x] **I-9: Footer copy is hardcoded English, bypassing i18n entirely**
  `base-layout.ts:104–112`: `"This email was sent by …"`, `"If you didn't expect …"`, `"Powered by Ouitransfer"`, `"Unsubscribe from these notifications"` — all hardcoded English. The locale files even have `common.footer`, `common.footerIgnore`, `common.poweredBy`, `common.unsubscribe` keys (see `en.json:2–7`) that are never read.
  The spec (Section 3, “Visual design”) explicitly lists the footer as part of the localized layout. Fix: call the translation function from inside `renderLayout` (requires passing it in as a `LayoutConfig` field or making `renderLayout` aware of the locale).

- [x] **I-10: `account_deactivated` payload type and Zod schema disagree**
  `templates/account-deactivated.ts:4–7` declares the data type with an optional `adminContactEmail`. The Zod schema at `catalog.ts:80–82` only allows `firstName` — Zod’s default `z.object` strips unknown properties, so any caller that passes `adminContactEmail` will have it silently dropped before the template runs. The `accountDeactivated.infoContact` translation key exists (catalog `requiredI18nKeys` line 250) but is unreachable in production.
  Fix: add `adminContactEmail: z.string().email().optional()` to the schema. (And ideally use `.strict()` on schemas to fail-fast on payload typos instead of silently stripping.)

- [x] **I-11: `_getMaxRetries` is dead code; `emailQueueMaxRetries` config has no effect**
  `queue.ts:51–59` defines `_getMaxRetries` (underscore prefix to silence the linter) but no caller invokes it. `EmailJob.maxAttempts` is read directly from the row at `:189` and never overridden. The config key `emailQueueMaxRetries` (documented in spec Section 4) therefore has **no effect** on the system. Either delete the dead helper or wire it: read `emailQueueMaxRetries` when inserting a job (in `service.ts`) so the configured value actually drives `maxAttempts`.

### Minor

- [x] **M-1: Cooldown query filters `status: { not: "failed" }` — a job stuck in `processing` (never recovered yet) blocks a retry**
  `service.ts:127–135`: if a previous job is locked in `processing` (e.g. SMTP timeout, scheduler hasn’t recovered it yet, < 5min), the new send is skipped because the “recent” row exists. Marginal — would only matter in a rare race during slow SMTP — but worth narrowing to `status: { notIn: ["failed", "processing"] }` or filtering on `sentAt: { not: null }`.

- [x] **M-2: `accessCount` increment on `ShareRecipient` should be atomic**
  Not visible in this review’s file scope but flagged because `share/service.ts` (out-of-scope here but referenced by spec Section 5) needs `{ accessCount: { increment: 1 } }` rather than read-then-write. Worth confirming in Review 2.

- [x] **M-3: `share-invitation.ts` `cta.url` not escaped for HTML-attribute context**
  `base-layout.ts:128`: `<a href="${cta.url}" …>`. Today `cta.url` is built by `url-builder.ts` from controlled inputs (alias, base64url tokens). It’s safe **as long as no template ever feeds a user-controlled URL into the CTA**. The contract isn’t enforced — `cta.url` is a free `string`. Add `escapeAttribute` (or just `escapeHtml`) to be defensive; cheap insurance.

- [x] **M-4: `interpolate` regex `\{(\w+)\}` misses placeholders with hyphens/digits-only keys**
  Not used today (all keys are camelCase identifiers), but the regex silently passes through `{name-with-dash}` or `{42}`. If anyone ever adds such a key the rendering fails silently. Either tighten the validator or document the constraint.

- [x] **M-5: `processBatch` errors per-job are caught, but the `lockedAt: null` clear happens via update — if that update itself throws, the job is permanently stuck**
  `queue.ts:198–223`: the catch block updates the job again. If Prisma is unavailable during the catch, the job remains `processing` with `lockedAt` set, until `recoverStuckJobs` runs on the next boot (which only happens on boot, not on tick). Consider running stuck-recovery periodically as well (e.g. once per cleanup cycle).

- [x] **M-6: `notificationCatalog` declares `cooldownSeconds` only on `share_accessed` / `share_downloaded` — but spec lists `cooldownSeconds` as the “dedup window” for all noisy types**
  Other configurable types like `reverse_share_uploaded` (which can fire on every upload batch) have no cooldown. Worth adding a default (e.g. 300s) to prevent accidental flooding from a script-driven upload burst.

- [x] **M-7: i18n loader uses synchronous `fs.readFileSync`**
  Acceptable today (files are tiny, loaded once at boot), but using sync I/O inside the Fastify request lifecycle (the first email send triggers `loadLocale`) blocks the event loop briefly. Migrate to `fs.promises.readFile` with an in-flight promise dedupe.

- [x] **M-8: `signUnsubscribeToken` produces non-standard JWT (no `typ` validation needed, but the header order matters for some validators)**
  Custom JWT impl is correct, but if there’s any plan to validate tokens with a third-party library later (or expose introspection), prefer `jose` (already a likely transitive dep) over a hand-rolled implementation. Pure tech-debt nit.

- [x] **M-9: `EmailService.send` swallows i18n key errors with `subject = type`**
  `service.ts:200–203`: a missing subject i18n key falls back to the raw type string (e.g. `"share_invitation"`). Combined with I-2, recipients of invitations end up with subject `"TestApp - {senderName} shared files with you"` (literal placeholder) — but if the i18n key is fully missing, the subject is just `share_invitation`. Either error out and create a `failed` job (consistent with render failures), or log a warn so the developer sees the misconfiguration.

- [x] **M-10: `templates.test.ts` and `catalog.test.ts` use `dummyT = (key) => key` — i18n key correctness is not asserted**
  All template tests check that the slot returns *some* string, not that the right i18n keys are passed. `validateAllI18nKeys()` is a static cross-check, but if a template typos `shareInvitation.bdoy` the test passes (any string is fine). Consider a smoke test that runs `t()` for real against `en.json` for every catalog entry’s sample payload — would have caught I-1/I-2 immediately.

- [x] **M-11: `i18n/loader.ts:117` uses `any` to traverse JSON**
  The Biome ignore is justified (`noExplicitAny` is enforced project-wide), but `unknown` + type narrowing would still work here without `any` and would survive future refactors. Optional polish.

- [x] **M-12: `notification.scheduler.ts:48` uses `share.expiration!` (non-null assertion)**
  Justified by the query filter (`expiration: { not: null }`), but a tiny refactor — `if (!share.expiration) continue;` — keeps the code free of `!` assertions and is friendlier to refactors.

## Assessment

**Not ready to merge.** Four Critical defects (silent List-Unsubscribe drop, broad XSS on HTML body, reverse-share expiration spam loop, and `share_expired` swallowed by `share_expiring`) make the system unsafe to ship to real users.

Most of the Important issues stem from the same root cause: the i18n + template layer was designed as two independent passes (interpolation, then HTML composition) without a contract about who escapes what or which params each template should receive. A small refactor — locale-aware `renderLayout`, an `appName/appUrl`-aware translation fn, escaped interpolation by default with a separate “html-fragment” opt-in — would fix C-2, I-1, I-2, I-8, I-9 in one pass.

The architecture (catalog → type-safe send → queue → transport, with wake events and stuck recovery) is sound. The implementation just has not finished plumbing the i18n parameter flow and the per-feature notification-state tracking through the system.

**Recommended path:**
1. Fix C-1 (List-Unsubscribe wiring) and C-3/C-4 (scheduler flags + ReverseShare column) immediately — these are pure logic bugs.
2. Settle on the i18n escaping/parameter contract once, refactor all templates and locale files to it, then close C-2 + I-1 + I-2 + I-9 in a single commit.
3. Address Important issues opportunistically along with the i18n refactor (I-3, I-4, I-5 are independent and small).
4. Minors can wait; M-10 (real i18n in template tests) is worth doing because it would have prevented this batch of bugs in the first place.
