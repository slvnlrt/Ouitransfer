### Important

#### ~~I-1~~ [x]: Per-recipient notify button has no in-flight state — double-clicks fire duplicate requests
- **File**: `apps/web/src/components/general/recipient-selector.tsx:113-150, 376-386`
- **Description**: The shared `notify()` helper has no concurrency guard. The per-recipient bell button at line 377-386 calls `notify([email])` on every click with no `disabled` state and no loading indicator. Rapid double-clicks (or a slow network) issue two `POST /api/shares/:shareId/notify` requests. The server-side rate limit + the queue's 15-minute cooldown for `share_invitation` will absorb the second one, but the user sees two loading toasts (the second `toast.loading(t("recipientSelector.sendingNotifications"))` overlays the first) and potentially two success/error toasts. The "Notify Selected" and "Notify All" buttons have the same issue.
- **Expected**: A button that has just fired off an async action should be disabled until the action completes, matching the existing pattern for `handleAddRecipient` (which uses `isAddingRecipient`).
- **Fix**: Track an in-flight set (or single bool) inside the component:
  ```ts
  const [notifyingEmails, setNotifyingEmails] = useState<Set<string>>(new Set());
  const notify = async (emails: string[] | undefined) => {
    const keys = emails ?? ["__all__"];
    setNotifyingEmails((s) => new Set([...s, ...keys]));
    try { /* … */ } finally {
      setNotifyingEmails((s) => { const c = new Set(s); keys.forEach((k) => c.delete(k)); return c; });
    }
  };
  ```
  Then `disabled={notifyingEmails.has(email)}` on the per-recipient bell, and show a spinner for the "Notify Selected" / "Notify All" buttons. Tied to M-4 (which calls out the same shape on the test side).

#### ~~I-2~~ [x]: `share-details-modal.test.tsx` mocks `security: null`, contradicting the `Share` type and masking future regressions
- **File**: `apps/web/src/components/modals/__tests__/share-details-modal.test.tsx:63-74` vs `apps/web/src/http/endpoints/shares/types.ts:81, 52-54`
- **Description**: `Share.security` is typed as the non-null object `ShareSecurity` (because the server's `ShareResponseSchema` requires it — `dto.ts:91-93`). The test fixture sets `security: null` and silences the type error with `as never` on line 105. The test still passes today only because all `share.security` consumers inside the modal use optional chaining (`share?.security?.hasPassword`), but the modal contains at least one non-optional access path indirectly (e.g., `share-actions-modals.tsx:224, 130, 383, 389, 397` all use `share.security.hasPassword` without `?.`, and that code path isn't exercised by this test).
- **Expected**: The mock should match the type. A future fix that removes a defensive `?.` in `share-details-modal.tsx` would not be caught by this test because the fixture deviates from reality.
- **Fix**: Change line 73 to `security: { hasPassword: false }` and remove the `as never` cast on line 105. This keeps the test honest and TypeScript-checked.

#### ~~I-3~~ [x]: `share-details-activity-section.tsx` translates `identificationSource` via a wildcard `as Parameters<typeof t>[0]` cast — runtime-only safety
- **File**: `apps/web/src/components/modals/share-details/share-details-activity-section.tsx:59-67`
- **Description**: The code does:
  ```tsx
  {visit.identificationSource !== "anonymous" && (
    <span …>{t(`shareDetails.activity.source.${visit.identificationSource}` as Parameters<typeof t>[0])}</span>
  )}
  ```
  The cast disables compile-time key validation. If anyone adds a new `identificationSource` value on the server (e.g. `"jwt"`), the conditional guard (`!== "anonymous"`) admits it, but the i18n key won't exist — the `t()` call throws and is caught by next-intl's error boundary (or surfaces as a missing-key console warning). The `locale-keys.test.ts` parity test doesn't catch dynamic keys.
- **Expected**: i18n keys for dynamic templates should be enumerated explicitly so the type-check enforces them.
- **Fix**: Switch to a small lookup map:
  ```ts
  const SOURCE_LABEL_KEY = {
    tracking_token: "shareDetails.activity.source.tracking_token",
    cookie: "shareDetails.activity.source.cookie",
  } as const;
  // …
  {visit.identificationSource !== "anonymous" && (
    <span …>{t(SOURCE_LABEL_KEY[visit.identificationSource])}</span>
  )}
  ```
  Now any new source value at the server is a TypeScript error here until the map is extended. Same pattern would be useful for `notification-preferences-table.tsx:250` (`types.${pref.type}`) where the cast also disables key validation.

#### ~~I-4~~ [x]: Recipient bell icon is hidden when `smtpEnabled` is `null` (loading state) — visible flash on cold load
- **File**: `apps/web/src/components/general/recipient-selector.tsx:244, 266, 376`
- **Description**: Every notify button (`Notify All`, `Notify Selected`, per-recipient bell) is gated by `smtpEnabled === "true"`. While the `useSecureConfigValue("smtpEnabled")` query is in flight, `value` is `null` and all notify controls disappear. Once the public config arrives (typically <100ms but slower on cold load or a slow link), the controls reappear. The user sees the recipient list without notify affordances for a beat, then they pop in. This is the kind of flash that drives the "is the button missing or am I not allowed?" support ticket.
- **Expected**: Either render the buttons as disabled with a loading spinner until the config resolves, or render them optimistically (since SMTP enabled is the common case) and let the click fail gracefully if SMTP is actually disabled.
- **Fix**: Show a disabled bell with a small spinner during `isLoading`, then enable when `smtpEnabled === "true"`. Same for the bulk buttons. Even simpler: read `smtpEnabled` via `useSecureConfigValue` once at the top, and during loading don't conditionally render — render disabled.

### Minor

#### ~~M-1~~ [x]: `notification-preferences-table.tsx` has a use-before-declaration that works thanks to hoisting but is hard to read
- **File**: `apps/web/src/app/notifications/components/notification-preferences-table.tsx:159, 173`
- **Description**: `handleSave` (line 152) references `preferences` on line 159. `preferences` is declared at line 173 — *after* `handleSave`. This works at runtime because `preferences` is a `const` evaluated each render and `handleSave` is a closure that only reads it on click (after render). But it's confusing on a first read and Biome's `useExhaustiveDependencies` does not flag it. Same shape on the `JSX` block (the table renders preferences on line 231 using a variable declared at line 173, also after the entire mutation/state setup).
- **Fix**: Move the `preferences` / `grouped` derivation block above `handleSave` (it's a pure computation, so order doesn't matter functionally). Cosmetic.

#### ~~M-2~~ [x]: `share-details-modal.tsx` invalidates `list` but never `byAlias` on edit — the public share page can show stale data after an edit
- **File**: `apps/web/src/components/modals/share-details-modal.tsx:83-89`
- **Description**: `invalidateShare()` invalidates `shares.detail(shareId)` and `shares.list()`. The public share page (`use-public-share.ts:54-69`) uses `queryKeys.shares.byAlias(alias)`. After the owner edits a share's name from the details modal, the public page (if open in another tab) keeps showing the old name until the query goes stale or a manual reload. Same for `byAlias` if the owner opens the public link in an iframe / preview.
- **Impact**: Very low. Owners are almost never viewing the public page in real time while editing. But it's an inconsistency with the wider invalidation strategy.
- **Fix**: If the share has an alias, also invalidate `queryKeys.shares.byAlias(share.alias.alias)`. Or use a broader invalidation pattern (predicate matching) for "anything to do with this share id."

#### ~~M-3~~ [x]: `identification-form.tsx` refs are set on whichever input renders first, but `firstInputRef` is reassigned across renders
- **File**: `apps/web/src/app/(shares)/s/[alias]/components/identification-form.tsx:138, 169`
- **Description**:
  ```tsx
  <Input ref={showNameField ? firstInputRef : undefined} … />  // name input
  <Input ref={!showNameField ? firstInputRef : undefined} … /> // email input
  ```
  This pattern correctly attaches the ref to the first visible input. But because both lines reference the same `firstInputRef`, if `showNameField` flips at runtime (e.g. metadata refetch returns different requirements), the ref gets detached from one and attached to the other on re-render — and the autofocus `useEffect` is gated by `hasFocusedRef.current`, so focus doesn't re-fire even if it should. Net: if a visitor first sees a name-only form, types into name, then the metadata refetches and now also shows email, focus stays on the name input (which is correct because the user is mid-typing). Edge case; behavior is acceptable. Flagging only because the dual-ref pattern is brittle and a reader has to think about it.
- **Fix**: Optional. The cleanest alternative is to compute `firstFieldKey = showNameField ? "name" : "email"` and use a single ref attached based on that. Pure refactor, no behavior change.

#### ~~M-4~~ [x]: `share-actions-modals.tsx` Edit button is enabled while metadata fetch is in flight after toggle on / off
- **File**: `apps/web/src/components/modals/share-actions-modals.tsx:418-425`
- **Description**: The Save button is gated by `isLoading || isPasswordInvalid`. `isLoading` is the modal-local "I'm currently calling the API" flag. There is no guard against double-submit between user click and the await resolving — first click sets `isLoading = true` synchronously. Good. But if `isPasswordInvalid` becomes true mid-await (e.g. user toggles password back on and clears the password while save is in flight), the user can't tell the save is still going. Cosmetic.
- **Fix**: Show a spinner inside the Save button while `isLoading` is true. Matches the pattern used in `share-item-modal.tsx:411-414` (`isLoading ? <Loader size="sm" /> : t("createShare.create")`).

#### ~~M-5~~ [x]: `email-admin-section.tsx` polls every 30s even when the tab is in the background
- **File**: `apps/web/src/app/settings/components/email-admin-section.tsx:24`
- **Description**: `refetchInterval: 30000` means TanStack Query polls every 30s while the component is mounted, regardless of tab visibility. By default v5 also pauses polling when the window is unfocused, but only if `refetchIntervalInBackground` is left at `false` (which it is by default — good). However, the 30s interval polls indefinitely while the user is on the Settings page. For a settings tab the user leaves open all day, that's 2880 requests/day. Probably fine for a dev app, but worth knowing.
- **Fix**: Consider increasing to 60s or only polling on first mount + on test-email-send success. Defer.

#### ~~M-6~~ [x]: `share-details-modal.tsx` early-return AFTER all hooks works but adds unused query slots
- **File**: `apps/web/src/components/modals/share-details-modal.tsx:72-79, 197`
- **Description**: The `useQuery({ enabled: !!shareId, queryKey: queryKeys.shares.detail(shareId!) })` runs (in disabled state) for every render where `shareId === null`. The early `return null` at line 197 happens after. The queryKey contains a `shareId!` non-null assertion that's safe (the query is disabled) but creates one cache slot per (component-mount, transient-null) that is never used. Minor memory overhead.
- **Fix**: Move the `if (!shareId) return null;` to the very top, before the hooks. The drawback is that React would warn about a different hook count if shareId transitions from non-null to null in the same mount lifecycle. The current placement (after hooks) is the React-idiomatic pattern. Leave it.

#### ~~M-7~~ [x]: `notification-preferences-table.tsx` localChanges retain stale entries when server preference matches the user's selection
- **File**: `apps/web/src/app/notifications/components/notification-preferences-table.tsx:148-150`
- **Description**: If the user changes a row to `disabled`, then changes it back to `immediate` (which matches the server-side current value), `localChanges` still contains `{type: "immediate"}`. The unsaved-changes counter shows "1 unsaved change" but the save is a no-op (the server upsert sets the same value). Cosmetic.
- **Fix**: On `handleFrequencyChange`, compare to the current server-side value and remove the entry from `localChanges` if they match:
  ```ts
  setLocalChanges((prev) => {
    const next = { ...prev, [type]: frequency };
    const serverPref = data?.preferences.find((p) => p.type === type);
    if (serverPref?.frequency === frequency) delete next[type];
    return next;
  });
  ```

#### ~~M-8~~ [x]: `share-details-modal.tsx:323-328` renders a `<Check>` icon next to "Notified" but no aria-label on the icon
- **File**: `apps/web/src/components/modals/share-details-modal.tsx:323-328`
- **Description**: The notified indicator is a green icon + text. The icon is decorative (the adjacent text labels it). But screen readers may double-announce or behave oddly. The icon doesn't have `aria-hidden="true"`. Same shape in `recipient-selector.tsx:355-358`. Not a real a11y bug, but consistent with the project's other lucide icons would benefit from `aria-hidden`.

#### ~~M-9~~ [x]: i18n parity check passes, but `shareDetails.fieldValue.HIDDEN` is intentionally missing
