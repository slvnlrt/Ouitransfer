## Strengths

- **API surface is well-organised.** A dedicated `notifications/` endpoint module with its own types file, integrated cleanly into the existing barrel export. The split between `getNotificationPreferences` / `updateNotificationPreferences` / `getEmailStats` / `sendTestEmail` follows the existing pattern (`shares/`, `users/`, …).
- **TanStack Query usage is correct.** Query-key factory updated with `notifications.preferences()`, `shares.visits(...)`, `shares.metadata(...)`, `admin.emailStats()`; cache invalidations after the relevant mutations (preferences save → invalidate preferences; identification → invalidate share-by-alias). `refetchInterval: 30000` on `getEmailStats` is reasonable for live queue status.
- **Notification catalog ↔ i18n map is in sync.** All 22 notification types declared in `apps/server/src/modules/email/catalog.ts` exist in `TYPE_TO_CATEGORY` (`notification-preferences-table.tsx:43–66`) and in `notificationPreferences.types.*` (`en-US.json:2671–2693`). `isCritical` types correctly render the “Always enabled” label instead of the Select.
- **RecipientSelector finally uses the typed `ShareRecipient`.** The previous local-and-narrower `Recipient` interface is gone; the component now refreshes recipients from the API response (`addRecipients`/`removeRecipients` return the updated share) instead of locally splicing strings, and displays `notifiedAt` / `accessCount`. Per-recipient `notifyRecipients(shareId, { emails: [email] })` is wired correctly.
- **EmailAdminSection is gated on `smtpEnabled`.** Settings form only renders the admin section when `configs.some((c) => c.key === "smtpEnabled" && c.value === "true")`. Sensible.
- **Privacy-section markup is reused via Radix `Collapsible`.** The shadcn wrapper (`components/ui/collapsible.tsx`) is minimal and correct; the `data-[state=open]:rotate-180` chevron animation is standard.
- **`identifyVisitor` request shape.** `{ name?, email? }` matches the server schema, and the hook propagates `name || undefined` / `email || undefined` so empty strings are dropped client-side.

## Issues

### Critical

- [x] **C-1: Password + required-identification flow is broken — user gets stuck on the password modal.**
  `apps/web/src/app/(shares)/s/[alias]/hooks/use-public-share.ts:83–107, 134, 61`.
  Flow: share requires both password and required identification.
  1. Initial `getShareByAlias` → 401 PASSWORD_REQUIRED → `shareQuery.error = PASSWORD_REQUIRED` → `isPasswordModalOpen = true`. ✅
  2. User submits password → `passwordMutation` calls `getShareByAlias(alias, { password })` → server validates password, then throws 403 IDENTIFICATION_REQUIRED → mutation lands in `onError`.
  3. `isInvalidPassword(error)` is false → falls into the `else` branch → toast “Failed to load share”.
  4. **`shareQuery.error` is still PASSWORD_REQUIRED** (the mutation’s error never reaches the query state). So `isPasswordModalOpen` stays `true` and `isIdentificationModalOpen = !share && isIdentificationRequired(shareQuery.error)` stays `false`.
  5. The user is shown a generic error toast and is asked to re-enter the same (valid) password forever, with no path to the identification form.
  Fix: in `passwordMutation.onError`, branch on `isIdentificationRequired(error)` — when true, either (a) refetch the share query so its error becomes IDENTIFICATION_REQUIRED, or (b) keep mutation success/error in derived state and OR them into `isIdentificationModalOpen`. Add a Playwright/Vitest integration test for this combined flow.

- [x] **C-2: `download-url-cache` ignores `shareId`, so share download tracking and `share_downloaded` notifications are silently disabled after the first call.**
  `apps/web/src/lib/download-url-cache.ts:21–27, 54–84`.
  `getCacheKey()` keys solely on `objectName` (+ optional password). `shareId` is accepted as a parameter but **not** part of the cache key. The server endpoint at `apps/server/src/modules/file/routes.ts:907–959` only creates the `ShareVisit` row and triggers the `share_downloaded` notification when the `POST /files/download-url` handler is invoked with `shareId`. When the client serves a cached URL, that handler is never re-called → no visit row, no notification email, no `lastDownloadedAt` update.
  This breaks the spec promise that `share_downloaded` fires on every download (subject to the 900 s cooldown). It also means the share owner’s Activity panel and inactivity scheduler miss every download after the first one in a 55-minute window.
  Cross-share leakage: if the same `objectName` is shared in two different shares, the second share’s downloads will be attributed to whichever share warmed the cache first.
  Fix: include `shareId` in `getCacheKey()`: e.g. `return [objectName, password, shareId].filter(Boolean).join("|")`. Add a unit test exercising two consecutive `getCachedDownloadUrl` calls with the same `objectName` but different `shareId` and assert that `getDownloadUrl` is called twice.

### Important

- [x] **I-1: Massive duplication between `share-item-modal.tsx` and `share-multiple-items-modal.tsx`.**
  `apps/web/src/components/modals/share-item-modal.tsx:360–431` vs `apps/web/src/components/modals/share-multiple-items-modal.tsx:419–492`. The entire Privacy & Notifications collapsible (two Selects + Switch + Input, ~70 lines) is copy-pasted byte-for-byte (only the Switch `id` differs). Both modals also duplicate:
  - the same `formData` shape and `nameFieldRequired`/`emailFieldRequired`/`notifyOnDownload`/`inactivityAlertDays` setters,
  - the `createShare(...)` call mapping form fields → request body (lines 162–176 vs 193–207),
  - the close-and-reset block (lines 244–256 vs 263–274).
  CLAUDE.md instructs “DRY — duplicate twice, abstract on the third occurrence”. This is the second occurrence and it adds ~70 lines of pure duplication with each new privacy field. Extract a `<SharePrivacySection value onChange />` component (and ideally a `useShareFormState()` hook) — the third feature touching these fields will otherwise diverge.

- [x] **I-2: `share.creatorId` typed `string` but server returns `string | null`.**
  `apps/web/src/http/endpoints/shares/types.ts:63` vs server DTO at `apps/server/src/modules/share/dto.ts:90` (`z.string().nullable()`). Currently nothing on the client crashes because no code path reads `creatorId`, but the lie will bite the next feature that needs it (e.g. “is current user the owner?”). Fix: `creatorId: string | null`.

- [x] **I-3: `ShareVisit` and `ShareFolder` types are incomplete — silently lose fields.**
  `apps/web/src/http/endpoints/shares/types.ts:211–220`. Server returns `shareId`, `fileId`, `recipient: { email, name } | null` (`apps/server/src/modules/share/routes.ts:850–870`); the client type declares none of them. `ShareFolder` (lines 24–36) is also missing `objectName` and `userId` that the server includes (`dto.ts:113, 115`).
  This is harmless today (the Activity section doesn’t use the missing fields), but it defeats the purpose of typed endpoints — any consumer asking `visit.recipient?.email` will get a TS error even though the data is there. Make the client types reflect the actual server payload, or generate them.

- [x] **I-4: Identification form has no client-side validation; users can submit empty required fields.**
  `apps/web/src/app/(shares)/s/[alias]/components/identification-form.tsx:75–104, 41–46`. The `required` attribute on a stand-alone `<Input>` (no enclosing `<form>` with `onSubmit`) does nothing — clicking the Submit button or pressing Enter calls `handleSubmit()` unconditionally, which sends `undefined` for empty fields. The server then returns 403 IDENTIFICATION_REQUIRED and the hook shows a generic error toast — the user has no idea which field was the problem. The email field also accepts anything (no `isValidEmail` check like `recipient-selector.tsx:42–45` does).
  Fix: block submit when a required field is empty; surface inline error text (e.g. “Email is required”); add a basic email-regex check before calling the mutation.

- [x] **I-5: Identification modal shows zero fields during the metadata fetch.**
  `use-public-share.ts:64–72` enables `metadataQuery` only after `isIdentificationModalOpen` becomes true, then renders `<IdentificationForm metadata={metadataQuery.data ?? null} />`. In `identification-form.tsx:36–37`, `metadata == null` ⇒ `showNameField = false`, `showEmailField = false`. So during the (brief) round-trip the modal shows the title, the subtitle, and a “Continue” button with no inputs. Clicking it during that window submits `{}` and lands back on IDENTIFICATION_REQUIRED.
  Fix: render a loader/skeleton or disable the Continue button while `metadataQuery.isLoading`. Bonus: fetch metadata up-front for any alias (it’s a lightweight public endpoint) so the form opens populated.

- [x] **I-6: 21 of 23 locale files now start with a UTF-8 BOM (regression).**
  `apps/web/messages/*.json`. Before this branch, all locale files began with `7B 0A 20` (`{` + LF + space). After: only `en-US.json` and `fr-FR.json` still start that way; the other 21 (including `pt-BR.json` — visible even in `git diff` as `﻿{`) begin with `EF BB BF 7B`. This is a side effect of how the agent wrote the placeholder translations on Windows (CLAUDE.md explicitly warns about this). Strictly speaking RFC 8259 forbids BOM, and many CLI JSON tools choke; Webpack’s JSON loader strips it so the dev/prod build appears to work, but it’s an unintentional inconsistency in 21 files. Fix: rewrite the affected files without BOM (`Set-Content -Encoding utf8NoBOM`) and add a lint check.

- [x] **I-7: EmailAdminSection renders even when the Email settings group is collapsed.**
  `apps/web/src/app/settings/components/settings-form.tsx:84–94`. The admin section is rendered as a sibling of `<SettingsGroup>` inside the same `<div>`, regardless of `collapsedGroups[group]`. When the user collapses the Email card to focus on something else, the queue stats + test-email panel stay visible below the (now empty) header. It should either be inside the collapsible content or also hidden by `collapsedGroups["email"]`.

- [x] **I-8: Notification preferences page has no error state — silent failure on GET.**
  `apps/web/src/app/notifications/components/notification-preferences-table.tsx:108–114, 189–249`. The `useQuery` exposes `error` but the component only reads `data` and `isLoading`. A 401 / network failure leaves the user with an empty table, no toast, no retry button. Same pattern in `EmailAdminSection` (`emailStatsQuery.error` is unused). Compare with `recipient-selector.tsx` which at least toasts on every failure path. Fix: surface the error (toast + inline message) and offer a retry.

- [x] **I-9: `notification-preferences-table.tsx` Save button gives no progress feedback.**
  Line 244: `<Button onClick={handleSave} disabled={saveMutation.isPending}>{t("save")}</Button>`. The button is disabled while saving but the label doesn’t change to “Saving…” and no spinner is shown. Compare with `email-admin-section.tsx:116–127` which does it properly (`testSending` + `Loader` icon).

- [x] **I-10: Activity-section relative time strings are hard-coded English.**
  `apps/web/src/components/modals/share-details/share-details-activity-section.tsx:29–32`. `${diffSeconds}s ago`, `${diffMinutes}m ago`, etc. are literal strings; non-English locales will still see “3h ago”. Either use `next-intl`’s `useFormatter().relativeTime(...)`, or add `shareDetails.activity.{secondsAgo,minutesAgo,…}` keys.

### Minor

- [x] **M-1: “Loading...” in the preferences table is not i18n’d.**
  `notification-preferences-table.tsx:190`. There is already `common.loadingSimple` (“Loading...”) and `common.loading` in `en-US.json:155–156`. Replace the bare string.

- [x] **M-2: `share-details-modal.tsx` re-declares a local `ShareRecipient` interface that shadows the canonical one.**
  Lines 47–52. The local type is a structural subset of the imported `ShareRecipient` from `@/http/endpoints/shares/types` (which is even already imported via `Share`). Use the shared type; the local one will go out of sync when fields are added (and indeed it’s already missing `name`, `trackingToken`, `notifiedAt`, `lastAccessedAt`, `accessCount`).

- [x] **M-3: `share-details-modal.tsx` useEffect missing dependency.**
  Lines 95–99: `useEffect(() => { if (refreshTrigger) invalidateShare(); }, [refreshTrigger]);`. `invalidateShare` is recreated on every render and the comment on line 94 hand-waves it as “stable”. Either move `invalidateShare` into a `useCallback` with the proper deps and add it to the dep array, or use an explicit `// eslint-disable-next-line react-hooks/exhaustive-deps`.

- [x] **M-4: `useEffect` in `use-public-share.ts:75–80` reads `t()` without listing it as a dep.**
  Pattern is OK in practice (`t` is identity-stable across renders for next-intl) but inconsistent with the rest of the codebase which adds `t` to the deps.

- [x] **M-5: `recipientSelector.views` translation uses no plural form.**
  `en-US.json:1120`: `"views": "{count} views"`. With `count === 1` the user sees “1 views”. Use ICU plural: `"{count, plural, =0 {no views} one {# view} other {# views}}"`. Same key already uses ICU plural elsewhere (`shareMultipleFiles.itemsToShare` etc.).

- [x] **M-6: Inline single-recipient notify handler duplicates the bulk-notify logic.**
  `recipient-selector.tsx:328–358` builds the link, shows the loading toast, calls `notifyRecipients`, and toasts on success/error — the same five-step dance as `handleNotifySelected` (lines 103–119) and `handleNotifyAll` (lines 121–135). Extract a `notify(emails: string[] | undefined)` helper to avoid the third copy.

- [x] **M-7: `accountCount > 0` / `notifiedAt` badges may collide with the bulk-action toolbar position.**
  `recipient-selector.tsx:310–326` adds two extra lines per row. With many recipients and the bulk-action bar pinned at the top, the per-row controls (notify / delete buttons on the right) get cramped at smaller widths. Confirm the layout still works on mobile (`sm:w-auto w-full` is already used on the action toolbar but not on row controls).

- [x] **M-8: `IdentificationForm`’s `Dialog onOpenChange={() => {}}` swallows the Escape key intentionally — but offers no alternative exit.**
  Lines 55. The intent is to prevent the user from dismissing the modal without identifying. Combined with no `onClose` prop, however, this is a forced-close-only modal — fine for the design, but it should at least announce that with `aria-modal="true"` (Radix Dialog handles this) and have a non-trapping label. Worth a UX pass.

- [x] **M-9: `IdentificationForm` has no `<form>` element, so the browser’s autofill heuristics may not recognise the email field.**
  Wrap inputs in a `<form onSubmit={(e) => { e.preventDefault(); handleSubmit(); }}>`. Bonus: this gives Enter-key submission semantics for free and lets `required` actually work.

- [x] **M-10: `formatRelativeTime` in `share-details-activity-section.tsx` re-implements a stdlib feature.**
  Use `useFormatter().relativeTime(date)` from `next-intl` — it’s already a transitive dependency and handles negatives, plurals, and i18n in one go (also solves I-10).

- [x] **M-11: `truncateIp` IPv6 heuristic is slightly off for `::1`.**
  `share-details-activity-section.tsx:35–47`. `"::1".split(":")` → `["", "", "1"]` (length 3) → returns `":" + ":…"` = `"::…"`. Minor cosmetic issue, but consider treating IPv6 with a dedicated regex.

- [x] **M-12: `query-keys.ts:53` puts an object into a query key as `params`.**
  TanStack Query stringifies keys deterministically (sorts object keys), so this is correct. Just worth noting that the caller passes a fresh object literal each render (`{ page, limit: PAGE_LIMIT }`) — that’s fine, just confirming the intent. No fix needed.

- [x] **M-13: `share-multiple-items-modal.tsx:519` total-size summary is hard-coded English.**
  `"Total size: ..."` — not i18n’d. Pre-existing in spirit (the literal was there before with file count), but the patch touches the immediate surroundings; worth fixing while we’re here.

## Assessment

**Not ready to merge as-is.** Two critical bugs need addressing before this can ship:

- **C-1 makes the “require identification” feature unusable on any password-protected share.** Spec 8.2 places visitor identification at the heart of the auditable-download story; a password-protected share that also requires a name/email is precisely the most security-conscious configuration, and it’s the exact configuration that traps the user.
- **C-2 silently breaks `share_downloaded` notification delivery and download auditing** for every download after the first within a 55-minute window — the central promise of this feature.

The Important issues are mostly UX (validation, error states, copy-paste duplication) and a Windows-toolchain BOM regression — these don’t block functionality but contradict the “zero technical debt / perfect implementation” bar in CLAUDE.md, especially I-1 (DRY) and I-6 (BOM) which will spread if left.

Recommended order:
1. Fix C-1 and C-2 (each is ~10 lines, with regression tests).
2. Address I-1, I-2/I-3, I-4/I-5, I-8/I-9, I-10 — the user-visible UX and type-contract gaps.
3. Mechanical cleanups: I-6 (strip BOMs), I-7 (collapse-state guard), M-* polish.
