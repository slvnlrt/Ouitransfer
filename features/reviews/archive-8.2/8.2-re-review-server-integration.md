# 8.2 Re-Review — Server Integration

**Reviewer**: AI Agent (principal-engineer mode)
**Date**: 2026-05-29
**Scope**: `apps/server/src/modules/share/{service,routes,dto,repository}.ts`, `modules/file/routes.ts`, `modules/notification/routes.ts`, `modules/reverse-share/service.ts`, `prisma/seed.js`, and the visitor-tracking/identification/notification integration tests.

## Summary

The prior review's Critical and Important findings have been addressed cleanly: tracking-token leakage is sealed via `formatShareResponse(isOwner)`, the identification gate now validates both `recipient.shareId === share.id` and cookie content against current requirements, `notifyOnDownload` is scoped to `share_downloaded`, the unsubscribe pages escape HTML, and `notifyRecipients` builds tracking URLs via `URL` + `searchParams.set()`. Good work.

However, **the end-to-end unsubscribe flow is broken**. The HTML confirmation page renders a `<form method="POST">` whose action and content-type cannot be processed by the current backend, so clicking "Confirm Unsubscribe" from an email never actually unsubscribes the user. The RFC 8058 one-click List-Unsubscribe path is broken for the same reason. The integration tests miss it because they POST JSON bodies, not the form-encoded body a real browser or mail client would send. This is a regression that ships if not caught.

Beyond the unsubscribe failure, several real issues remain: anonymous visitors still receive owner-only metadata fields via `ShareResponseSchema`, recipient-email casing is inconsistent between create/update/notify paths (causing tracking-token loss), the share invitation locale is the sender's rather than the recipient's, and `notifyRecipients` accepts an arbitrary `shareLink` from the client which is a phishing vector for a multi-user deployment.

## Findings

### Critical

#### C-1: Unsubscribe confirmation form is non-functional — no formbody parser registered
- **File**: `apps/server/src/modules/notification/routes.ts:51-73` (rendered form) + `apps/server/src/app.ts` (server setup) + `apps/server/src/modules/email/url-builder.ts:64-67`
- **Description**: Three independent defects make the rendered "Confirm Unsubscribe" button a dead end:
  1. **No form-body parser.** The Fastify app never registers `@fastify/formbody` (verified by grep across `apps/server`). A standard HTML form POST sends `application/x-www-form-urlencoded`, which Fastify cannot parse out of the box. The `POST /notifications/unsubscribe` handler declares `body: z.object({ token: z.string() })`; with no form parser, `request.body` is undefined or fails schema validation, returning 400.
  2. **Form action targets the wrong origin.** The rendered form is:
     ```html
     <form method="POST" action="/notifications/unsubscribe">
     ```
     `buildUnsubscribeUrl` (line 66) generates emails containing `{appUrl}/api/notifications/unsubscribe?token=...`. When the browser loads that GET, the page origin is `{appUrl}` and the form's absolute path `/notifications/unsubscribe` resolves to `{appUrl}/notifications/unsubscribe` — the **Next.js frontend**, not the Fastify API at `/api/...`. Even if the formbody parser were registered, the POST would 404 on the frontend.
  3. **RFC 8058 one-click is broken.** `apps/server/src/modules/email/transport.ts:129` sets the header `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. Per RFC 8058 the mail client POSTs `application/x-www-form-urlencoded` with body `List-Unsubscribe=One-Click` to the URL in `List-Unsubscribe`. Same parsing failure as (1), and even if it parsed, the handler reads `request.body.token` but the token is in the URL query, not the body.
- **Impact**: Every user who clicks an unsubscribe link from any email either gets a "404 not found" from Next.js (form-action issue) or a 400 from the API (body-parse issue), and Gmail/Outlook's one-click unsubscribe is silently broken (which also tanks deliverability — these providers may penalize senders whose one-click endpoints don't behave). The feature exists end-to-end in tests because tests bypass the real browser/mailer behavior by POSTing JSON.
- **Suggested fix**:
  1. Register `@fastify/formbody` in `app.ts` (before route registration), or change the POST handler to also accept the token from `request.query`.
  2. Fix the form action: either render `<form action="/api/notifications/unsubscribe">` (knowing the proxy/Traefik routes `/api/*` to the backend), or change `buildUnsubscribeUrl` to point to a frontend page that does the POST. The cleanest fix is to set form action to the full backend path: `{server-relative}/notifications/unsubscribe` — i.e., `"/api/notifications/unsubscribe"` if the backend is always behind the `/api` rewrite, and rendered as such.
  3. For one-click RFC 8058: in the POST handler, read the token from `request.query.token` AND/OR `request.body.token`, accepting either source. Accept the body `List-Unsubscribe=One-Click` as a no-op (just verify the token); do not require any specific body field.
  4. Add an integration test that POSTs `Content-Type: application/x-www-form-urlencoded` with body `token=...` and asserts 200 + upsert called. Add a one-click test: GET token in URL, `Content-Type: application/x-www-form-urlencoded`, body `List-Unsubscribe=One-Click`, expect 200 + upsert.

#### C-2: Owner-only metadata leaks to anonymous share viewers
- **File**: `apps/server/src/modules/share/dto.ts:81-152` + `apps/server/src/modules/share/service.ts:59-115`
- **Description**: `formatShareResponse` strips `recipients` from non-owner responses (good — that was C-1 in the prior review). But the same response object continues to expose owner-only fields through the shared `ShareResponseSchema`:
  - `creatorId` (line 90 in `dto.ts`) — exposes the share owner's user ID to any anonymous visitor.
  - `notifyOnDownload`, `inactivityAlertDays` (lines 133-134) — internal owner preferences.
  - `lastDownloadedAt` (line 135) — reveals other visitors' activity, useful for surveillance ("when was the last person here?").
  - `notifiedForExpiring`, `notifiedForExpired` (lines 136-137) — internal scheduler flags with no visitor utility.

  Service-layer `getShare(...)` returns this full schema to anonymous callers via `formatShareResponse(updatedShare, false)` (line 350). The Zod schema enforces presence of these fields, so they ARE serialized into the public response.
- **Impact**: Privacy leak. `creatorId` enables enumeration ("which user owns this share?"), and `lastDownloadedAt` lets a visitor monitor share activity. Less severe than the tracking-token leak that was fixed, but the same class of bug (no separation between public-share and owner-share response shapes).
- **Suggested fix**: Define a `PublicShareResponseSchema` that omits `creatorId`, `notifyOnDownload`, `inactivityAlertDays`, `lastDownloadedAt`, `notifiedForExpiring`, `notifiedForExpired`. Branch on `isOwner` in `formatShareResponse` to return one shape or the other. Update the route response schemas (`GET /shares/:shareId`, `GET /shares/alias/:alias`, `POST .../access`) to union the two or to use the public shape and switch via OpenAPI variants. (`fastify-type-provider-zod` supports `z.union`; alternatively, define two routes or return `ShareResponseSchema.partial()` and document.)

### Important

#### I-1: `notifyRecipients` sends emails in the share creator's locale, not the recipient's
- **File**: `apps/server/src/modules/share/service.ts:684-694`
- **Description**:
  ```ts
  await emailService.send("share_invitation", {
    to: recipient.email,
    locale: user?.locale ?? "en",   // <-- sender's locale
    ...
  });
  ```
  `user` is the share creator. A French-speaking owner inviting an English-speaking customer will send the email in French. There is no `locale` field on `ShareRecipient`, so the system cannot infer the recipient's preferred language from the existing model.
- **Impact**: Confusing UX for international shares. Especially poor for an externally-hosted file-transfer service that may serve mixed-locale audiences in a single org (e.g., a French agency sending to global clients).
- **Suggested fix**: Two options:
  1. **Use a configurable per-share locale.** Add `locale` to `ShareRecipient` and let the UI optionally set it. Fall back to creator's locale.
  2. **Use the system default.** For now, hardcode `"en"` or use `getConfigValue("defaultLocale")` as a more neutral choice. The current "creator's locale" is the worst of both worlds because it's invisible to the creator (who doesn't realize the email goes out in their language).

  At minimum: document the decision in the service file. The current behavior looks like an oversight.

#### I-2: `notifyRecipients` accepts arbitrary `shareLink` from the client (phishing vector)
- **File**: `apps/server/src/modules/share/routes.ts:689-696` + `apps/server/src/modules/share/service.ts:680-682`
- **Description**: The notify route accepts any `shareLink: z.string().url()` from the authenticated owner, then embeds it in an outbound email branded as the application:
  ```ts
  body: z.object({
    shareLink: z.string().url().describe("The frontend share URL"),
    ...
  })
  ```
  ```ts
  const linkUrl = new URL(shareLink);
  linkUrl.searchParams.set("t", trackingToken);
  ```
  A malicious authenticated user (or a compromised admin) can supply `https://attacker.example/phish?id=share-1` and the system will send recipients an email from the trusted app's SMTP identity containing the attacker URL. The recipient sees a legit-looking email and clicks. The application is now a phishing vector with the operator's SMTP reputation behind it.

  This is not a hypothetical: SaaS file-transfer services have been used this way (the attacker uses a trial account to harvest victim emails, then sends phishing under the service's brand).
- **Impact**: Brand/reputation/deliverability damage. Possible legal liability for hosting providers depending on jurisdiction.
- **Suggested fix**: Don't take `shareLink` from the client at all. The server already knows the share (`share.alias` or `share.id`) and the configured app URL (`getAppUrl()` from `email/url-builder.ts`). Build the link server-side:
  ```ts
  const linkUrl = await buildShareLink(share.alias?.alias ?? share.id, trackingToken);
  ```
  Delete `shareLink` from the route body schema. If the frontend needs to customize the URL (e.g., shorter alias variant), expose a server-side helper instead of accepting raw user input.

#### I-3: Recipient email case-handling is inconsistent between create / update / addRecipients / notify
- **File**: `apps/server/src/modules/share/repository.ts:113-114, 343-354, 356-368` + `apps/server/src/modules/share/service.ts:371-393, 647-652`
- **Description**: `PrismaShareRepository.createShare` normalizes emails via `email.trim().toLowerCase()` (line 113-114). But:
  - `updateShare` (service line 371-393) compares incoming `recipients` (raw) against existing-by-email (lowercased) without normalization. Submitting `Alice@Example.com` after creating with the same string treats it as a NEW email — the old row is deleted and a new row with a NEW tracking token is created. Any previously-sent invitation link breaks silently.
  - `PrismaShareRepository.addRecipients` (line 348) inserts raw emails without normalization.
  - `PrismaShareRepository.removeRecipients` (line 363) deletes by raw `email` — removing `Alice@Example.com` fails to find the stored `alice@example.com`.
  - `notifyRecipients` filters via `emailSet.has(r.email)` against raw `selectedEmails` — case mismatch leads to silent zero notifications.

  This is the kind of bug that surfaces only in production when a user with mixed-case-aware email habits hits an edge case.
- **Impact**: Tracking-token loss (invitation links become dead), silent no-ops on the notify endpoint, inability to remove recipients added with different casing.
- **Suggested fix**: Centralize email normalization. Either a shared `normalizeEmail(s: string): string` helper used everywhere recipient emails are accepted, or — better — a Zod transform on `UpdateShareRecipientsSchema` and `CreateShareSchema.recipients` that does `.transform(s => s.trim().toLowerCase())` at the route boundary. Apply to: createShare, updateShare, addRecipients, removeRecipients, notifyRecipients route schemas.

#### I-4: Visitor identification cookie payload is set even when `name`/`email` were not provided — pollutes ShareVisit
- **File**: `apps/server/src/modules/share/routes.ts:817-821` + `apps/server/src/modules/share/service.ts:309-312`
- **Description**: The identify endpoint always sets a cookie payload, even when `name`/`email` are absent:
  ```ts
  const payload = JSON.stringify({
    alias,
    name: request.body.name ?? null,
    email: request.body.email ?? null,
  });
  reply.setCookie(`sv_${alias}`, payload, ...);
  ```
  Later in `getShare`, when the visitor returns to the share:
  ```ts
  if (!recipientId && context?.visitorCookie) {
    visitorName = context.visitorCookie.name;   // could be undefined
    visitorEmail = context.visitorCookie.email; // could be undefined
  }
  ```
  And the `ShareVisit.create` (line 315-327) stores these as `undefined` (which Prisma persists as null). Functionally OK. But:
  - If the share requires neither name nor email (`HIDDEN`/`OPTIONAL`), the identify endpoint accepts an empty body and still issues a cookie, marking the visitor as "identified" even though they provided nothing. This is a minor UX bug but it pollutes ShareVisit with cookie-based visits indistinguishable from anonymous ones.
  - If the gate later checks `!!context?.visitorCookie` (which is what the prior code did before the fix), an empty cookie would bypass. The current code does properly re-validate, so this is mitigated — but the cookie's mere existence is misleading.
- **Impact**: Diagnostic noise in `ShareVisit` records (a cookie-bearing but content-empty visit is indistinguishable from a fresh anonymous visit). No security gap given the fix to re-validate.
- **Suggested fix**: Reject the identify request with 400 if both `name` and `email` are empty/undefined, regardless of share requirements. The endpoint's purpose is to collect identification — accepting nothing makes no sense. Add `.refine(data => data.name || data.email, { message: "Provide name or email" })` to the body schema.

#### I-5: `notifyRecipients` selected-emails filter silently no-ops on mismatch
- **File**: `apps/server/src/modules/share/service.ts:647-652`
- **Description**:
  ```ts
  if (selectedEmails?.length) {
    const emailSet = new Set(selectedEmails);
    recipientsToNotify = share.recipients.filter((r) => emailSet.has(r.email));
  }
  ```
  If the caller passes `selectedEmails: ["alice@nowhere.com"]` and no recipient matches, `recipientsToNotify` becomes `[]` — the route returns `{ notifiedRecipients: [] }` with a 200. The frontend believes its action "succeeded" but no email was sent.
- **Impact**: Silent failure mode; user submits a notify request and sees "0 emails sent" without explanation. Combined with I-3 (email casing), this can happen even when the user thinks they entered the correct emails.
- **Suggested fix**: After filtering, if `selectedEmails` was provided AND `recipientsToNotify.length === 0`, throw `ValidationError("None of the selected emails match this share's recipients")`. Same shape as the "No recipients found" error at line 643-645.

#### I-6: Two `prisma.shareRecipient.findUnique({ where: { trackingToken } })` calls per access — should be one
- **File**: `apps/server/src/modules/share/service.ts:244-253, 292-306`
- **Description**: When a tracking token is present, `getShare` queries `ShareRecipient` twice:
  1. Inside the identification gate (line 245-247) to verify `tokenSatisfiesRequirements`.
  2. After the gate passes (line 293-295) to resolve `recipientId`/`visitorEmail`/`visitorName` for the visit row.

  Both lookups have the same `where: { trackingToken }` clause; the second one's `select`/`include` is implicit (full row). On every share access via tracking token, this is a redundant round-trip.
- **Impact**: 2× DB queries per identified access. Not a correctness bug but a clean code-quality issue and a wasted query budget on SQLite.
- **Suggested fix**: Hoist the recipient lookup outside both branches:
  ```ts
  let recipient: ShareRecipient | null = null;
  if (context?.trackingToken) {
    recipient = await prisma.shareRecipient.findUnique({ where: { trackingToken: context.trackingToken } });
    if (recipient && recipient.shareId !== share.id) recipient = null;
  }
  // ...gate uses `recipient`, later visit-tracking also uses `recipient`
  ```

#### I-7: `notifyRecipients` token-backfill race can produce stale invitation links
- **File**: `apps/server/src/modules/share/service.ts:660-708`
- **Description**: The inline comment (lines 663-668) acknowledges that the three writes per recipient are non-transactional and accepts partial state. But there's a worse case the comment doesn't cover: **two concurrent `notifyRecipients` calls** for the same share. Both might see `recipient.trackingToken === null` for a pre-existing recipient. Both generate distinct random tokens. Both call `update`. The second update wins. The email sent by call #1 contains a token that no longer works — the recipient gets a dead link.

  Likelihood is low (you need two near-simultaneous notify calls), but realistic when an admin double-clicks the "Notify all" button in the UI.
- **Impact**: Email contains a tracking link that doesn't resolve to the recipient (the lookup `where: { trackingToken }` returns null), so the recipient is silently demoted to anonymous. They can still access the share but tracking is broken for them.
- **Suggested fix**: Either:
  - Wrap the token backfill in a conditional update: `UPDATE shareRecipient SET trackingToken = ? WHERE id = ? AND trackingToken IS NULL` and re-read if `count === 0`.
  - Or generate tokens on `ShareRecipient` insertion (the create paths in `createShare` already do this; only legacy/pre-fix rows need backfill). A one-shot migration to populate all null tokens would obviate the race entirely.

  Note: pre-fix legacy rows shouldn't exist in this project (no production, no legacy per CLAUDE.md). The backfill code can be removed entirely if the create paths are audited to guarantee tokens are always generated. Simpler and safer.

### Minor

#### M-1: `metadata` endpoint not rate-limited individually
- **File**: `apps/server/src/modules/share/routes.ts:738-768`
- **Description**: The metadata endpoint is unauthenticated and inherits the global `100/minute` rate limit (per IP). Alias enumeration is bounded by the 3-30-character alphanumeric alias regex, but a botnet could brute-force the namespace for valid shares and gather their metadata (name, description, file count, expiration state). Names/descriptions may contain sensitive labels.
- **Suggested fix**: Apply the same per-route rate-limit pattern used on `/identify`. Suggested: `max: 60, timeWindow: "1 minute", keyGenerator: (req) => req.ip`. The metadata is meant for OG-preview bots, which hit each URL ~once.

#### M-2: Unsubscribe HTML pages hardcode `lang="en"` and English copy
- **File**: `apps/server/src/modules/notification/routes.ts:53, 77, 97`
- **Description**: All three rendered pages (`renderConfirmPage`, `renderSuccessPage`, `renderErrorPage`) are English-only with `<html lang="en">`. A French user receives an email in French (via i18n loader), clicks the unsubscribe link, and lands on an English-only page.
- **Suggested fix**: Either localize via the `t()` helper from `email/i18n/loader.ts` (the user's locale can be carried in the JWT payload or fetched via `prisma.user.findUnique({ where: { id: userId }})` after verification), or accept this as a known limitation and document it.

#### M-3: `nameFieldRequired` / `emailFieldRequired` returned as plain `z.string()` in metadata response schema
- **File**: `apps/server/src/modules/share/routes.ts:758-759`
- **Description**:
  ```ts
  nameFieldRequired: z.string(),
  emailFieldRequired: z.string(),
  ```
  The actual values are `FieldRequirement` enum members (`HIDDEN`/`OPTIONAL`/`REQUIRED`). The `ShareResponseSchema` (`dto.ts:127-132`) correctly uses `z.nativeEnum(FieldRequirement)` for the same fields. Inconsistency; weaker contract for the metadata endpoint.

#### M-4: `notifyRecipients` sequential `await` per recipient
- **File**: `apps/server/src/modules/share/service.ts:662-709`
- **Description**: The `for (const recipient of recipientsToNotify)` loop awaits each recipient's three writes sequentially. For a share with 50 recipients, that's 50× (lookup + EmailJob insert + update), serial. The prior review flagged the partial-state concern but the sequential I/O cost remains.
- **Impact**: Slow notify operation for large recipient lists. Combined with the 30s default queue interval, the user might wait several seconds for the route to return.
- **Suggested fix**: `Promise.allSettled` over the per-recipient operations. SQLite single-writer means inserts will still serialize at the DB layer, but at least the round-trips and template renders can overlap. Bound concurrency to e.g. 10 if SQLite contention becomes visible.

#### M-5: `parseVisitorCookie` accepts a cookie missing both name and email
- **File**: `apps/server/src/modules/share/routes.ts:31-46`
- **Description**: The function returns `{ alias, name?, email? }`. It does NOT validate that at least one of `name`/`email` is present. The cookie content is later re-validated against share requirements in the gate, so security is preserved. But returning a cookie with both fields undefined is functionally equivalent to no cookie — yet the gate at `service.ts:259-262` treats it as "cookie present" via `!!context?.visitorCookie`.

  Under the current gate logic (cookieSatisfiesRequirements requires non-null `name`/`email` when REQUIRED), an empty cookie is correctly rejected when fields are REQUIRED. But for shares with `nameFieldRequired = OPTIONAL` and `emailFieldRequired = OPTIONAL`, the cookie passes the gate trivially because `!== "REQUIRED"` is true on both sides. So an empty cookie marks a visit as "identified-via-cookie" with no actual identification info — pollutes `ShareVisit` (related to I-4).
- **Suggested fix**: In `parseVisitorCookie`, return `undefined` if both `name` and `email` are null/undefined/empty-string. Treat content-less cookies as no cookie at all.

#### M-7: `ShareAccessQuery.t` accepts arbitrary string, triggers DB lookup
- **File**: `apps/server/src/modules/share/routes.ts:48-50` + `service.ts:244-247, 292-295`
- **Description**: The tracking token is generated as `crypto.randomBytes(24).toString("base64url")` — a fixed 32-character base64url string. The route schema accepts any string. A malicious caller can send arbitrarily long `t=` values; the server runs `prisma.shareRecipient.findUnique({ where: { trackingToken } })` regardless. Unique index lookup is O(log n) so no DoS concern, but it's a wasted query per malformed request and creates a small fingerprint of "share existed, query returned null."
- **Suggested fix**: Add `.regex(/^[A-Za-z0-9_-]+$/).min(20).max(64)` to `ShareAccessQuery.t`. Reject obviously-malformed tokens at the schema level.

#### M-8: `notifyRecipients` returns 200 with empty list even when `selectedEmails` is `[]` (not just absent)
- **File**: `apps/server/src/modules/share/service.ts:649`
- **Description**: `if (selectedEmails?.length)` is false for both undefined AND `[]`. An empty array is treated as "notify all" rather than "notify none." That's a surprising semantic. The frontend should probably never send `[]`, but server-side defensive handling is missing.
- **Suggested fix**: Distinguish `selectedEmails === undefined` (notify all) from `selectedEmails.length === 0` (notify none — reject as ValidationError). Or, simpler: if `selectedEmails` is explicitly an empty array, throw `ValidationError`. The current implicit "fall through to notify-all" is a foot-gun.

#### M-9: `reverse-share/service.ts:189-198` mirrors `share/service.ts` notification reset but uses a separate `prisma.reverseShare.update` after the main update
- **File**: `apps/server/src/modules/reverse-share/service.ts:189-198`
- **Description**:

  const updatedReverseShare = await this.reverseShareRepository.update(id, data);
  if (data.expiration && reverseShare.expiration) {
    const newExp = new Date(data.expiration);

Here, `updatedReverseShare` is returned to the caller WITHOUT the reset flags reflected (it was already serialized before the second update). The caller's response says `notifiedForExpiring: true` even though the row is now `false`. Stale read.
- **Impact**: Caller's response is out of sync with persisted state. Minor unless the frontend acts on the returned flag values.
- **Suggested fix**: Either merge the flag reset into the repository `update(id, data)` call (preferred — atomic), or re-fetch after the second update before returning. The share-service approach is the right pattern.

## Positive Observations

- **The C-1/C-2/C-3 fixes are clean.** `formatShareResponse(isOwner)` is a single-source-of-truth gate for recipient leakage. The cross-share token check (`recipient.shareId === share.id`) is applied in both the gate AND the visit-recording code. The cookie re-validation correctly handles requirement tightening after the cookie was set.
- **`trackShareDownload` extraction** (`file/routes.ts:141-208`) addressed the prior I-3 duplication concern cleanly. The helper is module-private, has a single clear responsibility, and is fire-and-forget at the call sites.
- **URL construction in `notifyRecipients`** now uses `new URL(...) + searchParams.set("t", ...)` (line 680-682) — addresses the prior I-5 query-string-clobber concern. Correct, robust.
- **Unsubscribe token verification** (`notification/service.ts:123-170`) is solid: base64url-only, constant-time signature check via `timingSafeEqual` with explicit length-mismatch handling, proper `exp` validation, payload type-checking. The hand-rolled HMAC JWT is correctly implemented.
- **Owner-vs-visitor branching** in `getShare` is correctly placed before any state mutation — owners don't increment views, don't trigger ShareVisit creation, don't fire `share_accessed`. The early-return at line 191-193 is the right pattern.
- **Test coverage of the security regressions is comprehensive:** `visitor-identification.test.ts` includes explicit regression tests for the prior C-1 (recipients stripped), C-2 (cross-share token rejected), and C-3 (cookie re-validated when requirements change).
