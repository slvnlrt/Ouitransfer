## Minor

### ~~M-1~~ [x]: `send()` is used as fire-and-forget but the EmailJob inserts can throw
- **File(s)**: `email/service.ts:245-257` (failed-job insert inside the render `catch`),
  `:298-313` (main insert)
- **Description**: Both `prisma.emailJob.create(...)` calls are unguarded. If the DB
  write fails (DB down, unique-constraint, disk full), the exception propagates out of
  `send()`. The render-failure path is the most fragile: the `catch (renderError)` block
  itself calls `create()` (line 245), so a DB error there escapes the handler meant to
  contain the failure. Most callers wrap `send()` in try/catch (`notifyShareCreator`
  in `share/service.ts:147-159`, `trackShareDownload` in `file/routes.ts:151-233`, all
  scheduler checks, `upload.service.ts:489`) so impact is contained in practice — but
  the admin test route awaits `send()` directly (`notification/routes.ts:424`) inside a
  handler whose only explicit failure path is the 400 "not enqueued"; a DB error there
  would surface as a 500 rather than a clean response. Severity is Minor because callers
  largely guard it, but the documented "insert a row and return immediately" contract is
  not actually guaranteed.
- **Expected**: `send()` should never throw due to an email/DB problem — log and return
  `{ enqueued: false }`.
- **Fix**: Wrap both inserts in try/catch returning `{ enqueued: false }` on failure,
  and document the no-throw contract on the method.

### ~~M-2~~ [x]: `appUrl` is read twice per send with a comment asserting a cache this file can't guarantee
- **File(s)**: `email/url-builder.ts:5-17`, `service.ts:141-147` + `:203`→`:390-392`
- **Description**: `getAppUrl()` calls `getConfigValue("appUrl")` on every call; `send()`
  invokes it once for the gate (line 143) and again via `buildUnsubscribeUrl()`
  (line 203, for types with `hasUnsubscribe`). The doc comment claims this is cheap due
  to an "in-memory config cache" — a property of `config/service.ts` (out of scope) this
  file cannot guarantee. If config isn't cached this is extra DB round-trips per email.
  Not a correctness bug.
- **Fix**: Resolve `appUrl` once at the top of `send()` and pass it to the builders, or
  verify the config cache and drop the comment.

### ~~M-3~~ [x]: `appName` fallback is a hardcoded literal duplicated from the config default
- **File(s)**: `email/service.ts:150-155`
- **Description**: On `getConfigValue("appName")` failure the code falls back to the
  literal `"Ouitransfer"`, duplicating a magic string that could diverge from the seed
  default. Harmless, low impact.
- **Fix**: Centralize a shared `DEFAULT_APP_NAME` constant.

### ~~M-4~~ [x]: `digest_pending` jobs have no consumer/cleanup — confirmed unreachable in 8.2 but inert
- **File(s)**: `service.ts:286-313` (would create it), `queue.ts:207-211` (selects only
  `pending`), `:178-182` (cleanup only `sent`); gated by
  `notification/service.ts:8,83-87` (rejects `daily_digest`)
- **Description**: `send()` can create a `digest_pending` job when
  `frequency === "daily_digest"`, which no `processBatch()` or `cleanupSentJobs()` would
  ever touch. **Confirmed unreachable**: `updateUserPreferences()` restricts frequencies
  to `["immediate","disabled"]` (lines 83-87), so no `NotificationPreference.frequency`
  can be `daily_digest`, so `resolveFrequency()` never returns it. Dead-but-correct,
  matching the spec's explicit deferral. Flagged only to track the latent accumulation
  risk for when digest ships. Note: the route Zod schema (`routes.ts:209-216`) types
  `frequency` as `z.string()` and relies entirely on the service-layer
  `ALLOWED_FREQUENCIES` check — that check is present and correct, so it is not
  exploitable, but tightening the Zod enum would be defense in depth and keep OpenAPI
  honest.

### ~~M-5~~ [x]: Hand-rolled unsubscribe JWT (acknowledged tech debt) — verified correct
- **File(s)**: `unsubscribe-token.ts:42-43`
- **Description**: Not a defect. HS256, purpose-derived HMAC key from `JWT_SECRET`,
  `alg` header pinned (algorithm-confusion defense), `timingSafeEqual` with a length
  guard, `exp` enforced, required-field checks. Flagged only so the `// TECH DEBT` note
  isn't lost.
- **Fix**: None now; migrate to `jose` if rotation/revocation/RS256 is ever needed.

## Retracted findings (false positives — code is correct)
- **share_downloaded is unwired (RETRACTED)**: `file/routes.ts:145-234`
  `trackShareDownload()` records a `ShareVisit` with `action:"download"`, validates the
  file belongs to the claimed share (`:163-166`), excludes the owner (`:168-171`),
  resolves visitor identity from the tracking token, and calls
  `emailService.send("share_downloaded", { userId: creatorId, relatedId: shareId, … })`
  (`:217-230`). It is invoked from both download endpoints (`:1021`, `:1118`).
- **Inactivity alert can never re-arm (RETRACTED)**: `file/routes.ts:209-212` writes
  `Share.lastDownloadedAt = now()` **and** resets `inactivityAlertSent: false` on each
  non-owner download, so `notification.scheduler.ts:checkInactiveShares()` correctly
  re-arms. The lifecycle matches the scheduler's documented contract and the test at
  `notification.scheduler.test.ts:436`.
- **`reverse_share_uploaded` cooldown mis-scoped (RETRACTED)**:
  `reverse-share/upload.service.ts:480` passes `relatedId: reverseShare.id`, so the
  cooldown is correctly per-reverse-share, not in the global `NULL` bucket. (The generic
  `relatedId ?? null` coalescing in `service.ts:186` remains a theoretical hardening
  opportunity but is not triggered by any actual caller — all cooldown-bearing callers
  pass `relatedId`: `share_accessed`/`share_max_views` via `notifyShareCreator`
  `relatedId = share.id`, `share_downloaded` via `trackShareDownload` `relatedId = shareId`,
  `reverse_share_uploaded` via upload service `relatedId = reverseShare.id`. So this is
  not even a Minor finding.)
- **`notifyOnDownload` override fails without userId (RETRACTED)**: `trackShareDownload`
  always passes `userId: share.creatorId` (`file/routes.ts:220`), so the
  `resolveFrequency` override path (`service.ts:368-376`) is always reached for real
  downloads. The override + `skipCooldown` work as designed.

## Positive Observations
- **i18n drift is enforced at CI**: `i18n-placeholder-consistency.test.ts` invokes every
  render fn, extracts each `{token}` from every locale string, and asserts it maps to a
  schema field, the universal `appName`, or a declared computed extra
  (`fileList` for `files_auto_deleted` / `reverse_share_uploaded`), in **both** en and fr.
  This catches typos and payload/template drift that boot-time `validateAllI18nKeys()`
  (key existence only) would miss. Combined with the boot validator this is a solid
  two-layer i18n guard.
- **SMTP header injection is properly defended**: `sanitizeForSubject()`
  (`service.ts:25-31`) strips CR/LF from all subject params including `appName`; the i18n
  `interpolate()` HTML-escapes substituted values via `tHtml`/`createTranslationFn`
  (`loader.ts:302-306`). Clean split between plain-text (subject) and HTML-escaped (body)
  translation paths. `base-layout.ts` additionally escapes `appName`/`subtitle`/CTA label
  and validates `href` schemes via `safeHref()` (rejects `javascript:` etc.).
- **Unsubscribe is well-architected end to end**: stateless signed token; two-step
  GET-confirm / POST-perform flow to defeat email-scanner prefetch
  (`routes.ts:265-354`); GET does not mutate; POST is CSRF-exempt + rate-limited (30/h);
  and `unsubscribeUser()` (`notification/service.ts:112-135`) silently no-ops for
  unknown / critical / non-configurable types, so a crafted or replayed token can never
  disable `password_reset`/`welcome`. DisplayName badge and token are `escapeHtml`-ed.
- **Visitor tracking is correctly gated**: `trackShareDownload` validates file↔share
  membership before counting (prevents inflating another share's stats), excludes the
  owner, and awaits the `ShareVisit` insert before notifying (`share/service.ts:363-389`
  does the same for access) so the owner is never notified about a visit that wasn't
  recorded.
- **Queue locking is race-safe** for the single-process model:
  `updateMany({ where: { id, status: "pending" } })` compare-and-set with
  `lockResult.count !== 1` skip (`queue.ts:233-243`); `isProcessing`/`wakePending` flags
  are mutated only between awaits on the main thread, so deferred-wake is sound.
- **Payload validated at the boundary**: `send()` re-validates `options.data` against the
  catalog Zod schema (`service.ts:117-123`) and uses the parsed result — defense against
  untyped callers; `isoDateString` (`catalog.ts:11`) rejects ambiguous date formats.
- **Render failures fail fast**: render errors create a `failed` job with `maxAttempts: 0`
  and a descriptive `lastError` — no pointless retries of a deterministic error. (See M-1
  for the one residual gap: the insert itself can throw.)
- **Exponential backoff with cap** (`min(3600, 60·2^(n-1))`) + stuck-job recovery (5-min
  lock timeout, on-boot + periodic, treated as a failed attempt with backoff) — solid
  crash resilience.
- **Schedulers are idempotent & guarded**: `notification.scheduler.ts` filters on
  `notifiedForExpiring/Expired === false`, flips the flag only **after** a successful
  enqueue (`result.enqueued`), excludes deactivated creators, wraps each check in its own
  try/catch, and the expiring/expired split into two flags prevents one from suppressing
  the other. The inactivity check correctly re-arms via the download path's flag reset.
- **max_views notification uses a compare-and-set flag flip** (`share/service.ts:394-409`)
  with `updateMany({ where:{ notifiedForMaxViews:false } })` to prevent duplicate sends —
  good concurrency hygiene.
- **Admin endpoints correctly gated**: `/admin/email/stats` and `/admin/email/test` use
  `adminPreValidation({ allowSetupBypass: false })`; the test route resolves the admin's
  own locale and returns 400 when not enqueued.
