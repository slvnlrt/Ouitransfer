# 8.2 Email Notifications — Server Core Review (Pass 4)

**Date**: 2026-05-29
**Reviewer**: Code Review Agent
**Scope**: `apps/server/src/modules/email/` (catalog, service, queue, transport, templates, i18n, url-builder, unsubscribe-token, events, notification.scheduler), `apps/server/src/modules/notification/` (routes, service), all related tests.

## Summary

Overall the email subsystem is **well-engineered and largely matches the spec**. The 5-layer architecture (service → catalog → templates → i18n → queue → transport) is cleanly separated, the type derivation around `notificationCatalog` provides real compile-time safety, and the XSS / SMTP-injection defenses are taken seriously and verified by tests. Connection pooling, hash-based transporter recreation, exponential backoff, stuck-job recovery, cooldown-based deduplication, wake-on-priority — all the foundational pieces are present.

That said, there are a handful of **real bugs**, mostly around the notification scheduler treating "I called `send()`" as "the user was notified" when in fact the send was silently swallowed (preferences disabled, cooldown, SMTP off, missing appUrl). The result is a `notifiedForExpiring` / `notifiedForExpired` / `inactivityAlertSent` flag that gets set to `true` even when no email was queued, permanently preventing the user from ever receiving the notification once they re-enable it. This is the most important issue in the patch.

A few additional Important issues exist around the cooldown logic (failed jobs extend the cooldown), a race condition that can drop a `wake` event, and missing defense-in-depth in the unsubscribe flow.

The schema also deviates from the spec in one place: `notifiedForExpiration` was split into two flags (`notifiedForExpiring` / `notifiedForExpired`). The split is actually *better* than the spec, but should be documented as a deliberate deviation.

Tests are thorough. Coverage of the queue scheduler, the i18n loader, the base layout, and the catalog is genuinely good — including XSS regression tests against the real `en.json`. The main test gap is integration coverage: there is no `app.inject()`-level test that runs the full `send() → queue → SmtpTransport mock → DB state` cycle end-to-end.

## Critical

### C-1: Scheduler marks shares as "notified" even when no email was queued

- **File**: `apps/server/src/modules/email/notification.scheduler.ts:52-75, 102-126, 158-192, 219-242, 266-289`
- **Issue**: Every `check*` function calls `emailService.send(...)` and, on resolution, unconditionally updates the share's `notifiedForExpiring` / `notifiedForExpired` / `inactivityAlertSent` flag to `true`. But `emailService.send()` returns *successfully and silently* in multiple cases where **no email job is created**:
  - `smtpEnabled !== "true"` (line 75 of service.ts)
  - `appUrl` not configured (line 84)
  - User preference is `"disabled"` (line 102)
  - Cooldown window matched (line 118)

  Consequence: if SMTP is not yet configured, or the user disabled the notification once, or the user is unsubscribed at the time the scheduler runs, the flag flips to `true` permanently. The next daily run skips this share (filter `notifiedForExpiring: false`). When the user later re-enables the preference / SMTP comes online, **they will never receive the expiring / expired / no-activity email for this share** — the flag is set, but no email was ever sent.

  This silently breaks four spec-mandated notification flows (`share_expiring`, `share_expired`, `share_no_activity`, `reverse_share_expiring`, `reverse_share_expired`) for any user who happened to be unsubscribed or had SMTP off at the moment of expiration.

  Tests (`notification.scheduler.test.ts`) do not catch this because they mock `emailService.send` as a no-op resolved promise and only check that the flag was set "after a send call" — they never assert that the flag is *not* set when send is a no-op.

- **Fix**: `emailService.send()` should report back whether a job was actually created, e.g. return `{ enqueued: true | false, reason?: "smtp_disabled" | "preference_disabled" | "cooldown" | "render_failed" | ... }`. The scheduler then sets the flag only when `enqueued === true`. The render-failed branch (which creates a `failed` `EmailJob` row) should also count as "enqueued" so we don't retry on the next daily run.

  Alternative: drive the flag transition off of `EmailJob` insertion, e.g. mark the share as notified inside an `afterCreate` hook or in `send()` itself when a `pending`/`digest_pending` row is committed.

  Either way, add tests covering: SMTP disabled → flag NOT set; preference disabled → flag NOT set; cooldown match → flag NOT set.

### C-2: `notification.scheduler.ts` lives in the wrong module

- **File**: `apps/server/src/modules/email/notification.scheduler.ts` (whole file)
- **Issue**: The plan (Batch 9, file map line 60) and the review brief both state this file lives in `apps/server/src/modules/notification/`. It is in `apps/server/src/modules/email/`. The `notification/` module today contains only `routes.ts` and `service.ts` (user preferences + unsubscribe).

  Why this matters:
  1. It is genuinely a notification-domain concern (share expiration, inactivity), not an email-transport concern. The email module should know nothing about Share / ReverseShare models.
  2. It creates an awkward coupling: `email/notification.scheduler.ts` imports `prisma.share` and `prisma.reverseShare`, pulling business-model knowledge into the email layer. This is the kind of leak the layered design exists to prevent.
  3. The tests import `from "../notification.scheduler.js"` (i.e. `email/notification.scheduler.js`), so renaming/moving requires test churn — but the cost is acceptable and the cleanup is small.

- **Fix**: Move the file to `apps/server/src/modules/notification/expiration.scheduler.ts` (or `share-lifecycle.scheduler.ts`) and update the two `server.ts` imports + the test file. The file then imports `emailService` from `../email/service.js` (correct direction). Mark this as a clean-up step before the feature is declared "Done."

## Important

### I-1: Cooldown is extended by failed deliveries

- **File**: `apps/server/src/modules/email/service.ts:107-125`
- **Issue**: The cooldown query is:
  ```ts
  const recent = await prisma.emailJob.findFirst({
    where: { type, to: options.to, relatedId: effectiveRelatedId ?? null, createdAt: { gt: cutoff } },
  });
  ```
  No `status` filter. If a previous `share_accessed` notification was enqueued 14 minutes ago and SMTP failed (status `failed` after 3 retries, but the `createdAt` is still inside the 15-minute window), the next legitimate visit will be deduplicated against the failed job. The user is silently denied a notification for an *un*delivered prior event.

  This is the inverse of what cooldown is for. The intent is "don't re-notify about an event we already notified about" — a failed send is precisely the case where we *should* try again.

- **Fix**: Add `status: { in: ["pending", "processing", "sent", "digest_pending"] }` (i.e. exclude `failed`) to the cooldown `where` clause. Add a test that creates a `failed` job 5 minutes ago and verifies the next `send()` for the same triple is NOT deduplicated.

### I-2: `wake` event can be silently lost between `processBatch` completion and `scheduleNext`

- **File**: `apps/server/src/modules/email/queue.ts:300-326, 361-391`
- **Issue**: Sequence:
  1. Normal tick fires (handle X). `processTick()` calls `processBatch()` which sets `isProcessing = true`, runs, sets `isProcessing = false` in `finally`.
  2. `processBatch` finishes. Execution returns to the `setTimeout` callback in `scheduleNext`, which is about to call `void scheduleNext()` (line 349).
  3. Between those two synchronous lines there is no `await`, but if a `wake` event was emitted DURING `processBatch` while `isProcessing` was true, the `wakePending` branch in the `finally` already scheduled a new immediate-tick handle Y and set `currentTimeout = Y`.
  4. Back in the outer scheduleNext callback: `if (currentTimeout === handle)` — `handle` is X, `currentTimeout` is Y → returns early, no chained `scheduleNext()`. **OK in that case.**

  But the race that DOES drop the wake: handle X fires, `processBatch` runs and finishes with `wakePending === false`. `isProcessing` is set to `false`. Execution returns to scheduleNext callback. Before the next synchronous line runs, the event loop processes a microtask that triggers `onWake` (e.g. an external `emit` from `service.send` for a priority-1 job that was inserted right at this moment). `onWake` sees `isProcessing === false`, clears `currentTimeout` (still X — already fired, no-op), creates handle Y with `setTimeout(... , 0)`, sets `currentTimeout = Y`. Then the outer scheduleNext callback resumes, calls `void scheduleNext()` which creates handle Z with the normal interval and sets `currentTimeout = Z`. Handle Y fires next tick, checks `if (currentTimeout !== handle) return` — `handle` is Y, `currentTimeout` is Z → returns. The wake event is silently dropped.

  Note: in pure synchronous JS this is theoretically impossible, but `emit('wake')` from `service.send` runs inside an `await` boundary — at any of the `await` points in `processBatch` between `isProcessing = false` and the outer `scheduleNext()` call, the event loop can interleave. In practice this means the wake will be dropped under load.

- **Fix**: Either:
  - Use a single shared "pending wake" flag that survives across the scheduleNext boundary: `onWake` always sets `wakePending = true` and triggers a unified `maybeProcessNow()` that checks `if (wakePending && !isProcessing)`.
  - Or: clear `currentTimeout = null` BEFORE setting `isProcessing = false` and have `scheduleNext` short-circuit if `wakePending` is set, letting `onWake`'s own timer take over.

  The simpler / safer fix is the first: collapse `wakePending` and `isProcessing` into a single state machine.

  Add a test that emits `wake` repeatedly during `processBatch` and verifies no event is dropped (every `wake` results in either an immediate or deferred tick).

### I-3: Unsubscribe handler does not validate that the type is actually unsubscribable

- **File**: `apps/server/src/modules/notification/service.ts:107-113`, `apps/server/src/modules/notification/routes.ts:235-255`
- **Issue**: `unsubscribeUser(userId, type)` upserts `NotificationPreference` with `frequency: "disabled"` for *any* `type` string. The route handler trusts the verified JWT and calls it directly. There is no check that `notificationCatalog[type].hasUnsubscribe === true` or `.configurable === true`.

  Today this is "safe" because `emailService.generateUnsubscribeUrl` only runs when `hasUnsubscribe: true`, so no token for a critical type is ever signed in the wild. But:
  - Critical types like `password_reset` skip preference checks (`service.ts:98 if (!entry.isCritical && options.userId)`), so a forged "disabled" row is *currently* inert — but this is implicit defense, not explicit.
  - If a future change makes critical types respect preferences, or if `hasUnsubscribe` is ever toggled to `true` on a critical type, the user can silently disable password reset emails through a re-used token.
  - The catalog grows; the protective invariant is easy to break inadvertently.

- **Fix**: In `unsubscribeUser`, validate:
  ```ts
  const entry = notificationCatalog[type as NotificationKey];
  if (!entry || entry.isCritical || !entry.configurable) {
    // Don't throw — just no-op to avoid leaking which types exist
    return;
  }
  ```
  Same guard in `verifyUnsubscribeToken` would be even better (reject at parse time). Add a test: token signed for `welcome` → POST `/notifications/unsubscribe` → no `NotificationPreference` row created.

### I-4: SMTP header injection via admin-controlled `appName`

- **File**: `apps/server/src/modules/email/service.ts:88-94, 188-199`
- **Issue**: `sanitizeForSubject` strips CR/LF from payload params (`sanitizedParams = sanitizeForSubject(dataParams)`). Good. But the subject is interpolated as `{ appName, ...sanitizedParams }` — `appName` is **not** sanitized:
  ```ts
  appName = await getConfigValue("appName");
  // ...
  subject = await t(options.locale, `${prefix}.subject`, { appName, ...sanitizedParams });
  ```
  An admin who sets `appName` to `"Ouitransfer\r\nBcc: attacker@example.com"` would inject an SMTP header through the rendered subject. nodemailer normalizes some headers but is documented to pass `subject` through; long-form Unicode whitespace and certain CRLF sequences have been used in past exploits.

  Yes, the admin is trusted — but the existing `sanitizeForSubject` already implements exactly this defense for everything except the one value that comes from a *settings* page (the most likely vector for a typo, paste error, or compromised admin).

- **Fix**: Pipe `appName` through `sanitizeForSubject` as well, or just sanitize the final merged params object:
  ```ts
  const merged = sanitizeForSubject({ appName, ...dataParams });
  subject = await t(options.locale, `${prefix}.subject`, merged);
  ```
  Also apply to `createTranslationFn(options.locale, { appName })` — the layout footer interpolates appName via HTML-escape, so HTML is safe, but plain-text/text alt body uses `createPlainTranslationFn`-style behaviour for the footer in `renderText`. Defense-in-depth is cheap.

### I-5: Stale TODO comment on `share_downloaded` catalog entry

- **File**: `apps/server/src/modules/email/catalog.ts:341-347`
- **Issue**: The comment block reads:
  ```ts
  /**
   * Cooldown is per-share (not per-file). ...
   * TODO(8.x): Wire this type when download-specific notifications are needed.
   * Currently only `share_accessed` is wired in share/service.ts.
  ```

  But `share_downloaded` IS wired — in `apps/server/src/modules/file/routes.ts:191-205` (the `trackShareDownload` helper). The comment is misleading and will confuse the next reader into thinking the feature is incomplete.

### I-6: `getMaxRetries()` silently coerces `"0"` to `3`

- **File**: `apps/server/src/modules/email/queue.ts:65-73`
- **Issue**:
  ```ts
  const parsed = parseInt(value, 10);
  return Number.isFinite(parsed) && parsed > 0 ? parsed : 3;
  ```
  `parsed > 0` rejects `0`, falling back to the default `3`. So if an operator explicitly disables retries by setting `emailQueueMaxRetries = "0"`, the system silently retries 3 times anyway. The same pattern in `getIntervalMs` is correct for intervals (0 doesn't make sense), but for retry count `0` is a meaningful value: "don't retry, fail on first attempt."

- **Fix**: `parsed >= 0` for the retry count, with a separate guard `Number.isFinite(parsed)`. Document that `0` means no retries (fail-fast on first SMTP error).

### I-7: Daily scheduler tick happens at "server-start + N×24h," not aligned to wall clock

- **File**: `apps/server/src/modules/email/notification.scheduler.ts:341-358, 391-405`
- **Issue**: The scheduler runs once on boot and then every 24h. There is no alignment with `emailDigestHour` (the spec config key, seeded with default 8) or any other wall-clock target. If the server is restarted at 23:50, the next notification run is the next day at 23:50.

  The code has an acknowledging comment ("DESIGN LIMITATION") so this is a *known* deferral, but it's worth flagging because:
  - The `emailDigestHour` config key already exists in the schema/seed (per spec) and creates the implicit promise that timing is configurable.
  - Operators will be surprised that "expiring soon" emails arrive in the middle of the night.

  This is borderline Minor; I'm flagging it as Important because the seeded config key implies a feature that isn't actually wired.

- **Fix**: Either (a) compute the delta to the next `emailDigestHour:00` UTC and set the first timeout accordingly, then resume 24h intervals; or (b) remove `emailDigestHour` from the seed until the digest scheduler is implemented, to avoid creating an unfulfilled expectation. (b) is the YAGNI-consistent choice.

### I-8: Missing integration test exercising the full `send → queue → transport` path

- **File**: `apps/server/src/modules/email/__tests__/*.test.ts` (all)
- **Issue**: Every test file mocks the layer immediately below it. `email-service.test.ts` mocks `renderLayout`, `prisma`, `transport`. `queue.test.ts` mocks `prisma`, `transport`, `events`, `catalog`. There is no test that wires real `EmailService` → real catalog → real i18n → real `renderLayout` → DB-mocked `EmailJob` insert → real `processBatch` → mocked `transporter.sendMail` and verifies the entire round-trip produces the expected HTML/text/subject delivered to nodemailer.

  This is the exact category of test that CLAUDE.md flags as critical: *"Service-layer tests are necessary but not sufficient — for security-critical flows, always add at least one `app.inject()` integration test that exercises the full request lifecycle."* The email subsystem has plenty of unit coverage but no end-to-end smoke test. Three of the bugs I flagged above (C-1, I-1, I-2) would be hard to write a unit test for without inventing artificial mock boundaries — but trivial to surface in an integration test.

  `email-service-i18n.test.ts` is the closest, but it still mocks transport and queue.

- **Fix**: Add an integration test that:
  1. Builds the real app via `buildApp()`.
  2. Mocks ONLY `nodemailer.createTransport` to capture sent mails.
  3. Triggers a real flow (e.g. POST to a route that calls `emailService.send`).
  4. Drives the queue scheduler one tick (e.g. by mocking `setTimeout` with `vi.useFakeTimers` and advancing).
  5. Asserts the captured mail has the expected `to`, `subject`, `html`, `text`, and `List-Unsubscribe` header.

## Minor

### M-1: `notification/routes.ts` confirmation/success/error pages are English-only

- **File**: `apps/server/src/modules/notification/routes.ts:42-106`
- **Issue**: The file acknowledges this with a `LIMITATION:` comment. Fine to defer, but as written the page hardcodes `<html lang="en">` and English strings. A French user clicking unsubscribe sees an English page. The JWT contains `userId` but not `locale`. Could be resolved by a DB lookup on `userId` to fetch `user.locale` and a localized render — modest extra DB call.
- **Fix**: After verifying the token, do `const user = await prisma.user.findUnique({ where: { id: userId }, select: { locale: true } })` and pick page strings from a small inline map keyed by `user.locale ?? "en"`. Or accept the current state explicitly.

### M-2: `isoDateString` Zod refinement is overly permissive

- **File**: `apps/server/src/modules/email/catalog.ts:11-13`
- **Issue**: `z.string().refine((s) => !Number.isNaN(Date.parse(s)))` accepts `"2026"`, `"12/31/2026"`, `"December 31, 2026"`, etc. The name suggests strict ISO 8601. Since payloads come from server-trusted sources today this is acceptable, but the type-safety guarantee implied by Zod is weakened.
- **Fix**: `z.string().datetime({ offset: true })` for full ISO 8601 datetime, or accept the current state and rename the variable to `dateLikeString` to be honest.

### M-3: No date localization or pluralization in email body strings

- **File**: `apps/server/src/modules/email/i18n/messages/en.json`, all template files
- **Issue**: Emails read like `"will expire on 2025-12-31T23:59:59.000Z"` and `"no activity for 1 days"`. Spec section 3 mentioned a two-key plural approach (`"key.one"` / `"key.other"`) but it's not implemented. ISO timestamps in user-facing copy are ugly.
- **Fix**: For 8.2 this is probably acceptable; document as known deferral in the spec or in a TODO in the file. For 5.2 / the i18n pass, plug `Intl.DateTimeFormat(locale).format(date)` into the scheduler before passing to the template, and add `.one` / `.other` keys for the strings that take a count.

### M-4: `cooldownSeconds: 300` on `reverse_share_uploaded` is undocumented

- **File**: `apps/server/src/modules/email/catalog.ts:441-442`
- **Issue**: Spec section 4 only mentions cooldown for noisy types `share_accessed` and `share_downloaded` (both 900s). The catalog also sets `cooldownSeconds: 300` on `reverse_share_uploaded` with a one-line comment. This is a reasonable addition (script-driven upload bursts), but it diverges from the spec without being recorded there.
- **Fix**: Either remove the cooldown if it's not in scope, or add a one-paragraph note to the spec documenting it as a deliberate addition during implementation. Pick one.

### M-5: Schema split `notifiedForExpiration` into two fields

- **File**: `apps/server/prisma/schema.prisma:119-120, 335-336`
- **Issue**: Spec section 2 defines a single `notifiedForExpiration` boolean. Implementation has two: `notifiedForExpiring` and `notifiedForExpired`. The split is *better* — it lets the same share send both an "expiring soon" warning and later an "expired" notification — but it's a silent deviation from the spec.
- **Fix**: Update the spec to reflect the implemented schema. Acknowledge the split as the correct design.

### M-6: `share_expiring` payload schema dropped `daysRemaining`

- **File**: `apps/server/src/modules/email/catalog.ts:132-136`, spec section 3
- **Issue**: Spec defines `ShareExpiringData = { shareName, expiresAt, daysRemaining, shareManageUrl }`. Implementation has `{ shareName, expiresAt, shareManageUrl }`. The template body in en.json doesn't use a days count, so removing it is consistent — but the spec promised the field. Either restore it (and add e.g. "expires in N days" copy) or update the spec.
- **Fix**: Update the spec. Optionally enrich the email body with a relative-time string in a follow-up.

### M-7: `reverse_share_uploaded` body can produce awkward output for empty `fileNames`

- **File**: `apps/server/src/modules/email/templates/reverse-share-uploaded.ts:18-30`
- **Issue**: `const fileList = data.fileNames.join(", ");` — if `fileNames` is `[]`, the resulting body reads `"uploaded 0 file(s) to Upload Request: ."` with a trailing colon and period. Caller is expected to never send empty list, but the template has no guard.
- **Fix**: Either Zod-enforce `z.array(z.string()).nonempty()` on the payload schema, or branch the template body for `fileCount === 0`.

### M-8: `processBatch` job-lock is not atomic

- **File**: `apps/server/src/modules/email/queue.ts:197-208`
- **Issue**: `prisma.emailJob.update({ where: { id: job.id }, data: { status: "processing", lockedAt: ... } })` does not include `status: "pending"` in the where-clause. Two workers concurrently would both lock the same job. The spec explicitly assumes a single Node.js process, so this is documented and OK — but a simple `where: { id, status: "pending" }` would make the queue safe to run on multiple workers without further refactor. Cheap defense-in-depth.
- **Fix**: Use `prisma.emailJob.updateMany({ where: { id: job.id, status: "pending" }, data: ... })` and check `result.count === 1` before sending.

### M-9: `recoverStuckJobs` does not increment attempts

- **File**: `apps/server/src/modules/email/queue.ts:110-126`
- **Issue**: A job stuck in `processing` for 5+ minutes gets reset to `pending` with `lockedAt: null`, but its `attempts` counter is not incremented and `nextAttemptAt` is not pushed back. If the previous attempt actually started sending before the process died (e.g. SMTP send hung for 5+ minutes), the email may have been delivered already — re-sending would duplicate. Also, no backoff: the recovered job will be picked up on the very next tick.
- **Fix**: Treat recovery as a failed attempt — increment `attempts`, set `lastError: "Recovered from stuck processing state"`, and apply the same backoff as a normal SMTP failure. If `attempts >= maxAttempts` after the bump, mark as `failed`.

### M-10: `safeHref` returns `"#"` for invalid URLs, silently producing a useless email

- **File**: `apps/server/src/modules/email/templates/base-layout.ts:65-73`
- **Issue**: If `data.shareLink` is somehow invalid (bug in `buildShareLink`, mis-typed appUrl, etc.), the CTA `href` becomes `"#"`. The email looks normal but the button does nothing. There's no logging.
- **Fix**: In `safeHref`, when the URL is rejected, log a warning via `getLogger()` so the operator can detect the issue from logs. The `"#"` fallback for the actual href is the right user-facing behaviour (better than an XSS vector); logging closes the silent-failure gap.

### M-11: `email-service-i18n.test.ts` does not assert subject-line content

## Positive Observations

- **Type derivation around `notificationCatalog`** is the cleanest part of the patch. `EmailPayloads = { [K in NotificationKey]: z.infer<...> }` gives genuine compile-time safety with zero duplication. The `as const satisfies Record<string, NotificationTypeConfig>` pattern is the right way to get both literal key preservation and shape-checking.

- **XSS defense is taken seriously and verified.** The split between `t()` / `createPlainTranslationFn` (no escaping, plain-text contexts) and `tHtml()` / `createTranslationFn` (HTML-escaping, HTML body) is the right design, and `catalog.test.ts` has direct regression tests with `<script>alert(1)</script>` payloads that exercise the full render pipeline and assert the raw script tag does not appear in the HTML output. `base-layout.test.ts` adds `safeHref` tests for `javascript:`, `data:`, `ftp:` schemes. Good coverage of the security-critical surface.

- **SMTP header injection defense** via `sanitizeForSubject` (CR/LF stripping on payload params before subject interpolation) is the right approach. Only `appName` slipped through (I-4).

- **`SmtpTransport` design** — pooled connection, SHA-256 config hash for change detection, separated draft-config testing (`testConnection` with override), translation of `listUnsubscribeHeader` → RFC 8058 headers — is well-thought-out and well-tested. The "exclude `smtpFromName`/`smtpFromEmail` from the hash" detail (`transport.ts:250-262`) is a thoughtful touch that avoids needless transporter recreation on cosmetic config changes.

- **Unsubscribe JWT implementation** is correct: HS256 algorithm header enforced (prevents algorithm-confusion attacks), constant-time signature comparison via `crypto.timingSafeEqual`, key derivation via HMAC of `JWT_SECRET` + `"unsubscribe"` label (isolates key space without adding a new env var), `exp` enforced and `iat` documented as informational. The two-step GET-confirm + POST-perform flow correctly prevents email-scanner auto-unsubscribe.

- **Queue scheduler patterns** — chained `setTimeout` (not `setInterval`, prevents overlap), `currentTimeout` handle comparison to invalidate superseded timers on stop/wake, periodic stuck-job recovery and sent-job cleanup driven by tick counters, single-retry-on-DB-failure for status updates — these are all idiomatic and match the codebase's other schedulers.

- **Catalog tests** are thorough and act as a living spec — exactly 22 entries, critical types invariants, cooldown values, configurable/unsubscribe matrix, and a real-i18n smoke test that catches missing keys in `en.json`. The `not.toMatch(/\{[a-zA-Z][a-zA-Z0-9]*\.[a-zA-Z][a-zA-Z0-9.]*\}/)` regex to detect "raw i18n key leaked into output" is a clever way to find missing keys without enumerating every key by hand.
