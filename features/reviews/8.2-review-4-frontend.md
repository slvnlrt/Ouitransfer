# 8.2 Email Notifications — Frontend Review (Pass 4)

**Date**: 2026-05-30
**Reviewer**: Code Review Agent (principal-level)
**Scope**: `apps/web/` — components, pages, hooks, types, tests related to email notifications, visitor identification, share creation/edit, recipient management, notification preferences, and admin email section.
**Baseline**: All prior-pass findings (`8.2-review-frontend.md`, `8.2-re-review-frontend.md`) are addressed and re-verified here. This pass looks for issues that survived the previous rounds and a few that the previous rounds introduced.

## Summary

The previous rounds did real work. The C-1/C-2 fixes from pass 1 hold, all I-1..I-9 items from pass 2 land cleanly:

- `IdentifyVisitor200` is now `{ success: boolean }` (matches server).
- `share-details-modal` uses a controlled-Dialog with a Loader state and an outer `if (!shareId) return null` — both contracts now make sense and the dedicated test (`share-details-modal.test.tsx:127-139`) asserts the loader path.
- `identification-form.tsx` surfaces a metadata error branch with a Retry button (lines 100-112).
- `share-item-modal` now disables the Create button when password protection is toggled on but the password field is empty (lines 405-410). Same guard in `share-actions-modals` (`isPasswordInvalid`, lines 190-193).
- `share-multiple-items-modal` defaultName/footer breakdown are fully i18n'd (`shareMultipleFiles.defaultNameFiles`/`...Folders`/`...Connector`/`...Suffix`/`itemsBreakdown`).
- The rate-limit branch is now distinguished (`use-public-share.ts:142-147` toasts a dedicated message on HTTP 429).
- `share-details-activity-section.tsx` has a destructive-toned error block + retry (lines 152-159), uses `keepPreviousData` (line 94), and auto-recovers from empty-page states (lines 111-115).
- `email-admin-section.tsx` now distinguishes loading/error/value (lines 56-62, etc.) and shows `(unavailable)` on error.
- `download-url-cache.ts` keys by `objectName | password | shareId` (line 29).
- `share-details-modal` invalidates only `detail` + `list`, not `all` (line 86-87).

That said, this pass uncovered a few real issues that the earlier passes missed, plus a couple of regressions introduced while fixing other things:

- **A genuine showstopper** in the visitor identification flow: the React Query wrapper for `GET /shares/alias/:alias/metadata` reads `response.data.metadata`, but the server returns the object flat at the root (not wrapped). The identification modal therefore never gets metadata and any visitor on a share that requires identification is locked out — they see the metadata-error fallback regardless of what they do.
- **A real UX bug in the preferences page**: the table filters by `!isCritical` only. Two catalog entries (`share_invitation`, `reverse_share_invitation`) are `configurable: false, isCritical: false` per spec — the UI renders an editable dropdown for them, but the server rejects the PUT with 400 ("not user-configurable"). Users see a control that lies and an error on save.
- **Type drift for `ShareVisit`**: the server's `/shares/:shareId/visits` response includes an `identificationSource` discriminator the client type doesn't declare. Currently un-rendered, so silent — but it's the same shape of bug as the `IdentifyVisitor200` drift we just fixed last round.
- A few quality issues: `_isLoading` dead variable, the literal-`"null"` ICU sentinel in `share-details-modal`, no test coverage for any of the new 8.2 frontend code (notification preferences table, recipient selector, identification form, activity section, email admin section, `use-public-share` hook).

Overall: the C-1 metadata bug must ship a fix before 8.2 can be called done; everything else is Important or Minor.

## Findings

### Critical

#### C-1: Share metadata response is double-wrapped on the client — identification is broken
- **File**: `apps/web/src/app/(shares)/s/[alias]/hooks/use-public-share.ts:82-83` vs `apps/server/src/modules/share/routes.ts:790-807`
- **Issue**: The server route `GET /shares/alias/:alias/metadata` returns the metadata object directly at the response root: `reply.send(metadata)` (`routes.ts:806`), with the Zod response schema declaring `{ name, description, totalFiles, totalFolders, hasPassword, isExpired, isMaxViewsReached, nameFieldRequired, emailFieldRequired }` (lines 790-800). The client wrapper, however, returns `response.data.metadata`:
  ```ts
  const metadataQuery = useQuery({
    queryKey: queryKeys.shares.metadata(alias),
    queryFn: async () => {
      const response = await getShareMetadata(alias);
      return response.data.metadata; // ← undefined; server response is flat
    },
    enabled: !!alias && isIdentificationModalOpen,
    retry: false,
  });
  ```
  - The frontend type `GetShareMetadata200` (`http/endpoints/shares/types.ts:261-263`) declares `{ metadata: ShareMetadata }`, which doesn't match the server schema.
  - When the queryFn returns `undefined`, TanStack Query v5 throws (`queryFn must not return undefined`). The query enters an error state, `metadataQuery.isError` becomes `true`, and `identification-form.tsx:101-107` renders the "metadataError" branch — a destructive message + Retry button. Hitting Retry just reproduces the same failure.
  - The other consumer of the same endpoint (`apps/web/src/app/(shares)/s/[alias]/layout.tsx:39-49`) reads the flat shape correctly (`metadata?.name`, `metadata?.description`, `metadata?.totalFiles`), confirming the server contract. Only the React Query wrapper is wrong.
  - **Net effect**: Any share with `nameFieldRequired === "REQUIRED"` or `emailFieldRequired === "REQUIRED"` is unusable for any visitor that doesn't already have a tracking token cookie. The identification modal cannot be passed.
- **Why this wasn't caught**:
  - There is no Vitest coverage of `use-public-share.ts` or `identification-form.tsx`.
  - The server-side integration test (`visitor-tracking.test.ts:402-451`) checks the status code but never asserts the body shape.
  - The dev-mode E2E never reaches a share that requires identification.
- **Fix**:
  - **Quickest**: change the queryFn to `return response.data;` and update `GetShareMetadata200` (and `ShareMetadata`) so the response type and the in-use shape match.
  - **Better**: align both ends to one wrapping convention. The rest of the share endpoints wrap (`{ share }`, `{ visits, total, ... }`, `{ preferences }`) — pick the convention. If you keep flat, also update the type. If you adopt `{ metadata }`, fix the SSR layout.tsx consumer at the same time. The latter is safer for consistency.
  - Add a unit test on the hook that mocks `getShareMetadata` returning the canonical server shape and verifies `metadataQuery.data` is populated.

### Important

#### I-1: Notification preferences UI shows editable dropdowns for non-configurable types
- **File**: `apps/web/src/app/notifications/components/notification-preferences-table.tsx:161` vs `apps/server/src/modules/email/catalog.ts:282-300, 302-320` and `apps/server/src/modules/notification/service.ts:69-87`
- **Issue**: The table filters out only critical types:
  ```ts
  const preferences = (data?.preferences ?? []).filter((pref) => !pref.isCritical);
  ```
  The catalog has two entries with `isCritical: false, configurable: false` (per spec §10: "one-shot, not configurable"): `share_invitation`, `reverse_share_invitation`. The server returns them with `configurable: false` (`notification/service.ts:51`), the client filter keeps them, and the table renders a `<Select>` over `["immediate", "disabled"]` for each.
  - When the user changes the value and clicks Save, the server's `updateUserPreferences` throws `ValidationError('Notification type "share_invitation" is not user-configurable')` (`service.ts:78-79`), which becomes a 400 + toast "Failed to save preferences: …".
  - The categories map in the table (`TYPE_TO_CATEGORY`) routes `share_invitation` to "shares" and `reverse_share_invitation` to "reverseShares" — so they show up mid-list, not visually distinguished from configurable rows.
- **Impact**: User-visible broken control. The user thinks they configured it, hits Save, gets a generic save-error toast with no indication of which row failed. Any other valid changes in the same Save batch are blocked: the loop in `updateUserPreferences` aborts on the first invalid pref before any upsert (`service.ts:69-88`). So a user toggling 5 preferences and accidentally touching the invitation row loses all 5 changes.
- **Fix**:
  - Filter by `(!pref.isCritical && pref.configurable)` at the table level. Same change in any future read-only "non-configurable" display you want to add (e.g. greyed-out row saying "always sent — not configurable").
  - Defense in depth: the table could also skip non-configurable types from the Save mutation payload, so a partial-success scenario is not silently lost. Or split into per-row mutations with their own error states (matches the spec UI mock in §6).

#### I-2: `ShareVisit` type drift — server's `identificationSource` field is not declared on the client
- **File**: `apps/web/src/http/endpoints/shares/types.ts:219-229` vs `apps/server/src/modules/share/routes.ts:900-922`
- **Issue**: The server response declares `identificationSource: z.enum(["tracking_token", "cookie", "anonymous"])` (lines 916-921), but the client `ShareVisit` interface only lists `id, action, visitorName, visitorEmail, createdAt, recipientId, shareId, fileId, recipient`. No `identificationSource`. This is the exact same shape as the I-3 drift the last review flagged for `IdentifyVisitor200` and rated Important.
- **Impact**: Today nothing reads the field — the activity section only uses `visit.action`, `visit.visitorName`, `visit.visitorEmail`. So it's silent. The risk is the same as last round: any future caller that tries `visit.identificationSource` gets `undefined` at runtime with no static-analysis hint.
- **Fix**: Add the field to `ShareVisit` (and document the discriminator values in a comment). Then surface it in the UI — the activity section currently renders "Anonymous" for anything without `visitorName || visitorEmail`, but tracking-token visits without an explicit name would also fall into that branch, which is misleading. Showing a small badge ("invited", "self-identified", "anonymous") would close the loop on the privacy/audit promise of feature 8.2.

#### I-3: `recipientAccess` ICU string relies on the literal string `"null"` as a sentinel
- **File**: `apps/web/src/components/modals/share-details-modal.tsx:325-330` and `apps/web/messages/en-US.json` (`shareDetails.recipientAccess`)
- **Issue**:
  ```tsx
  {t("shareDetails.recipientAccess", {
    count: recipient.accessCount,
    lastAccess: recipient.lastAccessedAt
      ? format.relativeTime(new Date(recipient.lastAccessedAt))
      : "null",
  })}
  ```
  is paired with the ICU template:
  ```
  "{count, plural, one {# access} other {# accesses}}{lastAccess, select, null {} other { · last {lastAccess}}}"
  ```
  This is a clever-but-fragile workaround: `select` discriminates by the literal string `"null"` to drop the suffix. It works, but:
  - The branch is unreachable in practice — `accessCount > 0` implies `lastAccessedAt` is set on the server (visit recording updates both together in `share/service.ts`).
  - If anyone ever localizes the `null` key in another `.json`, the message breaks (the placeholder is the discriminator, not a translated word). The locale-keys test enforces nested key parity but does NOT enforce that the ICU `select` cases stay identical — a translator could rename it.
  - String `"null"` as a discriminator is the kind of "magic value" that won't survive a refactor.
- **Fix**: Use ICU `select` against an explicit boolean, or split into two messages and choose at render time:
  ```tsx
  {recipient.lastAccessedAt
    ? t("shareDetails.recipientAccessWithLast", { count: recipient.accessCount, lastAccess: format.relativeTime(...) })
    : t("shareDetails.recipientAccess", { count: recipient.accessCount })}
  ```
  Or pass a real `hasLast` boolean to `select` and use the standard ICU `true`/`false`/`other` casing.

#### I-5: `notifyOnDownload` label is ambiguous — it overrides only `share_downloaded`, not `share_accessed`
- **File**: `apps/web/src/components/modals/share-privacy-section.tsx:92` (label key `createShare.notifyOnDownload`) vs `apps/server/src/modules/email/service.ts:269-278`
- **Issue**: The server's `resolveFrequency` only applies the per-share `notifyOnDownload` upgrade when `type === "share_downloaded"`. The UI label is "Notify me on each download" (en-US.json), which is correctly scoped. But the server-side comment says "per-share override" and the spec §6 uses the same wording — the user reading the UI might reasonably expect "notify me on each access" too. The current copy is technically accurate; the issue is that if the user has `share_accessed: disabled` and `share_downloaded: disabled` globally, toggling this per-share switch upgrades only downloads. There's no per-share override for `share_accessed` at all.
- **Impact**: Low. Functional behaviour matches the spec exactly. UX gap: the user has no way to bypass their global preference for the "access" event on a specific share. The label is currently fine; the gap is a missing feature.
- **Fix**:
  - Option A: leave it. Spec §6 only specifies the download override.
  - Option B: add a per-share `notifyOnAccess` field if user research shows this is wanted. Defer to a follow-up.
  - Either way, document the asymmetry in a tooltip or helptext on the switch so the user understands the scope.

#### M-2: Non-owner consumers of `GET /shares/:shareId` see lie-typed fields
- **File**: `apps/server/src/modules/share/service.ts:104-127` vs `apps/web/src/http/endpoints/shares/types.ts:65-78`
- **Issue**: The server strips `notifyOnDownload`, `inactivityAlertDays`, `lastDownloadedAt`, `notifiedForExpiring`, `notifiedForExpired`, `creatorId`, and `recipients` from non-owner responses (replacing booleans with `false`, nulls, empty arrays). The frontend `Share` type declares all of these as always-present, so a non-owner caller reading e.g. `share.notifyOnDownload` gets `false` even when the underlying share has it set to `true`. The current frontend doesn't display these fields on the public share page (only owner contexts), so it's silent.
- **Impact**: Low. Pre-existing pattern. Worth noting because the next person who adds a public share UI for these fields will be confused.
- **Fix**: Either:
  - Declare these as `boolean | null` / `... | undefined` on the client to reflect the reality.
  - Split into `Share` (full) and `PublicShare` (subset) types and have the endpoint wrappers return the right one.
  - Document the redaction in a comment on the type.

#### M-3: `share-details-modal.tsx:195` declares an `if (!shareId) return null` after running queries above it

#### M-7: `share-actions-modals.tsx` `handleEdit` issues a sequence of writes that can partially fail
- **File**: `apps/web/src/components/modals/share-actions-modals.tsx:195-230`

#### M-9: Cookie path `/api` + sameSite=strict + Next.js dev proxy
- **File**: `apps/server/src/modules/share/routes.ts:867-874` and `apps/web/src/config/api.ts`
- **Issue**: The visitor-identification cookie is scoped `path: /api`. In production (Traefik), the frontend and backend share an origin, so `/api/*` requests carry the cookie automatically. In dev, the web app at port 3000 proxies `/api/*` to the server at 3333 (via `proxy.ts`). The cookie is set by the server's response to `POST /api/shares/alias/:alias/identify`, scoped to `path: /api`, and then sent by the browser on subsequent `/api/*` requests through the proxy. This should work — but it's worth a dev smoke test, because if anyone changes the proxy to forward at a different path (e.g. `/srv/`), the cookie scope silently breaks identification on dev.
- **Fix**: Document in the dev-server README that visitor identification cookies are path-scoped, or add a dev-only E2E that goes through the full identify → access flow.

#### M-10: `share-details-modal` query for `getShare` is unauthenticated-safe but the component is owner-only by intent
- **File**: `share-details-modal.tsx:70-77` and `apps/server/src/modules/share/routes.ts:175-191`
- **Issue**: `getShare` allows anonymous callers (the `try/catch` on `jwtVerify`). The details modal is opened from the owner's My Shares page, so this is fine in practice. But because the server uses `isOwner` to strip fields, a non-owner accidentally gaining access to the modal would see a half-redacted share with `notifyOnDownload: false` etc. (see M-2). The modal doesn't gate by `creatorId === currentUserId`. Worth adding an explicit assertion.
- **Fix**: Either guard the modal at the parent level (don't open it for non-owners — already the case in My Shares) or assert in the component that `share.creatorId` matches the auth context's user id before allowing edits. Defensive but cheap.
