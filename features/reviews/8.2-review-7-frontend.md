## Minor

### M-1: Write-side `frequency` type is `string`, not mirroring the server's `"immediate" | "disabled"` enum
- **File(s)**: `apps/web/src/http/endpoints/notifications/types.ts:18` (`UpdatePreferenceItem.frequency: string`); produced in `notification-preferences-table.tsx:131-135`
- **Description**: The PUT body types `frequency` as a bare `string`. The server Zod schema restricts it to `z.enum(["immediate","disabled"])` (spec §6 "Frequency validation"). The client write-contract therefore does not mirror the server contract — a caller could pass an arbitrary string and only learn of the rejection at runtime via the 400 toast. The UI itself only ever emits `"immediate"`/`"disabled"` (the two `<SelectItem>` values), so this is latent, not an active bug. But the project's quality bar is "make invalid states unrepresentable when the type system allows it," and this is a cheap win.
- **Expected**: The write-side type is a union mirroring the server enum, so bad values are a compile error at the call site.
- **Fix**: Add `type NotificationFrequency = "immediate" | "disabled"` (ideally exported from `@ouitransfer/shared` next to `NotificationType` for a single source of truth) and use it for `UpdatePreferenceItem.frequency`. Keep the **read-side** `NotificationPreference.frequency` wider (`string`) since the GET can legitimately return a stored `daily_digest` value the UI must tolerate — that asymmetry (read wide, write narrow) is correct and already handled by `getFrequency`.

### M-2: `notifications/layout.tsx` `generateMetadata` uses a root translator + dotted key, and a redundant template literal
- **File(s)**: `apps/web/src/app/notifications/layout.tsx:9-13`
- **Description**: `const t = await getTranslations()` (root namespace) then `t("notificationPreferences.pageTitle")`, wrapped in `` `${...}` ``. It works, but (a) it's inconsistent with the page component which scopes to `useTranslations("notificationPreferences")`, and (b) the template literal is redundant since the value is already a string. Purely cosmetic; no functional impact.
- **Expected**: Consistent namespaced access; no redundant interpolation.
- **Fix**: `const t = await getTranslations("notificationPreferences"); return { title: t("pageTitle") };`

### M-3: Activity "load more" / pagination is offset-based and can render stale/empty intermediate states under `keepPreviousData`
- **File(s)**: `apps/web/src/components/modals/share-details/share-details-activity-section.tsx:120-131`, `:198-219`
- **Description**: Minor UX edge, not a correctness bug. With `placeholderData: keepPreviousData`, when the user clicks "Load more" the previous page's rows stay visible until the next page resolves; meanwhile `page` has already advanced, so the "← / Load more" buttons and the `showingCount` reflect the *new* page index while the *old* rows are shown for a beat. This is generally acceptable (it avoids a flash), and the auto-reset effect at `:127-131` is correctly guarded with `visitsQuery.isSuccess` (so it no longer fires during loading — the Pass 6 concern). The only residual nit: the "Load more" label suggests append-style pagination, but the list actually *replaces* the page (it's classic prev/next paging, not infinite scroll). Consider relabeling to a "Next" affordance or making it truly append, for clarity. Low priority — the data is correct.
- **Expected**: Pagination affordance label matches behavior.
- **Fix**: Either rename `shareDetails.activity.loadMore` to a "Next page" semantic (it already has a `←` prev button, so prev/next paging is the actual model), or accumulate pages for true "load more." Cosmetic.
