## Verdict on the owner-noise question (#1)

**Confirmed real and Important.** `apps/web/src/components/modals/share-details-modal.tsx:74-81` runs a TanStack Query whose `queryFn` calls `getShare(shareId)` → `GET /api/shares/:shareId` → `ShareService.getShare`, which now (service.ts:252-278) fire-and-forgets an owner `authenticated_user` visit *before* the early return. This modal is the owner's own details/activity panel (opened from the shares table / dashboard). Consequences:

- Opening the modal to **view the activity log** writes a new owner "access" visit — the act of reading the log mutates the log (self-referential noise).
- `invalidateShare()` (share-details-modal.tsx:85-96) is called after editing name/description and on `refreshTrigger`; it invalidates `queryKeys.shares.detail(shareId)`, which causes the `getShare` query to refetch → **another** owner visit per edit/refresh. A single editing session can mint many owner rows.
- The public-share path is fine for owners viewing logged-out (treated anonymous) but an owner viewing their own *public* link while logged in (`getShareByAlias` → `getShare`) also generates a visit.

The spec ("Track owner self-accesses too") technically asked for this, but did not anticipate that the **owner's own management UI is the primary caller** of `GET /shares/:shareId`. The result is the log fills with owner self-access entries generated by routine management actions, drowning real visitor activity. Recommended fix below.

## Findings

### Critical
- None.

### Important
- [ ] **Owner self-visit noise from the management UI** — `apps/server/src/modules/share/service.ts:252-278` writes an owner `authenticated_user` "access" visit on every `GET /shares/:shareId`, but that endpoint is the owner's own share-details modal (`apps/web/src/components/modals/share-details-modal.tsx:74-81`), refetched on open and on every `invalidateShare()` (edit name/description, `refreshTrigger`). The activity log therefore fills with self-access rows generated by the owner merely *reading* it. **Fix (recommended):** do **not** track owner self-access on the share-management `getShare` path. Either (a) drop the owner-branch tracking entirely (revert service.ts:252-278; the owner-download path already does NOT track owners, so this also restores access/download consistency — see Minor below), or (b) gate it to only the genuine public share-view route by threading a context flag (e.g. `context.publicView`) that the owner-management caller does not set. Option (a) is simplest and matches the spec's own "Out of scope / revisit if noisy" escape hatch — it has proven noisy. If kept, at minimum the share-details modal should stop being the trigger.

### Minor
- [ ] **Access vs. download owner asymmetry** — owner self-**access** now creates a visit (service.ts:252-278) but owner self-**download** still early-returns with no visit (`apps/server/src/modules/file/routes.ts:197-199`, asserted by the "owner download still does NOT create visit" test). The two halves of the same feature now disagree on whether the owner is tracked. Resolving finding #1 via option (a) also removes this inconsistency.
- [ ] **GDPR: snapshotted email not redacted on user deletion** — authenticated visits snapshot `visitorEmail`/`visitorName` from the user record (service.ts:493-494, file/routes.ts:232-233). On user deletion `ShareVisit.userId` goes `SetNull`, but `deleteUser` only purges the user's *own* shares (`purgeUserContent`) and redacts the email from **audit logs only** (`apps/server/src/modules/user/service.ts:176-193` → `redactEmailFromAuditLogs`, which touches `auditLog` exclusively, `apps/server/src/modules/audit/service.ts:485-491`). A deleted user's email/username therefore persists indefinitely in `ShareVisit` rows belonging to *other* owners' shares. The spec (lines 30-31) waved this off as "same PII profile as today's external visits," but `self_declared` emails were *typed by the visitor into that share's form*, whereas here the email is auto-captured from a registered account the visitor never offered to that share. **Fix:** extend the deletion path to also null/redact `visitorEmail`/`visitorName` on `ShareVisit` rows for the deleted user (e.g. `prisma.shareVisit.updateMany({ where: { userId: id }, data: { visitorEmail: null, visitorName: null } })` — note this must run *before* the FK SetNulls `userId`, or key off the snapshot). This pre-exists for self_declared, but B-29 widens the exposure to involuntary captures, so it is worth closing now.
- [ ] **Authenticated identity discarded when an unmatched cookie is present** — `service.ts:485` guards the authenticated fallback with `!context?.visitorCookie`. If a logged-in user carries a stale/unmatched `sv_` cookie, the visit is written with `visitorName`/`visitorEmail` from the cookie, `identificationSource = null`, and **no `userId`** — so a verified registered user is downgraded to a spoofable "cookie" attribution in the `/visits` mapping (routes.ts:1207-1239, `visitorEmail || visitorName → "cookie"`). The spec explicitly intends cookie-over-authenticated precedence, so this is acceptable by design, but discarding the verified `userId` entirely (rather than recording `userId` while still honoring the cookie's display name) loses audit value. Consider recording `userId` even when the cookie supplies the display identity. Flagged as a design nuance, not a defect.
- [ ] **`identified=false` filter omits `userId`** — `apps/server/src/modules/share/routes.ts:1188-1192` filters anonymous visits by nulling `recipientId`/`visitorEmail`/`visitorName` but does **not** add `userId: null`, whereas the `identified=true` branch (1182-1187) *was* updated to include `{ userId: { not: null } }`. Harmless today because every `authenticated_user` visit also snapshots name+email (so it is already excluded by the `visitorName`/`visitorEmail` null filters), but the asymmetry is a latent trap if a future authenticated visit is ever written without a name/email snapshot. Add `where.userId = null` to the `false` branch for symmetry.

## Categories explicitly clean

- **Precedence (#2):** token > self_declared/cookie > authenticated_user > anonymous is correctly ordered in `service.ts:437-496` and verified by three dedicated tests (token, cookie, and authenticated fallback). Owner early-return guarantees the fallback is never reached for the owner.
- **Notifications (#3):** owner self-visit sends no `share_accessed` (service.ts:277, asserted by two owner tests); non-owner authenticated visit still notifies, now with a name (asserted).
- **`/visits` exposure (#4b):** route is owner-gated (`creatorId !== userId → Forbidden`, routes.ts:1171-1173); `userId` is stripped from the payload and `isOwner` derived before stripping (routes.ts:1222-1224); a test asserts no `userId` property leaks.
- **Migration (#5):** `20260613142552_share_visit_user` is the standard SQLite RedefineTables pattern — additive `userId TEXT`, FK `ON DELETE SET NULL`, preserves all columns via INSERT…SELECT and recreates `share_visits_shareId_createdAt_idx`. Existing rows get `userId = NULL`. Matches schema (`prisma validate` passes). No `userId` index — correct, queries are `shareId`-scoped (spec line 109).
- **Download path (#6):** the `jwtVerify()` fallback (file/routes.ts:1097-1103, 1238-1244) runs only when `!request.user`, after access is already granted, and silently swallows failure for anonymous downloaders — it cannot break token/password/anonymous flows. Owner is filtered before tracking (`isOwner` early return, 197-199). Single `trackShareDownload` call per handler → no double-tracking.
- **Frontend (#7):** `authenticated_user` routes to the plain verified badge, not the cookie tooltip (`share-details-activity-section.tsx:73-92`); `isOwner` renders the "You" badge (67-71); type union widened + `isOwner` added (`types.ts:270-271`). Authenticated-owner shows both the verified badge and "You" — acceptable and informative. No physical-direction CSS introduced; a11y unaffected.
- **i18n (#8):** all 23 locales carry both keys, genuinely translated (RTL ar/he/fa, CJK zh/ja verified); parity test covers them.
- **Tests (#9):** owner-tracked-without-notify, non-owner-authenticated-identified, token/cookie precedence, `/visits` isOwner shape + userId-strip, and the authenticated download path are all covered. The prisma `user.findUnique` mock defaults to `null` and is set per-test — it does *not* mask the owner-noise issue (that issue is architectural/caller-level, not visible from the service unit mocks).
