# 8.2 Email Notifications — Server Core Review (Pass 5)

**Date**: 2026-05-30
**Reviewer**: Agent (Server Core)
**Scope**: Email module internals (catalog, service, queue, transport, templates, i18n, scheduler) + notification module

---

## Summary

This is a mature and well-structured email subsystem. Five prior review passes have hardened it considerably: payload validation via Zod, atomic job locking, exponential backoff with cap, HMAC-derived key isolation, CR/LF sanitization for SMTP header injection, in-flight dedup in the i18n loader, stuck-job recovery on boot, and a fail-fast i18n key validator. Test coverage is solid (catalog, service, queue, transport, i18n, templates, notification scheduler, routes integration).

Despite that, this pass surfaces one real **critical** bug (a user-enumeration oracle in the password-reset flow introduced by the migration), one **important** correctness bug in the `share_max_views_reached` flow that loses the notification on any transient failure, and several **minor** issues around inconsistent API usage, missing payload fields, vacuous tests, and spec deviations. None of these threaten the queue infrastructure itself, which is the strongest part of the module.

## Critical

### C-1: Password-reset email flow leaks user existence via 400 ValidationError when `appUrl` is unconfigured

- **File(s)**: `apps/server/src/modules/auth/service.ts:164-208`, `apps/server/src/modules/email/url-builder.ts:47-50`, `apps/server/src/modules/email/url-builder.ts:13-17`
- **Description**:
  `AuthService.requestPasswordReset` is designed not to reveal whether an email is registered — unknown emails return silently (line 168-170). The migration to the new email system, however, calls `await buildResetPasswordUrl(token)` *before* `emailService.send(...)` (line 193-203), and `buildResetPasswordUrl` throws synchronously when `appUrl` is missing or empty (url-builder.ts:14-16). That throw is caught at line 204 and re-thrown as `ValidationError("Failed to send password reset email")` → HTTP 400.

  Result: an attacker can distinguish "registered email" (400 error) from "unregistered email" (200 silent) by probing the password-reset endpoint when the admin hasn't yet configured `appUrl`. Worse, the password-reset DB row is still created at line 185-191 *before* the URL build, so an orphan token is also created for every attack probe.

  `EmailService.send` itself handles missing `appUrl` correctly (silent `enqueued:false`, service.ts:89-95). The bug is that the caller computes the URL *outside* `emailService.send`, so the protection doesn't reach it.
- **Expected**:
  - Spec Section 4 explicitly says: "Server refuses to send emails if `appUrl` is not configured (logs a warning, marks job as failed with 'appUrl not configured')."
  - Spec Section 12 / general security posture: password-reset must not expose user existence.
  - Auth callers should never throw to the API when the email subsystem cannot enqueue — the user-facing semantics should be identical to "no such user".
- **Fix**:
  Either (a) move URL construction inside `EmailService` (e.g., add `data: { resetToken, ... }` and let the service call `buildResetPasswordUrl(token)` after the `getAppUrl` check), or (b) in `requestPasswordReset`, only treat exceptions as errors when they truly originate from the user's request (validation, etc.); catch infrastructure failures (URL build, send) and log without throwing. Concretely in `auth/service.ts`:

  ```ts
  try {
    const resetUrl = await buildResetPasswordUrl(token);
    await emailService.send("password_reset", { ... });
  } catch (error) {
    getLogger().error({ err: error }, "Failed to send password reset email");
    // Do NOT throw — preserve the no-user-enumeration contract.
  }
  ```

  Add an integration test that drives the endpoint with `appUrl=""` and asserts both responses (known email, unknown email) are identical 200s.

## Important

### I-1: `share_max_views_reached` notification is silently dropped on any failure (lost notification)

- **File(s)**: `apps/server/src/modules/share/service.ts:363-399`
- **Description**:
  The "share just hit its max view count" flow sets `notifiedForMaxViews = true` **before** the email is even enqueued (line 374-378), then fires `emailService.send(...)` in a `.then()` chain (line 379-396). If `send` returns `{ enqueued: false }` (SMTP disabled, `appUrl` missing, user preference disabled, invalid payload, cooldown), or if it throws (caught at line 393-395 and only logged), the flag stays `true` and the notification is permanently lost.

  This is structurally different from the (correct) pattern used by `notification.scheduler.ts:71-75`, which only flips the flag *after* `result.enqueued === true`. The scheduler test at `notification.scheduler.test.ts:469-485` explicitly verifies "does NOT set inactivityAlertSent when send returns enqueued=false" — the same invariant is violated here.

  Worst-case scenario: an admin enables SMTP a week later, fixes their `appUrl`, and the user is still missing the notification because the flag is permanently set. There is no recovery path — the share cannot exceed maxViews again because `incrementViewsAtomic` already blocks it.

  Note: I considered and dismissed a race-condition risk. `incrementViewsAtomic` (`repository.ts:271-284`) uses `updateMany` with a `views < maxViews` guard, so only one concurrent visitor can ever cross the threshold. The "set flag first to prevent duplicate sends" rationale in the comment is therefore not a real concern — a real fix should pivot to the scheduler pattern.
- **Expected**:
  Same lifecycle as the scheduler: enqueue the email, then set the flag only after confirmed enqueue. If enqueue fails, leave the flag `false` so the next call to `getShare` retries.
- **Fix**:
  Rewrite the block to mirror `notification.scheduler.ts:60-76`:

  ```ts
  if (
    share.maxViews !== null &&
    newViewCount >= share.maxViews &&
    !share.notifiedForMaxViews &&
    share.creatorId &&
    share.creator?.email &&
    share.creator?.isActive !== false
  ) {
    // Fire-and-forget, but only flip the flag after confirmed enqueue
    (async () => {
      try {
        const shareManageUrl = await buildShareManageUrl(shareId);
        const result = await emailService.send("share_max_views_reached", {
          to: share.creator!.email,
          locale: share.creator!.locale ?? "en",
          userId: share.creatorId!,
          relatedId: shareId,
          data: { shareName: share.name ?? "Unnamed share", maxViews: share.maxViews!, shareManageUrl },
        });
        if (result.enqueued) {
          await prisma.share.update({ where: { id: shareId }, data: { notifiedForMaxViews: true } });
        }
      } catch (err) {
        getLogger().error({ err }, "Failed to send share_max_views_reached notification");
      }
    })().catch(() => {});
  }
  ```

  Add a test mirroring `notification.scheduler.test.ts:469-485` that asserts the flag is *not* set when `send` returns `enqueued: false`.

### I-2: `share_accessed` payload omits `ipAddress` despite spec requirement, making anonymous-visitor notifications uninformative

- **File(s)**: `apps/server/src/modules/email/catalog.ts:115-120`, `apps/server/src/modules/email/templates/share-accessed.ts`, `apps/server/src/modules/email/i18n/messages/en.json:48`, `apps/server/src/modules/share/service.ts:348-360`
- **Description**:
  Spec Section 1/10 specifies the `share_accessed` data shape as `{ shareName, visitorName?, visitorEmail?, ipAddress?, accessedAt }`. The implemented schema (catalog.ts:115-120) drops `ipAddress` entirely, the template doesn't reference it, and the `bodyAnonymous` translation is just `"Someone accessed your share <strong>{shareName}</strong> on {accessedAt}."`. The share/service.ts caller actually has the IP in `context.ipAddress` and could pass it — but doesn't because the schema rejects it (Zod strict parse would refuse the extra field).

  Practical impact: for the noisy/default-disabled `share_accessed` notification — the exact case where an admin manually opts in because they want to know who's hitting their public link — the email contains zero forensic information beyond the share name. It defeats much of the value of opting in.
- **Expected**:
  The spec catalog (Section 10) lists `ipAddress?` as part of the payload; the user-facing email body should surface it for anonymous accesses ("Someone from IP `x.x.x.x` accessed …").
- **Fix**:
  1. Add `ipAddress: z.string().optional()` to `shareAccessedSchema` in catalog.ts.
  2. Extend `bodyAnonymous` in en.json/fr.json to render IP when present (e.g., `"Someone from {ipAddress} accessed your share <strong>{shareName}</strong> on {accessedAt}."`) and add a fallback key for when IP is absent.
  3. Pass `ipAddress: context?.ipAddress` in `share/service.ts:354-358`.

### I-3: Inconsistent use of deprecated `shareId` parameter throughout `emailService.send` callers

- **File(s)**: `apps/server/src/modules/email/service.ts:50-58`, callers: `share/service.ts:352`, `share/service.ts:386`, `file/routes.ts:210`, `notification.scheduler.ts:64`, `notification.scheduler.ts:116`, `notification.scheduler.ts:181`
- **Description**:
  `EmailService.send` declares `shareId` as `@deprecated Use relatedId instead`. Six of the call sites pass `shareId` (deprecated), one passes `relatedId` (`share/service.ts:386` for max_views), and `notification.scheduler.ts` for reverse-shares doesn't pass either. The "deprecation" was added but no caller was actually migrated — so the deprecation marker is misleading. New code (added in this batch) was added under the deprecated alias.

  This isn't a runtime bug — `effectiveRelatedId = options.relatedId ?? options.shareId` (service.ts:73) unifies them. But it's a maintenance hazard: a future cleanup that removes the `shareId` alias will silently break cooldown grouping for `share_accessed`, `share_downloaded`, expiration emails, and inactivity emails. The deprecation also signals to readers that some code is "older" when in fact it was all written in this batch.
- **Expected**:
  If `shareId` is genuinely deprecated, *every* caller should use `relatedId`. If both are equivalent and supported, drop the deprecation tag.
- **Fix**:
  Either (a) migrate all callers to `relatedId` (preferred — `shareId` is misleading for reverse-share callers anyway) and remove the `shareId` parameter entirely, or (b) drop the `@deprecated` JSDoc and keep `shareId` as a documented alias. Pick one and apply uniformly.

### I-4: Notification scheduler runs daily at `emailDigestHour` UTC — conflates digest scheduling with non-digest notifications

- **File(s)**: `apps/server/src/modules/notification/notification.scheduler.ts:347-358`, `apps/server/src/modules/notification/notification.scheduler.ts:385-410`
- **Description**:
  The notification scheduler (which runs `checkExpiringShares`, `checkExpiredShares`, `checkInactiveShares`, etc.) keys off `emailDigestHour` (default 8 UTC). The plan/spec describes `emailDigestHour` as the daily digest send time, but the notification scheduler hijacks it as its own tick time.

  Consequences:
  - An admin moves the digest hour to 02:00 UTC to send overnight; they now also shift the lifecycle-notification cron, which is a side effect they didn't ask for.
  - The 5-day inactivity threshold gets evaluated only once a day at digest hour — so a "3-day inactivity" share can fire its alert anywhere between 3.0 and 4.0 days late depending on when boot happens to align.
  - When digests are eventually implemented (deferred per spec), the same wall-clock slot will be doing two unrelated jobs, with no separation.
  - The function name `getDigestHourUtc()` inside a non-digest scheduler reinforces the conflation.

  A single dedicated `notificationCheckHour` (or even just "once per 24h from boot") would be conceptually cleaner and avoids future entanglement.
- **Expected**:
  Spec Section 4 introduces `emailDigestHour` only for the (deferred) digest path. The notification scheduler isn't a digest — it's an event detector.
- **Fix**:
  Introduce a separate config key (e.g., `notificationCheckHour`, default 8) for the notification scheduler. Keep `emailDigestHour` reserved for when digest aggregation is implemented. Rename the local helper `getDigestHourUtc` → `getNotificationCheckHourUtc` in this file. Update the log line at notification.scheduler.ts:422 to remove "wall-clock aligned" if you instead opt for a 24h-from-boot model.

### I-5: Visitor identification cookie scoped to `path: "/"` — over-broad, leaks cookies to non-`/api` routes

- **File(s)**: `apps/server/src/modules/share/routes.ts:875-888`
- **Description**:
  The visitor identification cookie `sv_{alias}` is set with `path: "/"` (line 882). The comment justifies this as a workaround for the dev-mode Next.js proxy (lines 875-880). But spec Section 9 explicitly specifies `path: /api`:

  > "Sets an httpOnly signed cookie `sv_{alias}` scoped to `path: /api`, `sameSite: Strict`, valid 24h."

  The comment claims `path: "/api"` doesn't work through the proxy. That's likely incorrect: the Next.js proxy rewrites `/api/*` server-side; the *browser* sees `/api/foo` and stores the cookie under that path. The browser then sends the cookie on any `/api/*` request, which the proxy still receives and forwards. The path issue only arises if the cookie was set in a context where `path` resolves on the rewritten side — but `Set-Cookie` paths are pure browser-side.

  Even if the workaround is correct, the result is a security regression vs. spec: the cookie is now sent on every Next.js page navigation, every static asset request, every WebSocket upgrade, and every misconfigured endpoint. With `httpOnly` + `sameSite: strict` + signed payload + alias-equality check, the practical exposure is small — but `httpOnly` doesn't help if a future endpoint inadvertently logs the `Cookie` header, and "broad path" is a defense-in-depth weakening.
- **Expected**:
  Per spec: `path: "/api"`. The dev-mode proxy claim should be verified before deviating from the spec.
- **Fix**:
  1. Verify the proxy claim with an integration test — set `path: "/api"` and confirm the visitor identification cookie round-trips successfully in both dev and prod mode.
  2. If the claim holds (which I doubt — browsers store cookies by the path they appear at, not the rewritten path), keep `path: "/"`, but update the spec to match reality and document the security trade-off.
  3. If the claim doesn't hold, restore `path: "/api"` per spec.

### I-6: Visitor-tracking integration test makes assertions inside an `if (res.statusCode === 200)` branch and can pass vacuously

- **File(s)**: `apps/server/src/modules/share/__tests__/visitor-tracking.test.ts:494-531`
- **Description**:
  The "creates ShareVisit with action 'download' when shareId is provided" test wraps its key assertions inside `if (res.statusCode === 200)` (line 517). If the file-service mock can't satisfy the request — which is what the test code itself hints at with "The file service mock may not be wired — just check for 200 or 500" — the test silently passes without exercising the assertion path at all.

  Moreover, the assertion at line 526-529 expects `data: { lastDownloadedAt: expect.any(Date) }` — an exact match (not `objectContaining`). The actual code at `file/routes.ts:189` updates `data: { lastDownloadedAt: new Date(), inactivityAlertSent: false }` — two fields. If the assertion ever fired, it would fail. So this test exists in a state where (a) it usually doesn't fire because of the `if`, and (b) when it does fire, it would fail. That's a "test that pretends to verify the contract" — exactly what BUG-comment-discipline (CLAUDE.md) warns about.
- **Expected**:
  Tests should assert what they claim, fail loudly when broken, and not hide behind conditional branches.
- **Fix**:
  1. Make the test set up the file-service mock so the 200 path is deterministic (or replace the integration test with a unit test that calls `trackShareDownload` directly).
  2. Remove the `if (res.statusCode === 200)` wrapper.
  3. Change the assertion to `objectContaining({ lastDownloadedAt: expect.any(Date), inactivityAlertSent: false })`.

## Minor

### M-1: i18n `interpolate` regex `\w+` silently passes through unmatched placeholders, masking template authoring bugs

- **File(s)**: `apps/server/src/modules/email/i18n/loader.ts:294-320`
- **Description**:
  The regex `/\{(\w+)\}/g` replaces only when the key exists in `params`. Unknown placeholders (e.g., a typo `{shareNme}` instead of `{shareName}`) are left in the output verbatim. There's a dev-only warning at line 309-317, but in production the email is silently sent with `{shareNme}` literally in the body. The startup `validateI18nKeys` checks that *catalog-required* keys exist in en.json, but doesn't validate that *placeholders inside those values* are actually provided by the templates.

  Combined with the fact that two locales drift (en.json may add a `{newParam}` that fr.json doesn't have, or vice versa), this is a pattern that quietly degrades quality over time.
- **Fix**:
  Tighten the dev-only warning to a hard error in CI / tests:
  ```ts
  if (process.env.NODE_ENV !== "production") {
    const unresolved = result.match(/\{(\w+)\}/g);
    if (unresolved) {
      throw new Error(`[email-i18n] Unresolved placeholders: ${unresolved.join(", ")} in template "${template}"`);
    }
  }
  ```
  This would fail the test suite the moment any template/locale drift is introduced.

### M-2: Date values in email bodies (`expiresAt`, `accessedAt`, `downloadedAt`) are rendered as raw ISO 8601

- **File(s)**: `apps/server/src/modules/email/service.ts:151-164` (TODO comment), `apps/server/src/modules/email/templates/share-invitation.ts:22, 26`, `templates/share-expiring.ts`, `templates/share-expired.ts`, `templates/share-accessed.ts`, `templates/share-downloaded.ts`
- **Description**:
  The author acknowledged this with a TODO in service.ts. Users seeing "expires on `2026-12-31T23:59:59.000Z`" in their email is unfriendly and inconsistent with the localized look-and-feel everywhere else. `Intl.DateTimeFormat(locale, { dateStyle: "long" })` exists for exactly this and is Node-native. The TODO defers it for tractable reasons but it should not ship to production this way.
- **Fix**:
  Format date-shaped payload values (detected by ISO parse + the catalog `payloadSchema` field type being `isoDateString`) with `Intl.DateTimeFormat(locale, { dateStyle: "long", timeStyle: "short", timeZone: "UTC" })` before passing to the translation function. This can be done generically in `EmailService.send` by inspecting which keys are dates (e.g., named `*At` or matching ISO regex).

### M-3: `share_invitation` to external recipients uses sender's locale, which may not match the recipient's preference

- **File(s)**: `apps/server/src/modules/share/service.ts:762-767`
- **Description**:
  The code uses `locale: user?.locale ?? "en"` (the sender's locale) for the share invitation. The comment (line 763-766) acknowledges this as a deliberate compromise. But it's worth noting in the review because the email content is one of the few user-facing surfaces where the external recipient might receive content in a wrong language — defeating some of the i18n investment. ### M-4: Notification scheduler "boot-time initial check" runs *before* the scheduler is started (good), but has no exponential-backoff or retry on transient DB errors

- **File(s)**: `apps/server/src/modules/notification/notification.scheduler.ts:445-459`
- **Description**:
  If the initial `runAllChecks()` fails (e.g., the DB is slow to start, brief connection blip), the error is logged but the next attempt is at the next `emailDigestHour:00 UTC` — possibly 23 hours later. The email queue scheduler in contrast has `recoverStuckJobs` running every 5 minutes (queue.ts:80, 348-355) precisely because the boot-time recovery isn't enough. The notification scheduler should similarly have a fallback that catches up faster than 24 hours.
- **Fix**:
  Either (a) retry the boot-time check up to 3 times with backoff before deferring to the next scheduled tick, or (b) add a "missed-tick" detector that retries within 5-10 minutes if the previous run failed.

### M-5: Unsubscribe pages localized via inline string map duplicating the email i18n system

- **File(s)**: `apps/server/src/modules/notification/routes.ts:46-104`
- **Description**:
  The unsubscribe confirmation/success/error pages have their own English/French translations in a `PAGE_STRINGS` map.   - Add a `displayName` field per `notificationCatalog` entry (e.g., `share_accessed: { displayName: "Share Access Notifications" }`) and render that instead of the raw key. Add the corresponding i18n keys so the displayName is localized.

## Positive Observations

1. **Catalog as single source of truth** — the `notificationCatalog` derives types, the i18n key validator, the preferences page contents, and the EmailPayloads map. Adding a new notification is one catalog entry + template + i18n keys + payload schema. This is exactly what the spec described and was delivered cleanly.

2. **Atomic job locking via `updateMany` with status guard** (queue.ts:233-239) is the correct SQLite-friendly approach. Combined with sequential batch processing (line 228), this is race-safe even if the scheduler is ever run from multiple processes (modulo the documented single-process assumption).

3. **HMAC sub-key derivation** for unsubscribe tokens (unsubscribe-token.ts:21-23) is the right pattern. The token format is a hand-rolled JWT but the implementation correctly validates the `alg` header (line 87-89) to prevent algorithm-confusion attacks, uses `timingSafeEqual` for signature comparison (line 106), and explicitly limits `iat` to informational use (line 119-120) — addressing exactly the JWT footguns that often appear in code review.

4. **CR/LF sanitization for SMTP header injection** (service.ts:25-31, 204-206) is applied uniformly to all payload values *and* `appName` before any subject interpolation. The integration test at email-service-i18n.test.ts:235-257 confirms this end-to-end.

5. **Fail-fast i18n key validation at boot** (queue.ts:474-481) catches missing keys before any user-visible failure. The `validateAllI18nKeys` test (queue.test.ts:550-560) verifies the failure path.
