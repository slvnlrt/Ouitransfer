**Range reviewed:** `b966223..HEAD` (17 commits, 5 batches: schema → read-time gating + pause/resume → two-phase sweeps → endpoint+UI → config-retirement+docs).

Full suites pass: **server 1344/1344, web 310/310**; both apps type-check clean; no production `as any`.

Findings are all **Minor** (auditability gap + three doc/comment nits). No Critical or Important issues. The auditability finding (M-1) is the only one with behavioral weight and should be fixed to satisfy the spec's stated audit surface.

## Findings

### Minor

- [ ] **[Minor] Reactivation-on-extend (renew) is not audited as a reactivation** — `apps/server/src/modules/share/service.ts:564-575` (and `apps/server/src/modules/reverse-share/service.ts:225-233`).
  When the owner renews a deactivated share by extending `expiration` / raising `maxViews`, `updateShare` reactivates it via `Object.assign(updateData, reactivationFields())` but the only audit event written is the generic `SHARE_UPDATE` (emitted by the route, `share/routes.ts:252`). The spec's new audit surface (`features/specs/5.2-cleanup.md:211`) and BOTH docs pages explicitly state that reactivation transitions write `SHARE_REACTIVATED` / `REVERSE_SHARE_REACTIVATED` ("Chaque réactivation est enregistrée dans le Journal d'activité" / "Each reactivation is recorded in the Activity Log"; "Deactivation and reactivation write `SHARE_DEACTIVATED` / `SHARE_REACTIVATED`"). The manual `resumeShare` / `activateReverseShare` paths DO emit the reactivation action, so renew-via-extend is an inconsistent, silent lifecycle transition in the audit log.
  *Why it matters:* the docs promise a complete, searchable lifecycle record; an admin auditing why a share went from deactivated back to active after a renew will only see `SHARE_UPDATE`, not `SHARE_REACTIVATED`.
  *Suggested fix:* when the reactivation branch fires in `updateShare` / `updateReverseShare`, emit `SHARE_REACTIVATED` / `REVERSE_SHARE_REACTIVATED` (reason metadata e.g. `{ via: "extend" }`). Either log it in the service (it already has `logAuditEvent` available — see `pauseShare`) or return a flag the route can act on. Add an integration assertion alongside the existing reactivation-on-extend tests (`share/__tests__/pause-resume.test.ts:220`).

- [ ] **[Minor] `ReverseShare.deactivationReason` schema comment lists `max_views`, which is impossible for reverse shares** — `apps/server/prisma/schema.prisma:340`.
  The column comment reads `// DeactivationReason: "expired" | "max_views" | "manual"`, but reverse shares have no view-count concept (`deactivateEndedReverseShares` only ever sets `expired`, and the manual path sets `manual`). The header comment one line up (`:339`) is already accurate ("expired/manual"). Cosmetic only — the shared `DeactivationReason` type is legitimately the union; the column just never stores `max_views`.
  *Suggested fix:* change the inline comment to `// DeactivationReason (reverse share): "expired" | "manual"`.

- [ ] **[Minor] `deactivateEndedReverseShares` doc comment claims it reuses `markExpiredInactive`, but it inlines the write** — `apps/server/src/modules/cleanup/service.ts:505-507` vs `:529-532`.
  The JSDoc says "Reuses the read-time `markExpiredInactive` repository write (compare-and-set on `isActive`, `deactivatedAt` stamped at the expiration instant)", but the body actually performs an inline `prisma.reverseShare.updateMany({ where: { id, isActive: true }, data: {...} })` instead of calling `this.reverseShareRepository.markExpiredInactive(...)`. The shape is identical (so behavior is correct and race-safe), but the comment is misleading and the duplication means a future change to `markExpiredInactive` would silently diverge from the sweep.
  *Suggested fix:* either call `markExpiredInactive` from the sweep (preferred — single source of truth, matches the comment) or correct the comment to say it "mirrors" the write rather than "reuses" it.

- [ ] **[Minor] (pre-existing, out of A.1 scope) Lifecycle audit-action i18n keys missing in locales** — `apps/web/messages/*.json` (`audit.actions.*`).
  `SHARE_AUTO_DELETED`, `REVERSE_SHARE_AUTO_DELETED`, `ACCOUNT_FILES_CLEANED`, `ORPHAN_S3_DELETED`, `ORPHAN_DB_DELETED` have no `audit.actions.*` translations (verified absent at base `b966223`, so this predates Phase A.1 — it is a Phase A gap, not introduced by this slice). The A.1 reactivation/deactivation keys (`SHARE_DEACTIVATED`, `SHARE_REACTIVATED`, `REVERSE_SHARE_DEACTIVATED`, `REVERSE_SHARE_REACTIVATED`) ARE present with full 23-locale parity. Flagging for completeness since the activity-log UI will render the raw enum for these auto-deletion actions.
  *Suggested fix:* add the five missing `audit.actions.*` keys (EN/FR authored, EN replicas elsewhere per convention). Tracking against Phase A if A.1 considers it out of scope.

## Dimensions confirmed clean

1. **State-machine correctness — clean.** `deactivationFields()` / `reactivationFields()` (`share/lifecycle.ts`) are the single source of truth; the read-time maxViews transition (`share/service.ts:372-379`), read-time reverse-share expiry (`markExpiredInactive`), and the scheduler deactivation sweep all write the identical shape with `deactivatedAt` = the real end instant (expiration for `expired`, now/hit-moment for `max_views`). The defensive read-time expiry check (`share/service.ts:276-278`) blocks a share that lapses between sweeps even while `isActive=true`. Owner-self access is returned before any gate (`:244-246`).

2. **Manual-pause invariant — clean (critical dimension).** `AUTO_DELETABLE_REASONS = ["expired","max_views"]` excludes `manual`; both the warn query (`service.ts:407-415`) and the delete query (`:451-456`) filter `deactivationReason: { in: autoDeletable }`, verified by tests `service.test.ts:504` and `:557` (and reverse-share equivalents `:708`). The manual→expired upgrade (`service.ts:255-298`) is compare-and-set guarded on `{ isActive:false, deactivationReason:"manual" }` so a concurrent resume is never clobbered, and re-anchors `deactivatedAt` to the expiration instant — tested at `service.test.ts:313`.

3. **Reactivation — clean (audit caveat in M-1).** `reactivationFields()` clears `isActive`/`deactivatedAt`/`deactivationReason` and resets `notifiedForPendingDeletion`; `updateShare` also resets `notifiedForExpiring`/`notifiedForExpired`/`notifiedForMaxViews` on the appropriate extend/raise (`service.ts:537-557`). `resumeShare` refuses with 400 `ValidationError` when still expired/maxed (`:640-646`), is owner-only (`:634`), and owner-self read access is never blocked. Integration-tested (`pause-resume.routes.test.ts:296,312`).

4. **Two-phase sweep — clean.** Scheduler runs phase-1 (deactivate shares + reverse shares) before phase-2 (delete), correctly ordered with a documented rationale (`cleanup.scheduler.ts:123-160`); grace measured from `deactivatedAt`; warn-once via `notifiedForPendingDeletion` flipped only on enqueue; per-item try/catch tolerance; idempotent compare-and-set on `isActive`. Reverse-share variants mirror exactly and free S3 storage. Scheduler no longer reads `maxViewsCleanupDays` (regression-guarded at `cleanup.scheduler.test.ts:165`); A7/A9 gating unchanged.

5. **Read-time gating by reason — clean.** `share/service.ts:260-271`: `max_views`→410 `MAX_VIEWS_REACHED`, `manual`→403 `SHARE_INACTIVE`, `expired`/null→410 `SHARE_EXPIRED`. Reverse-share upload paths (`upload.service.ts` × 3 entry points + `service.ts` read paths) all retain `assertOwnerActive` (A6) AND now persist expiry via `markExpiredInactive` before throwing 410. No A6 regression. Integration-tested per reason (`share-lifecycle.integration.test.ts:133-180`) plus the owner-self exemption (`:195`) and the read-time maxViews persistence (`:229`).

6. **Route / UI — clean.** `PATCH /shares/:id/pause` and `/resume` are owner-only (service checks `creatorId`), route↔Zod schemas in sync, correct status codes including resume 400. Frontend `getShareLifecycleState` maps the three reasons to badges (`paused` / `maxViewsReached` / `expired`) and affordances (`manual`→Resume, `expired`/`max_views`→Renew→`setShareToManageExpiration`), wired in both the shares page and dashboard with `onSuccess()` query invalidation. No dead UI.

7. **Config retirement — clean.** `maxViewsCleanupDays` removed from `config-validation.ts`, `seed.js`, web settings (`use-settings.ts`, `constants.ts`), and EN+FR docs (now "eight keys"); only the intentional scheduler regression-guard test references it. 23-locale parity holds for all new keys. The cross-field `notifyDaysBefore ≤ grace` rule is preserved (`use-settings.ts:87-107`).

8. **Hygiene — clean.** Old `cleanupExpiredShares`/`cleanupMaxViewsShares`/`cleanupExpiredReverseShares` replaced (not left dangling); retired audit actions `REVERSE_SHARE_ACTIVATE`/`REVERSE_SHARE_DEACTIVATE` removed and superseded by `*_DEACTIVATED`/`*_REACTIVATED`. No production `as any` (the lone `as unknown as` is a test-only prisma-mock cast following an existing pattern). Migration `20260603080020_share_lifecycle` is well-formed (additive columns + SQLite table-rebuild preserving all data). EN/FR docs at parity.

9. **Tests — clean.** `app.inject()` integration coverage for read-time gating per reason, pause/resume (incl. refused-400 and non-owner-403), reactivation-on-extend, and read-time maxViews persistence. Unit coverage for both sweeps including manual-exclusion (warn + delete), manual→expired upgrade, grace-from-`deactivatedAt` boundary, notify-once/retry-safe, and race-safety. Reverse-share lifecycle covered (`reverse-share/__tests__/lifecycle.test.ts`). No security/lifecycle path left with service-only coverage.
