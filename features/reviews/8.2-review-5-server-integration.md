# 8.2 Email Notifications — Server Integration Review (Pass 5)

**Date**: 2026-05-30
**Reviewer**: Principal-level code review (Codebase MCP + manual route/URL verification)
**Scope**: Integration points between the email system and `share/`, `file/`, `reverse-share/`, `user/`, `auth/`, `notification/` modules
**Reference**: `features/specs/8.2-email-notifications.md`, `features/plans/8.2-email-notifications.md`

---

## Summary

The pass 4 follow-ups are visibly in place: the preference cascade now distinguishes "explicit user disabled" from "implicit catalog default" (C-1), `notifyRecipients` only sets `notifiedAt` when the email was actually enqueued (C-2), `share_max_views_reached` and `account_deactivated`/`account_reactivated` triggers exist (C-3), notify is rate-limited (I-1), folder-shared downloads are tracked (I-2), the visitor cookie path was relaxed to `/` (I-3), `addRecipients` accepts names (I-4), share-accessed/downloaded triggers honour `creator.isActive` (I-5), and `EmailService.send()` Zod-validates payloads (I-6). `admin_user_registered` is wired for password registrations (C-3 partial). The catalog explicitly documents `reverse_share_invitation` as deferred (acceptable spec adjustment), so that's no longer an integration gap.

However, two **critical URL bugs** were missed by all previous passes. The CTA URLs baked into emails do not match any frontend route:

- `buildResetPasswordUrl` returns `{appUrl}/auth/reset-password/{token}` — the actual page is `/reset-password?token=...`. The frontend reads `useSearchParams().get("token")`, not a path segment. Result: every password-reset email and LDAP welcome email links to a 404.
- `buildShareManageUrl` returns `{appUrl}/shares/{shareId}` — the frontend only has `/shares` (list, no per-share detail route). Result: the CTA buttons in `share_expiring`, `share_expired`, `share_max_views_reached`, `share_no_activity` all link to the share list, which is misleading at best.

These are not minor cosmetic issues — the entire user-facing value of these emails depends on the link working.

A real but lower-probability **integration bug**: the per-share `notifyOnDownload` toggle now upgrades both `share_downloaded` AND `share_accessed`, but the spec only ties this field to download notifications. There is also a concurrency hole in the `share_max_views_reached` trigger where simultaneous accesses can silently swallow the notification.

LDAP-provisioned user creation does NOT fan out an `admin_user_registered` email even though password registrations do — so the C-3 fan-out from pass 4 has an asymmetric coverage gap. The reverse-share upload batch uses an in-memory `setTimeout` debouncer that loses queued notifications on server restart.

The remaining items are smaller: URL inconsistency between password-reset call sites (`buildResetPasswordUrl` vs hand-built `/reset-password?token=…` in LDAP), missing recipient-name support on `CreateShareSchema`/`UpdateShareSchema` (only on `addRecipients`), `notifyOnDownload` semantic confusion (named for downloads but applied to accesses), and a few missing regression tests for important pass-4 fixes.

## Critical

### C-1: `buildResetPasswordUrl` produces a URL that does not exist on the frontend

- **Files**:
  - `apps/server/src/modules/email/url-builder.ts:47-50`
  - `apps/server/src/modules/auth/service.ts:194-203` (caller, password reset)
  - `apps/server/src/modules/ldap/sync.service.ts:382-391` (LDAP welcome — uses a *different* URL shape, also doesn't match)
  - `apps/web/src/app/reset-password/page.tsx` + `apps/web/src/app/reset-password/hooks/use-reset-password.ts:32` (actual frontend route + how it reads the token)
- **Description**:
  ```ts
  // server: buildResetPasswordUrl(token) → `${appUrl}/auth/reset-password/${token}`
  // web:    /reset-password   (with token read from `useSearchParams().get("token")`)
  ```
  The frontend has no `/auth/reset-password/[token]` route, and the page that does exist reads its token from `?token=…`, not from the path. Every `password_reset` email therefore points to a 404. Same blast radius for the `welcome` email path from the LDAP sync (which itself uses an *inconsistent* third format — `${appUrl}/reset-password?token=…`, which *would* work but contradicts `buildResetPasswordUrl`).
  The url-builder test (`__tests__/url-builder.test.ts:112-118`) verifies the produced string format, but not that it resolves to an actual page — a textbook case of unit tests passing while the integration is broken.
- **Expected**: Reset-password and welcome links must point to a route the frontend actually serves. The frontend reads `?token=…` — the email URL must use that shape.
- **Fix**: Change `buildResetPasswordUrl` to return `${base}/reset-password?token=${encodeURIComponent(token)}` (drop the `/auth` prefix, switch to query string). Update the LDAP welcome path to use the same helper instead of its handwritten `new URL("/reset-password", appUrl)` (which is the only call site that produced the *correct* shape — but should not exist as a separate code path).
  Add an integration test or fixture asserting the URL shape matches the route the frontend defines. The cleanest way: import a tiny route table (or fetch `/reset-password` against the Next dev server) and assert non-404 for the constructed URL.

### C-2: `buildShareManageUrl` points to `/shares/{id}` — the frontend only has a flat `/shares` list

- **Files**:
  - `apps/server/src/modules/email/url-builder.ts:38-41`
  - `apps/server/src/modules/share/service.ts:380` (max-views trigger)
  - `apps/server/src/modules/notification/notification.scheduler.ts:59, 111, 176` (expiring / expired / inactivity)
  - `apps/web/src/app/(shares)/shares/page.tsx` (the only `/shares` page — list view, no `[shareId]` segment)
- **Description**: `buildShareManageUrl(shareId)` returns `${base}/shares/${shareId}`. The web app has no dynamic segment under `/shares`. A user clicking the CTA in `share_expiring`, `share_expired`, `share_max_views_reached`, or `share_no_activity` lands on the all-shares list page — the URL works only because Next's router treats unknown sub-paths as static routes; in practice the user gets either a 404 or, depending on Next configuration, the share list with the unknown segment ignored. Either way, the CTA does not select / open / scroll-to the specific share.
- **Expected**: The CTA should land the owner on the specific share's detail (or at least scroll-to-and-open it in the list).
- **Fix**: Either (a) implement a `/shares/[shareId]` route (preferred, makes deep linking possible), or (b) change `buildShareManageUrl` to point to a real page that *can* deep-link, e.g. `${base}/shares?shareId=${shareId}` and have the list page open the matching row on mount. The choice is a product decision, but the current state ships emails with broken CTAs to every owner whose share is approaching expiry — an actively user-visible bug.
  Add the same kind of "URL resolves" integration check as C-1.

### C-3: `share_max_views_reached` notification can be silently dropped under concurrent access

- **File**: `apps/server/src/modules/share/service.ts:289-399`
- **Description**: The trigger compares a snapshot view count (`share.views`, read at line 193 before the atomic increment) against `maxViews`:
  ```ts
  const newViewCount = share.views + 1;           // ← from the pre-increment snapshot
  if (share.maxViews !== null && newViewCount >= share.maxViews && !share.notifiedForMaxViews && ...) {
    // fire share_max_views_reached
  }
  ```
  Under two concurrent non-owner accesses with `share.views = 8`, `maxViews = 10`:
  1. Both requests read `views = 8`.
  2. `incrementViewsAtomic` runs serially on the DB; one wins with `views → 9`, the second with `views → 10`.
  3. Both compute `newViewCount = 8 + 1 = 9` (from the snapshot), neither passes `>= 10`.
  4. The next visitor sees `views = 10`, atomic increment fails (`views < 10` is false), `MAX_VIEWS_REACHED` is thrown *before* the notification code runs.
  5. Owner is never notified.
  The same snapshot also drives the `prisma.share.update({ notifiedForMaxViews: true })` write — which races with the read-modify-update of the flag itself. The current code only marginally protects against duplicate sends.
- **Expected**: A single guaranteed notification when the share crosses the threshold.
- **Fix**: Either (a) read the post-increment view count from `incrementViewsAtomic` (change its signature to return the new value), or (b) re-fetch the share's `views` after the atomic update before the comparison. The cleanest is to expose:
  ```ts
  incrementViewsAtomic(shareId, maxViews): Promise<{ incremented: boolean; newViews: number }>
  ```
  and gate the notification on `newViews === maxViews && !notifiedForMaxViews`. Use a compare-and-set on the flag itself (`updateMany({ where: { id, notifiedForMaxViews: false }, data: { notifiedForMaxViews: true } })`) — if `count === 1`, send; otherwise some other request already sent. That eliminates both the snapshot-race *and* the duplicate-send window.

## Important

### I-1: `notifyOnDownload` per-share toggle applies to `share_accessed` — spec only ties it to downloads

- **Files**:
  - `apps/server/src/modules/email/service.ts:298` (`["share_downloaded", "share_accessed"].includes(type)`)
  - `features/specs/8.2-email-notifications.md` §6 ("**Notify me on each download** — toggle (overrides global `share_downloaded` preference for this share)")
- **Description**: The spec's "Per-share overrides" section explicitly scopes the override to `share_downloaded`. The current implementation also upgrades `share_accessed` when `notifyOnDownload === true`. UX consequence: a user who opted into "notify on download" for a specific share will also start receiving notifications when someone merely *views* the share (no download). That's likely surprising and may flood the inbox of someone who only wanted download alerts.
- **Expected**: Per spec, only `share_downloaded` is upgraded by `notifyOnDownload`.
- **Fix**: Remove `"share_accessed"` from the list at service.ts:298. If the desired UX *is* to also upgrade access notifications, rename the field to `notifyOnActivity` (or add a separate `notifyOnAccess` toggle) and update the spec. Either way: the current state diverges from the spec without the spec acknowledging it.

### I-2: `share_max_views_reached` sets the dedup flag *before* the email is enqueued — render failure leaves the flag set forever

- **File**: `apps/server/src/modules/share/service.ts:374-398`
- **Description**: The flag update and the email send are wired as:
  ```ts
  prisma.share.update({ data: { notifiedForMaxViews: true } })
    .then(() => buildShareManageUrl(shareId).then((url) => emailService.send("share_max_views_reached", …)))
    .catch(…)
  ```
  The flag is committed unconditionally; if `emailService.send` returns `{ enqueued: false, reason: "invalid_payload" }` (or if `buildShareManageUrl` throws because `appUrl` is missing), no email is queued but the share is permanently marked as notified. The owner never receives the notification and never will (next access just sees `notifiedForMaxViews === true` and skips).
  Contrast the `notification.scheduler.ts` flow (line 71-75, 123-127, etc.) which correctly gates the flag update on `if (result.enqueued)`. That pattern was applied to expiring / expired / inactivity but not here.
- **Expected**: Flag set only when the email was actually enqueued.
- **Fix**: Mirror the scheduler pattern:
  ```ts
  const shareManageUrl = await buildShareManageUrl(shareId);
  const result = await emailService.send("share_max_views_reached", { … });
  if (result.enqueued) {
    await prisma.share.update({ where: { id: shareId }, data: { notifiedForMaxViews: true } });
  }
  ```
  The compare-and-set approach in C-3 makes this even cleaner — the flag flip *itself* becomes the lock that prevents concurrent duplicate sends.

### I-3: LDAP user creation never fires `admin_user_registered` — asymmetric admin notification coverage

- **Files**:
  - `apps/server/src/modules/user/service.ts:60-69` (password registration → fans out to admins)
  - `apps/server/src/modules/ldap/sync.service.ts:376-403` (LDAP creates user, sends `welcome`, but no admin fan-out)
- **Description**: Password-based `register()` correctly calls `emailService.sendToAdmins("admin_user_registered", …)` after creating a non-first user. The LDAP sync path (the *primary* user-creation path in production deployments using AD) creates users via `userRepository.createUser` directly and only sends `welcome` to the new user. Admins are not notified. From an admin-monitoring standpoint, this means the spec's "admin notifications" feature only fires for the rarer password-registration path.
- **Expected**: Both registration paths should fan out to admins.
- **Fix**: After the successful LDAP user creation (around `sync.service.ts:376-377`), add:
  ```ts
  emailService.sendToAdmins("admin_user_registered", {
    userName: `${newUser.firstName ?? ""} ${newUser.lastName ?? ""}`.trim() || newUser.username,
    userEmail: newUser.email,
    registrationMethod: "ldap",
  }).catch((err) => getLogger().warn({ err, userId: newUser.id }, "LDAP: admin_user_registered failed"));
  ```
  The catalog already supports `registrationMethod` as a free string — the template renders whichever value is passed.

### I-4: Reverse-share batch notification debouncer is in-memory and lost on restart

- **File**: `apps/server/src/modules/reverse-share/upload.service.ts:30-39, 484-516`
- **Description**: `uploadSessions` is a private Map living in the singleton service. Each upload schedules a 5-second `setTimeout` to fire the notification. If the server restarts during that window (deployment, crash, container kill), the pending notification is dropped — files were ingested, the recipient never learns. Also, there is no cleanup on shutdown (`onClose` hook) so `setTimeout`s prevent graceful exit and may double-fire if the singleton ever leaks across hot reloads in dev.
- **Expected**: Either (a) durable buffering of "uploads to notify on", or (b) accept the loss but bound it (clear timers on shutdown and document).
- **Fix**: For 8.2 scope: at minimum, register an `onClose` hook that walks `uploadSessions` and flushes pending notifications synchronously (immediate `send` instead of after-debounce). The proper fix — persisting batch state in DB (e.g., on `ReverseShareFile.notifiedAt` and a periodic sweep) — is bigger but matches how the rest of 8.2 handles "notify after N seconds of quiet" (it doesn't elsewhere; this is the only such mechanism). At absolute minimum the debounce window should be tested with a restart scenario, and the cooldown=300s entry in the catalog should be acknowledged as redundant with this 5-second window (a single window-truncation already deduplicates).

### I-5: `CreateShareSchema` and `UpdateShareSchema` only accept recipient emails, not names — asymmetric to `addRecipients`

- **File**: `apps/server/src/modules/share/dto.ts:18, 54`
- **Description**: `addRecipients` (`UpdateShareRecipientsSchema`, line 190-209) accepts `{ email, name? }` per recipient. But `CreateShareSchema` and `UpdateShareSchema.recipients` accept only `z.array(z.string().email())`. So the only way to add a recipient *with a name* is the two-step "create share with email-only recipients → call `/shares/:id/recipients` to set names." A frontend that uses the bulk create/update endpoint will silently lose names.
  Pass 4 I-4 raised this as a Minor; with the recipient `name` field now flowing into the visitor identification gate (`service.ts:272`), it has a stronger functional impact — recipients without names trigger the identification form even when their name is "known" (set in another tool).
- **Expected**: Either make the create/update endpoints accept rich recipients (`{ email, name? }`), or remove the recipients field entirely from those endpoints and document that recipients must be added via `/shares/:id/recipients`.
- **Fix**: Replace `recipients: z.array(z.string().email())` with `recipients: z.array(RecipientWithNameSchema)` on both `CreateShareSchema` and `UpdateShareSchema`. Update the recipient handling in `createShare` and `updateShare` to thread the name through. Both methods already use the repository's `addRecipients` (which accepts names) — only the DTO and one mapping line need to change.

### I-6: Password-reset failure when `appUrl` missing throws `400 — "Failed to send password reset email"` and leaks user existence

- **Files**: `apps/server/src/modules/auth/service.ts:193-207`, `apps/server/src/modules/auth/routes.ts:305-321`
- **Description**: Cross-cutting with the server-core review, but visible from the integration angle: the route returns the carefully vague *"If an account exists with this email, a password reset link will be sent."* for the *success* case. But when the user *does* exist and the email send pipeline throws (only path that throws is `buildResetPasswordUrl` failing because `appUrl` is unset), the `ValidationError` propagates and the client sees `400` + `"Failed to send password reset email"`. For unknown emails (line 167-170) the function returns silently and the route still returns the vague message. So a stranger can probe an email and distinguish "exists" from "does not exist" simply by misconfiguring (or DoS-ing into a state with) appUrl missing — though admittedly the attacker would need server access to *cause* the missing-config state. Real impact is small, but the asymmetry is also fixable for free.
- **Expected**: Same outward response in both branches.
- **Fix**: In `requestPasswordReset`, log the URL/render error but do not re-throw. Either (a) call `buildResetPasswordUrl` *inside* `EmailService.send` so the same swallow-then-log path that handles SMTP disabled handles missing appUrl too, or (b) wrap the build+send in a single try block that only logs:
  ```ts
  try {
    const resetUrl = await buildResetPasswordUrl(token);
    await emailService.send("password_reset", { … });
  } catch (error) {
    getLogger().error({ err: error }, "Failed to send password reset email");
    // Intentionally swallow — do not leak existence via status code
  }
  ```
  This makes the user-existence side-channel impossible regardless of admin config errors.

## Minor

### M-1: `notifyOnDownload` field name conveys "download" but governs access too (related to I-1)

- **File**: `apps/server/src/modules/share/dto.ts:27` (`notifyOnDownload: z.boolean().optional().describe("Notify owner on file download")`)
- **Description**: Field description and name explicitly say "download". The cascade also upgrades `share_accessed`. Even after I-1 is fixed (limiting the cascade to `share_downloaded` only), if the UX intent really is to cover access too, the field should be renamed `notifyOnActivity` or split into two booleans. Independent of how I-1 is resolved, the description in the Zod schema should match actual behaviour.
- **Fix**: Align field name, schema description, and cascade scope. Either narrow the cascade (I-1) or broaden the name; do not leave the mismatch.

### M-2: No integration test asserts `notifiedAt` is NOT set when SMTP is disabled

- **File**: `apps/server/src/modules/share/service.ts:778` (the `if (result.enqueued)` gate), no corresponding test
- **Description**: Pass 4 C-2 fixed `notifyRecipients` to only push to `notifiedRecipients` / set `notifiedAt` when `result.enqueued === true`. The fix is in place, but no test locks it in. A future refactor that accidentally drops the `if (result.enqueued)` would re-introduce the silent-success bug.
- **Fix**: Add an integration test: mock `smtpEnabled = "false"`, call the service, assert no `prisma.shareRecipient.update({ data: { notifiedAt: … } })` and `notifiedRecipients: []`.

### M-3: `admin_user_registered` is fan-out via `sendToAdmins`, including the admin who just clicked "Create user"

- **File**: `apps/server/src/modules/user/service.ts:60-69`
- **Description**: When an admin creates a user via `POST /auth/register`, `sendToAdmins` enumerates all `isAdmin: true, isActive: true` users — including the one who just performed the action. They receive a notification about a user they personally created. Cosmetic, low-impact, but the simple `where: { id: { not: actingAdminId } }` filter would clean it up.
- **Fix**: Plumb the acting admin's userId (from the request context) into `userService.register()` and pass it down to a `sendToAdmins(type, data, { excludeUserId })` variant. Optional — depends on product preference (some teams *want* the confirmation).

### M-4: `reverse_share_uploaded` has both a 5-second debounce *and* a 5-minute catalog cooldown — double-throttle

- **Files**: `apps/server/src/modules/email/catalog.ts:440-441` (`cooldownSeconds: 300`), `apps/server/src/modules/reverse-share/upload.service.ts:507-515` (`setTimeout(..., 5000)`)
- **Description**: The debounce already coalesces a batch into one notification. The catalog's 300-second cooldown then suppresses any second batch within 5 minutes. So the second uploader to the same reverse share within 5 minutes generates *no* notification to the owner at all, even though their upload is unrelated. This is more aggressive throttling than the debounce alone justifies. May be intentional anti-flood, but the two mechanisms layered together produce a behaviour neither alone would: "tell the owner about the first uploader; silently swallow uploaders 2..N if they show up within 5 minutes."
- **Fix**: Decide which mechanism owns "don't flood." If the 5-second debounce is the canonical batcher, drop `cooldownSeconds` from `reverse_share_uploaded`. If the 5-minute cooldown is meant for anti-abuse, document why the debounce is also needed.

### M-5: Audit metadata stores plaintext emails (PII) — unchanged from pass 4, still worth tracking

- **File**: `apps/server/src/modules/share/routes.ts:516, 569, 772`
- **Description**: Same observation as pass 4 M-2: notify / addRecipients / removeRecipients audit rows persist email addresses in `metadata.emails`. Pass 4 marked this acknowledged. For a deployment doing GDPR data-subject deletion, the user-deletion handler must also redact `AuditLog.metadata.emails`. The current `deleteUser` (`user/service.ts:156-162`) does not.
- **Fix**: When the data-deletion feature ships (likely 5.x), it must sweep `AuditLog` rows where the deleted user's email appears in `metadata.emails` and either redact or delete them. Tracked here so it's not lost.

### M-6: Visitor-tracking `share_accessed` notification doesn't include the share URL — the owner sees "someone accessed your share" with no clickable context

- **File**: `apps/server/src/modules/share/service.ts:346-361`
- **Description**: The `share_accessed` payload schema only includes `shareName`, `visitorName`, `visitorEmail`, `accessedAt`. No `shareManageUrl` / `shareLink`. The recipient (the owner) opens the email and can't click through to inspect the visit. Compare `share_expiring` / `share_no_activity` which both include `shareManageUrl`.
- **Fix**: Add `shareManageUrl: z.string()` to `shareAccessedSchema` and `shareDownloadedSchema`, build it at the call site, and surface a CTA in the template. Symmetric with the other share-event notifications.

### M-7: `share_invitation` is enqueued without `userId` — admin queue stats can attribute by share (via `relatedId`) but not by sender

- **File**: `apps/server/src/modules/share/service.ts:761-776`
- **Description**: Pass 4 M-7 was partially closed (relatedId is now passed), but `userId` is still omitted. The trade-off was deliberate (invitations are *to* the recipient, who has no account), but it means: (a) the admin queue dashboard can't pivot "X emails sent on behalf of user Y," and (b) the cooldown machinery can't attribute "this is the third time the same sender invited the same recipient." Currently `share_invitation` has `cooldownSeconds` unset, so the second case is irrelevant *today*, but if a cooldown is ever added it will dedup based on `(type, to, relatedId)` rather than the more meaningful `(type, to, senderId)`.
- **Fix**: Either accept the trade-off explicitly (a comment near the call site stating why `userId` is omitted) or pass `userId: share.creatorId` and treat it as "the sender's userId, used for queue analytics only, not for preference checks." Note: passing `userId` would currently trigger the preference cascade because `entry.isCritical === false` — the `share_invitation` entry is configurable: false / hasUnsubscribe: false, but the cascade still runs. That cascade would no-op because no `NotificationPreference` row will exist for that type (it's not configurable), but the extra DB roundtrip is wasted. If preserving the no-roundtrip path is preferred, document.

### M-8: `share_downloaded` notification loses visitor identity even when the same visitor just accessed the share via a tracking token

- **File**: `apps/server/src/modules/file/routes.ts:194-218`
- **Description**: Same as pass 4 M-8 — re-flagged because the deferred status was logged but no follow-up issue captures it. The `trackShareDownload` function intentionally omits visitor name/email even when an `sv_{alias}` cookie or `?t=…` would identify them, because the download endpoints don't currently parse the cookie or query. Cost to fix is low (parse the cookie like the share routes do), benefit is consistent visitor attribution across access + download notifications.
- **Fix**: Either implement it (parse `sv_{alias}` cookie and `?t=…` query in `POST /files/download-url` and `POST /files/download`, thread the result into `trackShareDownload`) or open a tracked follow-up issue and stop carrying the comment in code.

### M-9: `getShareByAlias` accepts a `shareAccessQuery` with the tracking token but the `getShare` (`/shares/:shareId`) route does not parse a visitor cookie

- **File**: `apps/server/src/modules/share/routes.ts:154-193` vs `659-707`
- **Description**: `GET /shares/alias/:alias` and its POST sibling both call `parseVisitorCookie(request, alias)` and feed `visitorCookie` into the service context. `GET /shares/:shareId` does *not* — the context is `{ trackingToken, ipAddress, userAgent }` with no `visitorCookie`. So a visitor who identified via the form for an alias `foo` can still trigger the IDENTIFICATION_REQUIRED gate if anyone (e.g., the share creator inspecting a UUID-based URL) hits `/shares/{shareId}`. In practice the by-ID route is mostly used by authenticated owners, so this is rare, but it's an inconsistency: the gate enforces stricter conditions on the by-ID route than on the by-alias route.
- **Fix**: Either pass the cookie through on the by-ID route (would require resolving alias→shareId before reading the cookie, or storing cookie keyed by shareId in addition to alias), or document that the by-ID route does not support visitor cookies (only tracking tokens). The first is more defensive; the second is simpler.

### M-10: `notifyOnDownload` change does not reset notification cooldown — toggling on/off mid-session has unintended behaviour

- **File**: `apps/server/src/modules/share/service.ts:451-471`
- **Description**: When the owner toggles `notifyOnDownload` true→false→true within 15 minutes, the cooldown logic in `EmailService.send` still suppresses notifications. Not a bug per se (cooldown is "(type, to, relatedId)" scoped — toggling settings shouldn't bypass spam protection), but worth being aware of: the owner may toggle the setting expecting "now I want immediate notifications" and not see any until 15 minutes after the last visit. Not specifically a fix-worthy item, just a note.
