## Critical

- [x] **FIXED — The new seed module is not shipped in the production image → boot crash loop (same failure class as B-27).** Added `"src/db"` to `apps/server/package.json` `files`. Re-verified empirically: `pnpm --filter ouitransfer-api deploy --legacy --prod /tmp/...` now ships `src/db/seed-data.ts` (was absent before). — `apps/server/package.json:18-25` (`files` array) + `apps/server/prisma/seed.js:2` — `prisma/seed.js` is shipped (because `files` includes `"prisma"`) and imports `../src/db/seed-data.js`, but the `files` allowlist contains only `"src/scripts"` and `"src/shared"` — **not `"src/db"`**. `pnpm deploy --legacy --prod` (Dockerfile:71) honors the `files` field, so `src/db/` is never copied into `/app/deploy` → `/app/ouitransfer-app`. At boot, `server-start.sh:75` runs `tsx ./prisma/seed.js`, which fails to resolve `../src/db/seed-data.js`; with `set -e` the script aborts before `exec node dist/server.js`, and the container crash-loops on every fresh AND existing volume. This is the very outcome the fix exists to prevent — only the mechanism changed (missing module instead of skipped seed). **Verified empirically**: a real `pnpm --filter ouitransfer-api deploy --legacy --prod --ignore-scripts /tmp/deploy-test` copied only `src/scripts` and `src/shared`; `src/db/seed-data.ts` was confirmed absent from the deploy output. (`src/generated` is also absent from deploy but is regenerated by the explicit `prisma generate` at Dockerfile:78 — nothing regenerates `src/db`.) The old `seed.js` only imported `src/shared/prisma-factory.js`, which *is* in `files`, so the prior code happened to work. **Fix:** add `"src/db"` to the `files` array in `apps/server/package.json`. (Strongly consider also adding `"src/generated"` explicitly rather than relying on the post-deploy `prisma generate`, but that is pre-existing.) Note: BUGS.md:25 itself flags "the seed/check scripts importing `../src/...` (only resolvable via tsx + shipped `src/`)" as a known latent issue — the fix moved the import to a path that is *not* shipped, firing that exact latent issue.

## Important

- [x] **ADDRESSED — The regression cannot be caught by PR CI.** Added a static packaging guard test (`seed.integration.test.ts` describe "seed runner is packaged for the production image") that parses every `../src/<dir>` import in `prisma/seed.js` and asserts each is in `package.json` `files` — this fails fast in `ci.yml` for the exact omission class above, without a Docker build (PR CI stays fast, per the project's deliberate release-only Docker policy). The end-to-end runner/boot remains covered by `e2e.yml` at tag time. Also corrected the test header comment to stop overstating coverage (it now states the runner process itself is covered by e2e, not this test). — `.github/workflows/e2e.yml:4-7` + `apps/server/src/__tests__/seed.integration.test.ts:29` — The new integration test imports `seedDatabase` and the data arrays directly from the source tree (`../db/seed-data.js`), where `src/db` always exists locally. It therefore can never detect the packaging/deploy problem above, nor does it exercise the `prisma/seed.js` runner wiring (dotenv `quiet`, client creation, the `../src/...` resolution under tsx). The only workflow that builds and boots the real Docker image (`e2e.yml`) runs solely on `tags: ["v*"]`, not on PRs. So the Critical finding would sail through `ci.yml`, reach `main`, and only surface at the next release — the identical detection gap B-27 had. **Fix:** after correcting `files`, add coverage that actually runs the shipped runner against a packaged layout (e.g. a test that `execSync`s `tsx prisma/seed.js` against a temp `DATABASE_URL`, asserting it exits 0 and populated the DB), or — better — gate Docker build+boot smoke on PRs. At minimum, the test comment at `seed.integration.test.ts:5,17` ("runs `prisma/seed.js` UNCONDITIONALLY", "lets server-start.sh seed on every boot to backfill") overstates what is covered, since the runner and packaging are untested.

## Minor / Nits

- [x] **ADDRESSED — `embedSecret` regenerates on every boot but is discarded by protected mode.** Added a 4-line comment at the `embedSecret` entry explaining the regenerated value is intentionally discarded when the row exists, so the seeded secret is stable. — `apps/server/src/db/seed-data.ts:84-88` — `defaultConfigs` is evaluated at module load, so a fresh 32-byte secret is computed on *every* `tsx prisma/seed.js` invocation (now every boot). On a non-fresh DB the `embedSecret` row already exists, so `seedDatabase` skips the `create` and the freshly-generated value is thrown away — the persisted secret is stable. This is correct (no secret churn across restarts), but it is non-obvious given "always seed on every boot." Checked-OK functionally; worth a one-line comment that the regenerated value is intentionally discarded when the row exists.

- [x] **ACCEPTED (no change) — `seedDatabase` partial-failure leaves a half-seeded DB, self-healing on next boot.** Correct behaviour for protected-mode idempotent seeding; the new no-op-on-re-run test covers the self-heal property. — `apps/server/src/db/seed-data.ts:520-568` — Seeding is a per-row `findUnique`+`create` loop with no surrounding transaction. If it throws midway (e.g. DB lock), some rows are inserted and the process exits 1 (`set -e` aborts boot). Because the loop is idempotent and skips existing rows, the next boot completes the remaining inserts. This is the correct behavior for "protected mode" and matches the old `main()` exactly. Checked-OK — flagging only because the prompt asked; no change required.

- [x] **FIXED — Log noise on every boot.** Dropped the per-key "⏭️ already exists, skipping" console lines in both the config and provider loops (~60 lines/boot); the summary still reports the skipped counts. — `apps/server/src/db/seed-data.ts:514-573` — On a steady-state DB the seed now emits ~60 "⏭️ already exists, skipping" lines plus two summaries on every single boot/restart. Harmless but noisy in container logs and a slight regression vs. the old gate (which skipped the run entirely when nothing was missing). Consider summarizing skips into a single count line, or only logging individual creates. Performance is a non-issue (≤60 indexed `findUnique` lookups). Checked-OK on correctness.

The fragility is not the import per se but that it is silently dependent on the `files` allowlist (see Critical). Once `files` is corrected, this is fine. No separate action beyond the Critical fix; logged for completeness.
