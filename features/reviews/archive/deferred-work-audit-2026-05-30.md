### AR-1: Register-with-invite error handling relies on English string matching

- **File**: `apps/web/src/app/register-with-invite/[token]/components/register-form.tsx:69`
- **Marker**: `TODO: Server should return structured error codes instead of English messages`
- **Context**: The catch block for the invite registration form detects specific error conditions
  by `includes()`-matching English strings from the server response body
  (`"already been used"`, `"expired"`, `"Username already exists"`, `"Email already exists"`).
  If any server message changes wording (e.g., during a refactor or locale change), the
  error detection silently breaks and the user sees the generic "createFailed" toast.
- **Recommendation**: Add structured `AppError` error codes to the server-side registration
  handler (e.g., `INVITE_TOKEN_USED`, `INVITE_TOKEN_EXPIRED`, `USERNAME_EXISTS`, `EMAIL_EXISTS`)
  and replace the string matching with code comparisons on the frontend. This is a low-effort,
  high-reliability improvement consistent with how other endpoints return structured codes.

### AR-3: Password reset tokens stored in plaintext

- **File**: `apps/server/src/modules/ldap/sync.service.ts:361`
- **Marker**: `NOTE: Password reset tokens are stored in plaintext — this is pre-existing tech debt affecting the entire password reset system, not just LDAP.`
- **Context**: The `PasswordReset` Prisma model stores the raw random hex token (`crypto.randomBytes(32).toString("hex")`) as a plaintext string in the database. If the database is compromised, all active reset tokens are immediately usable. The note in the LDAP sync code correctly identifies this as pre-existing debt affecting the entire `passwordReset` flow (the same pattern is in `auth/service.ts` and everywhere password resets are generated).
- **Impact**: Security hygiene. Not exploitable without database access, but violates defense-in-depth. Acknowledged in the LDAP review (M-10, `features/reviews/archive/5.3-ldap-server.md:37`) but never formally tracked in `TECHNICAL-DEBT.md`.
- **Recommendation**: Hash reset tokens before storing (SHA-256 is sufficient; bcrypt is unnecessary since the token is already high-entropy). At verification time, hash the incoming token and compare. This pattern is standard (used by GitHub, Django, etc.). Add a formal TD entry and schedule as a standalone low-risk refactor.

### AR-5: Global error boundary hardcoded in English — no i18n possible

- **File**: `apps/web/src/app/global-error.tsx:12`
- **Marker**: `TODO: i18n — hardcoded English; providers are dead so useTranslations() is unavailable`
- **Context**: `GlobalError` catches root layout crashes where providers (i18n, theme, auth) are
  unavailable, so `useTranslations()` cannot be called. The component renders hardcoded English
  strings ("Something went wrong", "An unexpected error occurred", "Try again", "Go to home page").
  The comment itself explains the constraint and why it cannot easily be fixed.
- **Assessment**: This is a known, correct trade-off — root layout crashes are rare, and loading
  provider infrastructure into the error boundary would introduce its own failure modes. The
  TODO is accurate but the fix is non-trivial (would require inlining pre-translated strings
  for each locale via some other mechanism). **Severity: Very Low** — the error boundary exists
  precisely for catastrophic failures where UX perfection is secondary to recovery.
- **Recommendation**: Accept as an acknowledged limitation. Optionally, inline a small static
  translation map (similar to what `notification/routes.ts` does for the unsubscribe page)
  covering the handful of strings in the most common supported locales. If this approach is
  taken, do it alongside AR-2 using the same pattern.

### PO-1: Sequential notification processing could use batched `updateMany`

- **File**: `apps/server/src/modules/notification/notification.scheduler.ts:51`
- **Marker**: `TODO: Performance — batch updateMany after processing. Current sequential per-share approach is fine for typical deployments (< 1000 active shares).`
- **Context**: The `checkExpiringShares()` function processes shares sequentially in a `for...of`
  loop and updates `notifiedForExpiring` one by one. For large deployments (>1000 active shares),
  this is suboptimal. The fix is to collect successful IDs and issue a single
  `prisma.share.updateMany({ where: { id: { in: successIds } } })`.
- **Impact**: Zero at current scale. The comment correctly identifies the threshold.
- **Recommendation**: Implement when/if deployment scale demands it, or as part of 5.2 scheduler work.

### PO-2: `checkInactiveShares()` filters in JS instead of SQL WHERE clause

- **File**: `apps/server/src/modules/notification/notification.scheduler.ts:144`
- **Marker**: `consider using prisma.$queryRaw with a computed WHERE clause`
- **Context**: `checkInactiveShares()` fetches all shares with `inactivityAlertDays` set and
  filters them in JavaScript to find shares that exceeded their inactivity threshold. For large
  datasets, moving the date math into a SQL `WHERE` clause (via `prisma.$queryRaw`) would be
  more efficient. The comment explicitly flags this as only relevant for 10k+ shares.
- **Recommendation**: Acceptable at current scale. Revisit if performance metrics show this
  check becomes slow under load.

### PO-3: Email queue processes jobs sequentially (by design, intentional)

- **File**: `apps/server/src/modules/email/queue.ts:226`
- **Marker**: `NOTE: Sequential processing is intentional — SQLite has a single writer`
- **Context**: Email jobs are processed one at a time to avoid SQLite write contention and
  SMTP connection pressure. This is an explicit architectural decision, not an oversight.
  The NOTE explains the rationale: parallel processing would cause SQLite write conflicts.
- **Assessment**: This is informational, not a performance problem. Upgrading to Postgres would
  be the prerequisite for meaningful parallelization. No action needed.
