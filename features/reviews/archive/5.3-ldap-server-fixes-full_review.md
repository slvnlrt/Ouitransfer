⚠️ C6 — Chained setTimeout — PARTIAL (race condition bug)
-

🐛 NEW BUG (Important): The "stop check" inside the timer callback is unsound:
function scheduleNext(intervalMs: number): void {
  schedulerNextSyncAt = new Date(Date.now() + intervalMs);
  currentTimeout = setTimeout(async () => {
    try { await syncService.runSync("scheduled"); } catch {...}
    if (currentTimeout !== null) { scheduleNext(intervalMs); }  // ← BUG
  }, intervalMs);
}
Race scenario: A scheduled sync is running (awaiting runSync). During that await, an admin saves a new config (different interval). startScheduler() → stopScheduler() (nulls currentTimeout) → scheduleNext(NEW_INTERVAL) (sets currentTimeout = T2). The original callback resumes, sees currentTimeout !== null (because it now holds T2), and calls scheduleNext(OLD_INTERVAL), overwriting T2 and leaking it. Result:
1. 
The new interval is silently reverted to the old one.
2. 
The leaked timer T2 will fire too — and will chain its own scheduleNext(NEW_INTERVAL). You now have two parallel scheduler chains at different intervals, both writing to currentTimeout and schedulerNextSyncAt.
Fix: capture the timer handle in a local variable and compare strict equality:
function scheduleNext(intervalMs: number): void {
  schedulerNextSyncAt = new Date(Date.now() + intervalMs);
  const handle = setTimeout(async () => {
    try { await syncService.runSync("scheduled"); } catch {...}
    if (currentTimeout === handle) {  // only we should chain
      scheduleNext(intervalMs);
    }
  }, intervalMs);
  currentTimeout = handle;
}
Test scenario: programmatically call startScheduler(60) then startScheduler(15) mid-sync.
- 
Also: schedulerNextSyncAt is left stale (points to a moment in the past) during the entire await runSync(...) window. Minor UI quirk (getNextSyncAt() returns a past time during sync execution).

NEW ISSUES INTRODUCED BY FIX COMMITS
🐛 Important Scheduler race condition (C6 fix)
The if (currentTimeout !== null) check fails to identify "are we still the active timer?". A concurrent startScheduler() call (e.g., admin changing sync interval) during an in-flight sync produces parallel scheduler chains. See C6 above for fix.
🐛 Important getSyncLogs querystring schema drift (I1 fix)
The route declares its own inline schema that lacks the defaults and bounds present in SyncLogsQuerySchema. The controller's type assertion lies, and Prisma receives undefined for take/skip when query params are omitted → unbounded result set possible. Use SyncLogsQuerySchema as the route schema directly.
🐛 Important requestPasswordReset not updated (C4 fix incomplete)
Only resetPassword was patched. requestPasswordReset still blocks LDAP users when passwordAuthEnabled=false. An LDAP user whose welcome token expires has no recovery path.
🐛 Minor LDAP-vs-LDAP collision falls through to P2002 (I2 fix)
if (conflict && !conflict.ldapDn) only handles non-LDAP conflicts. Two LDAP users with the same username/email but different DN → silent fallthrough to user.create → unique constraint error caught as generic message.
🐛 Minor I4 phase field functionally inert
Only set in one place ("sync"). Needs to be set at each error site to be useful.
🐛 Minor I9 5-minute cutoff is arbitrary
Should mark all stale "running" rows on boot, not just those >5 min old.
🐛 Minor scheduleNext leaves schedulerNextSyncAt stale during sync
While await runSync(...) is in flight, getNextSyncAt() returns a past timestamp. Admin UI shows "next sync: 2 minutes ago". Cosmetic.
🐛 Minor Welcome email href not URL-escaped
<a href="${appUrl}/reset-password?token=${resetToken}"> interpolates without escaping. Token is hex, appUrl is Zod-validated, so currently safe. Use URL construction for defense-in-depth.
