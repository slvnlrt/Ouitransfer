# Post-Fix Review — 5.3 LDAP/AD Sync (Server)

Review of fix commits `b6d84e0` + `dfefb49` (base: `87ad758`). All original findings were checked; incomplete fixes and new issues introduced by the fixes are listed below. **ALL must be fixed.**

---

## Important

- [x] **PF-S-I-1.** C4 fix incomplete — `requestPasswordReset` blocks LDAP users. `auth/service.ts:146-152`: the `passwordAuthEnabled=false` guard was only removed from `resetPassword` (which processes the token). But `requestPasswordReset` (which generates and sends the reset link) also gates on this setting. An LDAP user whose 7-day welcome token expires has no recovery path: requesting a new reset link hits the guard and returns `ForbiddenError`. Fix: in `requestPasswordReset`, look up the user by email, and if `user.ldapDn` is set, skip the `passwordAuthEnabled` check.

- [x] **PF-S-I-2.** C6 fix introduces a scheduler race condition. `sync.scheduler.ts` — the `if (currentTimeout !== null)` check inside the chained `setTimeout` callback doesn't identify whether the current timer is still the active one. Race scenario: sync is running (awaiting `runSync`); admin saves new config → `startScheduler(NEW)` → `stopScheduler()` nulls `currentTimeout` → `scheduleNext(NEW_INTERVAL)` sets `currentTimeout = T2`. Original callback resumes, sees `currentTimeout !== null` (it's now T2), calls `scheduleNext(OLD_INTERVAL)`, overwrites T2 and produces two parallel scheduler chains at conflicting intervals. Fix: capture the `setTimeout` handle in a local `const` and compare `currentTimeout === handle` inside the callback:
  ```ts
  function scheduleNext(intervalMs: number): void {
    schedulerNextSyncAt = new Date(Date.now() + intervalMs);
    const handle = setTimeout(async () => {
      try { await syncService.runSync("scheduled"); } catch (err) { ... }
      if (currentTimeout === handle) {
        scheduleNext(intervalMs);
      }
    }, intervalMs);
    currentTimeout = handle;
  }
  ```

- [x] **PF-S-I-3.** I1 fix incomplete — `getSyncLogs` querystring schema drift. `routes.ts` — the querystring for `GET /admin/ldap/sync-logs` was not updated to use `SyncLogsQuerySchema`. It still declares an inline schema `{ limit: z.coerce.number().optional(), offset: z.coerce.number().optional() }` — no defaults, no `min(1)/max(100)` bounds. The controller type-asserts `request.query as z.infer<typeof SyncLogsQuerySchema>` which is a lie: values can be `undefined`, and omitting `?limit` passes `undefined` to Prisma `take`, making the query unbounded. Fix: replace the inline querystring schema with `SyncLogsQuerySchema` (import from dto).

## Minor

- [x] **PF-S-M-1.** I4 phase field functionally inert. `sync.service.ts` — the `phase` field was added to `SyncDetail` and only set in one error path with the hardcoded value `"sync"`. Every other error path (createNewUser catch, updateExistingUser catch, deactivation, welcome-email failure, boot stale-log cleanup) has no `phase`. The field's purpose was to distinguish where a failure occurred — currently all errors say `"sync"`. Fix: tag each error site with a meaningful phase string: `"connect"`, `"search"`, `"create-user"`, `"update-user"`, `"deactivate"`, `"welcome-email"`, `"boot-recovery"`.

- [x] **PF-S-M-2.** I9 stale-log cleanup cutoff is wrong. `sync.scheduler.ts:initSchedulerOnBoot` — the `updateMany` filters for `startedAt: { lt: fiveMinAgo }`. When the server boots, `syncInProgress` is reset to `false`; no sync can be running. Any "running" row is stale by definition, regardless of age. The 5-minute filter means a sync that crashed within the last 5 minutes before boot keeps the `running` status forever. Fix: drop the time filter — mark ALL `status === "running"` rows as error on boot.

- [x] **PF-S-M-3.** Welcome email href is not URL-constructed. `email/service.ts:sendLdapWelcomeEmail` — the link is built by string interpolation: `<a href="${appUrl}/reset-password?token=${resetToken}">`. Both values are currently safe (`appUrl` is Zod URL-validated, `resetToken` is hex), but constructing hrefs via `new URL()` is the correct practice. Fix: `const url = new URL('/reset-password', appUrl); url.searchParams.set('token', resetToken); const resetUrl = url.toString();` — then use `resetUrl` in the template.

- [x] **PF-S-M-4.** I2 LDAP-vs-LDAP collision falls through to P2002. `sync.service.ts:288-303` — the conflict check is `if (conflict && !conflict.ldapDn)`. If two LDAP users somehow share the same email or username but have different DNs (e.g., after an AD DN rename), both conditions are false (`conflict.ldapDn` is set), the check is skipped, and `tx.user.create` throws a unique constraint error that surfaces as a generic message. Fix: tighten the check: `if (conflict && conflict.ldapDn !== adUser.dn)` (covers non-LDAP conflicts AND same-email/different-DN LDAP conflicts).

- [x] **PF-S-M-5.** `schedulerNextSyncAt` stale during sync execution. `sync.scheduler.ts` — `schedulerNextSyncAt` is set to `new Date(Date.now() + intervalMs)` at the start of each `scheduleNext` call, which is correct for the next run. But during `await runSync(...)`, the value still points to a time that is now in the past (it's not updated on completion). `getNextSyncAt()` therefore returns a past timestamp while sync is running, and the admin UI shows "next sync: 3 minutes ago". Fix: update `schedulerNextSyncAt` after the sync completes (or set it to `null` while sync is in progress and update it post-run).

- [x] **PF-S-M-6.** I7 — O(n·m) in batch deactivation logging. `sync.service.ts:176` — `localLdapUsers.filter((u) => toDeactivateIds.includes(u.id))` is O(n·m) because `Array.includes` scans the array on each iteration. Fix: either capture the user objects directly before the `.map(u => u.id)` step (so no reverse lookup is needed), or use a `Set<string>` for `toDeactivateIds` and call `.has()` instead of `.includes()`.

- [x] **PF-S-M-7.** I8 — Tautological `else if` in reactivation/update logic. `sync.service.ts` — after the reactivation branch, the code does `else if (Object.keys(changes).length > 0)`. But we already return early at ~line 259 when `changes` is empty, so if we reach the `else` branch, `changes` is guaranteed non-empty. Simplify to just `else`.

- [x] **PF-S-M-8.** C2 — No regression test for LDAP filter injection. `ldap.client.ts` — the fix uses `ldapts` built-in `EqualityFilter` which handles RFC 4515 escaping internally, and the review verified this is correct. However, there is no test asserting that injection payloads (e.g., `*)(uid=*)`) are neutralized. Add at least one unit test in the LDAP client test file that passes a malicious username/email containing LDAP special characters and verifies the resulting filter is safe (either by inspecting the filter object or by mocking the search and checking the actual filter string sent).

- [x] **PF-S-M-9.** I9 — Boot stale-log cleanup detail lacks `phase`. `sync.scheduler.ts:initSchedulerOnBoot` — when marking stale "running" logs as error on boot, the detail object has `{ type: "error", message: "..." }` but no `phase` field. For consistency with PF-S-M-1's fix, this should include `phase: "boot-recovery"`.
