# 6.3 Visual Redesign — Code Review

Reviewer: principal engineer (critical mode)
Verification: 205/205 web tests pass, `tsc --noEmit` clean, `biome lint` clean (3 pre-existing warnings unrelated to this work).

Overall assessment: **REQUEST_CHANGES**

The redesign delivers on the headline goals (indigo palette, Inter font, new background mesh, calmer loading screen, fixed `StaticBackgroundLights` hardcoded green). However, three findings break spec compliance and one introduces a customization regression that contradicts decision 13. None are catastrophic, but they are not "minor polish" either — they were each explicitly called out in the spec.

---

## Critical

### 1. Auth-form inputs still carry `backdrop-blur-md` — spec violation
- [x] Resolve

Spec decision 10 (Inputs): *"no backdrop-blur (was overused)"*. The plan's Task 8 even instructed *"Remove any remaining backdrop-blur references"*. The base `<Input>` component was cleaned up, but the call sites that override it via `className` were not touched:

- `apps/web/src/app/login/components/login-form.tsx:78,101` — `bg-transparent backdrop-blur-md`
- `apps/web/src/app/login/components/register-form.tsx:89,108,127,147,168`
- `apps/web/src/app/forgot-password/components/forgot-password-form.tsx:35`
- `apps/web/src/app/reset-password/components/reset-password-form.tsx:44,73`

These nine `<Input>` instances are exactly the ones the spec was targeting — the auth flow is the user's first impression of the new identity. Result: the input fields inside the new sober-corporate auth cards still render as 2015-style frosted glass.

**Fix:** drop `bg-transparent backdrop-blur-md` from every auth-form `<Input>` className. The base component already defines a sensible focus-ring and dark-mode background; let those take over.

### 2. `Button` default variant bypasses `--primary-foreground` and breaks customization — spec decision 13 violation
- [x] Resolve

`apps/web/src/components/ui/button.tsx:12`:
```ts
default: "bg-primary dark:text-black text-white shadow-sm hover:bg-primary/90 hover:shadow-md",
```

Two problems:

1. **Customization regression.** Decision 13 mandates "user overrides take precedence" — but `ThemeColorProvider` only rewrites `--primary`/`--ring`/etc.; it doesn't touch hardcoded `text-white` / `dark:text-black`. If a user picks a *light* primary color (yellow, light green, sky-blue) the button text stays white in light mode → unreadable. The CSS variable system was designed precisely to pair `--primary` with `--primary-foreground`.
2. **Dark-mode contrast is borderline.** Default `--primary` in dark mode is `oklch(0.65 0.18 265)` (Y≈0.35); `text-black` (#000) gives ~8:1 — fine. But the *theme variable* `--primary-foreground: oklch(0.13 0.01 265)` gives ~6.25:1 — also fine. The current hardcode is *visually* close to the variable, just disconnected from it.

This is preexisting code that the spec scope explicitly covered (decision 10 redesigns buttons; decision 13 mandates preservation of customization). Since `button.tsx` was modified anyway in this PR, this is the moment to fix it.

**Fix:** replace `dark:text-black text-white` with `text-primary-foreground`. Equivalent visual output in defaults, and customization now works end-to-end.

### 3. Public landing-page navbar was not updated — visual inconsistency
- [x] Resolve

The spec calls out *the* navbar (decision 10 / scope: "Navigation: navbar"). Two navbars exist:

- `apps/web/src/components/layout/navbar.tsx` — updated ✓
- `apps/web/src/app/(home)/components/navbar.tsx` — **untouched**, still uses `border-border/50 bg-background/70 backdrop-blur-sm` and `font-bold text-2xl` for the app name.

`(home)/components/navbar.tsx` is what an anonymous visitor sees first on `/`. Leaving it in the old style means the landing page mixes the new sober look (HomeContent below it) with the old frosted-glass look (navbar above it). It would have been a one-line copy of the changes already applied to the main navbar.

**Fix:** apply the same `border-border/60 bg-background shadow-sm` + `font-semibold text-xl tracking-tight` treatment.

## Important

### 4. Primary button missing the gradient + scale spec'd in decision 10
- [x] Resolve — added hover:scale-[1.02]; gradient dropped (doesn't work with oklch relative syntax in arbitrary Tailwind values)

Spec decision 10 (Buttons): *"Primary: gradient fill (indigo-dark to indigo-light), subtle shadow, scale(1.02) on hover"*.

Implementation: solid `bg-primary`, no gradient, **no hover scale**. The home page's one-off CTA adds `hover:scale-105` on top of `<Button>` directly (`home-content.tsx:90`), but it's not part of the component contract — every other primary button in the app stays flat.

If the design team explicitly decided to drop the gradient post-spec, document the change in the spec file. Otherwise this is a partial implementation of decision 10.

**Fix options:**
- Add `bg-gradient-to-b from-primary to-[oklch(from_var(--primary)_calc(l-0.05)_c_h)]` and `hover:scale-[1.02]` to the `default` variant, OR
- Update the spec to record the design pivot.

### 5. `chart-3` is still green in light mode while dark mode uses amber — inconsistent
- [x] Resolve — all chart colors now consistent between light/dark modes

`globals.css:69` light: `--chart-3: oklch(0.55 0.12 150)` (cyan-green)
`globals.css:104` dark: `--chart-3: oklch(0.75 0.15 75)` (warm amber)

These are completely different hues for the same chart slot. Any chart legend coloring will swap between themes, which is jarring and a data-viz UX bug. Light-mode chart-3 also keeps a green that the rest of the redesign carefully removed.

**Fix:** pick one hue for chart-3 and use it in both blocks. If the intent was an amber accent that complements indigo, set both to `oklch(0.65 0.15 75)`-ish. Apply the same audit to chart-4 and chart-5 (light has 75/320, dark has 320/30 — also rotated/inconsistent).

### 6. `transition-all` on every Button — overly broad
- [x] Resolve — scoped to transition-[background-color,box-shadow,transform] (Button) and transition-[box-shadow,transform] (Card)

`button.tsx:8` uses `transition-all duration-150`. With `hover:shadow-md` this animates shadow, but `transition-all` also animates every other property change (color, background, transform, opacity, even border-radius if it ever shifts). On a page with dozens of buttons this is more work than `transition-[background-color,box-shadow,transform]`. The same change was made to `Card` (`card.tsx:7`).

This is a polish concern, not a bug — but the spec explicitly cites *performance* as a reason to drop backdrop-blur from the navbar. Being precise about transitions is the same kind of micro-optimization.

**Fix:** scope to the properties that actually change (`transition-[background-color,box-shadow,transform]` on Button; `transition-[box-shadow,transform]` on Card).

### 7. Input lost its focus-ring transition
- [x] Resolve — changed to transition-[color,box-shadow,border-color]

Diff for `input.tsx`:
```
- transition-[color,box-shadow]
+ transition-colors duration-150
```
The new value only transitions `color`. Focus brings up `ring-2 ring-ring/30` and `border-ring`. Border-color animates (covered by `transition-colors`), but the **ring (which is a box-shadow under the hood) now appears instantly**. Pre-redesign code animated it (`transition-[color,box-shadow]`).

This is the opposite of decision 11's intent ("refined transitions, attention to micro-interactions").

**Fix:** `transition-[color,box-shadow,border-color] duration-150` (or `transition-all`, accepting the trade-off — at least state intent).

## Minor

### 8. Other surfaces still use the old frosted-glass header pattern
- [x] Resolve — share page headers updated to bg-background shadow-sm

Outside the review scope but identical pattern, identical spec section:
- `apps/web/src/app/(shares)/r/[alias]/components/default-layout.tsx:125` — `bg-background/70 backdrop-blur-sm`
- `apps/web/src/app/(shares)/s/[alias]/components/share-header.tsx:14` — same
- `apps/web/src/app/(shares)/r/[alias]/components/we-transfer-layout.tsx:45,48,177` — frosted glass cards

These are the share/reverse-share recipient pages — public surfaces, also a first impression. Same fix as finding #3.

### 9. `AnimatedSendIcon` uses an infinite 4s scale-pulse glow
- [x] Resolve — slowed to 12s, amplitude 1.08, lower opacity

`home-content.tsx:38-42`:
```tsx
<motion.div
  className="absolute inset-0 rounded-full bg-primary/15 blur-2xl -z-10"
  animate={{ scale: [1, 1.3, 1], opacity: [0.4, 0.7, 0.4] }}
  transition={{ duration: 4, repeat: Number.POSITIVE_INFINITY, ease: "easeInOut" }}
/>
```

Spec decision 9: *"No more infinite scale animations (felt cheap). If animated, use very slow color shifts (20s+ cycle)."* That guidance was about the background lights, but the *aesthetic principle* (scale-pulse = cheap) clearly applies to a hero icon glow too. The hero icon is the visual anchor of the landing page — a 4s scale-pulse is exactly the "breathing blob" pattern the spec is rejecting.

**Fix:** drop the scale animation, keep the icon's `y` float (already animating subtly). Or slow the cycle to 12-15s with smaller amplitude (`scale: [1, 1.1, 1]`).

### 10. `quick-access-cards.tsx` translate value is 1px off
- [x] Resolve — changed to hover:-translate-y-px duration-150

Spec decision 11: *"Card hover: translateY(-1px), shadow grow (150ms ease)"*.
Implementation (`quick-access-cards.tsx:37`): `hover:-translate-y-0.5` = 2px, `transition-all duration-200`.

Cosmetic, but the spec was explicit.

**Fix:** `hover:-translate-y-px duration-150`.

### 11. `Card`'s outer wrapper carries hover/transition while click handlers live on the inner element
- [x] Resolve — deferred to backlog (pre-existing issue, Card API contract change)

Pre-existing issue, not introduced here, but worth recording while the file is fresh:

```tsx
<div className={cn("border p-1.5 rounded-xl ... transition-all duration-200", className)}>
  <div data-slot="card" className="..." {...props} />  // ← onClick lands here
</div>
```

In `quick-access-cards.tsx` the consumer passes `onClick` to `Card`. That `onClick` ends up on the **inner** `<div>`. The hover-translate (`hover:-translate-y-0.5`) lives on the **outer** wrapper (because that's where `className` is composed). When a user clicks the 1.5-padding gap between outer and inner, the hover effect fires but nothing happens. The Card is also a `<div>` with no `role="button"` / `tabIndex` / keyboard handler — fails basic a11y for an interactive card.

**Fix:** if `Card` is now a clickable surface (the redesign added `cursor-pointer group` consumer-side, so this is the intent), forward `onClick`/`role`/keyboard handlers to the outer wrapper as well, or expose a `clickable` prop that wires it up properly. Worth a separate ticket since it touches the Card API contract.

### 12. `HomeContent` partner card still uses `backdrop-blur-sm`
- [x] Resolve — removed backdrop-blur, now solid bg-card

`home-content.tsx:109`: `bg-card/80 backdrop-blur-sm`. Spec decision 3 (Gradients): "Keep flat design for: Regular content cards". The partner card is a regular content card. Lower-blur than the auth cards but inconsistent with the flat-card guidance.

**Fix:** `bg-card border border-border/60 p-8 shadow-sm` — drop the transparency and blur. The card sits over the background-mesh — a solid surface reads better.

### 13. Tagline gradient `from-primary to-primary/70` is opacity-based, not a true 2-color gradient
- [x] Resolve — reverted to solid text-primary (simpler, more readable)

`home-content.tsx:73`. `bg-clip-text` + `text-transparent` makes the text inherit the gradient pixel-for-pixel — `primary/70` means 70% alpha *text*, not a 70% blend with another color. On a near-transparent page background, the right edge of "tagline" partially fades. This works but it's a slight readability hit on the most prominent piece of marketing copy on the site.

**Fix:** `bg-gradient-to-r from-primary to-[oklch(from_var(--primary)_calc(l+0.12)_c_h)]` — two solid colors at the same alpha, smooth lightness ramp, no readability hit.

### 14. Two navbars exist; redesign should consolidate
- [x] Resolve — deferred to backlog (out of 6.3 scope, both are now visually consistent)

`apps/web/src/components/layout/navbar.tsx` and `apps/web/src/app/(home)/components/navbar.tsx` are 80% the same component with divergent styling (and now divergent design eras after this PR). Out of scope for 6.3, but flagging for 6.x backlog: the `(home)` variant should either compose the shared one or be deleted.

### 15. Inter font has `display: "swap"` but no `preload: false` — keep behavior intentional
- [x] Resolve — informational, no fix needed (intentional change)

`layout.tsx:29-33`: Inter is loaded with default preload (no `preload: false`). Outfit and the 8 secondary fonts are `preload: false`. Inter is now the primary font so this is correct, but it's worth documenting (the Outfit `preload: false` was correct *before* the swap, and now Inter implicitly gets `preload: true` because the option was omitted).

No fix needed — informational.

## What works well

- `globals.css` color tokens match the spec values almost exactly. The blue undertone is present at every neutral.
- `StaticBackgroundLights` (decision 13) properly fixed: hardcoded `rgba(34,197,94,...)` replaced with `oklch(from var(--primary) ...)`. This was a real bug.
- `BackgroundLights` redesign matches decision 9 — 3 blobs, 20–25s drift, translate (not scale), accent gold layer.
- Loading screen is genuinely calmer (2s opacity pulse + 1.5s width sweep) and looks intentional rather than wobbly.
- Dialog overlay tightening (`bg-black/60 backdrop-blur-[2px]`) and slide-in-from-bottom-4 are sensible.
- `ThemeColorProvider` was correctly left untouched and still cascades into `BackgroundLights` etc. via `oklch(from var(--primary) ...)`. Customization for color/radius/background still works end-to-end (modulo the `Button` foreground issue in finding #2).
- Empty/error state entrance animations (opacity + small y/scale) are appropriately subtle.
- Test suite (205/205) still passes — the `data-slot="card"` contract is preserved, ErrorDisplay variants still detectable.
- Typecheck and biome clean.

---

## Summary

The redesign nails its identity goals but stops at the dashboard/auth-card *frame* and leaves the *contents* (inputs, secondary navbar, share/reverse-share headers, button foreground theming) in the old design language. The contrast between the new sober card and the old frosted-glass input inside it is the most visible regression to fix. Findings #1–#3 are blockers; #4–#7 should land before merge; the rest are polish.

After fixing #1–#7, this is ready to ship.
