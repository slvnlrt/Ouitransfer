## Summary

The unsubscribe flow that broke in pass 2 has been fixed correctly: `@fastify/formbody` is registered in `app.ts:174`, the POST handler accepts the token from body OR query, the form uses an implicit action (so it posts to the current URL — `{appUrl}/api/notifications/unsubscribe?token=...`), and the test suite covers form-urlencoded body, RFC 8058 one-click, and the JSON path. The end-to-end unsubscribe story works.

Recipient email normalization is now consistent (Zod transform on the route schemas plus repository-level `trim().toLowerCase()`), the cross-share token check is correctly applied to both the gate and the visit-tracking path, owner-only fields are stripped from anonymous responses, `notifyRecipients` builds links server-side via `getAppUrl()` + `URL.searchParams.set("t", …)`, the tracking-token backfill uses a race-safe conditional `updateMany`, and the cookie path correctly rejects content-empty cookies. Most of the pass-2 findings have landed cleanly.

However, **two critical regressions remain.** First, `requestPasswordReset` (`auth/service.ts:163`) still accepts a client-supplied `origin` and uses it as the base for the reset URL (`auth/service.ts:198`) — the EXACT phishing vector the spec warned against in Section 4 ("No `Origin` header fallback — the admin must configure it explicitly"). Any unauthenticated caller can request a password reset for someone else's email with `origin=https://attacker.example`; the legitimate user receives an SMTP-trusted email containing an attacker-controlled link to a real, valid reset token. Second, `notifyRecipients` falls back to `${appUrl}/s/${share.id}` when the share has no alias (`service.ts:683`), but the frontend only has `/s/[alias]/page.tsx` — there is no `/s/{shareId}` route. Invitations for shares without an alias contain dead links. Both issues need to be fixed before this ships.

A few important issues remain too: the share update path skips the schema parse on its return value, the `notifyRecipients` audit log persists recipient emails as plaintext for 365 days (carried over from pass 2 as M-12 and still unaddressed), and `trackShareDownload` calls `request.jwtVerify()` after the route handler may have already done so. Minor inconsistencies and one missing rate-limit clarification round out the list.

## Findings

### Critical

#### ~~C-1~~ [x]: `requestPasswordReset` accepts client-controlled `origin` → password-reset phishing
- **File**: `apps/server/src/modules/auth/service.ts:163, 198` + `apps/server/src/modules/auth/dto.ts:19-22` + `apps/server/src/modules/auth/routes.ts:305-307`
- **Description**: The DTO schema accepts `origin: z.string().url()` from the unauthenticated body of `POST /auth/request-password-reset`. The service embeds that string directly into the reset email:
  ```ts
  resetUrl: `${origin}/auth/reset-password/${token}`,
  ```
  The token is a real, valid 64-byte reset token stored in `PasswordReset`. An attacker can call the endpoint for a victim's email with `origin=https://attacker.example/phish`; the victim receives an email "from" the trusted SMTP identity, addressed to them, containing what looks like a legitimate reset link. They click, the attacker captures the token, the attacker calls the real `POST /auth/reset-password` with that token and resets the victim's password.

  The 8.2 spec explicitly forbids this in Section 4 (config table for `appUrl`):
  > "Hard required because the queue scheduler runs detached from HTTP requests. No `Origin` header fallback — the admin must configure it explicitly."

  The `email/url-builder.ts:58-61` already exposes `buildResetPasswordUrl(token)` for exactly this purpose. It is not called.

  This is the same class of bug as I-2 in the pass-2 re-review (`notifyRecipients` accepting `shareLink`), but more severe because (a) the email goes to a verified user inbox without any prior consent, (b) the reset token is genuinely valid, and (c) the user has explicit motivation to click (they may believe they requested the reset on a sibling device).
- **Impact**: Account takeover via spoofed reset emails. Trivial to exploit — only needs the victim's email address. The endpoint is rate-limited at 3/minute but that does not mitigate the attack; one email is enough.
- **Suggested fix**:
  1. Remove `origin` from `RequestPasswordResetSchema` and from the `requestPasswordReset` signature.
  2. In `auth/service.ts`, build the URL via `buildResetPasswordUrl(token)` (already imported across the email module).
  3. Update the route handler `auth/routes.ts:305-307` accordingly.
  4. Add an integration test asserting that the rendered URL begins with the configured `appUrl`, independent of any request header.

#### ~~C-2~~ [x]: `notifyRecipients` sends dead links for shares without an alias
- **File**: `apps/server/src/modules/share/service.ts:680-683`
- **Description**:
  ```ts
  const shareAlias = share.alias?.alias;
  const baseShareLink = shareAlias ? `${appUrl}/s/${shareAlias}` : `${appUrl}/s/${share.id}`;
  ```
  Alias creation is a separate step (`POST /shares/:shareId/alias`). A user can create a share, add recipients, and call `POST /shares/:shareId/notify` before creating an alias. The fallback URL `${appUrl}/s/{shareId}` is broken — the frontend only registers `apps/web/src/app/(shares)/s/[alias]/page.tsx`. There is no `/s/{shareId}` route. Visitors clicking the invitation hit the public Next.js 404 page (or the route tries to look up `shareId` as an alias, which fails because the alias DB has no row matching that string, and the user gets `Share not found`).

  This is silent: the email is queued (200 OK), recipients receive a real-looking email, and clicking takes them to an error page. The owner is unaware until a recipient complains.
- **Impact**: Broken invitations for any share that hasn't been aliased. Combined with the migration test `migration.test.ts:217-235` which only mocks shares WITH aliases, this code path is never exercised in tests.
- **Suggested fix**:
  1. Reject the notify request with `ValidationError("Share must have an alias before notification")` when `share.alias` is null. This forces the UX to create the alias first.
  2. OR: auto-create an alias when notifying (random adjective-noun like the existing UX). The migration test should then cover both branches.
  3. Add an integration test that exercises `notifyRecipients` on an aliasless share and asserts a 400 response.

  Option 1 is the safer fix — silent fallback to a broken link is worse than a clear error.

### Important

#### ~~I-1~~ [x]: `updateShare` returns un-parsed response object — inconsistent with all other service methods
- **File**: `apps/server/src/modules/share/service.ts:430`
- **Description**: Every other ShareService method that returns a share runs `ShareResponseSchema.parse(await this.formatShareResponse(...))` (see lines 183, 204, 364, 465, 488, 526, 553, 576, 591). `updateShare` does not:
  ```ts
  return await this.formatShareResponse(shareWithRelations);
  ```
  Fastify's route response schema (`apps/server/src/modules/share/routes.ts:241-246`) will still validate the outgoing payload at serialization, so this isn't a runtime bug. But:
  - The parse acts as a service-layer contract — callers that bypass the route (other services, tests, future internal callers) get an un-validated object.
  - Subtle shape differences (e.g. a date that's still a Date object instead of an ISO string) would surface as Fastify 500s rather than service-layer errors that the caller can handle.
  - The inconsistency hides intent — a reader has to check every method to know whether the schema is parsed or not.
- **Impact**: Maintenance hazard. Future refactors might rely on the schema parse running at the service layer and silently break only in this method.
- **Suggested fix**:
  ```ts
  return ShareResponseSchema.parse(await this.formatShareResponse(shareWithRelations));
  ```
  One-line fix. Matches the rest of the service.

#### ~~I-2~~ [x]: `trackShareDownload` calls `request.jwtVerify()` a second time after the route handler
- **File**: `apps/server/src/modules/file/routes.ts:161-167` (helper) + `apps/server/src/modules/file/routes.ts:961, 984, 1063, 1081` (callers)
- **Description**: Both `POST /files/download-url` and `POST /files/download` call `checkFileAccess(...)` which internally runs `request.jwtVerify()` (`routes.ts:121-130`) to fall back to ownership-based access. Then they call `trackShareDownload(...)` which runs `request.jwtVerify()` AGAIN (`routes.ts:162`). `request.user` is already populated from the first call; the second call is wasted CPU verifying the same JWT.

  More concerning: `trackShareDownload` runs fire-and-forget (`.catch(...)`). If the response is already flushed when this helper executes, calling `request.jwtVerify()` against a request whose context is winding down is at best wasteful and at worst could surface unexpected errors in newer Fastify versions.
- **Impact**: Minor performance cost (verifies HS256 twice per download request). Latent risk for unexpected behavior in fire-and-forget context with newer Fastify-JWT versions.
- **Suggested fix**: Compute `requestUserId` once at the route handler before calling `trackShareDownload`, and pass it in as an argument. The helper becomes pure of `request.jwtVerify` side effects. Bonus: the helper signature gets clearer ("did this user authenticate?" is now an explicit parameter, not a hidden re-verification).

#### I-3: `notifyRecipients` audit-log entry stores recipient emails verbatim for 365 days
- **File**: `apps/server/src/modules/share/routes.ts:732-743` (plus `routes.ts:498` and `routes.ts:545` for SHARE_RECIPIENT_ADD / REMOVE)
- **Description**: The audit log retention defaults to 365 days. Three audit events (`SHARE_RECIPIENT_ADD`, `SHARE_RECIPIENT_REMOVE`, `SHARE_RECIPIENT_NOTIFY`) include the full recipient email list in the `metadata` JSON. This was flagged as M-12 in the pass-2 re-review and was not addressed; promoting to Important because:
  - GDPR-like regimes treat email as PII. A "send invitation" audit event keeping plaintext emails for a year by default is a defensible business decision, but it must be a conscious one — currently it appears as a leftover from the route plumbing, not a documented choice.
  - There is no code comment justifying the choice. The retention bridge (audit retention scheduler) doesn't redact this content.
- **Impact**: Long-lived PII store with no rotation. Operators deploying Ouitransfer in privacy-sensitive contexts inherit this without warning.
- **Suggested fix**: Either:
  - Hash emails before storing in audit metadata (`crypto.createHash("sha256").update(email).digest("hex").slice(0,12)`), preserving forensic uniqueness without storing the address; OR
  - Document the choice with a code comment explaining the trade-off and add a config knob `auditPiiRedaction` defaulting to false but available for privacy-aware operators.

  The two-line comment already added at `routes.ts:730-731` ("PII retention follows auditRetentionDays") is acknowledgment but not mitigation. Decide explicitly.

#### I-4: Share visit endpoint's `recipient` shape includes email but no field-level documentation of when it's null
- **File**: `apps/server/src/modules/share/routes.ts:889-894`
- **Description**: The response schema for `GET /shares/:shareId/visits`:
  ```ts
  recipient: z.object({
    email: z.string(),
    name: z.string().nullable(),
  }).nullable(),
  ```
  `recipient` is nullable but is loaded via `prisma.shareVisit.findMany({ include: { recipient: { select: { email: true, name: true } } } })`. If the recipient was deleted after the visit was recorded (`onDelete: SetNull` on `ShareVisit.recipientId`), the Prisma include returns `null`. Good.

  But there's a subtler case: if `visit.recipientId` is null (anonymous visit), Prisma's `include` will return `recipient: null` as well — same shape. The frontend can't distinguish "anonymous visit" from "identified visit where recipient was deleted." Both look the same.

  Additionally, when there IS a recipient, the schema returns `email` without restriction — even for visits where the visitor identified anonymously (cookie path), the recipient's email is exposed. This is the share creator viewing their own data so the privacy concern is internal, but it does mean stale recipient emails persist in visit logs after recipient removal (the recipient row's deletion sets `ShareVisit.recipientId = null`, but `visitorEmail` on the ShareVisit might still hold the original email).
- **Impact**: Owner sees ambiguous data: "no recipient" can mean three things (anonymous, deleted recipient, cookie-based with no recipient association). Hard to debug after the fact.
- **Suggested fix**: Add a derived field at the route level — e.g. `identificationSource: "tracking_token" | "cookie" | "anonymous"` computed from `(recipientId != null) ? "tracking_token" : (visitorEmail || visitorName) ? "cookie" : "anonymous"`. Adds clarity for the frontend without changing the data model.

### Minor

#### M-1: `repository.addRecipients` does not generate tracking tokens at creation time
- **File**: `apps/server/src/modules/share/repository.ts:343-355`
- **Description**: The repository's `addRecipients` writes recipients with no `trackingToken`. Token generation is deferred to `notifyRecipients` via the conditional `updateMany` backfill. This works correctly (race-safe), but it deviates from spec Section 5A: "Each `ShareRecipient` receives a unique `trackingToken` at **creation time** (not at notify time)".

  In contrast, `createShare` (the Prisma repository at `repository.ts:113-114`) does NOT generate tokens either. The ONLY paths that generate tokens at creation are:
  - `updateShare`'s upsert branch (`service.ts:405`)
  - `notifyRecipients`'s backfill (`service.ts:711-714`)

  The spec rationale was: "Generating at creation ensures tokens survive share updates (the current updateShare flow deletes and recreates recipient rows — this must be changed to upsert by `[shareId, email]` to preserve tokens and access stats)."

  The upsert change WAS made, so the spec's concern is addressed. But the spec rule "tokens at creation" is violated for the createShare and addRecipients paths. Currently, a recipient added via `POST /shares/:shareId/recipients` will have `trackingToken: null` until the first notify call. If the owner shares the public alias link (no `?t=...`) with that recipient out-of-band before sending the formal notification, no tracking happens.
- **Impact**: Specification violation, mild UX inconsistency. Not a correctness bug — the backfill handles the lazy case.
- **Suggested fix**: Generate the token at creation in `createShare` and `addRecipients` (one `crypto.randomBytes(24).toString("base64url")` per recipient). Removes the backfill complexity from `notifyRecipients`. Then the per-recipient `updateMany` block can be deleted entirely — the spec's no-legacy/no-production stance means there are zero pre-existing rows to backfill.
