# Review — 5.2 Lifecycle Management & Automatic Cleanup, Phase A

**Reviewer pass over commit range `31139c7^..HEAD`** (spec/plan + server + web + docs + tracking).
Reviewed against the binding contract in `features/specs/5.2-cleanup.md` (axes A1–A10, Config
Keys, Data-model clarification, Notification/Audit sections), the 8-batch plan, and CLAUDE.md's
zero-tech-debt bar + Rules 9/10/11.

## Overall verdict

The implementation is high quality and largely spec-compliant: the data-model clarification is
honored (regular-share cleanup deletes link-only, reverse-share cleanup frees storage), opt-in
gating is correct, audit events are emitted on every automated deletion path, the scheduler
mirrors the established pattern with proper re-entrancy/teardown/live-config re-read, config
validation and i18n parity (23 locales) are clean, and unit coverage is thorough.

**However there is one Critical data-loss defect** (the orphan sweep does not protect
`BackgroundImage` and `Folder` S3 keys and will delete them when enabled), and **one Important
security gap** (the A6 deactivated-owner block is not enforced on the reverse-share *upload*
paths, only on the metadata-fetch GETs) **with no reverse-share A6 test coverage at all**. These
two must be fixed before Phase A is Done. The remaining findings are Important/Minor polish.

Counts: **1 Critical, 4 Important, 6 Minor.**

## Critical

- [x] **[Critical] Orphan sweep deletes BackgroundImage and Folder S3 objects as "orphans" (data loss)**
  - Resolution: `sweepOrphans` now builds `knownKeys` from the full S3-key registry — `File.objectName`, `ReverseShareFile.objectName`, `Folder.objectName`, `BackgroundImage.s3Key`, `BackgroundImage.thumbnailS3Key` (`cleanup/service.ts` S3→DB phase). A doc-comment registry lists every source table. Schema grep confirmed no other S3-key columns exist (`AppConfig.key` is unrelated). Added regression test asserting background image + thumbnail + folder objects are never swept while a truly-orphan object still is. — `apps/server/src/modules/cleanup/service.ts:713-737` — The S3→DB phase builds `knownKeys` from **only** `File.objectName` and `ReverseShareFile.objectName`. But three other places store keys in the *same bucket*: `BackgroundImage.s3Key` and `BackgroundImage.thumbnailS3Key` (written under `backgrounds/{id}.webp` / `backgrounds/{id}_thumb.webp` — see `modules/background-image/service.ts:75-92`) and `Folder.objectName` (`prisma/schema.prisma:432`, written/deleted by `modules/folder/service.ts`). `listObjects()` enumerates the whole bucket with no prefix, so when an admin enables `autoCleanupOrphansEnabled`, every background image + thumbnail (and folder objects) will be `lastModified < cutoff`, absent from `knownKeys`, and **permanently deleted from S3**. This destroys all admin-uploaded background images. (Note: this *also* contradicts the TD-17 "resolved" claim, which cites background-image orphan safety.) **Fix**: include all S3-key-bearing tables in the known-keys union — add `prisma.backgroundImage.findMany({ select: { s3Key: true, thumbnailS3Key: true } })` and `prisma.folder.findMany({ select: { objectName: true } })`, adding every `s3Key`, `thumbnailS3Key`, and folder `objectName` to `knownKeys`. Add a regression unit test asserting a `backgrounds/*` object referenced by a `BackgroundImage` row (and a folder object) is never swept. Consider a comment/registry so future S3-owning tables aren't forgotten.

## Important

- [x] **[Important] A6 deactivated-owner block is missing on the reverse-share upload paths**
  - Resolution: factored a shared `assertOwnerActive(reverseShare)` helper (`reverse-share/assert-owner-active.ts`) that throws `AppError(403, …, OWNER_INACTIVE)`. Applied at every external entry point: `getReverseShareForUpload`/`…ByAlias` (refactored to use the helper — one source of truth), `upload.service.ts` `getPresignedUrl`/`getPresignedUrlByAlias`/`registerFileUpload`/`registerFileUploadByAlias`, and `multipart.service.ts` `validateReverseShareAccessByAlias`. `findById`/`findByAlias` already select `creator.isActive` (Batch 4) — no select changes needed. — `apps/server/src/modules/reverse-share/upload.service.ts:43,92,147,234` and `apps/server/src/modules/reverse-share/multipart.service.ts:14` (and the by-id variants) — The A6 `creator.isActive === false → 403 OWNER_INACTIVE` gate was added only to `service.ts` `getReverseShareForUpload` / `getReverseShareForUploadByAlias` (the GET metadata fetch). The actual upload endpoints — `getPresignedUrl`, `getPresignedUrlByAlias`, `registerFileUpload`, `registerFileUploadByAlias`, and the multipart `validateReverseShareAccessByAlias` path — re-load the reverse share and check `isActive`/`expiration`/password but **not** `creator.isActive`. An external party who already has the reverse-share id/alias (the upload page URL is semi-public/bookmarkable) can therefore still presign + register + multipart-upload files into a deactivated owner's reverse share, bypassing A6. Spec A6 says deactivation must "immediately block the user's shares (block access)" — for reverse shares that must include the upload action. **Fix**: add the same `if (reverseShare.creator?.isActive === false) throw AppError(403, …, OWNER_INACTIVE)` guard to all upload/presign/register/multipart entry points (`findById`/`findByAlias` already select `isActive` per the repository diff). Factor a shared guard helper to avoid drift.

- [x] **[Important] No test coverage for the reverse-share A6 block (security flow)**
  - Resolution: added `reverse-share/__tests__/owner-active.integration.test.ts` with `app.inject()` coverage — GET `/reverse-shares/:id/upload` (metadata gate): active → 200, deactivated → 403 `OWNER_INACTIVE`; POST `/reverse-shares/:id/presigned-url` (upload gate): active → 200, deactivated → 403; POST `/reverse-shares/:id/register-file` (upload gate): deactivated → 403 and asserts no file row is created. 5 tests, all green. — `apps/server/src/modules/reverse-share/` has **no `__tests__` directory** — Rule 11 and the plan (Batch 4 step 1, "Add integration tests (active vs deactivated owner)") require `app.inject()` integration coverage of the deactivated-owner block for *both* regular and reverse shares. The regular-share block is covered (`share/__tests__/visitor-tracking.test.ts` now asserts 403/`OWNER_INACTIVE`), but the reverse-share block has zero tests — neither the GET gate nor (once fixed) the upload gate. **Fix**: add `app.inject()` integration tests for the reverse-share upload-access and upload endpoints with an active vs deactivated owner. This is the coverage that would have caught the gap above.

- [x] **[Important] `purgeUserContent` never deletes Folder S3 objects**
  - Resolution: `purgeUserContent` now snapshots the user's `Folder.objectName`s before deletion and best-effort deletes them alongside the File objects (DB-before-S3, failures counted into `s3Errors`). Added a unit test asserting folder S3 objects are deleted (and null object names skipped), and extended the A8 cascade integration test to assert a folder placeholder object is deleted. — `apps/server/src/modules/cleanup/service.ts:504-508` — The purge deletes `Folder` rows via `deleteMany` but only collects/deletes `File.objectName` S3 objects (step 1/5). `Folder.objectName` is a real S3 key (`schema.prisma:432`; written/deleted in `modules/folder/service.ts`). So both A7 (deactivated-account cleanup) and A8 (user-deletion cascade) leave every folder object dangling in S3 — exactly the orphaning A8 was meant to fix. Today the orphan sweep can't even reclaim them (it doesn't know folder keys — see the Critical). **Fix**: snapshot the user's `Folder.objectName`s before deletion and best-effort delete them alongside the File objects (same DB-before-S3 pattern), counting failures into `s3Errors`.

- [x] **[Important] No "pending deletion" warning before maxViews cleanup (A4/A5)**
  - Resolution: `cleanupMaxViewsShares` now has a warn phase mirroring `cleanupExpiredShares` — for maxViews-reached shares whose deletion moment (`(lastDownloadedAt ?? updatedAt) + inactiveDays`) is within `notifyDaysBefore`, it sends `share_pending_deletion` and sets `notifiedForPendingDeletion` only when enqueued. Signature changed to `{ inactiveDays, notifyDaysBefore }`; the scheduler now passes `autoCleanupNotifyDaysBefore`. Added warn-phase + notify-0 skip tests; updated all existing maxViews tests and the scheduler test for the new signature. Spec A5 "warn before A2–A4" is now satisfied. — `apps/server/src/modules/cleanup/service.ts:259-316` — Spec A5 is "warning email **before A2–A4**", and the Config Keys table's `autoCleanupNotifyDaysBefore` is the single warning lead time. `cleanupExpiredShares` and `cleanupExpiredReverseShares` both warn, but `cleanupMaxViewsShares` deletes with no warning phase at all, so a maxViews-reached share is removed with no advance notice to the owner. The plan called this "optional" but the spec (A5 covers A2–**A4**) treats it as in-scope. **Fix**: add a warn phase to `cleanupMaxViewsShares` reusing `share_pending_deletion` and the `notifiedForPendingDeletion` flag (mirroring the expired path), gated on `inactiveDays`/`notifyDaysBefore`; or, if it is genuinely intended to be out of scope, record that decision explicitly in the spec so A5's "before A2–A4" wording is corrected. Don't leave the contract and code disagreeing.
