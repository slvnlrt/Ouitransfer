# 5.2 Phase B — Quota overage policy

Spec: [`features/specs/5.2-cleanup.md`](../specs/5.2-cleanup.md) "Phase B" section is binding
(B1 threshold warnings, B2 opt-in smart deletion, B3 reverse-share soft enforcement; config-key
table; schema; audit). Same quality bar as Phase A/A.1 (zero tech debt, full suites, `app.inject()`
integration tests for enforcement/security flows). Subagents dispatched **sequentially**. Reuses the
existing `quota_warning`/`quota_exceeded`/`admin_quota_alert`/`files_auto_deleted` notifications, the
Phase A cleanup scheduler, and 8.1 audit.

## Batch 1 — Schema + config + quota-service core helpers + migration

- `User`: add `quotaLastWarnedThreshold Int?`, `quotaExceededSince DateTime?`.
- Seed + validate the 7 Phase B config keys (spec table) in a sensible group (reuse an existing
  `quota` group if one exists, else add it; be consistent with how limits are grouped). Booleans
  via the existing `booleanString` helper; ints via `intMin`; `quotaWarningThresholds` validated as
  a CSV of 1–99 integers; `reverseShareMaxOverageFactor` integer ≥ 1; `reverseShareAbsoluteMaxBytes` ≥ 0.
- `QuotaService` pure helpers (no triggers yet): `parseThresholds(csv)`, `crossedThreshold(oldUsed,
  newUsed, limit, thresholds)` → the highest newly-crossed threshold (or null), `isReverseUploadAllowed(used,
  size, limit, factor, capBytes)` (soft-enforcement formula; unlimited limit ⇒ always allowed),
  and `pickDeletionCandidates(userId, bytesToFree, inactiveShareDays)` (returns ordered File ids:
  orphan uploads oldest-first, then inactive-share files oldest-first; never active-share content).
- Migration `quota_overage`. Regenerate client. Unit tests for every helper + the validators.

## Batch 2 — B1 threshold warnings + B3 reverse-share soft enforcement (event-driven)

- **B1**: at direct-file-register (`file/routes.ts` / service) AND reverse-share file register
  (`reverse-share/upload.service.ts`), after usage updates, use `crossedThreshold` + dedup via
  `User.quotaLastWarnedThreshold`; enqueue `quota_warning` (configured threshold) / `quota_exceeded`
  (≥100%); set/clear `quotaExceededSince` when crossing/leaving 100%; re-arm `quotaLastWarnedThreshold`
  when usage drops below the lowest threshold. Finalize the `quota_warning`/`quota_exceeded` template
  notes (remove the "Phase B pending-trigger" comments).
- **B3**: replace the reverse-share upload hard check (`used + size <= limit`) with
  `isReverseUploadAllowed(...)` when `reverseShareQuotaSoftEnforcement` is true (else keep hard block);
  on landing in the overage zone, alert the owner (`admin_quota_alert`/`quota_exceeded`). Keep DIRECT
  uploads (owner's own) on the hard limit. Keep the A6 `assertOwnerActive` guard intact.
- `app.inject()` integration tests: warning crossing + dedup (no re-spam), exceeded set/clear, reverse
  soft-allow under factor, reverse hard-block at factor/cap, reverse hard-block when soft disabled,
  direct upload still hard-blocked. Unit tests for the trigger logic.

## Batch 3 — B2 smart deletion sweep (opt-in)

- `cleanup/service.ts`: `enforceQuotaOverage({ graceDays, inactiveShareDays }): Promise<{ usersProcessed; filesDeleted; bytesFreed; blocked; errors }>` — for users with `quotaExceededSince < now-grace`, compute `bytesToFree = used - limit`, get ordered candidates via `pickDeletionCandidates`, delete (DB + S3, DB-before-S3, failure-tolerant) until under limit or no safe candidate; if none, count as `blocked` (no deletion). Audit `QUOTA_FILES_DELETED` (add the action) + `files_auto_deleted` notice (deleted names or the account-style variant). Clear `quotaExceededSince` if back under.
- A share left empty by a deletion is NOT removed (§7).
- `cleanup.scheduler.ts`: call `enforceQuotaOverage` only when `quotaSmartDeletionEnabled` (new sub-gate, like A7/A9), using `quotaGracePeriodDays` + `quotaInactiveShareDays`. Add to the aggregated run summary.
- Tests: candidate ordering (orphans before inactive-share, oldest-first), never deletes active-share files, stops at limit, "all active ⇒ blocked, nothing deleted", grace boundary, S3 failure tolerance, scheduler gate.
