# 8.3 — Download Tracking — Implementation Plan

Spec: [`features/specs/8.3-download-tracking.md`](../specs/8.3-download-tracking.md) is binding
(état des lieux + 8 décisions). Most of the original scope was delivered by 8.2; this plan covers
the **5 remaining lots A/B/C/D/F** (lot E — per-recipient password — is out of scope). Same quality
bar as prior features (zero tech debt, full suites, `app.inject()` integration tests for every
tracking/security decision). Subagents dispatched **sequentially**.

## Key facts established by the audit (don't re-discover)

- **Schema decision:** extend `ShareVisit` — no `DownloadEvent` model. Per-recipient download status
  is **denormalized** onto `ShareRecipient` (mirrors the existing `accessCount`/`lastAccessedAt`
  pattern), not derived by querying visits on every list.
- **Audit actions already exist** in `audit/service.ts`: `FILE_DOWNLOAD` (51),
  `REVERSE_SHARE_FILE_DOWNLOAD` (73) — lot F only needs to **emit** them on the public download path
  (verify they aren't already emitted there to avoid double-logging).
- **Convergence point:** lots A (server side), C, F all land in `trackShareDownload`
  (`file/routes.ts:159-268`), which today resolves **no** recipient — it only reads the visitor cookie
  for `visitorName`/`visitorEmail` and creates a `ShareVisit` with `recipientId` unset.
- **Recipient resolution today** lives inline in the access flow (`share/service.ts:319-411`):
  token → `ShareRecipient.trackingToken`; cookie fallback sets `visitorName/Email` but **does not**
  link `recipientId` (that NULL gap is exactly lot C).
- **Retention:** none added — `ShareVisit`/`ShareRecipient` already cascade-delete with the share.
- **Visibility:** owner already sees own-share tracking; no authz change needed.

## Batch 1 — Schema + shared recipient resolution + download-path wiring (A-server / C / F)

The structural core. One coherent change because A/C/F all hinge on resolving the recipient at
download time and recording it consistently.

- **Schema** (`prisma/schema.prisma`):
  - `ShareRecipient`: add `downloadCount Int @default(0)`, `lastDownloadedAt DateTime?`
    (denormalized download status — distinct from `accessCount`, which counts page accesses).
  - `ReverseShareRecipient`: add `uploadCount Int @default(0)`, `uploadedAt DateTime?`
    (lot D schema — added here so there's a single migration).
  - Migration `download_tracking`. Regenerate client.
- **Shared resolver** — extract the recipient-resolution logic (token + cookie-email match) into a
  reusable helper (e.g. `share/recipient-resolution.ts`) so both the access flow and the download
  path use ONE implementation: given `{ shareId, trackingToken?, cookie? }` → `ShareRecipient | null`.
  - Token branch: `findUnique({ trackingToken })` guarded by `shareId` match (current logic).
  - **Cookie-email branch (lot C):** if no token recipient and the cookie carries an email,
    `findUnique({ shareId_email: { shareId, email } })` → link it. Normalize email (lowercase/trim,
    same as `addRecipients`).
- **Access flow (`share/service.ts:391-411`):** use the resolver; when a recipient is matched via the
  cookie-email branch, set `recipientId` AND bump `accessCount`/`lastAccessedAt` (closes the lot-C NULL
  gap for cookie-identified visitors, not just token arrivals).
- **Download flow (`file/routes.ts trackShareDownload`):**
  - Resolve the recipient via the shared helper (cookie-email match for downloads; tracking token too
    if the download request carries `?t=`). Set `recipientId` on the `download` `ShareVisit`.
  - Bump `ShareRecipient.downloadCount` (+1) and `lastDownloadedAt` when a recipient is matched.
  - **Lot F:** emit `logAuditEvent({ action: "FILE_DOWNLOAD", targetType: "file", targetId })`
    (non-owner downloads only; fire-and-forget like the existing audit calls). Verify owner downloads
    aren't already emitting it elsewhere — no double-log.
  - Keep existing behavior intact: `share.lastDownloadedAt`, `inactivityAlertSent` reset,
    `share_downloaded` notification.
- **Tests** (`app.inject()` integration — this is the security/tracking surface):
  - Download by a cookie-identified recipient → `ShareVisit.recipientId` set, `downloadCount`
    incremented, `lastDownloadedAt` set, `FILE_DOWNLOAD` audit row created.
  - Download by an anonymous visitor → `recipientId` NULL, no recipient counter change, audit still
    logged (anonymous target).
  - Access (no download) by cookie-identified recipient → `recipientId` linked, `accessCount` bumped,
    `downloadCount` untouched.
  - Owner download → no visit, no counter, no notification (unchanged).
  - Unit tests for the resolver (token hit, token wrong-share rejected, cookie-email hit, no-match).

## Batch 2 — Recipient download-status badge (A-UI)

- Expose `downloadCount` + `lastDownloadedAt` on the share-recipient DTO
  (`share/dto.ts`) and the web endpoint types (`apps/web/src/http/endpoints/shares/types.ts`).
- `recipient-selector.tsx` (status block at lines 376-394): add an explicit status badge —
  **Téléchargé** (green, `downloadCount > 0`, with `lastDownloadedAt` tooltip) vs **En attente**
  (muted, notified but `downloadCount === 0`). Keep the existing `accessCount` "views" line as a
  secondary signal (access ≠ download). Don't conflate the two.
- i18n: `recipientSelector.downloaded` / `recipientSelector.pending` across all 23 locales
  (en/fr authored, EN replicas for the rest per the TD-36 reality — flag for later translation).
- Web tests for the badge logic + locale-parity test green.

## Batch 3 — Manual reminder for non-downloaders (B)

- **Server:** add a reminder path filtered to `downloadCount === 0` recipients. Prefer a dedicated
  route `POST /shares/{id}/remind` over overloading `/notify`, so semantics + audit are clean.
  Reuse `notifyRecipients` plumbing (personalized `?t=token` links) but a distinct notification type.
  - New email type `share_download_reminder` in `email/catalog.ts` + template
    (`templates/share-download-reminder.ts`) with reminder copy (subject/preheader differ from the
    first invitation). Wire notification preference + i18n catalog entry.
  - New audit action `SHARE_RECIPIENT_REMIND` in `audit/service.ts` (+ label key); emit on send.
  - Update `notifiedAt` on reminded recipients. No scheduler (decision: manual only).
- **Web:** "Relancer les non-téléchargeurs" button in `recipient-selector.tsx` (SMTP-gated like the
  existing notify controls); disabled when zero pending. Show the pending count.
- **Tests:** `app.inject()` — remind targets ONLY `downloadCount===0`, skips downloaders, enqueues the
  reminder type, writes the audit row, updates `notifiedAt`; SMTP-off → gated. Unit test the filter.

## Batch 4 — Reverse-share per-recipient upload tracking (D)

- **Server:** in the reverse-share upload finalize path (`reverse-share/upload.service.ts`, the
  per-file register around 590-608), match `uploaderEmail` against
  `ReverseShareRecipient({ reverseShareId, email })` (normalized) → set `uploadedAt` on first match
  and increment `uploadCount`. Fire-and-forget, failure-tolerant (don't block the upload). Keep the
  existing `reverse_share_uploaded` owner notification + debounce untouched.
- Expose `uploadCount`/`uploadedAt` on the reverse-share recipient DTO + web types.
- `reverse-share-recipient-selector.tsx`: status badge **A uploadé** vs **En attente** (mirror of
  Batch 2). i18n keys (23 locales).
- **Tests:** `app.inject()` — upload by a known recipient links + bumps `uploadCount`/`uploadedAt`;
  upload by an unknown/anonymous uploader leaves recipients untouched; second upload increments.
  Web test for the badge.

## Batch 5 — GDPR notice + docs + tracking + review

- **GDPR (lot F policy):** add a short i18n notice under the visitor identification form
  (`s/[alias]/components/identification-form.tsx`) — "vos accès/téléchargements peuvent être visibles
  par l'expéditeur". New i18n key across 23 locales.
- **Docs (EN + FR):** extend the shares + reverse-shares Fumadocs pages — download tracking, the
  Downloaded/Pending status, manual reminders, reverse-share upload tracking, the GDPR note.
- **Tracking:** `features/README.md` (8.3 → Done + open-debt/next-feature lines), `features/SESSIONS.md`
  entry, spec status line. If any lot is deferred, record it as a TD instead of silently dropping.
- **Review pass** → `features/reviews/8.3-download-tracking.md` (checkboxes) → fix ALL → 2nd pass if any
  Critical/Important. Scrutinize: recipient-resolution correctness (no cross-share linkage via email),
  audit double-emit, counter race-safety (concurrent downloads), and the access-vs-download distinction.

## Test discipline
- Full `pnpm --filter ouitransfer-api test` + `pnpm --filter ouitransfer-web test` per touched batch
  (not just new tests).
- `app.inject()` integration tests for every tracking decision: recipient linkage (token + cookie),
  counter increments, audit emission, reminder filtering, reverse-upload linkage.
- Type-check both apps + locale-parity test after any i18n change.

## Sequencing notes
- Batch 1 is the foundation (schema + resolver + counters) — 2/3/4 depend on its fields and helper.
- 2, 3, 4 are independent of each other once Batch 1 lands; keep them sequential per the no-parallel rule.
- Batch 5 closes out (cross-cutting docs/i18n/review).
