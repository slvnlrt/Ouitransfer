# 8.3 — Download Tracking — Implementation Plan

Spec: [`features/specs/8.3-download-tracking.md`](../specs/8.3-download-tracking.md) is binding
(état des lieux + décisions). Most of the original scope was delivered by 8.2; this plan covers
the remaining lots **A/B/C/D/F** (lot E — per-recipient password — is out of scope). Same quality
bar as prior features (zero tech debt, full suites, `app.inject()` integration tests for every
tracking decision). Subagents dispatched **sequentially**.

> **Revised after a plan-review pass** (findings folded in). This is a **comfort feature**, not a
> security control: a self-declared visitor name/email is expected to be spoofable and that is
> accepted. We simply **record the identification source** (`token` = verified vs `self_declared`)
> so the audit/UI can label unverified attributions and a tooltip can warn the owner.

## Key facts established by the audits (don't re-discover / don't regress)

- **`FILE_DOWNLOAD` audit is ALREADY emitted** for every download (anonymous + owner) at
  `file/routes.ts:1056-1064` (`/files/download-url`, `method: "presigned-url"`) and
  `file/routes.ts:1166-1174` (`/files/download`, `method: "stream"`). **Lot F must NOT add a second
  emission** — it would double-log. Lot F = **enrich** those two existing emits with
  `recipientId` + `identificationSource` metadata, nothing more (plus the GDPR notice).
  `REVERSE_SHARE_FILE_DOWNLOAD` (`reverse-share/routes.ts:727-735`) is the **owner** downloading
  received files — a different event; do not touch it for lot D.
- **The tracking token does NOT reach the download path.** `getDownloadUrl` (web,
  `http/endpoints/files/index.ts:91-105`) sends only `{ objectName, password?, shareId? }`. So a
  download cannot be linked by `?t=` directly. We bridge the access-time identity to download-time
  via the **signed visitor cookie** (see Batch 1).
- **Identity carriers, by trust level:**
  - **Token** (`?t=`, `crypto.randomBytes(24)`, `repository.ts:132`) — verified. Resolved at access
    in `share/service.ts:319-332`.
  - **Self-declared cookie email** (`sv_{alias}`, set from the identification form
    `share/routes.ts:929-933`) — signed for integrity only, **not** authentication. Acceptable for a
    comfort feature; always labeled `self_declared`.
- **Schema decision:** extend `ShareVisit`; per-recipient status **denormalized** onto
  `ShareRecipient` (mirrors `accessCount`/`lastAccessedAt`).
- **Retention:** none added — visits/recipients cascade-delete with the share.
- **Visibility:** owner already sees own-share tracking; no authz change.
- **Counters are race-safe via `{ increment: 1 }`** (atomic). First-set timestamps must use a
  conditional `updateMany({ where: { …, uploadedAt: null } })` to avoid a read-then-write TOCTOU.

---

## Batch 1 — Schema + identity bridge + download-path wiring (A-server / C / F-enrich)

The structural core: carry the access-time identity to the download moment, link the recipient, and
record the source — all converging in `trackShareDownload`.

- **Schema** (`prisma/schema.prisma`):
  - `ShareRecipient`: add `downloadCount Int @default(0)`, `lastDownloadedAt DateTime?`.
    (Status badge keys off `lastDownloadedAt != null`; `downloadCount` = **files fetched**, not
    sessions — `trackShareDownload` runs once per file, so a "download all" of N files adds N.
    Document this in a schema comment to avoid the I4 misread.)
  - `ReverseShareRecipient`: add `uploadCount Int @default(0)`, `uploadedAt DateTime?` (lot D — one
    migration for all four fields).
  - `ShareVisit`: add `identificationSource String?` (`"token" | "self_declared" | null`) so each
    download/access row records how the recipient was attributed.
  - Migration `download_tracking` (authored via `prisma migrate dev`, committed — not `db push`).
    Existing rows backfill to `0` / `NULL`. Regenerate client.
- **Visitor cookie** (`share/visitor-cookie.ts`): extend the signed payload with optional
  `recipientId?`. It is written **only server-side after a token is verified** — never from form
  input — so its presence vouches for a verified recipient.
- **Access flow** (`share/service.ts:319-411`):
  - When a recipient is resolved **by token** (existing branch :324-332), set `cookie.recipientId`
    on the identification cookie so later downloads inherit the verified identity. Keep bumping
    `accessCount`/`lastAccessedAt`.
  - **Lot C (close the NULL gap for self-identified visitors):** when there is no token recipient but
    the cookie carries an email, match `findUnique({ shareId_email: { shareId, email } })`
    (normalize lower/trim like `addRecipients`; guard `if (cookie?.email)` — the cookie can be
    name-only, `visitor-cookie.ts:39`). Set `recipientId` + bump access stats, mark
    `identificationSource = "self_declared"`. Token path marks `"token"`.
- **Download flow** (`file/routes.ts trackShareDownload :159-268`):
  - Resolve the recipient from the cookie: `cookie.recipientId` → source `"token"`; else
    `cookie.email` → `shareId_email` match → source `"self_declared"`; else anonymous.
  - Set `recipientId` + `identificationSource` on the `download` `ShareVisit`.
  - Bump `ShareRecipient.downloadCount` (`{ increment: 1 }`) + `lastDownloadedAt` in one atomic
    `update` (no read-then-write).
  - Keep existing behavior: `share.lastDownloadedAt`, `inactivityAlertSent` reset,
    `share_downloaded` notification.
- **Lot F enrich (NOT a new emit):** at the two existing `FILE_DOWNLOAD` emits
  (`file/routes.ts:1056`, `:1166`), add `recipientId` + `identificationSource` (+ `shareId`) to the
  audit `metadata`. Resolve them from the same cookie logic (share-scoped). Do not add an emit inside
  `trackShareDownload`. Verify no other `FILE_DOWNLOAD` call exists (grep) to be sure we don't regress.
- **Tests** (`app.inject()` — the tracking surface):
  - Access via token → `cookie.recipientId` set; a subsequent download → visit `recipientId` set,
    `identificationSource: "token"`, `downloadCount` incremented, `lastDownloadedAt` set.
  - Self-identified (form email matching a recipient) download → linked,
    `identificationSource: "self_declared"`.
  - **Spoof-labeling test:** anonymous visitor types a *known* recipient's email → linkage happens but
    the row is `self_declared` (asserts we never mark it `token`/verified). This is the intended
    comfort-feature behavior, pinned by a test.
  - Anonymous (no cookie) download → `recipientId` NULL, no counter change, `FILE_DOWNLOAD` still
    logged once (regression guard against double-log).
  - Owner download → no visit/counter/notification (unchanged), `FILE_DOWNLOAD` still emitted once.
  - Unit tests for the shared resolver (token-id present, email hit, email absent/name-only, no match).

## Batch 2 — Recipient download-status badge + source tooltip (A-UI)

- **Serializer (I1):** the recipient mapper at `share/service.ts:111-118` spreads `...recipient` then
  `toISOString()`s Date fields. Add `lastDownloadedAt: recipient.lastDownloadedAt?.toISOString() ?? null`
  there; `downloadCount` (Int) flows via spread. Expose both on the share-recipient DTO
  (`share/dto.ts`, the `z.string().datetime().nullable()` pattern) and the web types
  (`apps/web/src/http/endpoints/shares/types.ts`). An `app.inject()` test must assert the fields are
  present **in the HTTP response body** (not just the DB).
- **UI:** `apps/web/src/components/general/recipient-selector.tsx` (status block ~lines 376-394 —
  re-derive line numbers, they drift). Add an explicit badge: **Téléchargé** (green,
  `lastDownloadedAt != null`, tooltip with the date) vs **En attente** (muted, notified but not
  downloaded). Keep the existing `accessCount` "views" line as a secondary, distinct signal
  (access ≠ download).
- **Source tooltip (comfort-feature honesty):** when a recipient's attribution comes from a
  `self_declared` source, show a subtle info tooltip ("identité auto-déclarée, non vérifiée"). Plumb
  whatever minimal signal the recipient DTO needs (e.g. a derived `lastDownloadSource`), or surface it
  in the activity list where per-visit `identificationSource` already exists.
- i18n: `recipientSelector.downloaded` / `.pending` / `.selfDeclaredHint` across all 23 locales
  (en/fr authored, EN replicas elsewhere per the TD-36 reality). Locale-parity test green.
- Web tests for the badge + tooltip logic.

## Batch 3 — Manual reminder for non-downloaders (B)

- **Server:** add `POST /shares/{id}/remind`, reusing the `notifyRecipients` plumbing (personalized
  `?t=token` links) but filtered to recipients with `lastDownloadedAt == null`.
  - **New email type `share_download_reminder`** modeled on **`share_invitation`**
    (`email/catalog.ts:309-328`): `configurable: false`, `hasUnsubscribe: false`,
    `defaultFrequency: "immediate"`, **`userId` omitted** in `emailService.send` (external recipients
    have no account/preference — do NOT wire it into the notification-preference system; cf.
    `service.ts:969-971`). Requires: catalog entry + `payloadSchema` + render fn + template file
    (`templates/share-download-reminder.ts`) + `requiredI18nKeys` authored in the email message set.
  - **New audit action `SHARE_RECIPIENT_REMIND`** in `audit/service.ts` (+ label key); emit on send.
  - Update `notifiedAt` on reminded recipients. **No scheduler** (decision: manual only).
- **Web:** "Relancer les non-téléchargeurs" button in `recipient-selector.tsx` (SMTP-gated like the
  existing notify controls); disabled when zero pending; show the pending count.
- **Tests:** `app.inject()` — remind targets ONLY `lastDownloadedAt == null`, skips downloaders,
  enqueues `share_download_reminder`, writes the audit row, updates `notifiedAt`; SMTP-off → gated.
  Unit test the filter.

## Batch 4 — Reverse-share per-recipient upload tracking (D, best-effort)

- **Server:** in the reverse-share file-register paths — `registerFileUpload` (~`upload.service.ts:238`,
  `createFile`) **and** `registerFileUploadByAlias` (~`:276`); NOT the `:590` notification method —
  match the (optional) `uploaderEmail` against `ReverseShareRecipient({ reverseShareId, email })`
  (normalized). On match: set `uploadedAt` via conditional `updateMany({ where: { id, uploadedAt: null },
  data: { uploadedAt: now } })` (first-upload timestamp, TOCTOU-safe) + atomic `uploadCount { increment: 1 }`.
  Fire-and-forget, failure-tolerant. Keep the `reverse_share_uploaded` owner notification + debounce
  untouched.
- **Best-effort, displayed everywhere (decision):** `uploaderEmail` is `.optional()` (`dto.ts:160`)
  and reverse-share `emailFieldRequired` defaults to OPTIONAL, so linkage often won't fire and is
  self-declared when it does. Badge shows **A uploadé** vs **En attente** for all recipients, with a
  tooltip noting it's approximate when email isn't required (so "En attente" never implies certainty).
- Serializer: map `uploadedAt?.toISOString() ?? null` in the reverse-share recipient serializer;
  expose `uploadCount`/`uploadedAt` on the DTO + web types.
- UI: badge + tooltip in `reverse-share-recipient-selector.tsx`. i18n keys (23 locales).
- **Tests:** `app.inject()` — upload with a matching `uploaderEmail` links + sets `uploadedAt` +
  bumps `uploadCount`; second upload increments but `uploadedAt` unchanged (conditional set); upload
  with absent/unknown email leaves recipients untouched; spoofed email links but is treated as
  best-effort. Web test for the badge.

## Test discipline
- Full `pnpm --filter ouitransfer-api test` + `pnpm --filter ouitransfer-web test` per touched batch
  (not just new tests).
- `app.inject()` integration tests for every tracking decision: token vs self_declared linkage,
  counter increments, **no audit double-log**, response-field presence, reminder filtering,
  reverse-upload linkage (matched / absent / second-upload).
- Type-check both apps + locale-parity test after any i18n change.

## Sequencing notes

- 2, 3, 4 are independent of each other once Batch 1 lands; keep them sequential per the no-parallel rule.
- Batch 5 closes out (cross-cutting GDPR/docs/i18n/review).
