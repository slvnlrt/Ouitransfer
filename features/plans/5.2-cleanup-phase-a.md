# 5.2 Phase A — Implementation Plan

Spec: [`features/specs/5.2-cleanup.md`](../specs/5.2-cleanup.md) (Decisions + Phasing sections are binding).

**Principles**: zero tech debt, perfect implementation, state-of-the-art, evolutive. Fix
pre-existing issues encountered along the way. Conservative defaults; auto-deletion opt-in/off
by default. Reuse 8.1 audit + 8.2 email infra. Every automated deletion → audit event. Run the
**full** test suite for every touched package. TypeScript must compile on every commit.

**Execution**: batches are dispatched to implementer subagents **strictly sequentially** (Rule 0).
Each batch is one atomic concern → one (or few) commits. After all batches: a review pass
(reviewer subagent) → fix ALL findings → update tracking.

## Batch 1 — Schema + config foundation + migration

**Files**: `prisma/schema.prisma`, `prisma/seed.js`, `modules/config/config-validation.ts`,
`modules/user/service.ts`, `modules/share/service.ts` (notified-flag reset), migration.

1. Schema (additive): `User.deactivatedAt DateTime?`,
   `Share.notifiedForPendingDeletion Boolean @default(false)`,
   `ReverseShare.notifiedForPendingDeletion Boolean @default(false)`.
2. `deactivateUser` sets `deactivatedAt: new Date()`; `activateUser` clears it (`null`).
3. Reset `notifiedForPendingDeletion` wherever `notifiedForExpiring`/`notifiedForExpired`/
   `notifiedForMaxViews` are reset on share/reverse-share update.
4. Seed 9 config keys in group `cleanup` (see spec table) with conservative defaults.
5. Add per-key validators in `config-validation.ts`: booleans (`autoCleanupEnabled`,
   `accountDeactivationCleanupEnabled`, `autoCleanupOrphansEnabled`) accept `"true"`/`"false"`;
   integers with the documented bounds. Factor small reusable Zod helpers
   (`booleanString`, `intMin(n)`). Keep single + bulk update paths in sync (both already call
   `validateConfigValue`).
6. `prisma migrate dev --name cleanup_lifecycle` (authored migration committed). Regenerate client.
7. Tests: extend `config-validation` unit tests for all 9 keys (valid + invalid bounds).

**Done when**: migration applies cleanly, client regenerated, server type-check + full server
test suite green.

## Batch 3 — Cleanup module: expired / maxViews share & reverse-share cleanup (A2–A5)

**Files**: new `modules/cleanup/service.ts` (+ `__tests__/`), `modules/audit/service.ts`
(new actions).

1. Audit actions: `SHARE_AUTO_DELETED`, `REVERSE_SHARE_AUTO_DELETED`, `ACCOUNT_FILES_CLEANED`,
   `ORPHAN_S3_DELETED`, `ORPHAN_DB_DELETED` (add all now; later batches use them).
2. `deleteShareLink(shareId)` — delete Share + cascade dependents (security, recipients, visits,
   alias). **Never** touches File/Folder/S3. (Confirm cascade vs explicit deletes against schema.)
3. `deleteReverseShareWithStorage(rsId)` — collect `ReverseShareFile.objectName`s, delete
   ReverseShare (DB cascade removes the file rows), then best-effort delete S3 objects
   (DB-before-S3 ordering, TD-23 convention).
4. `cleanupExpiredShares({ graceDays, notifyDaysBefore })`:
   - Warn: shares where `expiration` is within `notifyDaysBefore` of the deletion moment
     (`expiration + grace`) and `notifiedForPendingDeletion=false` → send `share_pending_deletion`,
     set flag. Only when SMTP/notifications viable (reuse existing send() contract — it no-ops if not).
   - Delete: shares where `now > expiration + grace` → `deleteShareLink` + audit `SHARE_AUTO_DELETED`
     + `share_auto_deleted` notification to creator.
5. `cleanupMaxViewsShares({ inactiveDays })`: shares with `maxViews != null && views >= maxViews`
   and (`lastDownloadedAt ?? updatedAt`) older than `inactiveDays` → `deleteShareLink` + audit +
   notification. (Optional warn reuses `share_pending_deletion`.)
6. `cleanupExpiredReverseShares({ graceDays, notifyDaysBefore })`: mirror (4) with
   `deleteReverseShareWithStorage` + `reverse_share_pending_deletion` /
   `reverse_share_auto_deleted` + audit `REVERSE_SHARE_AUTO_DELETED`.
7. All functions return a summary `{ warned, deleted, errors }` for scheduler logging. Each item
   wrapped so one failure doesn't abort the batch.
8. Tests: unit (mocked prisma + storage + emailService) covering grace boundary, warn-once
   idempotency, S3 best-effort failure tolerance, maxViews+inactivity boundary.

## Batch 4 — Account lifecycle: read-time block + purge + deletion cascade (A6–A8)

**Files**: `modules/share/service.ts`, `modules/reverse-share/service.ts`,
`modules/user/service.ts`, `modules/cleanup/service.ts`, shared purge helper.

1. **A6** (ungated, reversible): in `getShare` (regular) and reverse-share access path, when the
   loaded `creator`/owner has `isActive === false`, block with `AppError(410/403, …, code)`.
   Ensure the creator's `isActive` is selected. Add integration tests (active vs deactivated owner).
2. `purgeUserContent(userId)` (in cleanup service): collect `File.objectName` + the user's
   `ReverseShareFile.objectName`s; delete (DB, in a transaction) the user's shares, reverse shares,
   files, folders; then best-effort delete all S3 objects. Returns counts. DB-before-S3.
3. **A8**: refactor `deleteUser` to call `purgeUserContent` (so no orphaned shares / S3 objects
   remain — fixes the current `SetNull` orphaning), then delete the user row + existing audit
   redaction. Enrich `USER_DELETE` audit metadata with removed counts. Keep ungated (admin action).
4. **A7**: `cleanupDeactivatedAccounts({ days })` in cleanup service — users with
   `isActive=false && deactivatedAt < now - days` → `purgeUserContent` (keep the user row) +
   `files_auto_deleted` notification + audit `ACCOUNT_FILES_CLEANED`. Gated by
   `accountDeactivationCleanupEnabled` (checked in scheduler).
5. Tests: integration on `DELETE /users/:id` (S3 deletes + share removal asserted), unit on
   `purgeUserContent` + `cleanupDeactivatedAccounts`, plus the A6 access blocks. This also lands
   meaningful coverage for the `user`/`reverse-share` services → resolves **TD-49**.

## Batch 5 — Orphan sweep (A9) + storage `listObjects`

**Files**: `providers/s3-storage.provider.ts` (+ interface), `modules/cleanup/service.ts`,
`scripts/cleanup-orphan-files.ts` (retire/absorb).

1. Add paginated `listObjects(prefix?)` to the storage provider → `{ key, size, lastModified }[]`
   (ContinuationToken loop). Unit test with mocked S3 client.
2. `sweepOrphans({ minAgeHours })`:
   - DB→S3: `File`/`ReverseShareFile` rows with `createdAt < now-minAge` whose object is missing
     (`fileExists=false`) → delete the DB row + audit `ORPHAN_DB_DELETED`.
   - S3→DB: objects with `lastModified < now-minAge` whose key matches no `File.objectName` nor
     `ReverseShareFile.objectName` → delete the S3 object + audit `ORPHAN_S3_DELETED`.
   - minAge guard protects in-flight uploads. Batched, failure-tolerant, returns counts.
3. Retire `scripts/cleanup-orphan-files.ts`: either delete it and document the new sweep, or make
   it a thin CLI wrapper calling `sweepOrphans`. Resolves **TD-17** and **TD-25**.
4. Tests: unit covering both directions + minAge boundary + the multi-share safety (an object
   referenced by any row is never deleted).

## Batch 6 — Cleanup scheduler (A1) + server registration

**Files**: new `modules/cleanup/cleanup.scheduler.ts` (+ `__tests__/`), `server.ts`.

1. Mirror `modules/audit/retention.scheduler.ts`: `scheduleNext()` chained `setTimeout`,
   `start*/stop*`, `init*OnBoot()`, module-level handle, guarded re-entrancy.
2. Interval from `autoCleanupIntervalHours`. On each run, if `autoCleanupEnabled`:
   run A2–A5 (Batch 3) + A7 (if `accountDeactivationCleanupEnabled`) + A9 (if
   `autoCleanupOrphansEnabled`), reading all config each run (live config changes respected).
   Immediate first run on boot (cache-recovery style). Structured Pino summary per run.
3. Register in `server.ts` (`void initCleanupOnBoot()`) + stop in the `onClose` hook.
4. Tests: scheduler unit tests modeled on `retention.scheduler.test.ts` (disabled → no-op,
   enabled → calls cleanup fns, stop cancels timer, interval read from config).

## Review (after all batches)

Dispatch a reviewer subagent over the full Phase A diff (spec compliance + code quality +
security: destructive ops, opt-in gating, audit coverage, S3 best-effort ordering, race safety
on schedulers, i18n parity). Write findings to `features/reviews/5.2-cleanup-phase-a.md` as
checkboxes. **Fix every finding** (Critical/Important/Minor). Re-run full suites. Only then is
Phase A Done.

## Test discipline (Rule 9/10/11)

- Service-layer unit tests for every cleanup function (mock prisma/storage/email).
- `app.inject()` integration tests for the security-relevant flows: deactivated-owner share block,
  user-deletion S3 cascade, config validation round-trips.
- Full `pnpm --filter` suite for every touched package per batch.
